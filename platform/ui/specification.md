# Shared Platform UI Widgets — Specification

## Overview
This document specifies `DropdownWidget`, a generic, reusable, hand-drawn dropdown/list-popup GUI control, and establishes `platform/<module>/src/main/java/de/lazuli/ui/` as this repo's shared, non-feature-owned home for custom-drawn widgets intended to be reused by more than one feature's rendering code.

This document is deliberately **not** a `features/*/specification.md` — `DropdownWidget` is Minecraft-GUI-coupled (it necessarily extends a per-Minecraft-version widget base class, e.g. `net.minecraft.client.gui.components.AbstractWidget` on Mojang-mapped 26.x, the Yarn-mapped `ClickableWidget` equivalent on `fabric-1.21.11`) and therefore cannot live in `api` (`architecture.md:13`, "No Minecraft imports") or `services` (`services/specification.md:39`, NFR5, "plain JVM... no Minecraft classes on classpath") or inside any single feature's own `services`/`api` sub-package (Feature code that needs a widget class today lives in Platform, not Features — see Existing Implementation below), or inside `common` (`common/build.gradle:1-3` — no Fabric Loom plugin applied, confirmed no Minecraft dependency available there either, same constraint as `api`/`services`). The only layer in this repo's Dependency Rules table (`architecture.md:64-71`) that is both allowed to depend on Minecraft classes and is not subject to the Feature→Feature prohibition is **Platform**. This document's placement follows directly from that elimination, not from a new exception being carved out.

### Existing Implementation (research, this revision)
- `FriendSidebarWidget` and `FriendContextMenuWidget` (`platform/fabric-26.2/src/main/java/de/lazuli/friends/FriendSidebarWidget.java`, `.../FriendContextMenuWidget.java`, structurally mirrored in `platform/fabric-26.1` and `platform/fabric-1.21.11`) are this repo's **only** existing hand-drawn custom widgets, confirmed via a repo-wide search for `extends AbstractWidget` / `extends ClickableWidget` (12 matches, all `FriendSidebarWidget.java`/`FriendContextMenuWidget.java` across the three platform modules plus an in-progress worktree copy — no other custom widget class exists anywhere in the repo). Both already live in the **Platform** layer (`platform/fabric-<version>/src/main/java/de/lazuli/friends/`), not inside `features/friends-sidebar` itself — `features/friends-sidebar`'s own source only contains `api`/`config`/`services` sub-packages (plain-JVM business logic: `FriendsSidebarConfig`, `FriendsSidebarConfigIO`, `FriendsSidebarFacade`, `FriendSidebarStateMachine`); the actual `AbstractWidget` subclasses are Platform-module code, one structurally-identical copy per Minecraft version, exactly the "Feature → Platform API → Version Adapter → Minecraft" shape `architecture.md:47-62`'s Multi-version Strategy already describes for widget-level code specifically (as opposed to `api`-level hook interfaces, which follow the `MainMenuHook`-style "Platform API + Version Adapter" pair instead).
- `features/server-browser` (`features/server-browser/specification.md`, `plan.md`) contains **no** `src/` yet and is not registered in `settings.gradle` (confirmed: `settings.gradle:20-29` lists `api`, `common`, `services`, `features:hello-world-main-menu`, `features:steam-cloud-sync`, `features:friends-sidebar`, `features:steam-world-hosting`, and all three platform modules — no `features:server-browser` entry) — it is spec-only, in-flight, unbuilt. A repo-wide search of its `specification.md` for `dropdown`/`AbstractWidget`/hand-drawn-widget terminology returns zero hits; nothing in that spec today establishes or requires a custom-drawn widget, dropdown or otherwise. This document does not assume anything about `server-browser`'s eventual widget needs, does not modify any `features/server-browser` file, and does not require `server-browser` to adopt `DropdownWidget` — it is made available for that feature (or any other) to use later, at that feature's own planning phase's discretion. **This revision (v2) confirms this is still true** — `features/server-browser` has since gained real `src/` (`ServerBrowserScreen`/`ServerBrowserListWidget`/`ServerBrowserPasswordPromptScreen`) but none of it imports `de.lazuli.ui.DropdownWidget` or otherwise touches this document; this revision does not modify, read further, or coordinate with any `features/server-browser` file.
- No pre-existing `ui`/`widgets`/`common`-style shared widget package exists anywhere in the repo prior to this document — every finding above confirms this is greenfield, not an extraction of existing duplicated code (unlike the `services/` graduate-on-second-use precedent, there is no first "duplicate" to consolidate; this is a from-scratch, deliberately-shared, first-use component, justified below).
- **(this revision, re-confirmed for the z-order correction below)** `FriendContextMenuWidget` and `FriendSidebarWidget` are both drawn manually via a public `renderNow(GuiGraphicsExtractor, int, int, float)` method, invoked once per frame from `FabricFriendsSidebarInjector`'s single `ScreenEvents.afterExtract(screen)` registration (`platform/fabric-26.2/.../friends/FabricFriendsSidebarInjector.java:111,121-129`, structurally mirrored on the other two platform modules), never through their own `extractWidgetRenderState(...)` override (both leave that method deliberately empty, `FriendSidebarWidget.java:252-261`, `FriendContextMenuWidget.java:90-96` — each still stays registered in `Screens.getWidgets(screen)` purely so vanilla's own input dispatch continues to reach it; only *rendering* is pulled out of the normal per-screen widget draw order). The injector's `onAfterExtract` calls `activeSidebar.renderNow(...)` then, if present, `openMenu.renderNow(...)`, in that fixed order — the order is documented as authoritative by `de.lazuli.api.friends.FriendsSidebarZOrder` (`api/src/main/java/de/lazuli/api/friends/FriendsSidebarZOrder.java`), an enum whose two ordinals (`SIDEBAR`, `CONTEXT_MENU`) exist specifically so each platform's injector draws layers "in ascending ordinal order (lowest first/furthest back)" per that enum's own Javadoc, rather than relying on incidental widget-list position. This is the exact mechanism this revision's correction (below) requires `DropdownWidget`'s open-state option list to also use.

### v2 Amendment — Polish pass (this revision)
**Trigger.** Live in-game testing of the v1 (`DropdownWidget` UI-FR1-UI-FR7, shipped) control, embedded as `features/friends-sidebar`'s v1.4 join-policy selector, surfaced four problems, plus a fifth found during this revision's own specification review before implementation. This revision's own research confirms all five directly against the current, identical-across-all-three-platforms source (`platform/fabric-26.2/.../ui/DropdownWidget.java`, byte-for-byte structural twin confirmed against `fabric-26.1` and `fabric-1.21.11`, differing only in the pre-existing `GuiGraphicsExtractor`/`Minecraft`/`Font` vs. `DrawContext`/`MinecraftClient`/`TextRenderer` per-module idiom UI-FR7 already documents):

1. **No button chrome.** `render()` (`DropdownWidget.java:71-97`) draws exactly one `fill(...)` (a flat `BACKGROUND = 0xCC202020` rectangle) plus one `text(...)` call per row, for both the closed row and every open-state row. There is no border/outline draw call anywhere in the class, and `mouseX`/`mouseY` are used **only** to gate the open-state per-row hover-description reveal (`render()`'s `overRow` check, line 83) — they are never used to pick a different background color for the closed row or for whichever open-state row is currently hovered. Confirmed identical across all three platform copies. Net effect: the control is visually indistinguishable from a plain text label; nothing in its current rendering communicates "this is clickable."
2. **No visible label.** Neither `DropdownWidget` itself nor its sole caller (`FriendSidebarWidget`) renders any text identifying what the control governs — `render()`'s closed-row `text(...)` call draws only `selected.label()` (i.e. today, `"Join: Friends"`-shaped copy, `FriendSidebarWidget.joinPolicyShortLabel`, confirmed the short label already embeds a leading "Join: " prefix, `features/friends-sidebar/specification.md` FR7.4) — so in practice there **is** a degree of self-labeling already, entirely via the caller's own chosen label text, not a structurally separate "label" element. The four-problems trigger for this document frames it as "no visible label" because that embedded prefix is easy to miss (styled identically to the rest of the row, no visual separation from the value) — this revision treats it as a legibility/design gap, not a total absence of any text, and resolves it with a real design decision (below) rather than by disputing the premise.
3. **Expansion direction/sizing.** Confirmed via direct read: `render()`'s open-state loop (lines 81-95) and `mouseClicked()`'s open-state hit-test loop (lines 118-128) both already stack every option row directly beneath the closed row, at the exact same `x`/`width` the closed row itself used that same call (`FriendSidebarWidget.java:390-391`'s single `joinPolicyDropdown.render(guiGraphics, dropdownX, dropdownY, dropdownWidth, DROPDOWN_HEIGHT, mouseX, mouseY)` call feeds one consistent `x`/`width` pair to the whole method for both the closed row and every open row — there is no separate/divergent width computation for the open state anywhere in either `DropdownWidget` or `FriendSidebarWidget`). **The horizontal alignment/width-matching the trigger describes is therefore already correct in the current code** — this revision's own research found no bug there. The actual sizing defect is vertical: each open-state row's hover-triggered description text (lines 86-93) is drawn *below* that row, using additional rows of `DESCRIPTION_LINE_HEIGHT`-tall text that are **not** included in `render()`'s returned total height (line 96's `rowHeight * (1 + options.size())` counts only the fixed option rows, never the variable, hover-conditional description text drawn beneath whichever row currently has the mouse over it). Consumers that use the returned height to reserve/scissor layout space (`FriendSidebarWidget.listTopOffset()`/`v1.4-FR7.14`'s scissor rectangle) can therefore have the last open-state row's hover description visually overlap or get clipped by content positioned using that undercounted height — this is the real, confirmed "sizing" defect, not a width/horizontal-direction one. This revision's fix (Requirements, below) removes the inline description text entirely in favor of a native tooltip (Problem 4), which also eliminates this defect at the source (a tooltip never participates in layout/height accounting).
4. **Non-native hover text.** The per-row description (open state) is drawn as plain wrapped body text directly beneath the hovered row (lines 86-93, `wrapMessage(...)`), sharing the same flat `BACKGROUND` fill as every other row rather than using Minecraft's native dark rounded tooltip box. Confirmed no call to any tooltip API (`setTooltipForNextFrame`/`drawTooltip`/`renderTooltip`) anywhere in `DropdownWidget.java` or in `FriendSidebarWidget.java`'s dropdown-related code on any of the three platform modules — this is a from-scratch gap, not a partially-done integration.
5. **(new, this revision — correction to an earlier draft of this same v2 amendment) Open-state list is not a top-level overlay layer.** `DropdownWidget.render()` (today, and as UI-FR8-UI-FR14 were originally drafted) draws the open-state option rows **inline**, as part of the single `render()` call `FriendSidebarWidget.renderNow()` invokes at `FriendSidebarWidget.java:390-391` — i.e. entirely inside the `SIDEBAR` z-order layer (Existing Implementation, above), the same manually-driven call that also draws every other sidebar row. Anything `FriendSidebarWidget.renderNow()` draws *after* that call within the same `SIDEBAR`-layer pass (e.g. the scrollable friend-row list beneath the join-policy control, `FriendSidebarWidget.java`'s own row-drawing loop) can therefore clip or visually cover the expanded option list, because both are painted within the same single top-level layer with no ordering guarantee beyond incidental call order inside one method body — unlike `FriendContextMenuWidget`, which is guaranteed to always draw on top of `SIDEBAR` via its own dedicated `CONTEXT_MENU` ordinal (`FriendsSidebarZOrder`, Existing Implementation). This is a distinct defect from Problem 3 (which was about *height accounting*, not draw order) and is not fixed by UI-FR12/UI-FR13's tooltip change, since the open-state *rows themselves* (not their hover descriptions) are what can be covered. Fixed by UI-FR15-UI-FR18 below, which give the open-state option list its own top-level overlay render entry point, driven the same way `FriendContextMenuWidget`'s `renderNow()` already is.

**Per-platform discrepancy check.** None found — all three platform copies of `DropdownWidget.java` are structural twins with identical logic, differing only in the already-documented `GuiGraphicsExtractor guiGraphics` + `Minecraft.getInstance().font` (Mojang, `fabric-26.1`/`fabric-26.2`) vs. `DrawContext context` + `MinecraftClient.getInstance().textRenderer` (Yarn, `fabric-1.21.11`) render-call idiom (UI-FR7, unchanged). The correct native-tooltip API per mapping set (Problem 4's fix) is a genuine per-module divergence, though, confirmed via `.claude/context/minecraft.md`'s Obfuscation Boundary / Known Cross-Version API Differences table (row "Queuing a simple text tooltip..."):
- **Yarn (`fabric-1.21.11`):** `net.minecraft.client.gui.DrawContext.drawTooltip(net.minecraft.text.Text text, int mouseX, int mouseY)`.
- **Mojang (`fabric-26.1`, `fabric-26.2`):** `net.minecraft.client.gui.GuiGraphicsExtractor.setTooltipForNextFrame(net.minecraft.network.chat.Component text, int mouseX, int mouseY)` — identical signature/behavior confirmed on both 26.1 and 26.2.

Both take a single `Text`/`Component` and a mouse position — multi-line descriptions (today's `wrapMessage(...)`-wrapped body text) map to a single `Text.literal("line1\nline2...")`-with-embedded-newlines argument, or (equivalently, planning's choice) `Component`/`Text`'s own multi-line `.append(...)`-with-explicit-newline construction — vanilla's native tooltip renderer already wraps/lays out multi-line tooltip text itself, so `DropdownWidget`'s own `wrapMessage(...)` helper (currently used only for the inline description text this revision removes) is no longer needed for the description path once this fix lands (it may still be retained/unused, or deleted, at planning's discretion — not a spec-level requirement either way).

**Confirmed identical z-order mechanism across all three platform modules.** `FriendsSidebarZOrder` lives in `api/` (one copy, not per-platform, since it is a plain enum with zero Minecraft imports), so all three platform modules' injectors already reference the exact same enum/ordinal ordering — `platform/fabric-26.2`, `platform/fabric-26.1`, and `platform/fabric-1.21.11`'s `FabricFriendsSidebarInjector.java` and `FriendSidebarWidget.java`/`FriendContextMenuWidget.java` were all read for this revision and confirmed structurally identical in their `renderNow()`/`extractWidgetRenderState()`/`onAfterExtract` split (differing only in the already-documented `GuiGraphicsExtractor` vs. `DrawContext` render-call idiom, same as every other per-platform difference this document already tracks). No discrepancy found; Problem 5's fix (UI-FR15-UI-FR18) applies uniformly to all three modules.

## Goals
- Provide one generic, reusable dropdown/list-popup control — a list of labeled options, a selected index, open/closed state, click-to-open, click-an-option-to-select, close-on-outside-click, close-on-selection — usable by any current or future Platform-layer widget code, not hardcoded to any one feature's option set (e.g. not hardcoded to `friends-sidebar`'s three-value `JoinPolicy`).
- Avoid a second, independently-invented dropdown/popup interaction the next time a feature needs one (the concrete trigger for building this now: `features/friends-sidebar`'s v1.4 amendment, `features/friends-sidebar/specification.md`, replacing its v1.3 cycling-label control — see that document's Requirements).
- Fit the existing hand-drawn rendering convention this repo's only other custom widgets (`FriendSidebarWidget`/`FriendContextMenuWidget`) already use — plain `guiGraphics.fill(...)`/`guiGraphics.text(...)` calls, no dependency on vanilla's built-in widget-list pipeline — `DropdownWidget` must be embeddable inside that same manually-driven render loop, not assume it owns its own top-level `Screen`-managed render/input pass. **(v2 amendment)** The one narrow exception is vanilla's *tooltip* pipeline specifically (Requirements UI-FR8-UI-FR10) — every other Minecraft screen/widget already coexists with native tooltips without owning its own top-level render pass, so adopting `setTooltipForNextFrame`/`drawTooltip` does not conflict with this Goal's "no vanilla widget-list pipeline" framing, which was always about the *list/selection* pipeline (`AbstractSelectionList` and friends), not tooltips.
- **(v2, new)** Look and behave recognizably like a clickable control at rest, not merely react correctly to clicks — the v1 control was functionally correct but visually indistinguishable from static text (Overview, Problem 1); this revision's goal is closing that gap with the smallest chrome addition consistent with this repo's existing hand-drawn, `fill`/`text`-only rendering convention (no new texture/sprite assets).
- **(v2, new — Problem 5's fix)** Give the open-state option list the same top-level, always-on-top overlay guarantee `FriendContextMenuWidget` already has, by reusing that exact mechanism (`FriendsSidebarZOrder` + a manually-invoked `renderNow()`-equivalent, driven by the embedding widget's own `afterExtract` hook) rather than inventing a second, `DropdownWidget`-specific z-order/layering scheme.
- Keep the component's public shape free of any single feature's option type — it operates on a caller-supplied list of `(label, value)`-shaped entries (or simply a `List<String>` of labels plus an externally-tracked selected index — exact generic shape a planning decision), never an enum belonging to any feature.

## Non-goals
- No keyboard navigation (arrow keys/Enter to select) in this revision — mouse-only, matching every other control in this repo's only existing custom widgets, none of which implement `keyPressed`-driven interaction today.
- No nested/multi-level dropdowns, no searchable/filterable option lists, no multi-select — a single flat list of options, single selection, matching exactly what `features/friends-sidebar`'s v1.4 consumer needs (three options) and no more.
- No animation (open/close transitions) in this revision — instant open/close, unlike `FriendSidebarWidget`'s own width-animation convention (`WIDTH_ANIM_PX_PER_SECOND`, `FriendSidebarWidget.java:72`), which this component does not need to replicate; a future revision may add it if a consumer needs it (Future Extensions).
- Does not itself solve the "two features extend the same vanilla `Screen`" collision `architecture.md:76`'s Shared-screen extension point already covers — that is a different concern (screen-level layout coordination) from this document's (a single reusable control's own internal rendering/hit-testing), and is out of scope here.
- Does not become a new Gradle submodule (no `settings.gradle` change, no new `build.gradle`) — it is plain source duplicated per platform module, following exactly the same non-modularized duplication convention `FriendSidebarWidget`/`FriendContextMenuWidget` already use, not a new shared *library*.
- **(v2, new)** No `features/server-browser` involvement of any kind — confirmed (Overview, v2 Amendment) that feature does not consume `DropdownWidget` today; this revision does not modify, reference, or make any assumption about that feature's `src/`.
- **(v2, new)** No 9-slice/textured button chrome (e.g. reusing vanilla's `Button`/`widgets.png` sprite) — Problem 1's fix (Requirements UI-FR8) stays within this repo's existing `fill`/`text`-only convention (border via a second, inset `fill` or explicit outline draw, hover-highlight via a brighter/alternate fill color), matching this document's pre-existing UI section's "no 9-slice/texture assets" line (unchanged).
- **(v2, new)** No change to `DropdownWidget`'s selection/open-close state machine, constructor shape, or `onSelectionChanged` callback contract (UI-FR1/UI-FR3, unchanged) — this revision is rendering-and-hover-affordance-only; `mouseClicked()`'s hit-testing logic is unaffected except where UI-FR11 below explicitly extends `render()`'s height contract.
- **(v2, new — Problem 5's fix)** `DropdownWidget` itself does not gain any import of, or dependency on, `FriendsSidebarZOrder` or any other `friends-sidebar`-specific type (UI-FR6, unaffected) — the overlay render entry point (UI-FR15) is a generic, feature-agnostic method; it is each embedding widget's own responsibility (Architecture, `friends-sidebar`'s own v1.5 amendment addendum) to invoke it from whatever z-order/overlay mechanism that embedding widget already uses. `DropdownWidget` does not itself know it is being layered above or below anything.

## Requirements

**Core control shape**
- **UI-FR1.** Constructed with an ordered list of options, each carrying a short label (`String`) and an optional longer description (`String`, nullable/empty), plus an initial selected index. Exact constructor/record shape is a planning decision; illustrative shape: `new DropdownWidget(List<DropdownWidget.Option> options, int initialSelectedIndex, IntConsumer onSelectionChanged)` where `record Option(String label, String description)`.
- **UI-FR2.** Two visual states: **closed** (renders only the current selection's short label inside a single-row control, matching the closed-state footprint of the control it replaces, `FriendSidebarWidget`'s existing `DROPDOWN_HEIGHT`-sized strip, `FriendSidebarWidget.java:87`) and **open** (renders the closed-state row *plus* a list of every option stacked directly beneath it, each option row the same height as the closed-state row, each individually hit-testable). **(v2 amendment — Problem 5)** The open-state option list is now rendered via a separate overlay entry point (UI-FR15), not as part of the same draw call as the closed-state row — see UI-FR15-UI-FR18 for the exact split; this does not change the *visual* stacking/footprint this requirement describes, only *which method call* paints it and *when, relative to other content,* that call happens.
- **UI-FR3.** Clicking the closed-state row toggles it to open. Clicking an option row while open selects that option (invokes the caller's `onSelectionChanged`/equivalent callback with the new index), then closes. Clicking anywhere else while open (a caller-supplied "outside" test, since this widget does not itself know the full screen's bounds) closes without changing the selection. Clicking the closed-state row's own area while already open closes it without changing the selection (a second click on the same spot toggles closed, not re-opens). **(v2 amendment)** Unaffected by Problem 5's render-call split (UI-FR15) — `mouseClicked(x, y, button)` (UI-FR4) remains a single method covering both the closed row and, while open, every option row, regardless of which of the two render methods (UI-FR15) most recently painted them; only *rendering* is split, not hit-testing.
- **UI-FR4.** Exposes enough state/hit-testing surface for an embedding widget's own `mouseClicked`/`renderNow`-equivalent methods to drive it correctly inside a manually-driven render loop (Goals) — at minimum: `boolean isOpen()`, a way to render the closed state (plus label/chrome) at a given `(x, y, width)` for a frame and get back the total height it consumed that frame (since the open state is taller than the closed state and the embedding widget's own layout, e.g. `FriendSidebarWidget.listTopOffset()`, must account for that), a way to render the open-state option list as a separate overlay call (UI-FR15), and a way to feed a `mouseClicked(x, y, button)` event to it and learn whether it was consumed. Exact method names are a planning decision; the shape must not assume it is itself a `Screen`-registered `AbstractWidget`/`ClickableWidget` — it may optionally *be* one, or may be a plain helper object an embedding widget composes, whichever a planning pass determines fits `FriendSidebarWidget`'s existing hand-drawn convention more cleanly (Architecture).
- **UI-FR5.** Renders both label and (while open, per-row) description content, matching this repo's existing legibility requirements for the control it is first built to replace (`features/friends-sidebar/specification.md` FR7.4). **(v2 amendment — supersedes the "hover-reveals-description... beneath the row" delivery mechanism only, not the legibility requirement itself)** Per-row description text is delivered via a native tooltip (UI-FR12/UI-FR13), not inline body text drawn beneath the row (Overview, Problems 3/4) — this changes *how* the description is revealed, not *whether* it is available or *when* (still hover-gated, still per-row, still optional/omitted when a row's `description()` is null/empty). The tooltip call itself is issued from whichever of the two render methods (UI-FR15) is currently painting the hovered row (the closed-row/label render call when closed or when the mouse is over the closed row while open; the open-state overlay render call for any option row).

**Reusability**
- **UI-FR6.** Contains zero import of any feature's `api`/`services` types (no `JoinPolicy`, no `FriendSummary`, etc.) — the caller supplies plain `String` labels/descriptions and receives back a plain `int` index; feature-specific meaning is entirely the caller's responsibility to map to/from. **(v2 amendment)** Also contains zero import of `de.lazuli.api.friends.FriendsSidebarZOrder` or any other `friends-sidebar`-specific type (Non-goals) — the overlay split (UI-FR15) is expressed purely as "a second render method the caller may invoke separately, whenever/wherever it chooses," never as a dependency on any specific z-order enum.
- **UI-FR7.** Duplicated identically (structural twin, same convention as `FriendSidebarWidget`/`FriendContextMenuWidget`) across all three platform modules (`platform/fabric-1.21.11/src/main/java/de/lazuli/ui/DropdownWidget.java`, `platform/fabric-26.1/...`, `platform/fabric-26.2/...`), differing only in the per-version base-class/`GuiGraphics`-vs-`GuiGraphicsExtractor` render-call idiom each module's other widgets already differ by (`FriendSidebarWidget`'s own already-confirmed per-module differences, implementation-plan-v1.3's Existing Implementation, "each module's own render-call idiom") — **(v2 amendment)** including, now, the per-module native-tooltip API call itself (Overview's per-platform discrepancy check: `DrawContext.drawTooltip(...)` on `fabric-1.21.11`, `GuiGraphicsExtractor.setTooltipForNextFrame(...)` on `fabric-26.1`/`fabric-26.2`), which joins the existing render-call-idiom list of "differs per module, otherwise structurally identical" concerns UI-FR7 already covers — this is not a new kind of divergence, just a new instance of the same already-established pattern.

**v2 — Button chrome (Problem 1)**
- **UI-FR8.** The closed-state row (and, while open, each option row) renders visible border/outline chrome in addition to today's flat background fill, so the control is visually identifiable as clickable at rest, without hovering it — e.g. a 1px inset or edge-drawn outline `fill`/rectangle in a lighter shade than `BACKGROUND`. Exact pixel values/colors are a planning/UX decision; the requirement is only that some non-flat, border-bearing chrome exists where none exists today (Overview, Problem 1). Applies identically regardless of which of the two render methods (UI-FR15) paints a given row.
- **UI-FR9.** The row currently under the mouse (the closed row when not open and the mouse is over it, or whichever open-state row the mouse is currently over) renders a visibly different (brighter/highlighted) background fill than a non-hovered row, so hovering communicates interactivity — matching the affordance vanilla's own `Button`/list-row hover-highlight convention already establishes elsewhere in the game, without adopting vanilla's texture-based button rendering itself (Non-goals). Since the open-state overlay render call (UI-FR15) happens in the same frame, immediately after the closed-row/label render call, both calls receive the same frame's `mouseX`/`mouseY`, so hover state is consistent across the split (no stale/lagging hover highlight from one frame to the next).

**v2 — Label (Problem 2)**
- **UI-FR10.** `DropdownWidget` gains an optional, generic `label` (`String`, nullable) — set once at construction, not per-`Option` — rendered by the control itself directly above (or, planning's choice, to the left of, if horizontal space allows within the caller-supplied `width`) the closed-state row, in addition to (not instead of) the row's own current-selection text. When `label` is `null`/empty, nothing renders and the control's total footprint is unchanged from today (backward compatible with any future caller that does not need a label). This is a **generic** capability (a plain `String`, UI-FR6-compliant, no feature-type leak) — the specific copy ("Who can join:") remains entirely the caller's own choice, supplied at construction the same way `Option` label/description text already is. **(v2 amendment — Problem 5 clarification)** The label always renders as part of the closed-row render call (UI-FR15's `render(...)`), never the open-state overlay call — it is always visible whenever the control's row is reserved space in the embedding widget's layout (open or closed), and its position within that layout is already accounted for by the embedding widget's own reserved footprint, so it does not share Problem 5's "content drawn afterward can cover it" defect the way the *transient, non-reflowing* open-state option list does (UI section, below, explains this distinction in full).
  - **Design decision (this revision, recommended):** own the label inside `DropdownWidget` itself (UI-FR10, above) rather than have each embedding widget draw a separate label string alongside the control. **Tradeoff considered:** the alternative (`FriendSidebarWidget` draws its own `"Who can join:"` text at a caller-chosen position next to/above the dropdown, `DropdownWidget` itself unchanged) avoids growing `DropdownWidget`'s height contract and keeps every rendering concern fully caller-owned, matching this document's existing "layout constants are the embedding widget's own choice, not hardcoded inside `DropdownWidget`" precedent (UI section, unchanged, "Closed-state footprint" bullet). It was rejected as the *primary* mechanism because a label is exactly the kind of "control needs a name" concern every future consumer of this generic component will independently re-solve if `DropdownWidget` does not offer it once, generically — the whole point of extracting a shared component (Goals) is to avoid each new consumer re-inventing presentation details like this; a plain nullable `String` constructor parameter is no less generic than `Option.label`/`Option.description` already are (UI-FR6 is unaffected either way — it constrains *types*, not *how many* strings the constructor accepts). The cost (every existing/future call site's total-height math, UI-FR11, must account for the label's extra row when present) is judged acceptable since `FriendSidebarWidget`'s `listTopOffset()`-style "read the returned height back from render()" pattern (UI-FR4/UI-FR11) already exists specifically to absorb variable-height changes like this without the caller needing to hardcode a height constant.
- **UI-FR11.** `render()`'s (UI-FR15's closed-row render call) returned total-height-this-frame (UI-FR4) includes the label row's height whenever `label` is non-null/non-empty, exactly as v1 already included the open-state option rows in that same return value — **(v2 amendment — Problem 5)** after this revision, that returned height covers only the closed-row-plus-label footprint (the fixed, reflow-reserved part of the layout); the open-state option rows are no longer part of this return value at all, since they now render via the separate, non-reflowing overlay call (UI-FR15) and were already established (Problem 3/UI-FR13) as not participating in layout/height accounting. No caller needs its own separate "did the label add a row" branch; the single returned `int` remains the sole source of truth for how much *reserved* vertical space this frame's closed-row render call consumed.

**v2 — Native tooltips (Problems 3 and 4)**
- **UI-FR12.** Per-row description text (UI-FR5) is delivered via Minecraft's native tooltip mechanism, queued for the current frame while the mouse hovers that specific row (closed row or, while open, any option row) with a non-null/non-empty `description()` — `DrawContext.drawTooltip(Text, mouseX, mouseY)` on `fabric-1.21.11` (Yarn), `GuiGraphicsExtractor.setTooltipForNextFrame(Component, mouseX, mouseY)` on `fabric-26.1`/`fabric-26.2` (Mojang) — per Overview's confirmed per-module API mapping. This entirely replaces the current inline wrapped-body-text-beneath-the-row rendering (`wrapMessage(...)`-based, `DropdownWidget.java:86-93` today) — no inline description text remains after this revision.
- **UI-FR13.** Because a native tooltip never occupies layout space (it draws in a separate, non-reflowing overlay pass) and is not counted in `render()`'s returned height (UI-FR4/UI-FR11) either before or after this revision, adopting UI-FR12 structurally resolves Problem 3's undercounted-height defect (Overview) — `render()`'s returned height after this revision reflects only the fixed closed-row-plus-label footprint (UI-FR11), never a variable, hover-conditional amount and never the open-state rows either (Problem 5), closing the gap between "what height was reserved" and "what was actually drawn" that the old inline-description mechanism left open.
- **UI-FR14.** Multi-line description text (today handled by `wrapMessage(...)` wrapping to the row's own pixel width) is instead handled by the native tooltip renderer's own line-wrapping/multi-line layout (both platforms' tooltip APIs already support multi-line `Text`/`Component` content) — `DropdownWidget`'s own `wrapMessage(...)` helper is no longer required for this purpose after this revision (may be removed or left unused/dead, planning's discretion — not itself a requirement).

**v2 — Open-state overlay / z-order (Problem 5, new this revision)**
- **UI-FR15.** `DropdownWidget`'s single `render(...)` method (v1 shape) is split into two separately-callable render methods:
  1. A **closed-row render call** (illustrative name: `render(guiGraphics, x, y, width, mouseX, mouseY, delta)`, keeping the v1 name/signature) that draws only the label (UI-FR10, if present), the closed-state row itself (current selection text, chrome, hover highlight — UI-FR8/UI-FR9), and (if a native tooltip applies to the closed row this frame) queues that tooltip (UI-FR12) — but never draws the open-state option rows, even while `isOpen()` is true. Returns the closed-row-plus-label height only (UI-FR11).
  2. A new **open-state overlay render call** (illustrative name: `renderOpenOverlay(guiGraphics, mouseX, mouseY, delta)`) that, only when `isOpen()` is true, draws the stacked option-row list (chrome, hover highlight, and — for whichever option row is hovered — its tooltip), using the `(x, y, width)` and row-height cached internally from that same frame's most recent closed-row render call (UI-FR16). Does nothing (no draw calls) when `isOpen()` is false, so an embedding widget may call it unconditionally every frame without its own `isOpen()` guard, though it may still choose to skip the call outright when closed as a minor optimization.

  This exactly mirrors the existing `extractWidgetRenderState()`-empty / public-`renderNow()` split `FriendSidebarWidget`/`FriendContextMenuWidget` already use (Existing Implementation) — the closed-row call is `DropdownWidget`'s own analogue of a normal, in-layer render call (invoked from within the embedding widget's own `renderNow()`, exactly as today, `FriendSidebarWidget.java:390-391`), while the new overlay call is `DropdownWidget`'s own analogue of `FriendContextMenuWidget.renderNow()` — a call the *embedding widget* is responsible for invoking from its own top-level, always-drawn-last overlay hook (`features/friends-sidebar/specification.md`'s v1.5 amendment addendum specifies exactly how `FriendSidebarWidget` does this).
- **UI-FR16.** `DropdownWidget` internally caches the `(x, y, width)`, row height, and open/closed option list from its most recent closed-row render call (UI-FR15 item 1), so `renderOpenOverlay()` (UI-FR15 item 2) needs no positional arguments re-passed by the caller — only `(guiGraphics, mouseX, mouseY, delta)`. This relies on the embedding widget calling the closed-row render method at least once earlier in the same frame before calling `renderOpenOverlay()` that same frame (true today: `FriendSidebarWidget.renderNow()`, called from the `SIDEBAR`-ordinal hook, always runs before the new overlay-ordinal hook within the same `onAfterExtract` invocation — `features/friends-sidebar/specification.md`'s v1.5 amendment addendum). If `renderOpenOverlay()` is ever called in a frame where the closed-row method was not first called that same frame, it draws using whatever bounds were cached from the last frame it *was* called (stale-but-harmless single-frame lag at worst — not a scenario expected to occur given the fixed call order above, but not a crash/exception condition either).
- **UI-FR17.** `mouseClicked(x, y, button)` (UI-FR4) is unaffected in its own external contract by the UI-FR15 render split — it continues to hit-test against the same cached `(x, y, width)`/row-height/open-option bounds (UI-FR16) regardless of which render method most recently painted them, so no embedding widget's existing click-forwarding code (`FriendSidebarWidget.java`'s existing `joinPolicyDropdown.mouseClicked(...)` call) needs to change as a result of Problem 5's fix.
- **UI-FR18.** Because `renderOpenOverlay()` (UI-FR15) is a plain method the embedding widget calls directly (like `FriendContextMenuWidget.renderNow()`), `DropdownWidget` itself requires no new constructor argument, no new dependency on any z-order type, and no awareness of *how* or *whether* the embedding widget layers it above other content (Non-goals) — the entire z-order integration is the embedding widget's own responsibility, exactly as it already is for `FriendContextMenuWidget` today.

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision.
1. `platform/fabric-<version>/.../ui/DropdownWidget.java` — the control itself (UI-FR1-UI-FR5, UI-FR8-UI-FR18), one structurally-identical copy per platform module (UI-FR7).
2. `platform/fabric-<version>/.../ui/DropdownWidget.Option` (nested `record`) — `(String label, String description)`, zero feature-type dependency (UI-FR6), unchanged by v2.
3. **(v2, new)** `DropdownWidget`'s constructor gains one new, optional, nullable `String label` parameter (UI-FR10) — illustrative shape: `new DropdownWidget(String label, List<DropdownWidget.Option> options, int initialSelectedIndex, IntConsumer onSelectionChanged)`, or an overload retaining the old no-label constructor for callers that don't need one — exact shape (new parameter position, overload vs. single new-arity constructor, `Optional<String>` vs. plain nullable `String`) is a planning decision.
4. **(v2, new — Problem 5's fix)** `DropdownWidget` gains a new public method for the open-state overlay render call (UI-FR15 item 2) — illustrative shape: `void renderOpenOverlay(GuiGraphicsExtractor guiGraphics, int mouseX, int mouseY, float delta)` on `fabric-26.1`/`fabric-26.2` (Mojang), `void renderOpenOverlay(DrawContext context, int mouseX, int mouseY, float delta)` on `fabric-1.21.11` (Yarn) — mirroring each module's existing `render(...)`/`renderNow(...)` parameter idiom (UI-FR7). Exact name is a planning decision but must be distinguishable from the existing `render(...)` method (UI-FR15 item 1) at the call site, since an embedding widget now calls both, from two different places, in the same frame.

## Architecture
```
platform/fabric-<version>/src/main/java/de/lazuli/
  friends/
    FriendSidebarWidget.java        (existing, feature-shaped widget; consumes DropdownWidget, v1.4; v2 polish + overlay wiring, this revision)
    FriendContextMenuWidget.java    (existing, unaffected)
    FabricFriendsSidebarInjector.java (existing; v2 amendment adds one new afterExtract-driven call for the dropdown overlay, see below)
  ui/                                (new, v1; polish + overlay split, v2, this revision)
    DropdownWidget.java
```
`de.lazuli.ui` is a new, non-feature-named package sibling to `de.lazuli.friends` within each platform module — same module, same "Platform-layer widget code" classification as the existing `friends` package, just not named after any one feature, so any future platform-layer widget code (for `server-browser` or otherwise) can import it the same way `FriendSidebarWidget` will (v1.4) without that import crossing a Feature→Feature boundary (it never did — both are Platform-layer classes; the Dependency Rules table's Feature→Feature prohibition governs `features/*` modules' own source, which this was never part of). No composition-root/ADR-0003-style bridging is needed for this dependency, unlike the cross-feature `JoinPolicy`↔`HostGateway` bridging `features/friends-sidebar/specification.md`'s v1.3 Architecture section required — `DropdownWidget` and any future consumer widget already coexist in the same Platform module and layer.

This is **not** registered as a `services/`-layer capability (`architecture.md:26`'s graduate-on-second-use rule) because `services/` is constrained to plain-JVM, Minecraft-class-free code (`services/specification.md:39`, NFR5) and this component is inherently Minecraft-GUI-coupled — the graduate-on-second-use rule's premise (a capability *could* live feature-local until a second consumer justifies extraction) does not apply to a class that structurally cannot live feature-local in the first place (Overview).

**(v2, new)** This revision touches `DropdownWidget.java` (rendering/hit-testing internals, UI-FR8-UI-FR18) and its sole existing call site's file, `FriendSidebarWidget.java` (construction/render/click-forwarding of `joinPolicyDropdown`, plus — new, Problem 5 — a small overlay-forwarding addition and one new method exposed for `FabricFriendsSidebarInjector` to call, `friends-sidebar` v1.5 amendment addendum, `features/friends-sidebar/specification.md`) and, **new this revision**, `FabricFriendsSidebarInjector.java` (one additional `onAfterExtract`-driven call, between the existing `activeSidebar.renderNow(...)` and `openMenu.renderNow(...)` calls — full detail in `features/friends-sidebar/specification.md`'s v1.5 amendment addendum, since the exact call site and ordering is that file's `FriendsSidebarZOrder`-integration concern, not a generic `DropdownWidget`-level one). `DropdownWidget` itself gains no dependency on `FriendsSidebarZOrder` or the injector (Non-goals, UI-FR18) — this document specifies only that `DropdownWidget` exposes the two-method split (UI-FR15); which concrete z-order ordinal a given embedding widget uses, and how its own injector wires the call, is that embedding widget's own specification's concern. No new package, class, or Gradle module is introduced.

## UI
- **Closed-state footprint**: single row, same height as the control it first replaces (`FriendSidebarWidget`'s `DROPDOWN_HEIGHT`, `FriendSidebarWidget.java:87`) — exact pixel constants are the embedding widget's own choice, not hardcoded inside `DropdownWidget` itself (UI-FR6's "no feature-specific values baked in" extends to layout constants, not only types). **(v2)** Plus, when `label` is set (UI-FR10), one additional row-equivalent of label text directly above it, and border/hover chrome (UI-FR8/UI-FR9). **(v2, Problem 5)** This entire footprint (label + closed row) is drawn by the closed-row render call (UI-FR15 item 1) and is the only part of `DropdownWidget`'s output whose height is reserved in the embedding widget's own layout (UI-FR11) — it is not affected by the overlay split, since it was never the part that could be covered (it occupies a fixed, reflow-reserved position other content is laid out around, the same way any other sidebar row is).
- **Open-state footprint**: closed-state row (plus label row, if any) + one row per option, each the same row height, stacked directly beneath, drawn on top of (not reflowing) whatever content would otherwise occupy that screen space for that frame — matching the transient, non-reflow-stable convention `FriendSidebarWidget`'s existing hover-description text already established (`FriendSidebarWidget.java:220`'s Decision 2 framing, carried into this component's own open state). **(v2)** Per-row description text is no longer part of this footprint at all (UI-FR12/UI-FR13) — it now renders via the native tooltip overlay, entirely outside this control's own layout footprint. **(v2, Problem 5 — new)** The option-row portion of this footprint (everything *except* the closed row/label, which stays part of the closed-state footprint above) is now drawn by the separate overlay render call (UI-FR15 item 2), invoked by the embedding widget from its own top-level, always-drawn-last overlay hook — for `FriendSidebarWidget`, this is a new ordinal in `FriendsSidebarZOrder`, drawn after `SIDEBAR` (so it is never covered by later `SIDEBAR`-layer content) — exact ordinal placement relative to `CONTEXT_MENU` is specified in `features/friends-sidebar/specification.md`'s v1.5 amendment addendum, not here, since `DropdownWidget` itself has no opinion on it (UI-FR18).
- **Visual style**: background fill + text, matching this repo's only existing precedent (`guiGraphics.fill`/`guiGraphics.text`, `FriendSidebarWidget.java` throughout) — no 9-slice/texture assets, no new resource files (Configuration/Networking/Persistence: none). **(v2)** Plus border/outline chrome and a hover-highlighted background variant (UI-FR8/UI-FR9), still `fill`-based, no new assets.
- **(v2, new) Tooltip style**: whatever vanilla's own native tooltip box looks like on each platform (dark rounded background, drop shadow, vanilla's own text color/padding) — this control does not customize tooltip appearance, it only supplies the text content and triggers the platform's existing tooltip call (UI-FR12).
- Manual, per-supported-version in-game verification is required (not unit-testable, consistent with every other rendering concern in this repo's only existing custom widgets) — **(v2)** including, specifically, confirming the native tooltip actually renders (not merely compiles) on all three platform modules, since tooltip-triggering APIs are frame-timing-sensitive (`setTooltipForNextFrame`'s name is a direct hint: it must be called during that frame's own render pass, not cached/deferred) and this class of bug would not surface at compile time. **(v2, Problem 5, new)** Also including confirming, specifically, that the open-state option list now visibly draws on top of the scrollable friend-row list beneath it (the concrete symptom that motivated this fix) — e.g. by opening the join-policy dropdown with enough friends online that the friend list extends into the same screen region the open option list occupies, and visually confirming no clipping/covering occurs, on all three platform modules.

## Compatibility
- Must be implemented identically (structural twin) across all three platform modules (UI-FR7) — differs only in per-version base-class (`AbstractWidget` vs. the Yarn-mapped `ClickableWidget`) and render-call idiom, exactly as `FriendSidebarWidget`'s existing per-module differences already established; no new cross-version risk beyond what that file already carries. **(v2)** The one specifically-tracked new per-module divergence is the native-tooltip API call itself (Overview's per-platform discrepancy check) — already resolved/documented, not an open risk.
- Any future consumer embedding `DropdownWidget` inside its own manually-driven render loop (Goals) should confirm, at its own planning phase, that its render loop calls this widget's render/click-hit-test methods with mutually consistent bounds across a single frame, mirroring the discipline `features/friends-sidebar/specification.md`'s v1.3 Architecture "Risk 2" (hit-testing across an animated-width state) already established for a comparable, previously-solved problem in `FriendSidebarWidget` itself.
- **(v2, new)** Any future consumer relying on `render()`'s returned total height (UI-FR4/UI-FR11) to reserve layout space must re-verify that reservation after this revision if it previously (incorrectly) assumed the old inline-description height was already included — it never was (Overview, Problem 3's root-cause finding) — this revision does not change that contract's meaning, only removes the one code path (inline description) that could have made a caller's layout look coincidentally-correct despite the undercount.
- **(v2, new — Problem 5)** Any future consumer of `DropdownWidget` must, at its own planning phase, wire `renderOpenOverlay()` (UI-FR15 item 2) into whatever top-level "always drawn last" overlay mechanism its own render loop already has (or add one, following `FriendContextMenuWidget`'s existing `FriendsSidebarZOrder`-driven pattern as precedent, if it doesn't yet have one) — a consumer that continues calling only the closed-row `render()` method and never calls `renderOpenOverlay()` will silently never draw the open-state option list at all (it will still be clickable-in-theory per `mouseClicked()`'s cached bounds, UI-FR17, but invisible), which is a straightforward integration mistake to catch during that consumer's own in-game verification (UI section).

## Performance
Negligible — a handful of extra `fill`/`text` calls only while a dropdown is actually open, no per-tick work when closed, no new native/IPC calls, no new asset loads. **(v2)** The native tooltip call is a single additional per-hovered-row method call per frame, no different in cost class from vanilla's own ubiquitous tooltip usage elsewhere in the game. **(v2, Problem 5, new)** The overlay render split (UI-FR15) adds one additional method call per frame from the embedding widget's own overlay hook (a no-op early-return when closed, UI-FR15) — the same negligible cost class as `FriendContextMenuWidget.renderNow()`'s existing per-frame call from the same hook.
