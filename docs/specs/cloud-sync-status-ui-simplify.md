# Cloud Sync Status UI — Simplification Specification

## Overview
The "Cloud Sync Status UI" feature (`docs/specs/cloud-sync-status-ui.md`, `docs/plans/cloud-sync-status-ui.md`) shipped a per-world row in `WorldsPanel.java` (near-identical across `platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`) with up to **four** 8px indicator squares plus the Play/Edit pill buttons: a toggle square (sync on/off), a terminal-status-or-in-progress square (synced/error/skipped/spinner), a freshness square (up-to-date/stale/unknown), and a conflict square (shown only when a two-sided conflict is pending). The user finds this too much information.

This spec **simplifies** the row to exactly **two** indicator squares: the existing toggle square (unchanged), and a single new **consolidated sync-state** square replacing the other three. It also adds a new requirement that a world with a sync in progress must not be playable **or editable**, and requires every indicator to carry a hover tooltip for every state it can be in.

This is a UI consolidation only. It reuses existing backend hooks/data wherever possible; it does not change `WorldSaveSyncService`'s sync algorithm, `CloudSyncCoordinator`'s trigger points, or `WorldRestoreService`. The one new backend capability it surfaces a gap for — a true "download in progress" signal — is flagged as a limitation, not built, per Non-goals.

## Goals
- Reduce the Worlds-tab row to exactly two indicator squares: the existing sync-toggle square (position/semantics unchanged) and one new consolidated status square.
- The consolidated status square has exactly four possible states: **Unsynced**, **Syncing** (with an upstream/downstream distinction inside that one state, see Requirements), **Synced**, **Conflict**.
- While a world's sync is in progress, that world's **Play and Edit buttons** must both be disabled (greyed out) and non-clickable, each with a tooltip explaining why.
- Every indicator square (both the toggle and the new consolidated status square) must show a hover tooltip with concrete, state-specific text for every state it can be in — this generalizes and continues the existing `FR-U` tooltip-detail work rather than replacing it.
- Remove the freshness square and the standalone conflict square as separate always-drawn elements; their information is folded into the one consolidated square.

## Non-goals
- No change to `WorldSaveSyncService`, `CloudSyncCoordinator`, `CloudSyncableReconciler`, `WorldRestoreService`'s internal sync/reconcile/restore algorithms — this is a `WorldsPanel.java` (+ the small hook-surface changes needed to feed it) rendering/consolidation change only.
- No change to `WorldConflictScreen`'s own contents, its "Keep Local"/"Keep Cloud" actions, or `WorldSyncAncestor`/`checkConflictFor`'s conflict-detection algorithm — this spec only changes how the Conflict state is *indicated* on the row (folded into the one square, still clickable, still opens `WorldConflictScreen`), not how it is *computed* or *resolved*.
- **True per-world "download/restore in progress" tracking is out of scope.** As documented at length in the base spec (F1–F4, F17), no backend signal for "downloading right now" exists for the ordinary world-row upload path — `WorldSyncStatusHook.isUploadInProgress` only ever reflects an *upload*. The base spec's `WorldRestoreService.activeRestores` tracks the cloud-only-world *restore* flow (a distinct row type, synthetic cloud-only rows, not a real world row), and that is deliberately not surfaced to `WorldsPanel` rows either (base spec's resolved Non-goal, F4). This spec's "distinguish upstream vs downstream direction" requirement is therefore satisfied using the one upload-in-progress signal that exists today plus a lightweight new signal for the one already-existing download-oriented operation that *can* apply to a real world row — see FR-3 for exactly what is and is not achievable without new backend work, and Future Extensions for what a true downstream (content-pull) progress signal would require.
- No new sync trigger points, no change to `WorldFingerprint`/`WorldSyncAncestor` persistence, no new Steam Cloud API calls.
- No change to the cloud-only synthetic world rows' own rendering (`cloudOnlyWorlds` loop) or to `WorldRestoreScreen` — those remain as-is; they already show their own honest progress/phase text and are unaffected by this consolidation.
- Not a redesign of row layout, icon size/shape conventions, colors chosen for unrelated states, or the general Play/Edit button visuals when not syncing — only the sync-related square count and the Play/Edit buttons' disabled-during-sync state change.

## Requirements

### Current-state findings (this pass, `platform/fabric-26.2/.../WorldsPanel.java` read in full; identical shape assumed in `fabric-26.1`/`fabric-1.21.11` per the base plan's confirmed per-module parity, to be re-verified at implementation time)

- **F1** Today's row draws, right-to-left from the row's right edge: toggle square (`syncIconLeft`, `COLOR_SYNC_ENABLED`/`COLOR_SYNC_DISABLED`, `WorldsPanel.java:398-400`), then a terminal-status-or-spinner square in the same slot (`drawTerminalStatusIcon`/`drawInProgressIndicator`, `WorldsPanel.java:422-425`), then (only if sync enabled and not in-progress) a freshness square (`drawFreshnessIndicator`, `WorldsPanel.java:428-430`), then (only if a conflict is pending) a conflict square (`drawConflictIndicator`, `WorldsPanel.java:432-438`). Up to 4 squares total, 0 minimum (no hooks available) or when disabled+not-in-progress, just 1 (toggle) or 2 (toggle + terminal-status if a terminal status is recorded).
- **F2** Backing hooks/enums already exist and are reused by this spec: `WorldSyncToggleHook.isSyncEnabled`/`toggleSync` (toggle square, unchanged by this spec); `WorldSyncStatusHook.statusFor` → `SyncStatus{NOT_SYNCED,SYNCED,SYNC_ERROR,SKIPPED_TOO_LARGE}` and `WorldSyncStatusHook.isUploadInProgress` (terminal/in-progress square); `WorldFreshnessHook.upToDateStatusFor`/`upToDateStatusDetailFor` → `UpToDateStatus{UP_TO_DATE,STALE,UNKNOWN}` + `FreshnessDetail` (freshness square); `WorldConflictHook.checkConflictFor` → `ConflictStatus{NONE,CONFLICT}` (conflict square). All four interfaces live in `api/src/main/java/de/lazuli/api/cloudsync/`.
- **F3** `isUploadInProgress` is upload-only (base spec F1/F2, confirmed unchanged in current code — `WorldSaveSyncService.onWorldUnload`/`syncWorldNow` are the only callers of `markUploadPending`/`markUploadFinished`). There is **no existing "downstream"/download-in-progress concept for a real (non-cloud-only) world row**. The only download-shaped operation that can touch an already-real world row today is `WorldConflictScreen`'s "Keep Cloud" action, which internally calls `WorldRestoreService.beginRestore` (base plan addendum, Decision 9) — this already has its own `RestoreProgressListener`/phase machinery, currently only consumed by `WorldRestoreScreen`/`WorldConflictScreen` itself, not read by `WorldsPanel`. **Flagged as new capability needed** if a literal "row shows spinner in the downstream direction while Keep-Cloud restore runs" behavior is desired — see FR-3 and Future Extensions. This spec's default (see FR-3) treats "downstream" as covering the case where the row's freshness data indicates the *other device* is ahead (a `STALE`/other-device-fingerprint condition) shown as a distinct sub-label within the Syncing state's tooltip when a "Keep Cloud" resolution is actively running, using `WorldConflictScreen`'s already-existing `RestoreProgressListener` wired to a new tiny per-world flag `WorldsPanel` can read — see FR-3.2.
- **F4** Play/Edit buttons: both rendered unconditionally for an expanded row (`WorldsPanel.java:341-350`), no disabled state exists today for either. `mouseClicked` already has a precedent for a row being made fully non-interactive: the `isUploadInProgress` check at `WorldsPanel.java:592-600` returns `true` (consumes the click, no-ops) for *any* click anywhere in the row, checked before the Play/Edit pill hit-test. This exact mechanism is the direct precedent FR-4 reuses for "Play and Edit must no-op during sync" — unlike the earlier draft of this spec, FR-4 now blocks **both** buttons identically (editing a world's settings while a background upload/download is running for that same world folder risks racing the sync's own file reads, so gating both is the correct, not merely simpler, choice).
- **F5** `WorldConflictHook`/`ConflictStatus` and `WorldFreshnessHook`/`UpToDateStatus` are already **separate, minimal, additive interfaces** (each hook file's own Javadoc states this deliberately) — consolidating their *display* into one square does not require merging these interfaces; `WorldsPanel` can (and should) keep reading all three hooks (`WorldSyncStatusHook`, `WorldFreshnessHook`, `WorldConflictHook`) and simply combine their outputs into one rendered square + one tooltip string, as specified in FR-2.

### New consolidated status model

**FR-1 (four-state model, computed from existing hooks, precedence order fixed).** The consolidated status square shows exactly one of four states, computed in this precedence order (highest first) each time the row's status is (re)computed (same cadence as today's freshness/conflict cache: at `reload()`, and at an `isUploadInProgress` true→false transition detected once per render frame, unchanged from the current `previouslyInProgress` mechanism):

1. **Conflict** — `WorldConflictHook.checkConflictFor(...) == ConflictStatus.CONFLICT`. Takes precedence over everything else, including an in-progress upload, since a conflict found before or during an upload still needs the player's resolution once the upload finishes; while the upload itself is running, both are true simultaneously and Conflict still wins for display purposes (the in-progress spinner does not visually appear during this specific overlap — Syncing's own precedence is only ever reached when Conflict is not already true).
2. **Syncing** — `WorldSyncStatusHook.isUploadInProgress(worldSlug) == true` (upstream case, always available), **or** a "Keep Cloud" restore is actively running for this world per the new lightweight tracking in FR-3.2 (downstream case). Not reached if Conflict (1) is already true.
3. **Synced** — sync is enabled (`WorldSyncToggleHook.isSyncEnabled == true`) and `WorldFreshnessHook.upToDateStatusFor(...) == UpToDateStatus.UP_TO_DATE`. Not reached if (1) or (2) apply.
4. **Unsynced** — the fallback: sync is disabled, or sync is enabled but freshness is `STALE` or `UNKNOWN`, or `WorldSyncStatusHook.statusFor(...)` is `SYNC_ERROR`/`SKIPPED_TOO_LARGE`/`NOT_SYNCED` and no upload has ever completed. This single "Unsynced" bucket intentionally collapses what were previously distinct terminal-status colors (`SYNC_ERROR` vs `SKIPPED_TOO_LARGE` vs never-synced) and the previous `STALE`/`UNKNOWN` freshness colors — the distinction survives only in the tooltip text (FR-5), not as a separate visual color/shape, per the user's explicit ask to reduce visual states to four.

**FR-2 (single square, single color-per-state, replaces three prior squares).** Remove `drawFreshnessIndicator` and `drawConflictIndicator` as independently-drawn squares. Replace `drawTerminalStatusIcon`/`drawInProgressIndicator`'s combined slot with one new `drawConsolidatedStatusIndicator` method occupying that same one slot (immediately left of the toggle square, same `SYNC_ICON_MARGIN`/`SYNC_ICON_SIZE` geometry as today). Four new distinct colors, one per FR-1 state (exact hex values are an implementation-time/planning decision; must be visually distinguishable from each other and from `COLOR_SYNC_ENABLED`/`COLOR_SYNC_DISABLED`; reusing the closest semantically-matching existing color per state — e.g. `COLOR_SYNC_ERROR`-family for Unsynced, `COLOR_SYNC_SYNCED`-family for Synced, `COLOR_IN_PROGRESS_*` for Syncing, `COLOR_CONFLICT` for Conflict — is an acceptable and encouraged starting point to minimize unrelated churn). The Syncing state's existing indeterminate spinner/marquee animation (`IN_PROGRESS_ANIMATION_PERIOD_MS`, `drawInProgressIndicator`'s highlight logic) is retained for the Syncing state specifically, not for the other three (which remain static fills, as today).

**FR-3 (upstream vs downstream distinction within Syncing).**
- **FR-3.1 (upstream — no new tracking).** When `WorldSyncStatusHook.isUploadInProgress(worldSlug)` is true, the square renders the Syncing state and its tooltip reads "Uploading to Steam Cloud..." (see FR-5 for full tooltip text table). This is the common case and needs no new backend work — it reuses the existing `isUploadInProgress` flag exactly as today's `drawInProgressIndicator` does.
- **FR-3.2 (downstream — new, minimal tracking, scoped to the "Keep Cloud" restore action only).** Add a small new session-only signal, `boolean isDownloadInProgress(String worldSlug)`, to a hook `WorldsPanel` already reads or a new minimal one (planning to decide: either widen `WorldSyncStatusHook` with a second default-`false` method, mirroring how `isUploadInProgress` itself was added as a default method, or add it to `WorldConflictResolutionHook`/a new tiny hook — the addition must not require any change to `WorldRestoreService`'s own internals). The single call site that sets this flag is `WorldConflictScreen`'s existing "Keep Cloud" action (`WorldRestoreService.beginRestore(...)`'s `RestoreProgressListener`): mark the flag true immediately before calling `beginRestore`, false in the listener's `onComplete`/`onFailed`. This is intentionally the **only** downstream case covered — a general "is Steam Cloud currently pushing data down to this world for any reason" signal does not exist and is not built (see Non-goals/F3); this is a narrow, cheap addition that covers the one concrete downstream flow already reachable from a real (non-cloud-only) world row. When true, the square renders the Syncing state and its tooltip reads "Downloading from Steam Cloud..." (FR-5). If both an upload and a "Keep Cloud" download were somehow concurrently true for the same world (should not occur in practice since Conflict/its resolution and an ordinary upload are not expected to race — flag as an edge case for implementation to confirm cannot actually happen given `hasPendingConflict`'s existing guard blocking `onWorldSaved`/`checkAndUploadStaleWorldsAtStartup` while a conflict is unresolved, per the base plan's Decision 9), upstream tooltip text takes precedence arbitrarily (implementation detail, not expected to be reachable).

**FR-4 (Play and Edit buttons disabled during sync).**
- **FR-4.1 (visual treatment, both buttons).** While the consolidated status is Syncing (FR-1 state 2, either upstream or downstream) for a given world, that row's **Play button and Edit button** (only relevant when the row is expanded, `WorldsPanel.java:341-350`) are both rendered in a visually disabled/greyed style — a muted fill color distinct from Play's normal `0xFF528A54`/hover `0xFF64A066` and distinct from Edit's normal `0xFF2E2E2E`/hover `0xFF3A3A3A` (e.g. a single shared flat grey such as `0xFF4A4A4A` for both buttons' fill while disabled, exact value an implementation decision), and each button's label text also dimmed (e.g. reuse the existing muted subtitle color `0xFF908C7F` in place of `0xFFFFFFFF`). Neither button visually reacts to hover (`playHover`/`editHover`) while disabled.
- **FR-4.2 (tooltip, both buttons).** While disabled per FR-4.1, hovering **either** button's bounds shows the same tooltip: **"Cannot play or edit while syncing with Steam Cloud."** This is a new tooltip attachment point for both buttons — today neither Play nor Edit has any tooltip at all.
- **FR-4.3 (click no-op, both buttons).** `mouseClicked`'s existing Play-button hit-test (`WorldsPanel.java:605-609`) **and** its Edit-button hit-test (`WorldsPanel.java:610-614`) must each check the same Syncing condition before calling `playWorld(summary)`/`editWorld(summary)` respectively; if syncing, the click on either button is consumed (return `true`, mirroring the existing full-row block precedent at `WorldsPanel.java:592-600`) but neither the world-open flow nor `EditWorldScreen` is invoked. This replaces the earlier, narrower draft of this requirement (which gated Play only) — both hit-tests now share the identical guard condition, most naturally expressed as a single boolean computed once per row (e.g. `boolean rowSyncing = ...`) and checked before both button branches, rather than duplicating the hook lookup twice.
- **FR-4.4 (Conflict does not gate Play/Edit).** A pending Conflict state (FR-1 state 1) does **not** by itself disable Play or Edit — only an active Syncing state (upstream or downstream) does. A world can be in Conflict without any operation currently running (the player simply hasn't opened `WorldConflictScreen` yet); blocking either button in that case would be an unrelated, unrequested restriction. If a conflict's resolution action is actively running (e.g. mid-"Keep Cloud" restore), FR-3.2's downstream Syncing state already covers gating both buttons for that window.

**FR-5 (tooltip content, every state, both squares).**

Toggle square (unchanged mechanism, tooltip content is *new* — today's toggle square has no tooltip at all per F1/current source, confirmed no `setTooltipForNextFrame` call exists in the toggle-square block, `WorldsPanel.java:396-400`):
- Enabled → **"Steam Cloud sync is ON for this world. Click to turn off."**
- Disabled → **"Steam Cloud sync is OFF for this world. Click to turn on."**

Consolidated status square, one tooltip string per FR-1 state, reusing the richest already-available detail exactly as today's `FR-U` tooltip work does (only computed when the row is hovered, per the existing `rowHovered` guard pattern, `WorldsPanel.java:467`/`541`):
- **Unsynced** → base text **"This world is not synced with Steam Cloud."**, extended with the most specific known reason when available (in priority order, reusing existing per-state detail exactly as today's collapsed states did): if `SyncStatus.SYNC_ERROR`, append the real error via `lastErrorFor` (e.g. "This world is not synced with Steam Cloud: {error}."); else if `SyncStatus.SKIPPED_TOO_LARGE`, append "(too large to sync automatically)"; else if sync is disabled, append "(sync is turned off for this world)"; else if `STALE`, append the existing `FR-U.1` detail text (same-device or other-device sub-case, reusing `FreshnessDetail` exactly as today's `freshnessTooltipFor`); else (`UNKNOWN`/never synced) append "(has not been synced yet)".
- **Syncing, upstream** → **"Uploading to Steam Cloud..."**
- **Syncing, downstream** → **"Downloading from Steam Cloud..."**
- **Synced** → **"Synced to Steam Cloud at {formatted ownSyncedAtTimestamp}."** (reuses today's existing `syncedTooltipFor`/`FR-U.3` logic verbatim).
- **Conflict** → unchanged from today's existing conflict tooltip text: **"This world changed on both this device and another device -- click to resolve."**

**FR-6 (removed elements — explicit, so planning treats this as removal work, not purely additive).**
- Remove `drawFreshnessIndicator` and its call site, `COLOR_FRESH_UP_TO_DATE`/`COLOR_FRESH_STALE`/`COLOR_FRESH_UNKNOWN` constants, and the freshness square's slot/geometry calculation (`freshnessLeft`) from `drawSyncIcons`.
- Remove `drawConflictIndicator` as an independently-rendered/independently-positioned square and its slot/geometry calculation (`conflictLeft`) — Conflict becomes one of the four states of the single consolidated square (FR-1/FR-2), not a 4th slot. Its click-to-open-`WorldConflictScreen` behavior (`mouseClicked`'s `conflictLeft` hit-test, `WorldsPanel.java:629-640`) moves to the consolidated square's hit-test region: clicking the consolidated square while its state is Conflict opens `WorldConflictScreen` exactly as today's dedicated conflict square did; clicking it in any other state is a no-op (display-only, matching today's freshness square's non-interactive behavior, `FR-Q.5`).
- Remove `drawTerminalStatusIcon`'s and `drawInProgressIndicator`'s standalone-method shape (folded into `drawConsolidatedStatusIndicator`, FR-2) — their existing color constants (`COLOR_SYNC_SYNCED`, `COLOR_SYNC_ERROR`, `COLOR_SYNC_SKIPPED`, `COLOR_IN_PROGRESS_BASE`/`HIGHLIGHT`) may be reused/renamed by the new method rather than necessarily deleted outright (planning's call — some map directly to the new four-state palette per FR-2's suggested reuse).
- `freshnessCache`/`conflictCache` fields may be retained as-is (they still back the FR-1 precedence computation) or merged into one `Map<String, ConsolidatedStatus>` cache — planning decision, not user-facing.
- The row's total sync-indicator footprint shrinks from up to 4 squares + margins to exactly 2 squares + margins, freeing horizontal space in the row (no requirement to use the freed space for anything else in this pass).

## Public API
- `WorldSyncStatusHook`: no signature change required for FR-3.1 (already has `isUploadInProgress`). FR-3.2 requires exactly one new default method, e.g. `default boolean isDownloadInProgress(String worldSlug) { return false; }`, added the same way `isUploadInProgress` was previously added (default method, backward compatible, per `WorldSyncStatusHook.java:72-74`'s own precedent) — planning to confirm final placement (this interface vs. a new minimal one) per FR-3.2.
- `WorldFreshnessHook`, `WorldConflictHook`: no interface changes required — both are read as-is, only `WorldsPanel`'s consumption of their outputs changes (combined into one rendered element instead of two).
- `WorldsPanel.java` (all three platform modules): remove `drawFreshnessIndicator`, `drawConflictIndicator` as separate rendering paths; add `drawConsolidatedStatusIndicator(GuiGraphicsExtractor, String worldSlug, int left, int top, int mouseX, int mouseY, boolean rowHovered)` returning/rendering the FR-1 state + FR-5 tooltip; extend both the Play-button and Edit-button rendering blocks and both of `mouseClicked`'s Play/Edit hit-tests per FR-4 (a single shared `rowSyncing` boolean, computed once per expanded row, should gate rendering for both buttons in `render()` and both hit-tests in `mouseClicked()`, to avoid the two call sites' guard conditions drifting out of sync with each other).

## Architecture
No new services, no new persisted state beyond FR-3.2's session-only in-memory flag (a `Set<String>`/`ConcurrentHashMap`, following the exact same shape as `WorldSyncStatusTracker`'s existing `inProgress` set — session-only, cleared on restart, consistent with the rest of this feature's session-only tracking discipline per the base spec's Non-goals). The consolidated-state computation (FR-1) is a pure function of three existing hooks' outputs, computed in `WorldsPanel` (not pushed down into a shared backend service), consistent with the base feature's existing pattern of `WorldsPanel` itself combining hook outputs (it already does this today across `drawSyncIcons`'s four separate calls) — this spec only narrows four separate draws into one.

## UI
- Row layout: two 8px squares at the row's right edge (toggle, then consolidated status immediately to its left), same `SYNC_ICON_MARGIN`/`SYNC_ICON_SIZE` spacing as today, same vertical position (`top = rowY + SYNC_ICON_MARGIN`).
- Play and Edit buttons (expanded row only): both render with their normal colors/hover-react as today when the row is not syncing; while syncing, both render with the shared muted grey fill, dimmed label, no hover-react, and a shared tooltip (FR-4). `render()`'s existing Play/Edit block (`WorldsPanel.java:341-350`) and `mouseClicked()`'s existing Play/Edit hit-test block (`WorldsPanel.java:601-614`) both need this guard added identically — this is the one place in this spec where two separate call sites (one per button, times two for render vs. click) must all read the same `rowSyncing` condition to avoid inconsistent behavior (e.g. Play greyed out but still clickable, or Edit clickable but not greyed out).
- No change to world icon, title/subtitle text, or the create-world/cloud-only-world row rendering.

## Configuration
No new configuration. No new config field, flag, or per-world preference is introduced — the consolidated view is always shown when the underlying hooks are available (unchanged from today's "no hook, no icon" rule, `FR-A.6`).

## Events
No new Fabric API event registrations. FR-3.2's downstream flag is set/cleared entirely from within `WorldConflictScreen`'s existing "Keep Cloud" button-click handler and its existing `RestoreProgressListener` callbacks — no new event source.

## Networking
No change. No new Steam Cloud API calls are introduced; FR-3.2 reads state that `WorldRestoreService.beginRestore` already produces as a byproduct of its existing, already-shipped restore call.

## Persistence
No new persisted (cross-restart) state. FR-3.2's downstream flag is session-only, in-memory, exactly like `WorldSyncStatusTracker.inProgress` today.

## Compatibility
- All three platform modules' `WorldsPanel.java` receive the same consolidation, in the same shape, matching the base feature's own established per-module-parity practice (`FR-R.1`) — a diff pass across all three at the end of implementation is required, as it was for the base feature.
- `WorldSyncStatusHook`'s new default method (FR-3.2, if placed on this interface) keeps any hypothetical out-of-tree implementer compiling, matching the precedent already set when `isUploadInProgress` itself was added.
- No change to `WorldFingerprint`/`WorldSyncAncestor`/`world-sync-ancestor-cache.json`/`cloudsyncable-upload-state.json` file formats — nothing here touches persisted data shapes.
- Existing tests for `WorldSyncStatusTracker`, `WorldSaveSyncService`, `CloudSyncableReconciler`, `CloudSyncCoordinator` are expected to be unaffected (no backend logic changes); any new test coverage is limited to the new `isDownloadInProgress`-style flag's set/clear pairing (if added to a testable class) and `WorldsPanel`'s consolidated-state precedence logic, if planning chooses to extract that precedence computation into a small, separately-testable pure function rather than inlining it in the render method.

## Performance
No new per-frame filesystem or Steam Cloud reads. The consolidated state is computed from the same already-cached values (`freshnessCache`, `conflictCache`, `isUploadInProgress`'s existing cheap in-memory check, and the new `isDownloadInProgress`'s equally cheap in-memory check) at the same existing checkpoints (`reload()`, and the existing `isUploadInProgress` true→false transition detection) — no new `Files.walk` or comparable expensive computation is introduced. Consolidating four draw calls into one is, if anything, a small net reduction in per-frame work (fewer hook lookups when a row's state doesn't require checking every hook, since FR-1's precedence order short-circuits: once Conflict is confirmed true, freshness/status detail doesn't need to be read for color purposes, only if needed for tooltip fallback text when hovered).

## Future Extensions
- **True byte-level/phase-level downstream progress on the Worlds tab row itself** (rather than the coarse boolean flag in FR-3.2): would require either exposing `WorldRestoreService`'s existing `RestoreProgress`/`Phase` data through a new hook `WorldsPanel` reads continuously (not just a boolean), or building an equivalent for a hypothetical future "auto-pull changed world content" feature — no such feature exists today (base spec's Non-goals explicitly forbid silent auto-overwrite of a local world), so this remains speculative until/unless that changes.
- **A general "any Cloud-Steam data transfer for this world is happening right now, in either direction" signal**, unifying FR-3.1/FR-3.2 into one true backend concept instead of two separately-wired flags — worth doing if a third transfer-direction case is ever added (currently there are exactly two: ordinary upload, and Keep-Cloud restore).
- Reusing the freed horizontal row space (from going 4 squares → 2) for something else (e.g. a compact last-synced timestamp displayed inline, not just in a tooltip) — no such requirement exists in this pass.
- A user-configurable minimum-severity filter (e.g. "only show the status square when it's not Synced") — not requested, not planned.

## Open Questions
1. **Exact hex colors for the four consolidated states** — this spec recommends reusing the closest existing color per FR-2 to minimize churn; final values are a planning/implementation-time call, not blocking.
2. **Placement of `isDownloadInProgress`** (FR-3.2) — on `WorldSyncStatusHook` (simplest, one new default method, mirrors `isUploadInProgress`'s own precedent) vs. a new minimal hook — recommend the former unless planning finds a reason `WorldConflictResolutionHook`/a new hook is architecturally cleaner; not blocking either way.
3. **Whether to extract FR-1's four-state precedence computation into a small, independently unit-testable pure function** (e.g. a package-private static method taking the three hook outputs as plain arguments) versus leaving it inlined in `WorldsPanel`'s render path — recommended (testability, and `WorldsPanel` today has no automated tests at all per the base plan's Test strategy, so this would be the first one), but not required by this spec; planning's call.
