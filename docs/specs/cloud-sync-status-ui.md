# Cloud Sync Status UI — Specification

**Status: AMENDED 2026-08-04, pending user approval on the new sections.** The prior 2026-08-03 finalization (FR-P/FR-T/FR-Q, all originally-open questions resolved, build green, 141 tests passing at that point) remains valid and unchanged below. This 2026-08-04 addendum adds two **new, not-yet-planned-or-implemented** requirement sections on top of that implemented baseline: **FR-U** (tooltip content) and **FR-V** (a new `WorldConflictScreen` for true two-sided sync conflicts, gated on new ancestor-tracking state per F20e — see FR-V.1's feasibility precondition before planning proceeds). Everything from the original 2026-08-03 pass (Goals through the original Open Questions list) describes the *already-shipped* feature; FR-U/FR-V describe *new, unimplemented* scope requiring their own planning pass. This includes the 2026-08-03 addendum folding the confirmed options.txt/servers.dat/cross-world-stats unconditional-upload bug fix into FR-T (FR-T.5, F16) — see "SCOPE EXPANSION NOTICE" below before proceeding to planning — and a further 2026-08-03 addendum (F17, FR-P1, FR-Q.1) finalizing the exact visual treatment of the in-progress indicator, previously left as "TBD after live testing."

## Overview
The per-world Cloud Sync toggle and cloud-only-world restore flow (`docs/specs/cloud-sync-restoration.md`) are now live in each platform module's `WorldsPanel` (`platform/<module>/src/main/java/de/lazuli/mainmenu/WorldsPanel.java`). Today a row shows only two static 8px-square icons: an on/off toggle (`COLOR_SYNC_ENABLED`/`COLOR_SYNC_DISABLED`) and, once at least one sync attempt has completed this session, a terminal-outcome icon (`SYNCED`/`SYNC_ERROR`/`SKIPPED_TOO_LARGE`, from `WorldSyncStatusHook`/`WorldSyncStatusTracker`). Nothing tells the player (a) whether a sync is *currently happening* right now, or (b) whether the local copy is actually *up to date* with what's on Steam Cloud in any sense beyond "did the last attempt this session succeed." This spec adds both signals to the Worlds tab, reusing existing backend state wherever it exists and specifying the minimal new tracking needed where it doesn't.

Following the resolution of this spec's open questions, the feature also now includes **new backend sync trigger points** (upload on-save and on-startup; download on-startup and on-return-to-main-menu) that did not exist before this pass — see the SCOPE EXPANSION NOTICE immediately below. A further addendum (F16/FR-T.5) folds in a confirmed bug fix to the *existing* settings/stats-file upload path: `options.txt`/`servers.dat`/cross-world-stats currently upload unconditionally at every startup reconcile and shutdown, regardless of whether the local file actually changed — this is now brought under the same "upload trigger points must be change-based, not unconditional-on-lifecycle-event" principle FR-T already applies to world saves. A final addendum (F17) resolves the previously-deferred exact visual treatment of the upload-in-progress indicator: a per-world progress bar (or, where determinate byte-level progress isn't available, an indeterminate spinner), covering both the actively-uploading state and any queued/pending-before-upload-starts state for that world.

## SCOPE EXPANSION NOTICE
**Read this before planning.** This spec was originally scoped as a pure UI/observability addition to `WorldsPanel.java` layered on top of *existing* sync operations (upload-on-disconnect, startup fingerprint pull). Answering this spec's open question #3 (freshness-check cadence) surfaced a **new, explicit trigger-point requirement** from the user that goes beyond display:

> "Upload should happen on-save and on startup. Download should happen on startup and on return to main menu press."

Per this spec's own F1–F10 investigation, current behavior is narrower than this:
- Upload today only happens at world-disconnect (`ClientPlayConnectionEvents.DISCONNECT` → `onPlayDisconnect` → `WorldSaveSyncService.onWorldUnload`, `platform/fabric-26.2/src/main/java/de/lazuli/SteamCloudSyncClientInitializer.java:278-287`). There is no on-save (mid-session/autosave) upload trigger, and no startup upload trigger.
- Download today only happens two ways: (1) `pullFingerprintsAtStartup()` at client startup, which pulls the *fingerprint metadata file* only, not any world's actual archive content (`WorldSaveSyncService.java:157-165`); and (2) the explicit, player-initiated cloud-only-world restore flow (`WorldRestoreService.beginRestore`, opened via `WorldsPanel.openRestoreFlow`) — never automatic, never triggered by startup or by returning to the main menu.

Implementing the user's answer as stated therefore requires **new work in `WorldSaveSyncService`/`CloudSyncCoordinator`** (a new on-save upload hook, a new startup upload check, and a new startup/return-to-menu download-side check), not just a `WorldsPanel.java` rendering change. This is a genuine scope expansion beyond "add two icons to a row." See "FR-T — Sync trigger points" below for the detailed proposal. All sub-decisions this expansion needed before implementation — the exact autosave hook mechanism, the startup-upload staleness threshold, and how far "download on startup/menu-return" should go given the codebase's existing deliberate design choice to never auto-overwrite a local world folder without an explicit player action (see `docs/specs/cloud-sync-restoration.md`'s restore-flow rationale) — are now resolved; see "Open Questions" at the bottom.

**Addendum (2026-08-03, confirmed real bug, not speculative):** while investigating FR-T's trigger points (F11-F14), it was confirmed that the *existing* startup-reconcile/shutdown upload path for `options.txt`/`servers.dat`/cross-world-stats (`CloudSyncableReconciler.reconcileAtStartup`/`pushOnShutdown`, driven from `CloudSyncCoordinator.reconcileAtStartup()`/`syncOnShutdown()`) uploads these three files **unconditionally** whenever the main menu is opened/loaded and again at shutdown, gated only on `config.enabled()`/`config.syncSettings()` and "Cloud timestamp is absent or not newer than local" — never on whether the local file actually changed since the last upload from this device. This is now folded into FR-T as **FR-T.5**, applying the same staleness-gating principle FR-T.2 already applies to world-save uploads.

**This notice must be visible to the user before implementation planning proceeds.**

## Goals
- Show an **in-progress** indicator on a world's row for a world that is either actively uploading (`WorldSaveSyncService.syncWorldNow` running) or queued/pending to upload for that world (e.g. waiting behind another world's in-flight upload on the single-threaded `CloudSyncWorker`, or in a post-save debounce window before the actual upload call fires), distinct from the existing enabled/disabled toggle icon and from the existing terminal-status icon. **Resolved (was Open Question #1, finalized 2026-08-03 per F17):** the indicator is a **per-world progress bar** — determinate where practical, otherwise an **indeterminate spinner/animation fallback** (see F17 for why determinate progress isn't currently practical, and FR-Q.1 for the exact rendering requirement). It remains **blocking**: while the row is in this state, that row's toggle and any other row-level actions are disabled/non-interactive, in addition to showing the progress bar/spinner. This element sits in (replaces, for the duration of the in-progress state) the existing terminal-outcome icon's slot in the row — the enable/disable toggle icon is completely unaffected, both in position and semantics.
- Show an **up-to-date / stale / unknown** indicator per world, built honestly from what the architecture can actually determine, with a clearly specified minimal new tracking mechanism for the parts that require net-new state.
- **New, per the SCOPE EXPANSION NOTICE:** add the sync trigger points needed to make the up-to-date/stale indicator meaningful in practice — upload on-save (in addition to the existing on-disconnect upload) and on-startup, plus a download-side check on startup and on return to the main menu — and recompute the displayed freshness status whenever a sync operation completes and whenever the Worlds tab is opened/re-shown (including via a return-to-main-menu event).
- **New, per the FR-T.5 addendum:** fix the confirmed bug where `options.txt`/`servers.dat`/cross-world-stats upload unconditionally on every startup reconcile and shutdown — gate these three adapters' uploads on actual local-file-modification detection, consistent with the change-based principle already required for world-save uploads (FR-T.2).
- Cover all three platform modules (`fabric-1.21.11`, `fabric-26.1`, `fabric-26.2`); each has its own `WorldsPanel.java` (verified present in all three, `Glob` result) implementing the same FR-A/FR-E pattern from `cloud-sync-restoration.md`. `fabric-26.2`'s `WorldsPanel.java` currently has uncommitted local edits (per prompt) — this spec targets its current on-disk shape (read directly, not the last commit) and expects the same shape to apply near-identically to the sibling modules once implemented, planning permitting per-module diffs.
- Keep the new state plain-JVM-testable where possible, matching the project's existing testing discipline (`WorldSyncStatusTrackerTest`, `CloudSyncCoordinatorTest`, etc. under `features/steam-cloud-sync/src/test`).
- **New, upload compression (resolved sub-question, see Current-state findings):** world archives uploaded to Steam Cloud must be compressed, not stored raw. This is already true of the existing implementation (`Deflater.BEST_COMPRESSION`) — this spec requires no regression of that behavior as part of any of the FR-T changes.

## Non-goals
- Redesigning the existing toggle/terminal-status icon semantics or colors (`COLOR_SYNC_ENABLED/DISABLED/SYNCED/SYNC_ERROR/SKIPPED`) — those are additive to, not replaced by, this spec. The new in-progress progress bar/spinner (F17) occupies the same row slot the terminal-status icon uses while a row is in-progress, but does not change that icon's colors/meaning for the non-in-progress case.
- True cryptographic or byte-for-byte content diffing between local and Cloud copies — "up to date" here means "no known reason to believe they differ," derived from timestamps/attempt outcomes, not a content hash comparison (Steam Cloud's `ISteamRemoteStorage` API exposes per-file timestamps but not content hashes to a client in a way this feature currently reads). This applies to the world-save freshness indicator (FR-P3); FR-T.5's per-adapter change detection is a separate, narrower mechanism (mtime or content hash local to this mod's own bookkeeping, not a Cloud-side comparison) and is unaffected by this non-goal.
- Changing `CloudSyncCoordinator`'s reconciliation algorithm, `WorldSaveSyncService`'s size-threshold/selective-fallback decision, or `WorldRestoreService`'s extraction/atomicity discipline — this spec only adds observability plus the specific new trigger points in FR-T, never changes the operations' internal behavior once triggered. (Archive compression, addressed above, is an existing, already-correct behavior confirmed by this pass — not a change to the archive-building algorithm's structure.) **FR-T.5 is a scoped exception to this non-goal**, explicitly changing `CloudSyncableReconciler`'s upload-gating condition (adding a local-modification check before the existing "else" branch fires) — the download/import side of `reconcileAtStartup` is unaffected, see below.
- **New, per F17:** adding true byte-level upload-progress instrumentation (e.g. streaming the archive to Steam Cloud in chunks and reporting `processedBytes`/`totalBytes` as `WorldRestoreService`'s restore path already does) is explicitly **out of scope** for this pass — see F17 and FR-P1 for why, and Future Extensions for this as a possible later enhancement. This spec only requires an indeterminate spinner fallback where determinate progress isn't already cheaply available.
- A global/tab-level "sync all" progress summary — this spec is per-world, row-level only (a future extension, see below).
- Persisting in-progress or up-to-date state across a client restart — consistent with the existing `WorldSyncStatusTracker`'s explicit "session-only" design (`WorldSyncStatusTracker.java:26-28`), the new state is also session-only unless stated otherwise. **FR-T.5's per-adapter last-uploaded state is the one exception**: it must persist across restarts (an in-memory-only flag would make every startup look "changed since last upload" the first time it's checked in a new process) — see Persistence.
- Handling the cloud-only-world restore flow's *own* screen (`WorldRestoreScreen`) UI — that screen already shows honest phase text and a progress bar (`WorldRestoreService.java` `RestoreProgress`/`Phase`, ported per FR-E.5 of `cloud-sync-restoration.md`) and is out of scope here.
- **Resolved (was Open Question #2): a dedicated restore-in-progress row-level overlay/indicator is explicitly SKIPPED for this feature.** The existing cloud-only-world restore screen (`WorldRestoreScreen`) already communicates in-progress-restore state to the player; a duplicate row-level indicator for that specific case is not worth building. Any row-level indicator work in this spec is limited to (a) upload-in-progress state and (b) freshness (up-to-date/stale) state.
- **New non-goal, per the SCOPE EXPANSION NOTICE:** this feature does not add automatic, silent overwriting of an existing local world's save folder from Cloud content. The new startup/return-to-menu "download" trigger points (FR-T) are scoped to *checking/reconciling metadata* (fingerprint pulls, freshness recompute, cloud-only-world list refresh) — actually pulling a full world archive down over an existing local folder remains the explicit, player-initiated restore flow only, consistent with `cloud-sync-restoration.md`'s existing design rationale of never auto-overwriting local save data. **Resolved (was Open Question #6): confirmed metadata-only** — the user's stated download-trigger requirement is satisfied by refreshing freshness/status metadata at these checkpoints; downloads that actually restore a world's content remain gated on explicit user action via the existing restore flow, with no silent auto-overwrite added by this spec.
- **New scoping boundary, per the FR-T.5 addendum: the existing startup-reconcile *download* path is explicitly OUT of scope and must not change.** `CloudSyncableReconciler.reconcileAtStartup`'s "if Cloud is strictly newer than local, import it" branch (the `if (cloudTimestamp.isPresent() && cloudTimestamp.getAsLong() > localTimestamp)` branch, `CloudSyncableReconciler.java:81-87`) is unaffected by FR-T.5 — pulling a newer Cloud copy of `options.txt`/`servers.dat`/cross-world-stats down to local when Cloud is ahead continues to work exactly as it does today. FR-T.5 only adds a guard to the sibling **upload** branch (the `else if (localTimestamp >= 0)` branch, `CloudSyncableReconciler.java:88-92`) and to `pushOnShutdown` (`CloudSyncableReconciler.java:126-139`), which is unconditional today. Planning/implementation must not touch the download/import branch or its timestamp comparison.

## Requirements

### Current-state findings

**In-flight-operation tracking**
- **F1** No existing in-flight/"sync in progress" flag exists anywhere in the backend. `WorldSyncStatusTracker` (`features/steam-cloud-sync/src/main/java/de/lazuli/features/steamcloudsync/services/WorldSyncStatusTracker.java:30-79`) only records **terminal** outcomes — `markSynced`/`markError`/`markSkippedTooLarge` — each called once, at the end of `WorldSaveSyncService.syncWorldNow` (`WorldSaveSyncService.java:219-263`). There is no `markStarted`/`markInProgress` call anywhere in that method, and no corresponding hook method to read one.
- **F2** `WorldSaveSyncService.onWorldUnload` (`WorldSaveSyncService.java:143-148`) fires `worker.submitBackgroundWork(...)` fully asynchronously (background thread for archive-building, then a queued tick-thread hop for the actual `archiveStore.streamWrite` call, per `CloudSyncWorker.java:37-46`). Nothing marks the world "busy" before this work starts; the terminal-status icon simply stays at whatever it was (commonly `NOT_SYNCED`, drawn as no icon at all) for the entire duration of the upload, then flips straight to `SYNCED`/`SYNC_ERROR`/`SKIPPED_TOO_LARGE`. A player currently has zero visual signal that anything is happening between "world unloaded" and "status icon appears."
- **F3** `WorldRestoreService.beginRestore` (`WorldRestoreService.java:102-153`) *does* have a full async progress model — `RestoreProgressListener.onProgress(RestoreProgress)` with `Phase.READING_FROM_CLOUD`/`Phase.EXTRACTING` and `processedBytes`/`totalBytes` — plus an `activeRestores` map (`ConcurrentHashMap<String, RestoreContext>`) that is, in effect, already an in-flight-operation registry keyed by `worldSlug` (`WorldRestoreService.java:54,121-122,157-161`). This listener is currently only ever supplied by `WorldRestoreScreen`, not by `WorldsPanel` itself. Per the resolved Non-goal above, this spec does **not** build a `WorldsPanel` row-level reader for this state — the finding is retained here only as background context for why that path was considered and declined.
- **F4** Conclusion (updated): an upload-in-progress signal requires genuinely new tracking (F1/F2 — nothing to reuse) and **is in scope**. A restore/download-in-progress row-level signal has reusable state (`activeRestores`/`RestoreProgress`) but **is out of scope per the resolved Non-goal** — `WorldRestoreScreen` already owns that moment for the player.

**Up-to-date vs. stale tracking**
- **F5** No existing per-world "local last-modified" vs. "Cloud last-modified" comparison exists anywhere. The only per-world Cloud-side timestamp tracked today is `WorldFingerprint.syncedAtTimestamp()` (`features/steam-cloud-sync/src/main/java/de/lazuli/features/steamcloudsync/api/WorldFingerprint.java`, read via `WorldSaveSyncService.readLocalFingerprintCache()`/`updateFingerprint`, `WorldSaveSyncService.java:358-364`), and it is used for exactly one purpose today: warning the player if a *different* device (`deviceLabel` mismatch) synced this world more recently than the local cache remembers (`checkFingerprintForConflict`, `WorldSaveSyncService.java:308-319`). It is never compared against the local world folder's own last-modified time, and it is not exposed through any hook `WorldsPanel` can read — it is a private implementation detail of `WorldSaveSyncService`.
- **F6** The mod does not currently read any raw `ISteamRemoteStorage` per-file timestamp API directly (`SteamRemoteStorageWorldArchiveStore`/`SteamRemoteStorageCloudFileStore` wrap Steam Cloud reads/writes but their interfaces — `WorldArchiveCloudStore`/`CloudFileStore` — expose no `getFileTimestamp`-style method to callers today). The mod's own `WorldFingerprint.syncedAtTimestamp` (F5) is a self-recorded value written at the moment of *this* mod's own successful upload — it is not read from Steam's own file metadata, so it is reliable for what this mod itself wrote but says nothing about a Cloud file if this mod's upload succeeded on Steam's side but the local fingerprint write (`updateFingerprint`) somehow didn't happen, or vice versa.
- **F7** There is no local "world folder was modified since last sync" detection either — no file-mtime read against the world's save folder, no dirty-flag set on world save/exit. `onWorldUnload` runs unconditionally whenever the preference is enabled (`WorldSaveSyncService.java:143-148`) — it does not check whether the world actually changed since last sync before re-uploading, so "was this world touched since last upload" is not tracked, only "did an upload just happen or fail."
- **F8** Conclusion: true up-to-date detection requires new tracking on both sides — a local signal ("has this world's save folder changed since the last successful upload from this device") and reuse of the existing self-recorded Cloud signal (`WorldFingerprint.syncedAtTimestamp`/`deviceLabel`, already fit for purpose per F5, just not currently exposed to UI). No new Steam API calls are required if the spec accepts "this mod's own last successful upload, compared to local mtime and to the fingerprint's own device/timestamp" as the definition of "up to date" (see Proposed New State Model below) rather than a true Cloud-side content check.

**Existing hooks/callbacks at operation start/finish**
- **F9** Upload finish: exactly two outcomes are hooked today, both inside the tick-thread callback in `syncWorldNow` (`WorldSaveSyncService.java:246-258`) — success calls `statusTracker.markSynced(worldSlug)` plus `playerNotifier.accept(...)`; failure calls `statusTracker.markError(worldSlug, message)` plus `warningLogger.accept(...)`. The `SKIPPED_TOO_LARGE` outcome is hooked earlier, synchronously, before any archive is built (`WorldSaveSyncService.java:224-229`). Upload **start** has no hook at all (F2).
- **F10** Restore start/finish: `beginRestore` calls `listener.onProgress` repeatedly during both phases and exactly one of `listener.onComplete`/`listener.onFailed` at the end (`WorldRestoreService.java:125-150,205-224`); `activeRestores.put(worldSlug, context)` at the very start (`WorldRestoreService.java:121-122`) is the closest thing to a "restore started" hook — retained here for context only, not used per F4/Non-goals.

**Lifecycle/trigger-point investigation (new, per SCOPE EXPANSION NOTICE)**
- **F11** The single existing upload trigger is wired through Fabric API's `ClientPlayConnectionEvents.DISCONNECT`, registered once per platform module in `SteamCloudSyncClientInitializer` (`platform/fabric-26.2/src/main/java/de/lazuli/SteamCloudSyncClientInitializer.java:84`, identical in `fabric-26.1`/`fabric-1.21.11` per the same file path/line). Its handler, `onPlayDisconnect` (`SteamCloudSyncClientInitializer.java:278-287`), calls `worldSaveSyncService().onWorldUnload(...)` only when `client.hasSingleplayerServer()` is true. For a singleplayer world this event fires precisely when the player exits the world back to the world-selection/main-menu screen — i.e. **today's only upload trigger already coincides with "return to main menu," but only in the leaving-a-world direction**, not on a periodic in-world save, and not on client startup.
- **F12** Client-startup and client-shutdown checkpoints are wired through Fabric API's `ClientLifecycleEvents.CLIENT_STOPPING` (`SteamCloudSyncClientInitializer.java:81`, calls `coordinator.syncOnShutdown()`) and an explicit `coordinator.reconcileAtStartup()` call (from the composition root's startup path — `CloudSyncCoordinator.java:152-165`). `reconcileAtStartup()` today calls `worldSaveSyncService.pullFingerprintsAtStartup()` only for Group 6 (world saves) — it does **not** call `onWorldUnload`/`syncWorldNow` for any world, so there is genuinely no "upload on startup" trigger today (confirms F11's gap). There is no `ClientLifecycleEvents.CLIENT_STARTED` registration found anywhere in the codebase to hang a startup-upload check on yet; `reconcileAtStartup()`'s existing call site is the natural place to add one instead.
- **F13** No mid-session, periodic, or autosave-triggered upload hook exists anywhere in the codebase. A repo-wide search for Fabric API save-related events (`ServerWorldEvents`, `LevelEvents`, autosave-style hooks) found none in use by this mod, and Fabric API does not expose a first-class "world was autosaved" client event out of the box for a singleplayer integrated server — the vanilla autosave path (`MinecraftServer`/`ServerChunkCache` periodic save) is not currently intercepted by any mixin in this codebase (`Glob` of `platform/*/src/main/java/de/lazuli/mixin/` shows title-screen-redirect, world-hosting bootstrap, and a number of other unrelated mixins, no save-related one). **Conclusion: "upload on-save" is 100% new work. Resolved (was Open Question #4): the chosen mechanism is a new Fabric mixin into the integrated server's/world's save path** (option (a) from the original two-option analysis), not a client-tick mtime-poll — see FR-T.1 and the Public API section for the mixin's target and shape.
- **F14** No existing "return to main menu" event distinct from `ClientPlayConnectionEvents.DISCONNECT` was found — for a singleplayer world, disconnect *is* the return-to-main-menu transition (there is no separate mixin/event on `TitleScreen`/`WorldSelectionScreen`/`MainMenuScreen` display beyond the already-referenced `ClientTitleScreenRedirectMixin`/`GuiTitleScreenRedirectMixin`, which are about redirecting *to* this mod's custom main menu UI, not a lifecycle signal about arriving there — confirmed by reading `platform/fabric-26.2/src/main/java/de/lazuli/mixin/GuiTitleScreenRedirectMixin.java`). **Conclusion: the existing `ClientPlayConnectionEvents.DISCONNECT`/`onPlayDisconnect` handler is the correct, already-existing hook to extend for "return to main menu" behavior** — both the new download-side check (FR-T) and the existing upload trigger belong in the same handler, since for this mod's purposes "disconnect from a singleplayer world" and "return to main menu" are the same event.

**Archive compression finding (new, per finalization pass — resolves the compression sub-question)**
- **F15 Verified: compression is already enabled today, no change required.** Both archive-building methods in `WorldSaveSyncService` — `buildWholeArchive` (`WorldSaveSyncService.java:265-276`) and `buildSelectiveArchive` (`WorldSaveSyncService.java:278-299`) — construct a `java.util.zip.ZipOutputStream` and immediately call `zip.setLevel(Deflater.BEST_COMPRESSION)` (`WorldSaveSyncService.java:268` and `:281` respectively) before writing any entries via the shared `addZipEntry` helper (`WorldSaveSyncService.java:301-304`, a plain `Files.copy(file, zip)` after `putNextEntry`, which does not override the entry's compression method — `ZipEntry`'s default method is `DEFLATED`, so entries are written compressed at the maximum `Deflater` level, not `STORED`). This was itself a deliberate change made by a prior finalized spec/plan pair (`features/steam-cloud-sync/specs/sync-diagnostics-ui-compression-spec.md`, `...-compression-plan.md`), which raised the level from the `Deflater` default (`DEFAULT_COMPRESSION`, level -1/6-equivalent) to `BEST_COMPRESSION` (level 9) — both settings are compressed, non-`STORED`, `ZipInputStream`-compatible archives; only the compression ratio/CPU-cost tradeoff differs between them, and the codebase is already on the maximum-compression setting. **No new functional requirement is added by this spec for archive compression** — the user's stated concern is confirmed already fully addressed by existing, already-shipped behavior.

**Unconditional settings/stats-file upload bug (new, confirmed real bug — 2026-08-03 addendum)**
- **F16** Confirmed: `options.txt`, `servers.dat`, and cross-world-stats upload **unconditionally** at every startup reconcile and again at every shutdown, regardless of whether the local file changed since the last upload. Specifically:
  - The three adapters — `OptionsTxtCloudSyncAdapter`, `ServersDatCloudSyncAdapter`, `CrossWorldStatsCloudSyncAdapter` (all `platform/fabric-26.2/src/main/java/de/lazuli/SteamCloudSyncClientInitializer.java:116-259`, identical shape expected in the sibling platform modules per FR-R.1's existing per-module-diff practice) — implement `CloudSyncable` and are registered as `cloudSyncables` (`SteamCloudSyncClientInitializer.java:63-66`).
  - `CloudSyncCoordinator.reconcileAtStartup()` (`CloudSyncCoordinator.java:152-165`) calls `CloudSyncableReconciler.reconcileAtStartup(...)` once per adapter (`CloudSyncCoordinator.java:156-159`), gated only on `settingsSyncEnabled = config.enabled() && config.syncSettings()` (`CloudSyncCoordinator.java:155`) — the same single flag for all three files, no per-file gate.
  - `CloudSyncableReconciler.reconcileAtStartup` (`CloudSyncableReconciler.java:67-93`) compares `cloudFileStore.fileTimestamp(cloudFileName)` against `syncable.localLastModifiedMillis()` (each adapter's `localLastModifiedMillis()` simply returns `Files.getLastModifiedTime(path).toMillis()`, e.g. `SteamCloudSyncClientInitializer.java:148-154` for `options.txt`). If Cloud is not strictly newer than local, the `else if (localTimestamp >= 0)` branch (`CloudSyncableReconciler.java:88-92`) **always** uploads — there is no comparison against "when did this device last successfully upload this file," only "is local newer than Cloud right now." Since a local file's own mtime does not change merely by being uploaded, and Cloud's timestamp is set to the upload time on a successful write, this branch's condition is true on essentially every startup where Cloud isn't ahead — i.e., in practice, on every normal startup that follows a prior successful upload from the same device (Cloud is never *newer* than the device that just wrote it), causing an upload every time regardless of whether the file's content actually changed.
  - `CloudSyncCoordinator.syncOnShutdown()` (`CloudSyncCoordinator.java:172-183`) calls `CloudSyncableReconciler.pushOnShutdown(...)` once per adapter (`CloudSyncCoordinator.java:174-177`), which is `if (!syncEnabled) return;` followed by an **unconditional** `exportSafely(...)` call (`CloudSyncableReconciler.java:126-139`) — no staleness check of any kind, by design (its own Javadoc, `CloudSyncableReconciler.java:95-99`, states it "pushes ... unconditionally, capturing whatever this session accumulated").
  - **Conclusion:** both the startup-reconcile upload branch and the shutdown push are unconditional-on-lifecycle-event today, exactly the same category of bug FR-T.2 already exists to fix for world-save uploads (F12: "does not check whether the world actually changed since last sync before re-uploading"). No equivalent per-adapter local-modification tracking exists yet for these three `CloudSyncable` adapters — see FR-T.5.

**Upload-progress instrumentation finding (new, 2026-08-03 addendum — resolves the deferred in-progress visual-treatment question)**
- **F17 Verified: no byte-level upload-progress tracking exists today; determinate progress is not cheaply available without new instrumentation.** Read in full: `WorldSaveSyncService.syncWorldNow` (`WorldSaveSyncService.java:219-263`). Findings:
  - The archive is built entirely in memory in one call — `buildWholeArchive`/`buildSelectiveArchive` (`WorldSaveSyncService.java:265-299`) write into a single `ByteArrayOutputStream` and return the complete `byte[]` only once finished; there is no per-entry or per-byte callback during archive construction.
  - The actual Cloud write is a single, non-chunked call: `archiveStore.streamWrite(archiveFileName, archiveBytes)` (`WorldSaveSyncService.java:247`), passing the whole already-built byte array at once. The `WorldArchiveCloudStore.streamWrite` seam (`features/steam-cloud-sync/src/main/java/de/lazuli/features/steamcloudsync/services/WorldArchiveCloudStore.java`) exposes no progress callback/listener parameter, and its real implementation wraps a single `ISteamRemoteStorage.fileWrite`-style call, not `ISteamRemoteStorage.fileWriteStreamOpen`/`WriteChunk`/`Close` (steamworks4j's chunked-write API, which *would* allow byte-level progress reporting but is not what this codebase uses).
  - Contrast with `WorldRestoreService` (F3/F10): that path *does* report `processedBytes`/`totalBytes` via `RestoreProgressListener.onProgress`, because its underlying read/extract operations are already naturally chunked (streaming read from Cloud, streaming zip extraction). No equivalent natural chunking exists on the upload path today.
  - **Conclusion:** a determinate, byte-accurate progress bar for the upload path is not available from existing state, and retrofitting one would require switching `WorldArchiveCloudStore.streamWrite` to steamworks4j's chunked-write API (or manually chunking archive construction and reporting per-file/per-chunk progress) — a meaningfully larger change than the rest of this spec, touching the Cloud-write seam's contract and its real/no-op implementations. **This instrumentation work is out of scope for this pass** (see Non-goals) and is recorded as a Future Extension. For this pass, the in-progress indicator uses an **indeterminate spinner/animation** for the actively-uploading portion of the state, since no real progress fraction is available to drive a determinate bar. See FR-P1/FR-Q.1 for how the pending/queued portion of the state (which has no "progress" concept at all, determinate or not) is handled — always shown the same way as the active-upload state (spinner), since distinguishing "queued" from "actively uploading" visually is not required by the resolved decision (both are simply "in progress" to the player).

### Proposed new state model

**FR-P1 (upload in-progress, covering both queued/pending and actively-uploading) — new tracking required, visual treatment finalized 2026-08-03 (F17).** Add an in-progress flag to the existing session-only tracker rather than introducing a parallel data structure: extend `WorldSyncStatusTracker` (or add a sibling `WorldSyncInProgressTracker` with the same `ConcurrentHashMap<String, Boolean>`/`Set<String>` shape — naming is a planning-time decision) with `markUploadPending(String worldSlug)` / `markUploadFinished(String worldSlug)`, and expose `boolean isUploadInProgress(String worldSlug)`, callable from `WorldsPanel` the same way `statusFor`/`lastErrorFor` are today.
- **Call-site timing is the key change from the original draft of this requirement:** `markUploadPending` must be called at the moment work is *handed off* for this world — i.e. at the top of `onWorldUnload` (immediately before `worker.submitBackgroundWork(...)`, `WorldSaveSyncService.java:143-148`) and, once added, at the equivalent point in FR-T.1's new on-save hook and FR-T.2's new startup-stale-upload check — **not** inside `syncWorldNow` itself. This is what makes the flag cover the queued/pending window (time spent waiting on `CloudSyncWorker`'s single background thread behind another world's in-flight upload, or any debounce delay a trigger point introduces before calling `onWorldUnload`/its equivalent) as well as the actively-uploading window, per the Goals decision that both states must be covered by the same indicator.
- `markUploadFinished` is called unconditionally in every terminal branch of `syncWorldNow` (success, error, skipped-too-large, and the existing `catch (IOException e)` branch, `WorldSaveSyncService.java:220,259-262`) — a `try/finally` around the whole method body is the natural shape, exactly as originally specified.
- **This flag also drives the resolved blocking-interaction requirement (Goals): while true for a given `worldSlug`, `WorldsPanel` must disable that row's toggle/action hit-testing.**
- The flag intentionally does not distinguish "queued" from "actively uploading" to its readers (`WorldsPanel`) — a single boolean is sufficient per F17's conclusion that the two sub-states render identically (spinner). If a future determinate-progress enhancement (Future Extensions) is built, this is the natural point to widen the flag into a richer progress value (e.g. an `Optional<Double>` fraction, `empty` meaning "queued/no progress data yet").

**FR-P2 (restore/download in-progress) — explicitly out of scope.** Per the resolved Non-goal, no `WorldsPanel`-visible restore-in-progress indicator is built. `WorldRestoreService.activeRestores` is left untouched by this spec.

**FR-P3 (up-to-date / stale / unknown) — new local-side tracking, reuse of existing Cloud-side fingerprint.** Given F5–F8, specify three states per world, computed without any new Steam API calls:
- **`UP_TO_DATE`**: this device has a recorded `WorldFingerprint` for this world whose `deviceLabel` matches this device's own label (`DeviceLabelResolver.resolve(...)`, already computed once per session in `CloudSyncCoordinator`, `CloudSyncCoordinator.java:135`), **and** the local world folder's most-recent file modification time (new: a lightweight recursive-or-top-level-mtime scan, reusing `WorldSaveSyncService.computeFolderSizeBytes`'s existing `Files.walk` pattern but computing `max(lastModifiedTime)` instead of summing sizes — a new static method, e.g. `computeFolderLastModifiedMillis(Path)`) is **not newer** than that fingerprint's `syncedAtTimestamp`.
- **`STALE`**: either (a) the local folder's last-modified time is newer than this device's own last recorded successful upload for this world, or (b) a `WorldFingerprint` exists for this world whose `deviceLabel` does **not** match this device — this second condition already has all its inputs computed today (`checkFingerprintForConflict`, F5) — surfacing it as `STALE` in the UI reuses that exact comparison.
- **`UNKNOWN`**: no `WorldFingerprint` exists at all for this world, or the fingerprint cache hasn't been pulled yet at this point in startup.
- This computation is a **derived value**, not a new persisted flag. Given a full recursive mtime scan on every render frame is not acceptable (Performance), see the caching approach specified there.
- This condition must be evaluated **only** when `isUploadInProgress` (FR-P1) is false for that world — an in-progress row shows the in-progress indicator instead of (not in addition to) an up-to-date/stale indicator.
- **Recompute cadence (resolves former Open Question #3's display-cadence half):** the freshness value is recomputed (a) whenever an upload for that world completes (success, error, or skipped — any `markUploadFinished` call, FR-P1), and (b) whenever the Worlds tab is opened or re-shown, which includes both a normal tab switch and a return-to-main-menu transition (F14 — the same `onPlayDisconnect`/disconnect handler that already triggers upload). This is in addition to, not a replacement for, the `WorldsPanel.reload()`-time snapshot already specified under Performance below.

### FR-T — Sync trigger points (NEW, per SCOPE EXPANSION NOTICE)
This section is net-new backend work in `features/steam-cloud-sync` (`WorldSaveSyncService`/`CloudSyncCoordinator`), required to make the user's stated trigger-point requirements real, and to make FR-P3's freshness indicator meaningfully "fresh" rather than stale-by-construction between rare disconnect events. As of the 2026-08-03 addendum, this section's unifying principle is: **every upload trigger point in this codebase — world saves (FR-T.1/FR-T.2) and settings/stats files (FR-T.5) alike — must fire only when the underlying local state actually changed since its last successful upload, never unconditionally just because a fixed lifecycle hook (startup reconcile, shutdown) ran.**

| Trigger | Direction | Status today | This spec |
|---|---|---|---|
| World disconnect / return to main menu | Upload | **Exists** (F11) — `onPlayDisconnect` → `onWorldUnload` → `syncWorldNow` | Unchanged; remains the primary upload trigger. |
| World save (mid-session, e.g. autosave) | Upload | **Does not exist** (F13) | **New (FR-T.1), via mixin — mechanism now decided.** |
| Client startup | Upload | **Does not exist** (F12) | **New (FR-T.2), only for worlds with actual changes since last upload — threshold now decided.** |
| Client startup | Download/reconcile | **Partial** (F12) — fingerprint *metadata* only, no world content | **New, metadata/reconcile-only (FR-T.3)** — no automatic full-archive download over an existing local world (see Non-goals). |

| Startup reconcile / shutdown (`options.txt`, `servers.dat`, cross-world-stats) | Upload | **Bug: unconditional** (F16) — uploads regardless of whether the local file changed since its last upload | **Fix (FR-T.5), gated on per-adapter local-modification detection, matching FR-T.2's principle for world saves.** |

- **FR-T.1 (upload on-save) — mechanism resolved (was Open Question #4): Fabric mixin into the integrated server's save path.** Add a new mixin, targeting the same class family this codebase's existing mixins already hook into for per-world lifecycle behavior — precedent: `IntegratedServerWorldHostingMixin` (`platform/fabric-26.2/src/main/java/de/lazuli/mixin/IntegratedServerWorldHostingMixin.java`), which `@Inject`s into `net.minecraft.client.server.IntegratedServer#initServer()` and `#isPublished()` for the world-hosting feature and documents its Mixin target via a `javap`-confirmed doc comment. Follow the same pattern for the save hook:
  - **Target class:** `net.minecraft.client.server.IntegratedServer` (the same class `IntegratedServerWorldHostingMixin` already mixes into for this mod, one mixin class per platform module, same as today's pattern).
  - **Target method:** the integrated server's save-everything method — vanilla's `MinecraftServer#saveEverything(boolean suppressLogs, boolean flush, boolean forced)` (inherited/overridden on `IntegratedServer`; exact obfuscated/mapped name and overload must be confirmed per platform module via `javap` against each module's resolved jar, mirroring `IntegratedServerWorldHostingMixin`'s own documented `javap`-verification practice, since Minecraft version skew across `fabric-1.21.11`/`fabric-26.1`/`fabric-26.2` is a known risk here per FR-R.4). Inject `@At("RETURN")` (mirroring `IntegratedServerWorldHostingMixin`'s `lazuli$onInitServer` shape) so the hook fires only after the save has actually completed, not before.
  - **New hook class, e.g. `WorldSaveHookMixin`** (naming to match the existing `*Mixin` convention), one per platform module's `de.lazuli.mixin` package, each registered in that module's `lazuli.mixins.json`.
  - **Bridge to feature code:** follow the same static-holder pattern this mixin package already uses for cross-module calls (precedent: `WorldHostingHookHolder`, referenced from `IntegratedServerWorldHostingMixin.java:4,17,36,45`) — add an equivalent holder in `features/steam-cloud-sync` (e.g. `WorldSaveHookHolder`, or extend an existing holder if one already exposes `WorldSaveSyncService`) that the new mixin calls into with the current world's slug/folder/display name, invoking the same `worldSaveSyncService.onWorldSaved(...)`-equivalent path used by `onWorldUnload` today (`WorldSaveSyncService.java:143-148`), without unloading the world.
  - Must not re-trigger a second upload while one is already `isUploadInProgress` for that world (FR-P1's flag doubles as a re-entrancy guard) — a save that happens to land mid-upload is a no-op for this hook, not queued or retried.
- **FR-T.2 (upload on startup) — staleness threshold resolved (was Open Question #5): confirmed, only stale worlds, never every world unconditionally.** At the `reconcileAtStartup()` checkpoint (`CloudSyncCoordinator.java:152-165`), after `pullFingerprintsAtStartup()`, check every sync-enabled world's local folder mtime (`computeFolderLastModifiedMillis`, FR-P3) against its own device's fingerprint `syncedAtTimestamp`; enqueue an upload **only** for worlds found `STALE` in the "local newer than this device's last upload" sense (FR-P3's `STALE` case (a)) — i.e. a world that changed since its last upload, most plausibly because a previous session ended without a clean disconnect (crash, force-quit). A world with no local changes since its last successful upload from this device is never re-uploaded at startup. This intentionally narrow behavior avoids a startup performance/quota-spend regression for worlds already up to date; no additional minimum-staleness time margin beyond "any local mtime newer than the last recorded upload" is required for this pass.
- **FR-T.3 (download/reconcile on startup).** No behavior change to `pullFingerprintsAtStartup()` itself is required beyond what already exists — it already runs at this checkpoint. What's new is *using* its result for FR-P3's freshness computation immediately after startup (rather than only when a `WorldsPanel` row happens to be drawn), so the Worlds tab's first paint already reflects an accurate freshness state rather than transiently showing `UNKNOWN` until first render. No full-world-archive auto-download is added here (see Non-goals) — the existing explicit `WorldRestoreService.beginRestore` flow remains the only path that pulls a full archive.
- **FR-T.4 (download/reconcile on return to main menu).** Extend `onPlayDisconnect` (`SteamCloudSyncClientInitializer.java:278-287`) to, alongside its existing `onWorldUnload` upload call, also re-pull the fingerprint cache (`pullFingerprintsAtStartup()` — name to be reconsidered at planning time since it will no longer run only "at startup," e.g. rename to `pullFingerprints()`/`refreshFingerprintCache()`) and refresh the cloud-only-worlds list (`CloudOnlyWorldsFacade`), so that returning to the main menu after playing picks up any changes another device made to Cloud while this session was in a world. As with FR-T.3, this is a metadata refresh, not a full-archive auto-download.
- **FR-T.5 (upload gating for `options.txt`/`servers.dat`/cross-world-stats at startup reconcile and shutdown) — NEW, 2026-08-03 addendum, confirmed bug fix.** Per F16, `CloudSyncableReconciler.reconcileAtStartup`'s upload branch (`CloudSyncableReconciler.java:88-92`) and `pushOnShutdown` (`CloudSyncableReconciler.java:126-139`) must gate their upload of each of the three file-based `CloudSyncable` adapters (`OptionsTxtCloudSyncAdapter`, `ServersDatCloudSyncAdapter`, `CrossWorldStatsCloudSyncAdapter`) on **actual local-file-modification detection since that adapter's own last successful upload**, not merely on `config.enabled()`/`config.syncSettings()` and "Cloud isn't newer than local right now."
  - **Mechanism:** each adapter needs a small piece of persisted state recording "what this device last successfully uploaded" — either the local file's mtime at the time of that upload, or a content hash (e.g. SHA-256) of the bytes last uploaded; either is acceptable, planning decides based on implementation simplicity (an mtime-based check is simpler and consistent with FR-P3's own mtime-based approach for world saves, but is vulnerable to a file being touched without content changing — e.g. some editors rewrite a file with an unchanged mtime granularity issue; a content hash is more precise but requires reading+hashing the file body on every check). Before deciding to upload (both at startup-reconcile time and at shutdown), each adapter's gating check compares the current local file's mtime/hash against its own last-recorded-upload mtime/hash; if unchanged, skip the upload for that adapter (this session's shutdown push, or this startup's reconcile-upload branch, becomes a no-op for that file). On a successful upload, update the recorded mtime/hash to the just-uploaded value.
  - **Where this lives:** the three adapters currently live entirely as private static nested classes inside each platform module's `SteamCloudSyncClientInitializer` (`platform/fabric-26.2/src/main/java/de/lazuli/SteamCloudSyncClientInitializer.java:116-259`, and the identical pattern in `fabric-26.1`/`fabric-1.21.11` per the same file/line range, to be confirmed via per-module diff same as FR-R.1). The gating check itself could live in one of two places (planning to decide): (a) inside each adapter itself (each adapter tracks its own last-uploaded mtime/hash, e.g. via a small sibling file in `featureConfigDir`, since these platform-module classes do not currently have access to `featureConfigDir` — this would need to be threaded through the adapter constructors, `SteamCloudSyncClientInitializer.java:63-66`), or (b) inside `CloudSyncableReconciler`/`CloudSyncCoordinator` itself (platform-independent, in `features/steam-cloud-sync`), keyed by each `CloudSyncable.cloudSyncId()` (already a stable per-adapter identifier — `"options"`, `"servers-dat"`, `"cross-world-stats"`, `SteamCloudSyncClientInitializer.java:125,172,226`) and persisted in a single small new file inside `featureConfigDir` (which `CloudSyncCoordinator` already has, `CloudSyncCoordinator.java:100,108`) — option (b) is recommended since it keeps the new state platform-independent and testable alongside `CloudSyncableReconcilerTest`/`CloudSyncCoordinatorTest`, and needs no adapter-constructor signature change.
  - **Explicit scope boundary (see also Non-goals): this only changes the UPLOAD side.** `CloudSyncableReconciler.reconcileAtStartup`'s download/import branch (`CloudSyncableReconciler.java:81-87` — "if Cloud is strictly newer than local, pull it down") is completely unaffected; it continues to run exactly as today, on the existing Cloud-timestamp-vs-local-timestamp comparison, with no new gating. Only the sibling upload branch (`:88-92`) and `pushOnShutdown`'s unconditional export (`:126-139`) receive the new local-modification guard.
  - Must not regress the existing "Cloud is newer → download" precedence: the new local-modification guard on the upload branch only ever *prevents* an otherwise-would-have-happened upload when nothing changed locally — it never causes an upload to happen when the existing logic wouldn't have attempted one, and it never suppresses the download branch.
  - A world-save-style "was this touched since last upload" concept already exists for Group 6 (FR-T.2/FR-P3's `computeFolderLastModifiedMillis`-vs-fingerprint comparison) — FR-T.5 is the same principle applied to Groups 1/3 (the three file-based `CloudSyncable` adapters), not a new invention, just closing a gap where it wasn't yet applied.

### FR-V — Conflict resolution screen (NEW, 2026-08-04 addendum)
When a **true two-sided conflict** is detected for a world — both the local copy and the Cloud copy changed since the last point this device knows they were in sync (distinct from the existing one-sided `STALE` classification, see F20 for why today's architecture cannot yet distinguish the two) — show a new modal screen, **`WorldConflictScreen`**, prompting the player to choose **"Keep Local"** or **"Keep Cloud"** before any further automatic sync activity proceeds for that world.

- **FR-V.1 (feasibility precondition — must ship before this screen can trigger correctly).** Per F20d/F20e, detecting a true two-sided conflict is **not possible with the data this feature tracks today** — the existing single, latest-writer-wins `WorldFingerprint` cache cannot tell "someone else changed it and so did I" apart from "someone else changed it and I didn't." **This requirement is therefore gated on the new local-ancestor tracking described in F20e** (a per-device, never-overwritten "last fingerprint I personally synced against" record, persisted locally per world) being implemented first — planning must sequence this as a prerequisite sub-task of FR-V, not assume it falls out of FR-P3's existing state. Until that tracking exists, `WorldConflictScreen` cannot be correctly triggered and must not be wired to the existing one-sided `STALE`/other-device signal as a stand-in (doing so would show a "conflict" screen for cases that are actually simple one-sided staleness, which is misleading).
- **FR-V.2 (trigger condition, once F20e's ancestor tracking exists).** Show `WorldConflictScreen` when, for a given world: `computeFolderLastModifiedMillis(worldFolder) > ownAncestor.syncedAtTimestamp()` (local diverged since this device's own last known sync) **and** the current global `WorldFingerprint` for that world has a `(deviceLabel, syncedAtTimestamp)` pair different from `ownAncestor`'s recorded pair **and** that current global fingerprint's `deviceLabel` is not this device's own (Cloud diverged, from another device) — the three-part condition derived in F20e. The natural checkpoints to evaluate this are the same ones already used for freshness recompute (FR-P3's cadence: upload completion, return-to-main-menu/`pullFingerprints`, Worlds-tab reload) — no new lifecycle event is required.
- **FR-V.3 (screen content — both versions' metadata).** `WorldConflictScreen` must display, for **both** the local and the Cloud version of the world, side by side:
  - **Last-modified time:** local via `computeFolderLastModifiedMillis(worldFolder)`; Cloud via the current global `WorldFingerprint.syncedAtTimestamp()` (the only Cloud-side timestamp this mod tracks, per F6/F20a — not a true Steam-side file timestamp).
  - **Size:** local via the existing `WorldSaveSyncService.computeFolderSizeBytes(Path)` (already used for the size-threshold/skip decision, F19); Cloud side has **no existing exposed size read** — `WorldArchiveCloudStore`'s interface (F6) does not currently expose a "remote archive size" query to callers, only `getQuota()`(total/available quota, not a per-file size) and `streamWrite`/read primitives. Planning must add a `long remoteArchiveSizeBytes(String archiveFileName)`-shaped method (or equivalent) to `WorldArchiveCloudStore` (and its Steam-backed and no-op/test implementations) if an accurate Cloud-side size is required for this screen — this is new surface area on an interface this spec's Architecture section otherwise commits to keeping untouched (see the Architecture note below), so planning should treat it as a scoped, explicitly-justified exception, or accept a coarser fallback (e.g. omit Cloud size, or show only "last synced by {deviceLabel}" without a byte count) if adding that interface method is judged out of proportion to this pass.
  - **Which device produced the Cloud version:** `WorldFingerprint.deviceLabel()` (already available, no new tracking).
  - Any other field planning finds meaningfully available at implementation time (e.g. `displayName` for confirmation display) should be included; the two categories above (last-modified, size) are the required minimum this spec mandates.
- **FR-V.4 (actions).** Exactly two player actions: **"Keep Local"** (skip/suppress the pending Cloud-divergence — either do nothing further this session, or explicitly re-upload the local copy so it becomes the new latest fingerprint entry, overwriting the Cloud version; planning decides which of these two "Keep Local" actually performs, but it must not silently pull Cloud content over local) and **"Keep Cloud"** (invoke the existing, already-built cloud-only-world restore machinery — `WorldRestoreService.beginRestore`, the same extraction/atomicity-safe path `WorldRestoreScreen` already drives, per the Architecture note below — to overwrite the local folder with the Cloud archive). Both actions must, on completion, update this device's local ancestor record (F20e) to the new agreed-upon state so the conflict does not immediately re-trigger next check.
- **FR-V.5 (explicitly separate from `WorldRestoreScreen` — must not replace or merge with it).** `WorldRestoreScreen` (`platform/<module>/src/main/java/de/lazuli/cloudsync/WorldRestoreScreen.java`, present in all three platform modules) handles a **different scenario**: a world that exists on Steam Cloud but has **no local copy at all** (the cloud-only-world restore flow, `docs/specs/cloud-sync-restoration.md`), and already shows honest phase text and a progress bar (`WorldRestoreService.java` `RestoreProgress`/`Phase`) for that one-directional pull. `WorldConflictScreen` handles the opposite precondition — **a local copy exists AND has diverged from a Cloud copy that has also diverged** — and is a new, separate screen class. FR-V's "Keep Cloud" action (FR-V.4) is permitted to *reuse* `WorldRestoreService.beginRestore`'s underlying extraction machinery as an implementation detail (avoiding duplicating atomic-extraction logic), but `WorldConflictScreen` itself remains a distinct UI screen with its own trigger condition (FR-V.2), never opened via `WorldsPanel.openRestoreFlow` (the existing cloud-only-world entry point), and `WorldRestoreScreen`'s own code/behavior is untouched by this requirement.
- **FR-V.6 (interaction with existing in-progress/blocking behavior).** A world showing `WorldConflictScreen`'s pending-decision state should be treated the same as `isUploadInProgress` for the purposes of blocking automatic sync activity (FR-P1/FR-T) — no automatic upload or fingerprint-driven action should run for that world while the player has not yet chosen "Keep Local"/"Keep Cloud", to avoid the automatic trigger points (FR-T.1/T.2/T.4) racing the player's pending decision and silently resolving the conflict before they've seen the screen.
- **FR-V.7 (cross-platform).** `WorldConflictScreen` must be added to all three platform modules (`fabric-1.21.11`, `fabric-26.1`, `fabric-26.2`), following the same per-module structure `WorldRestoreScreen` already establishes in each module's `de.lazuli.cloudsync` package (confirmed present in all three via `Glob`).

**Conflict-detection feasibility investigation (F20 — grounding for requirement 2)**
- **F20a — What is tracked today:** exactly one thing per world, in a single Cloud-synced JSON file (`FINGERPRINT_CLOUD_FILE_NAME`, read/written via `WorldFingerprintIO`, `WorldSaveSyncService.java:306-314,513-519`): a single `WorldFingerprint(worldSlug, displayName, deviceLabel, syncedAtTimestamp)` record per world, representing **whichever device most recently completed a successful upload of that world, and when**. `updateFingerprint` (`WorldSaveSyncService.java:513-519`) unconditionally removes any prior entry for `worldSlug` and replaces it with a new one stamped with `deviceLabel`/`System.currentTimeMillis()` — this is a **single latest-writer-wins pointer**, not a history, and it is shared globally (pulled to every device via `pullFingerprints()`, `WorldSaveSyncService.java:306-314`).
- **F20b — Local-side signal:** `computeFolderLastModifiedMillis(Path)` (referenced throughout FR-P3, added by this feature) gives a real, per-device, per-world "when did the local save folder last change" signal, independent of any Cloud state.
- **F20c — What is *not* tracked: a per-device "last known common ancestor."** Because `updateFingerprint` overwrites the single fingerprint entry on every successful upload from *any* device, a device's own record of "the state I last successfully synced" is destroyed the moment a *different* device syncs the same world afterward. Concretely: if Device A syncs at T1 (fingerprint = A@T1), then Device B syncs at T2 > T1 (fingerprint = B@T2, A's record is gone), Device A — if it later changes its own local copy and calls `upToDateStatusFor` — sees `fingerprint.deviceLabel() != deviceLabel` (line 263) and returns `STALE` immediately, **without ever checking whether Device A's own local folder actually changed since T1**. The code has no way to answer "did Device A's local copy also diverge from the T1 ancestor, or is it still exactly what it was at T1" — that information was never separately recorded by Device A itself; it only ever read the shared, mutable, single-slot fingerprint.
- **F20d — Conclusion: true two-sided conflict detection is NOT feasible with today's data model alone.** A genuine two-sided conflict requires knowing, for a specific common synced point in time, that (1) the local copy changed after it, **and** (2) the Cloud copy changed after it **from a different device**. Signal (1) is only reliably knowable today if the current device is also the one that holds the latest global fingerprint (the `!fingerprint.deviceLabel().equals(deviceLabel)` branch short-circuits before ever comparing local mtimes — see F20c) — once another device has synced more recently, the current device's own "last synced from my perspective" timestamp is unrecoverable from existing state. Signal (2) is only known in the coarse "someone else's label is now newest" sense, not "did Cloud change *after* the point I personally last synced from."
- **F20e — What new state closes this gap:** each device must persist **its own, locally-kept, never-overwritten-by-other-devices** record of "the fingerprint (deviceLabel + syncedAtTimestamp pair) that was in effect the last time *this* device itself completed a sync of this world" — effectively a private "last known common ancestor" marker, distinct from the shared/mutable global fingerprint cache. Concretely: a new small local-only file (not pushed to Cloud, e.g. `featureConfigDir.resolve("world-sync-ancestor-cache.json")`, following the same `WorldFingerprintIO`-style JSON shape), written by this device immediately after its own successful `updateFingerprint` call, storing `(worldSlug -> ownLastSyncedFingerprint)`. With that marker in place, a two-sided conflict is then computable as: `computeFolderLastModifiedMillis(worldFolder) > ownAncestor.syncedAtTimestamp()` (local diverged) **AND** the current global fingerprint's `(deviceLabel, syncedAtTimestamp)` differs from `ownAncestor` **AND** `globalFingerprint.deviceLabel() != thisDevice` (Cloud diverged, from elsewhere) — all three conditions checkable with the proposed new local-ancestor state plus data already read today. Without this new tracking, the system can only ever report the existing one-sided `STALE` (F20c's `deviceLabel` mismatch case), which conflates "someone else definitely changed it and I have no local changes" with "someone else changed it and *I also* changed it locally" — exactly the ambiguity requirement 2 must resolve.

## Architecture
- No new Feature→Feature dependency: all new state (FR-P1/FR-P3, FR-T) lives inside `features/steam-cloud-sync`, exactly where the existing toggle/status trackers already live; `WorldsPanel` (platform module) continues to read only through Hook interfaces/static holders, the same seam `cloud-sync-restoration.md` already established.
- The up-to-date/stale computation (FR-P3) deliberately avoids any new Steam Cloud API surface — it is a local-mtime-vs-self-recorded-fingerprint comparison, computed entirely from data this mod already owns (`WorldFingerprint` cache) plus one new cheap local filesystem scan. This keeps `WorldArchiveCloudStore`/`CloudFileStore`'s existing minimal interface untouched.
- Threading: `computeFolderLastModifiedMillis` must not run on the render thread per-frame (Performance) — it is invoked from a cached/periodic checkpoint (see Performance).
- **New, per FR-T:** `onPlayDisconnect` (`SteamCloudSyncClientInitializer.java:278-287`) becomes the single hook that both the existing upload trigger (F11) and the new return-to-menu download/reconcile check (FR-T.4) live in — no new Fabric API event registration is needed for FR-T.4, only additional logic inside the existing handler. FR-T.2 similarly extends the existing `reconcileAtStartup()` call, not a new lifecycle event. FR-T.1 is the only trigger point in this spec requiring a genuinely new hook — a Fabric mixin (`WorldSaveHookMixin`) into `IntegratedServer`'s save-everything method, following the same `@Mixin`/static-holder pattern already established by `IntegratedServerWorldHostingMixin`/`WorldHostingHookHolder` for a different feature in this same mixin package.
- FR-T.2's startup upload check must run its `computeFolderLastModifiedMillis` scans off the render thread (it happens during client startup before the main menu is first shown, but should still avoid blocking startup for a large number of worlds — consistent with the general Performance guidance below, this may itself warrant backgrounding via the existing `CloudSyncWorker`).
- Archive compression (F15) requires no architectural change — `WorldSaveSyncService`'s existing `ZipOutputStream`/`Deflater.BEST_COMPRESSION` archive-building path is unaffected by any change in this spec.
- **New, per FR-T.5:** the added gating check lives inside `CloudSyncableReconciler`'s two existing static methods (`reconcileAtStartup`/`pushOnShutdown`), reading/writing a new small persisted state object keyed by `cloudSyncId()` — no new class hierarchy or Feature-to-Feature seam is introduced; the change is confined entirely to `features/steam-cloud-sync`'s existing `CloudSyncableReconciler`/`CloudSyncCoordinator` pair, with zero changes required to the three platform-module adapter classes themselves (`OptionsTxtCloudSyncAdapter`/`ServersDatCloudSyncAdapter`/`CrossWorldStatsCloudSyncAdapter`) beyond their existing `CloudSyncable` contract, since `cloudSyncId()`/`localLastModifiedMillis()`/`exportState()` already provide everything the gate needs.
- **New, per F17/FR-P1:** `WorldSaveSyncService.onWorldUnload` (and, once added, `onWorldSaved`/the startup-stale-upload path) must call `statusTracker.markUploadPending(worldSlug)` **before** handing work to `CloudSyncWorker.submitBackgroundWork(...)`, not from within the submitted `Runnable`. This is a small but load-bearing ordering change from the original draft — calling it from inside the background-thread lambda would leave the queued-behind-another-upload window (`CloudSyncWorker`'s single background `ExecutorService`, `CloudSyncWorker.java:49,61-65`, serializes submitted work) completely unmarked, which is exactly the gap the finalized decision closes.

## Networking
- FR-P1/FR-P3 add zero new Steam API calls. **FR-T.1/FR-T.2 do add new Steam API traffic** relative to today — an on-save upload means uploads can now happen more frequently than once per world-session (previously exactly once, at disconnect), and a startup upload check means an additional potential upload per stale world at every client launch (bounded to actually-stale worlds only, per the resolved FR-T.2 threshold). This is an intentional behavior change requested by the user, not a bug, but planning should confirm this doesn't meaningfully stress Steam Cloud quota/rate limits for a player with many worlds who saves frequently — worth a brief check against `config.maxWorldArchiveSizeMb()`/existing quota-check code (`cloudFileStore.getQuota()`) during planning.
- FR-T.3/FR-T.4 add no new Steam API call shape beyond what `pullFingerprintsAtStartup()` already does today (a single small metadata-file read) — just calling it from an additional trigger point.
- **FR-T.5 reduces Steam API traffic relative to today** — the opposite direction from FR-T.1/FR-T.2's increase. Today, three small file uploads (`options.txt`/`servers.dat`/cross-world-stats) happen unconditionally at every startup and every shutdown regardless of change (F16); after FR-T.5, each of those three uploads only happens when its file actually changed since the device's last successful upload of it. This is a straightforward reduction in wasted Cloud writes, not a new networking concern.
- Archive compression (F15) already minimizes per-upload payload size at the maximum `Deflater` setting; no networking-relevant change from this pass.
- **F17/FR-Q.1 add zero new Steam API calls** — the in-progress indicator is a purely client-side rendering decision (spinner/indeterminate bar) driven off the existing `isUploadInProgress` poll; no new Cloud read is introduced to support it, and (per Non-goals) no chunked-upload API switch is made in this pass to obtain real progress data.

## Persistence
- No new persisted file for FR-P1/FR-P3. The in-progress flags (FR-P1) are pure in-memory, session-only state (`ConcurrentHashMap`-backed, matching `WorldSyncStatusTracker`'s existing pattern) — never written to disk, reset to "not in progress" on every client restart. This is unchanged by the FR-P1 hand-off-timing refinement (Architecture) — only *when* the flag is set changes, not its persistence model.
- The freshness computation (FR-P3) reads the existing `world-fingerprint-cache.json` (`WorldSaveSyncService.fingerprintCachePath`, unchanged) and the local world folder's own filesystem mtimes (not persisted separately — recomputed/cached per Performance below).
- No new persisted file for FR-T.1-T.4 either — the new trigger points invoke existing upload/download-metadata code paths with existing persistence (`world-fingerprint-cache.json`, the archive itself on Steam Cloud, already compressed per F15); no new local state file is introduced.
- **New for FR-T.5: one small new persisted file is required**, e.g. `featureConfigDir.resolve("cloudsyncable-upload-state.json")`, storing a map from `cloudSyncId()` (`"options"`, `"servers-dat"`, `"cross-world-stats"`, stable identifiers already returned today) to the last-uploaded mtime (or content hash, per the mechanism decision in FR-T.5) and, for symmetry with existing JSON-config patterns in this feature, ideally read/written via a small IO helper class following the same shape as this feature's existing config IO classes (e.g. `SteamCloudSyncConfigIO`, `CrossWorldStatsConfigIO`) rather than ad hoc serialization. Unlike the session-only in-progress flags, **this state must persist across client restarts** — the whole point is comparing "what did this device upload last time (a prior process)" against "what's on disk right now (this process)."
- No new persisted state for F17/FR-Q.1 — the in-progress visual treatment (progress bar/spinner) reads only the existing in-memory `isUploadInProgress` flag; nothing about the indicator itself is written to disk.

## Performance
- **Risk called out explicitly:** a full `Files.walk` mtime scan (FR-P3) run naively once per world per render frame would be a real performance problem. This spec requires the freshness scan be **cached and refreshed on a coarse cadence**, not computed inline in `render()`:
  - Compute `computeFolderLastModifiedMillis` once per world when the Worlds tab's world list is (re)loaded (`WorldsPanel.reload()`, already an async, non-per-frame checkpoint, `WorldsPanel.java:122-140`) and cache the result per `worldSlug` alongside `summaries`.
  - **Resolved (was Open Question #3):** additionally recompute on (a) every upload completion for that world (FR-P1's `markUploadFinished`), and (b) every return-to-main-menu event (F14/FR-T.4), since both are natural, already-existing-or-newly-added checkpoints rather than a fixed timer — no separate slow-tick poll is required for this pass; if a player leaves the Worlds tab open across a very long session without triggering either of those events, the displayed freshness may lag until the next natural trigger, which is an accepted tradeoff for this pass (a timer-based fallback is a Future Extension if this proves insufficient in practice).
  - The in-progress flag (FR-P1) is a cheap `ConcurrentHashMap` lookup, safe to call every frame exactly as `isSyncEnabled`/`statusFor` already are today (`WorldsPanel.java:297,306`) — no caching needed.
- FR-T.2's startup stale-check (a `Files.walk` scan per sync-enabled world at every client launch) should be backgrounded via the existing `CloudSyncWorker`/background-thread pattern rather than run synchronously on the startup path, consistent with how `syncWorldNow`'s own archive-building already avoids blocking the tick thread (`CloudSyncWorker.java:37-46`).
- No new background thread is introduced beyond reusing `CloudSyncWorker`; the freshness scan piggybacks on `WorldsPanel.reload()`'s existing `CompletableFuture`/`Minecraft.getInstance()`-executor pattern (`WorldsPanel.java:126-134`).
- Archive compression already runs at `Deflater.BEST_COMPRESSION` (F15) — the highest CPU-cost setting available — but this is pre-existing, already-accepted behavior from the prior compression spec/plan, not a new cost introduced by this spec.
- **FR-T.5's gating check is a net performance win, not a cost:** comparing a small stored mtime/hash against the current file's mtime (cheap `Files.getLastModifiedTime` call, already done today via `localLastModifiedMillis()`) or, if hash-based, hashing three small files (`options.txt`/`servers.dat`/cross-world-stats are all small, typically well under 1 MB) is trivial next to the network round-trip it now avoids for unchanged files, at both the startup-reconcile and shutdown checkpoints.
- The in-progress indicator's animation (FR-Q.1) is a trivial per-frame cost (a simple animated rectangle/spinner draw, no new allocations or filesystem/network calls per frame) — no performance concern beyond what any other animated vanilla widget already costs.

## Future Extensions
- A "force resync now" click action on a `STALE` world's freshness icon, immediately invoking the same upload path `onWorldUnload` uses.
- A global/tab-level summary (e.g. "3 worlds syncing…" badge on the Worlds tab button itself) — this spec is row-level only.
- A timer-based freshness re-check fallback (see Performance) if the event-driven recompute cadence (upload-completion + return-to-menu) proves insufficient for long-open-tab sessions in practice.
- Independent per-trigger-point config toggles (e.g. "sync on save: on/off" separate from "sync on disconnect: on/off") if the user wants finer control than this pass's single sync-enabled preference per world.
- Revisiting `STALE` detection to use a true Steam-side file timestamp instead of this mod's own self-recorded fingerprint, closing the F6 gap.
- **New, per F17:** adding real byte-level upload-progress tracking (switching `WorldArchiveCloudStore.streamWrite` to steamworks4j's chunked-write API, or instrumenting archive construction/upload with periodic byte-count callbacks) to upgrade the in-progress indicator from an indeterminate spinner/bar to a genuine determinate progress bar, matching `WorldRestoreService`'s existing restore-side progress model. Flagged as a real possible enhancement, not adopted now because it is a meaningfully larger lift than the rest of this spec (touches the Cloud-write seam's contract and both its real and no-op implementations) relative to its benefit for what is typically a small, fast per-world upload.
- Extending the in-progress indicator's visual/blocking treatment (colors, exact spinner style, whether Play/Edit pill buttons specifically should be blocked) once the user has tested this finalized minimal version live and has concrete feedback.
- Extending FR-T.5's per-adapter change-detection approach to a true content-hash mechanism uniformly (if mtime-based is chosen for the initial implementation) if mtime granularity/false-positive edge cases prove troublesome in practice.
