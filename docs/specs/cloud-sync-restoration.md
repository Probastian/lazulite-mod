# Cloud Sync Restoration — Specification

**Status: Finalized — approved pending planning.** All previously open questions (see history in git blame / prior revision) have been resolved by explicit user decision and are incorporated below; none remain open.

## Overview
`features/steam-cloud-sync` (spec: `features/steam-cloud-sync/specification.md`) already ships a working, tested Steam Cloud sync backend and several vanilla-screen UI hooks (bookmark toggle on the Multiplayer screen, per-world sync-toggle icon and cloud-only-world synthetic rows on the vanilla Singleplayer screen). The subsequent main-menu rework (`features/main-menu`, see `features/main-menu/specification.md`) replaced the vanilla `TitleScreen` — and, critically for this spec, replaced the vanilla Singleplayer world-select screen's role in the player's flow — with a wholly custom `MainMenuScreen` that renders its own **Worlds** tab (FR3) directly from `LevelSummary` data, never instantiating `WorldSelectionList`/`WorldSelectionList.WorldListEntry`. Because both (a) the per-world Cloud-sync toggle (`WorldListEntrySyncIconMixin`, Group 6/FR6.1 of the steam-cloud-sync spec) and (b) the cloud-only-world synthetic-row/restore-flow UI (`FabricCloudOnlyWorldListInjector`, `CloudOnlyWorldListEntry`, `WorldRestoreScreen`, Group 6/FR6.8–FR6.13) are injected directly into `WorldSelectionList`/`WorldSelectionList.WorldListEntry` (one via `@Mixin`, the other via reflection/subclassing against that same vanilla list), both are now **dead code**: that vanilla class is simply never constructed on the path a player actually uses to reach their worlds, so neither the toggle icon nor the cloud-only rows ever render, and a player can no longer change per-world sync preference or restore a cloud-only world. The backend driving both (`WorldSyncPreferenceService`, `WorldSaveSyncService`, `WorldSyncToggleHookHolder`/`WorldSyncStatusHookHolder`, `CloudOnlyWorldsFacade`/`CloudOnlyWorldDetector`, `WorldRestoreService`/`WorldArchiveCloudStore`, `CloudOnlyWorldsHook`/`WorldRestoreHook`) is intact and still wired up in `SteamCloudSyncClientInitializer` — only the two UI entry points were lost.

This spec restores both lost UI surfaces by re-attaching their existing logic to the new Worlds tab (Pattern 3, in-row rendering plus one synthetic-row rendering, but against the new feature's own row type instead of a mixin/reflection against vanilla's row), and separately expands cloud-sync scope so three additional, always-on categories are covered: `options.txt`, the multiplayer server list, and the Statistics tab's data — none of which the existing `steam-cloud-sync` feature syncs today (its own spec explicitly lists `options.txt`/`servers.dat` as Non-goals, and no `CloudSyncable` adapter for Cross-World Stats has ever been registered).

## Goals
- Restore a per-world Cloud Sync toggle, reachable from the main menu's Worlds tab, that lets a player opt a given local world into/out of Steam Cloud world-save sync — same semantics as the existing (currently unreachable) `WorldSyncPreferenceService`/`WorldSaveSyncService`/FR6.1–FR6.13 behavior in `features/steam-cloud-sync/specification.md`.
- Restore the cloud-only-world synthetic-row/restore-flow UI in the Worlds tab — a world that exists in this device's Steam Cloud fingerprint metadata but has no matching local save folder must be surfaced and restorable, same semantics as the existing (currently unreachable) FR6.8–FR6.13 behavior.
- Reuse the existing backend/service logic (`WorldSyncPreferenceService`, `WorldSaveSyncService`, `WorldSyncToggleHookHolder`, `WorldSyncStatusHookHolder`, `CloudSyncCoordinator`, `CloudOnlyWorldsFacade`, `CloudOnlyWorldDetector`, `WorldRestoreService`, `WorldArchiveCloudStore`, `CloudOnlyWorldsHook`, `WorldRestoreHook`) verbatim; only the injection/rendering point changes (new Worlds-tab rows instead of a mixin/reflection against vanilla's `WorldListEntry`/`WorldSelectionList`).
- Make `options.txt` always cloud-synced, with no user-facing toggle, using the existing Group 1 (`CloudSyncable`) mechanism.
- Make the player's server list (the same data source the Servers tab's Saved sub-view reads, i.e. vanilla's `ServerList`/`servers.dat`) always cloud-synced, with no user-facing toggle.
- Make the Statistics tab's underlying data (`features/cross-world-stats`'s `cross-world-stats.json`, per-Steam-account `AccountStats`) always cloud-synced, with no user-facing toggle, **excluding the local "offline" (non-Steam-logged-in) account bucket** — only Steam-account-linked stats data syncs (see FR-D.2).
- Preserve every existing steam-cloud-sync behavior not explicitly called out above (Groups 1–5, world-save quota/fallback strategy) unchanged.
- Delete the dead vanilla-`WorldSelectionList`-targeting mixin/reflection classes this restoration makes fully redundant (see FR-A.4/FR-E.6), rather than leaving unreachable code in the tree.

## Non-goals
- Redesigning `WorldSyncStatusHookHolder`'s status semantics (`SYNCED`/`SYNC_ERROR`/`SKIPPED_TOO_LARGE`), `WorldSaveSyncService`'s size-limiting/quota/fallback strategy (FR6.3–FR6.7 of the existing spec), or `WorldRestoreService`'s restore/extraction/atomicity logic (FR6.10–FR6.13) — all reused as-is; only their UI entry points change.
- Making `options.txt`, the server list, or Statistics data *optionally* toggleable — the user's request is explicit that these three are always-on, non-negotiable; no per-item settings UI is added for them.
- Syncing the local "offline" (non-Steam-logged-in) Cross-World Stats bucket across devices — deliberately excluded (FR-D.2); this bucket remains local-only, never read from or written to Cloud by this feature.
- Syncing Wardrobe equip-map data (`features/main-menu/specification.md:205` already explicitly defers this) — out of scope here.
- Any change to `features/steam-cloud-sync`'s Groups 3–5 (bookmarked servers *within that feature's own schema*, "continue where you left off" pointer, notes/waypoints) beyond what's needed to keep them compiling against any renamed/moved hook classes.
- Building a new generic "sync settings" screen — the three always-on categories need no UI at all beyond an optional read-only status indicator (see UI).
- Changing where/how `servers.dat` or `options.txt` are read for their *primary* (non-cloud) purpose — vanilla continues to own those files' normal read/write path; this feature only adds a secondary Cloud mirror/reconcile step.
- **Cleanup adjacency:** leaving `WorldListEntrySyncIconMixin`, `WorldListEntryReflection`/`EntryListWidgetReflection`, `FabricCloudOnlyWorldListInjector`, `CloudOnlyWorldListEntry`, `AbstractSelectionListReflection`, and the 1.21.11/26.1/26.2 `WorldSelectionListInvokerMixin`/`WorldListWidgetInvokerMixin`-family accessor mixins in place "just in case" is explicitly out of scope for this spec's end state — these are deleted outright (FR-A.4, FR-E.6), not deprecated or feature-flagged off, once their replacement Worlds-tab code ships. This is a definitive decision, not left to planning's discretion, save for the one explicit re-verification gate already noted under Compatibility (confirming no other code path still opens `SelectWorldScreen`).

### FR-A — Restore the per-world Cloud Sync toggle in the Worlds tab

No new hook interface, no changes to `WorldSyncPreferenceService`.
- **FR-A.3** Status coloring/tooltip behavior (`SYNCED`/`SYNC_ERROR`/`SKIPPED_TOO_LARGE`, hover tooltip text) is ported verbatim from `WorldListEntrySyncIconMixin.lazuli$drawSyncIcon` (lines 65-101) into the new Worlds-tab row rendering code — same three status colors, same two tooltip strings, same "no icon shown for `NOT_SYNCED`" rule.
- **FR-A.4** `WorldListEntrySyncIconMixin` and its supporting `WorldListEntryReflection`/`EntryListWidgetReflection` helper are deleted (all three platform modules) once the new Worlds-tab rendering ships (Non-goals cleanup requirement), since the vanilla `WorldSelectionList.WorldListEntry` row is unreachable from `MainMenuScreen` and keeping the dead mixin around only invites confusion about which code path is live (F2). - **FR-A.5** `WorldSyncToggleHookHolder`/`WorldSyncStatusHookHolder` publication in `SteamCloudSyncClientInitializer` (`:78-84`) is unchanged; `MainMenuClientInitializer`/`MainMenuScreen`'s row-rendering code simply becomes the new *reader* of these two holders, replacing the mixin as the reader. ### FR-B — `options.txt` always cloud-synced
- **FR-B.1** `options.txt` (path: `FabricLoader.getInstance().getGameDir().resolve("options.txt")`, vanilla-owned, never touched for its primary read/write path — Non-goals) is synced via a new adapter implementing the existing `CloudSyncable` contract (`api/src/main/java/de/lazuli/api/cloudsync/CloudSyncable.java`: `cloudSyncId()`/`exportState()`/`importState(byte[])`), registered into `SteamCloudSyncClientInitializer`'s `cloudSyncables` list (currently `List.of()` per F3) alongside any other adapters this spec adds.
- **FR-B.2** No config toggle exists for this adapter — it is unconditionally included in the `cloudSyncables` list whenever `SteamCloudSyncClientInitializer` constructs it, independent of `SteamCloudSyncConfig`'s per-group booleans (Group 1/2's existing `enabled` flags in `features/steam-cloud-sync/api/SteamCloudSyncConfig.java` govern Groups 1–5's *own* schemas; this new adapter is registered regardless of those flags' values, since the user's requirement is "always on," and the master `SteamCloudSyncConfig.enabled` / `isSteamAvailable()` gate — FR0.1 of the existing spec — is the *only* gate, same as every other synced item). This is a deliberate, spec-level exception to the existing feature's own "every group has an independent toggle" pattern (FR0.2) and must be called out clearly in code comments/JavaDoc to avoid a future maintainer assuming it follows that pattern.
- **FR-B.3** Reconciliation follows the existing FR0.4 last-write-wins-by-timestamp rule exactly as every other `CloudSyncable` entry does — no special-casing for `options.txt`'s content/format; it is synced as an opaque byte blob (`exportState()` reads the raw file bytes, `importState(byte[])` writes them back verbatim), matching how `HelloWorldMainMenuCloudSyncAdapter` treated its own JSON file (F3) rather than attempting to parse/merge individual option keys.
- **FR-B.4** Checkpoints match FR0.3: reconcile at client startup, write-back at client shutdown. `options.txt` can also change mid-session (player changes a setting and leaves the Options screen) — this spec does not add a mid-session write-back checkpoint beyond shutdown, to avoid adding new Options-screen hooks; a future extension could add a checkpoint on Options-screen close if staleness between sessions on the same device (not across devices) proves to matter.
- **FR-B.5** Edge case: if `options.txt` does not exist locally at startup (fresh install) but a Cloud copy exists, the Cloud copy is pulled and written to `options.txt` before vanilla's own options-loading code runs (ordering constraint: this adapter's startup reconcile must run before `Minecraft`'s own `Options` object is constructed/read, or, if that ordering cannot be guaranteed for the target Fabric lifecycle event, the sync writes the file and takes effect on the *next* launch rather than the current one — this ordering question is flagged for planning to confirm against each supported Fabric API version's actual entrypoint/lifecycle ordering relative to `Minecraft`'s own options load).

### FR-C — Server list always cloud-synced
- **FR-C.1** The vanilla server list (`servers.dat`, path: `FabricLoader.getInstance().getGameDir().resolve("servers.dat")`, the same data source `features/main-menu`'s Servers tab Saved sub-view reads per F7) is synced via a second new `CloudSyncable` adapter, registered unconditionally in the same `cloudSyncables` list as FR-B, same "always on, no toggle" rule (FR-B.2 applies identically here).
- **FR-C.2** Synced as an opaque byte blob (`servers.dat`'s NBT binary format is not parsed/reinterpreted by this adapter — same "don't invent a schema for a file Mojang also writes" caution the existing spec already applies to its own decision not to touch this file, `features/steam-cloud-sync/specification.md:18`), same FR0.4 reconciliation and FR0.3 checkpoints as FR-B.
- **FR-C.3** This is explicitly a **separate** Cloud file/sync target from `features/steam-cloud-sync`'s own `BookmarkedServer` list (Group 3, F7) — the two continue to coexist unchanged; this spec does not merge or deprecate either.
- **FR-C.4** Edge case: same fresh-install/new-device ordering concern as FR-B.5 — pulling a Cloud `servers.dat` before or after the Servers tab has already read the local (possibly-empty) file for that session needs the same planning-time lifecycle-ordering confirmation.

### FR-D — Statistics data always cloud-synced (excluding the offline account bucket)
- **FR-D.1** `config/cross-world-stats.json` (F6, `features/cross-world-stats/src/main/java/de/lazuli/features/crossworldstats/config/CrossWorldStatsConfigIO.java`) is synced via a third new `CloudSyncable` adapter, registered unconditionally, same "always on, no toggle" rule — with the exclusion in FR-D.2.
- **FR-D.2 (decided)** Only Steam-account-linked `AccountStats` entries (keyed by a real `steamId64`) are cloud-synced; the local `"offline"`-keyed bucket (a player who was not logged into Steam, or Steam was unavailable, while that stats data accumulated) is **explicitly excluded** from both `exportState()` and `importState(byte[])` — never read from Cloud, never written to Cloud, and never overwritten by an incoming Cloud payload. Rationale: the offline bucket has no natural cross-device identity (it isn't tied to a Steam account that could plausibly be "the same player" on another machine), and under Steam Cloud's no-merge/last-write-wins semantics (`features/steam-cloud-sync/specification.md:6,34`), syncing it verbatim would let one machine's locally-accumulated offline-play stats silently clobber a different machine's independently-accumulated offline-play stats on next reconcile — a real data-loss risk with no compensating benefit, since there is no legitimate "this is the same offline session, continued on another device" scenario to support. Concretely: `exportState()` serializes a copy of the on-disk JSON with the `"offline"` entry (if present) filtered out before upload; `importState(byte[])` merges/overwrites only the non-`"offline"` entries of the local file, always preserving whatever `"offline"` entry (if any) is already present locally, regardless of what the incoming Cloud payload contains.
- **FR-D.3** For every other (Steam-account-keyed) entry, reconciliation (FR0.4, timestamp-based) applies at whole-file granularity as with every other Group 1 adapter — i.e. "whole file minus the offline bucket" is the effective sync unit. If two different devices logged into the *same* Steam account have each accumulated stats independently between syncs, the older device's copy is still overwritten on next reconcile per FR0.4 — this residual limitation (inherited from Steam Cloud's own no-merge model) is unchanged and is not addressed by this spec; it applies only to the genuinely cross-device-identified (Steam-account) data, which is the scenario Steam Cloud sync is meant to support in the first place, unlike the offline bucket excluded above.
- **FR-D.4** Checkpoints: reconcile at startup (before `CrossWorldStatsClientInitializer` constructs `CrossWorldStatsService` with `initialAccounts`, so the freshly-reconciled file is what gets loaded — ordering constraint for planning, same class as FR-B.5/FR-C.4), write-back at shutdown (`CrossWorldStatsMergeHook.flush` already runs on `ClientLifecycleEvents.CLIENT_STOPPING`/`DISCONNECT`, `CrossWorldStatsClientInitializer.java:71,78` — the Cloud write-back must happen *after* that local flush completes, not before, so the exported bytes reflect the final in-session stats, still excluding the offline bucket per FR-D.2).
- **FR-D.5** No change to `CrossWorldStatsService`/`CrossWorldStatsAggregator`/the Statistics tab's own rendering — this is purely an additional Cloud mirror of the (offline-bucket-excluded) on-disk file, following the exact same "wrap an existing feature's config file behind a `CloudSyncable` adapter, no import of that feature's internal package beyond its already-public `ConfigIO`" shape `HelloWorldMainMenuCloudSyncAdapter` already established (F3) before it was deleted. The Statistics tab continues to display the local offline bucket (if present) exactly as it does today — FR-D.2 only affects Cloud transport, not local read/display.

### Non-functional
- **NFR1** All three new adapters (FR-B/C/D) are thin (a few lines each: read file bytes / write file bytes, or filter-and-read/merge-and-write for FR-D's offline-bucket exclusion), consistent with `CloudSyncable`'s existing "no Feature→Feature dependency" rule (`architecture.md:74`) — each adapter lives in its platform module's `SteamCloudSyncClientInitializer.java` as a private nested class, mirroring exactly where `HelloWorldMainMenuCloudSyncAdapter` used to live (F3), not inside `features/steam-cloud-sync` itself (that feature must not gain a compile-time dependency on `features/cross-world-stats` or vanilla file-format knowledge beyond raw bytes).
- **NFR2** No uncaught exception from any of the three new adapters reaches the client tick/render thread or blocks startup/shutdown — same discipline as the existing feature's NFR2.
- **NFR3** The restored Worlds-tab toggle (FR-A) and restored cloud-only-world row/restore flow (FR-E) must not regress the existing steam-cloud-sync test suite (`features/steam-cloud-sync/src/test/**`) — those tests exercise `WorldSyncPreferenceService`/`WorldSaveSyncService`/`CloudSyncCoordinator`/`CloudOnlyWorldDetector`/`WorldRestoreService` directly and are unaffected by which UI class reads `WorldSyncToggleHookHolder`/`CloudOnlyWorldsHook`/`WorldRestoreHook`.
- **NFR4** FR-D.2's offline-bucket exclusion is unit-testable on a plain JVM (a pure filter/merge function over `AccountStats` maps, no Minecraft/steamworks4j dependency) and must have direct test coverage for both directions (export excludes `"offline"`; import preserves the pre-existing local `"offline"` entry unconditionally, even when the incoming payload is otherwise newer) — consistent with `features/steam-cloud-sync/specification.md` NFR1's existing "plain-JVM-testable business logic" discipline.

## Public API
Illustrative only; final names/signatures are a planning-phase decision.

1. **`features/main-menu` (Worlds tab rendering code)** — no new `api`/`features/main-menu/api` types required; consumes the existing `de.lazuli.api.cloudsync.WorldSyncToggleHook`/`WorldSyncStatusHook` interfaces directly via `WorldSyncToggleHookHolder.getOrNull()`/`WorldSyncStatusHookHolder.getOrNull()` (FR-A), and the existing `de.lazuli.api.cloudsync.CloudOnlyWorldsHook`/`WorldRestoreHook`/`RestoreProgress`/`RestoreProgressListener`/`CloudOnlyWorldSummary`/`RestoreHandle` interfaces directly, presumably via analogous new `CloudOnlyWorldsHookHolder`/`WorldRestoreHookHolder` static holders published by `SteamCloudSyncClientInitializer` the same way the toggle/status holders are today (exact holder-publication mechanism for these two hooks is a planning decision — F8's current code receives them via constructor injection into `FabricCloudOnlyWorldListInjector`, which this spec's replacement Worlds-tab code cannot do without the same holder-pattern indirection `WorldSyncToggleHookHolder` already uses, since `MainMenuClientInitializer` and `SteamCloudSyncClientInitializer` are separate composition roots).
2. **`platform/fabric-<version>/.../SteamCloudSyncClientInitializer.java`** — three new private nested classes implementing `CloudSyncable`, added to the `cloudSyncables` list (currently `List.of()`):
   - `OptionsTxtCloudSyncAdapter implements CloudSyncable` — `cloudSyncId() -> "options"`, `exportState()`/`importState(byte[])` read/write `options.txt` raw bytes.
   - `ServersDatCloudSyncAdapter implements CloudSyncable` — `cloudSyncId() -> "servers-dat"`, same shape for `servers.dat`.
   - `CrossWorldStatsCloudSyncAdapter implements CloudSyncable` — `cloudSyncId() -> "cross-world-stats"`, same shape for `config/cross-world-stats.json` but with FR-D.2's offline-bucket filter applied on export and offline-bucket-preserving merge applied on import, obtained via `CrossWorldStatsConfigIO`'s existing public load/save methods (not raw bytes, since that file already has a typed IO class and this adapter now needs to inspect per-account keys to apply the exclusion — planning confirms the exact `CrossWorldStatsConfigIO` method shapes needed).
3. **Deleted**: `platform/fabric-<version>/.../mixin/WorldListEntrySyncIconMixin.java` (or `WorldEntrySyncIconMixin.java` on 1.21.11) and its reflection helper (`WorldListEntryReflection.java`/`EntryListWidgetReflection.java`) (FR-A.4); `platform/fabric-<version>/.../cloudsync/FabricCloudOnlyWorldListInjector.java`, `CloudOnlyWorldListEntry.java`, `AbstractSelectionListReflection.java`, and each module's `WorldSelectionListInvokerMixin`/`WorldListWidgetInvokerMixin`-family accessor mixin (FR-E.6); and each affected module's Mixin config JSON entries referencing any of the deleted classes.

## Architecture
- Layering unchanged: `features/steam-cloud-sync` still depends only on `api`/`services`; the three new adapters (FR-B/C/D) live in the platform composition root exactly where the one precedent adapter (`HelloWorldMainMenuCloudSyncAdapter`) used to live, so no new Feature→Feature edges are introduced (`architecture.md:74`).
- The Worlds-tab toggle (FR-A) moves the "who reads `WorldSyncToggleHookHolder`" responsibility from a platform-module `@Mixin` (Pattern 3 against vanilla's row class) to `features/main-menu`'s own already-custom row-rendering code (which is itself platform-module code per `features/main-menu/specification.md`'s own Public API item 3, `MainMenuScreen` living under each platform module's `de.lazuli.mainmenu` package, `features/main-menu/plan.md:99-104`) — this is a straightforward "same interface, different caller" change, not a new architectural pattern.
- The cloud-only-world row/restore flow (FR-E) makes the same kind of move, but is architecturally simpler in one respect and harder in another than FR-A: simpler, because the new Worlds-tab code already owns its own row list end-to-end (no need for the reflection/`@Invoker`-mixin trick `AbstractSelectionListReflection`/`WorldSelectionListInvokerMixin` used to force a synthetic entry into vanilla's private, protected-`addEntry` `WorldSelectionList` — the new tab can simply append a synthetic row model to whatever list structure it already builds from `LevelSummary` data); harder, because `WorldRestoreScreen` (F8) is a full vanilla `Screen` replacing the whole display, while the Worlds tab is one tab within `MainMenuScreen` — planning must decide whether restore-in-progress is shown by pushing `WorldRestoreScreen` on top (simplest, reuses F8 verbatim, but visually leaves the custom main menu chrome) or by rendering the same state machine as an in-tab overlay/modal (more consistent visually, but requires porting `WorldRestoreScreen`'s render logic into `MainMenuScreen`'s own render path rather than reusing the class as-is).
- No change to `CloudSyncCoordinator`'s reconciliation algorithm, `SteamRemoteStorage` usage, `CloudOnlyWorldDetector`'s set-difference logic, `WorldRestoreService`'s staging/atomicity discipline, or the FR0.1–FR0.6 cross-cutting rules in the existing spec — the three new adapters are ordinary Group-1-shaped `CloudSyncable` registrations, using a mechanism the existing feature already built and documented as extensible for exactly this purpose (`features/steam-cloud-sync/specification.md:45`, "Group 2 requires zero additional design ... beyond Group 1's mechanism").

## UI
- **Worlds tab, per-world toggle (FR-A)**: each real-world row (compact and expanded) gains one small toggle icon (visual design/exact placement is a planning/implementation decision, consistent with the design doc's overall Worlds-tab layout, `features/main-menu/specification.md` FR3.3/FR3.4) plus, when synced at least once, a second small status icon, both ported from the removed mixin's existing 8px-square, colored-fill convention (`COLOR_ENABLED`/`COLOR_DISABLED`/`COLOR_SYNCED`/`COLOR_SYNC_ERROR`/`COLOR_SKIPPED`) — reused verbatim rather than redesigned, since visual redesign was not requested.
- **Worlds tab, cloud-only synthetic rows (FR-E)**: a cloud-only world appears as one additional row in the same scrolling world list, using a small distinct icon (ported from `CloudOnlyWorldListEntry`'s existing filled-blue-square placeholder, pending a real `cloud_only.png` texture asset — same as the original), the world's `displayName`, and a detail line with `deviceLabel` + formatted `syncedAtTimestamp`. It has no expand/collapse state and no sync toggle. Triggering the tab's normal "open/play" gesture on this row opens the restore flow instead of loading a world: a status line reading "Restoring world from Steam Cloud..." (Phase `READING_FROM_CLOUD`) or "Extracting world files..." (Phase `EXTRACTING`) — never "Downloading..." — a progress bar sized to `processedBytes/totalBytes`, and a Cancel button. On success the row is replaced by a normal real-world row (list refresh) and that world's sync preference is enabled by default (FR6.10, unchanged); on failure/cancel the row remains cloud-only and shows a retryable inline error. Whether this is `WorldRestoreScreen` pushed as a full screen or an in-tab overlay is a planning-time visual decision (Architecture).
- **Statistics tab, Servers tab, Options screen**: no new UI for FR-B/C/D. Per the user's explicit requirement, these three categories are never user-toggleable, so no settings control is added anywhere for them. An optional, non-blocking "last synced" indicator (e.g. a small icon/tooltip on the Statistics tab header) is a Future Extension, not required by this spec. The Statistics tab's own display of the local offline bucket is unaffected by FR-D.2 (that exclusion is Cloud-transport-only).

## Configuration
- `config/steam-cloud-sync.json`'s existing `SteamCloudSyncConfig` schema (master `enabled` + per-group booleans for Groups 1–5) is **unchanged** — no new config fields are added for the three always-on categories (FR-B.2), since "always on" means "not configurable," not "configurable, defaulted to true." The only gate that can suppress FR-B/C/D syncing at all is the existing master `enabled` flag / `SteamAvailability.isSteamAvailable()` (FR0.1), applied uniformly to every `CloudSyncable` in the list, same as today.
- No new config field or flag is added to make the FR-D.2 offline-bucket exclusion optional — it is unconditional, not a toggle, per the user's decision.
- No new config file is introduced by this spec.

## Events
- No new Fabric API event registrations beyond what FR-B.4/FR-D.4 already note as open lifecycle-ordering questions for planning (confirming exactly which existing `ClientLifecycleEvents`/`ClientTickEvents`/`ClientPlayConnectionEvents` hook the new adapters' checkpoints should piggyback on — the same FR0.3 checkpoints every existing `CloudSyncable` already uses: startup reconcile, shutdown write-back). FR-A/FR-E reuse `ScreenEvents`/whatever event-or-non-event mechanism `MainMenuScreen`'s own row list already uses for population/refresh (`features/main-menu/specification.md`) — no new event type is introduced for either.

## Networking
- No change. All Cloud I/O continues to route through the existing `SteamRemoteStorage`/`SteamworksService` local-IPC-to-Steam-client path (`features/steam-cloud-sync/specification.md` Architecture) — this spec adds no new network calls, only new local files fed through the same existing pipe, plus reuse of the existing restore-flow's `fileReadAsync`/`fileReadAsyncComplete` calls (FR-E, unchanged from F8).

## Persistence
- Three new Cloud filenames are added to Steam Cloud's flat per-user namespace (naming convention per the existing spec's own guidance, `features/steam-cloud-sync/specification.md:135`, e.g. `lazuli-options.txt`, `lazuli-servers.dat`, `lazuli-cross-world-stats.json`) — exact names are a planning decision, but must follow the existing lowercase/prefixed convention to avoid collision with the six Cloud files Groups 1–6 already use.
- Local files (`options.txt`, `servers.dat`, `config/cross-world-stats.json`) remain the source of truth for single-device operation (FR0.5) exactly as today; this spec only adds a Cloud mirror, with FR-D.2's offline-bucket carve-out for the stats file.
- No new Cloud file is introduced for FR-E — it reuses the existing world-archive Cloud files and fingerprint metadata file (`features/steam-cloud-sync/specification.md` FR6.3/FR6.6) exactly as-is; only the reading/rendering code path changes.

## Compatibility
- No changes required to `steamworks4j`/the App ID/quota configuration beyond what `features/steam-cloud-sync` already assumes (Compatibility section of that spec). Three additional small-to-medium files add negligible quota pressure relative to the existing ~100MB reference budget (`features/steam-cloud-sync/specification.md:143`).
- FR-A.4/FR-E.6's deletion of `WorldListEntrySyncIconMixin`/`WorldListEntryReflection`/`FabricCloudOnlyWorldListInjector`/`CloudOnlyWorldListEntry`/`AbstractSelectionListReflection`/the accessor-mixin classes must be re-verified per target Minecraft version (1.21.11, and both 26.x lines) that `WorldSelectionList`/`SelectWorldScreen` is indeed never reachable from any code path in the shipped mod before deleting — confirmed unreachable in this research pass via `features/main-menu/specification.md` FR3.2's own wording, but planning should grep for any remaining reference to `WorldSelectionList`/`SelectWorldScreen` across all three platform modules to be certain no other feature (e.g. a debug menu, or vanilla's own "Edit World" flow reused per FR3.7) still opens that screen and would benefit from (or be confused by) now-dead UI reappearing. This single verification gate covers both FR-A.4 and FR-E.6's deletions, since both target the same underlying vanilla screen/list.

## Performance
- Unchanged from the existing spec's NFR1/Architecture "Threading" section — small file reads/writes stay on the existing checkpoint cadence (startup/shutdown), never per-tick/per-frame. The Worlds-tab toggle icon's render cost is equivalent to the deleted mixin's own (`graphics.fill` calls plus one hook lookup per visible row per frame) — no new performance concern introduced. The cloud-only synthetic row's render/detection cost (FR-E) is equivalent to `CloudOnlyWorldListEntry`/`FabricCloudOnlyWorldsHook.listCloudOnlyWorlds`'s existing cost — a cheap local set-difference against an already-pulled fingerprint file, no Steam I/O per frame or per Worlds-tab open (F8/FR6.8, unchanged). FR-D.2's offline-bucket filter/merge is a small in-memory map operation at the existing startup/shutdown checkpoints only, not a new per-tick cost.

## Future Extensions
- A visible "synced"/"last synced at" indicator for the three always-on categories (Statistics tab, Servers tab, Options screen), for player reassurance/troubleshooting.
- A mid-session write-back checkpoint for `options.txt` (e.g. on Options-screen close) if cross-device staleness within a single sitting proves to matter in practice (FR-B.4).

- A richer conflict-resolution UI for FR-E's same-slug collision case (FR6.13, unchanged) beyond "abort and tell the player" — still deferred, as in the original spec.
