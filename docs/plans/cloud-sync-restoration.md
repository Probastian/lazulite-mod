## Decisions (planning-time visual/lifecycle choices the spec leaves open)

1. **FR-E.5 restore-in-progress UI**: reuse `WorldRestoreScreen` verbatim, pushed as a full screen via `Minecraft.getInstance().setScreenAndShow(new WorldRestoreScreen(...))` from the cloud-only row's trigger handler, with its `onComplete` callback changed from "reopen a fresh `SelectWorldScreen`" to "reopen/refresh `MainMenuScreen`'s Worlds tab" (`Minecraft.getInstance().setScreenAndShow(owner)` + `WorldsPanel.reload()`-equivalent, or reconstruct `MainMenuScreen` fresh — implementation decides based on how `owner` is threaded through). Rationale: minimizes new rendering code, reuses F8's tested progress-bar/cancel logic exactly, at the acceptable cost noted in spec Architecture ("visually leaves the custom main menu chrome" during restore — acceptable since restore is a rare, short-lived, blocking-by-nature operation).
2. **FR-A/FR-E row-model additions to `WorldsPanel`**: introduce a small sealed/enum-discriminated row model (e.g. a `WorldRowKind` value — REAL vs. CLOUD_ONLY — or two side-by-side lists: `summaries: List<LevelSummary>` unchanged, plus a new `volatile List<CloudOnlyWorldSummary> cloudOnlyWorlds`) merged into one iteration order in `render`/`mouseClicked`. Interleaving choice (FR-E.2): cloud-only rows render **after** all real-world rows (simplest, avoids re-deriving `LevelSummary`'s natural sort order to interleave a different summary type; acceptable per spec's "planning-time visual decision" allowance).
3. **FR-A toggle icon placement**: an 8px square icon in the row's top-right corner (both compact and expanded states), to the left of the existing Play/Edit pills in expanded state and simply top-right in compact state, avoiding collision with existing text/icon layout. Status icon (second 8px square, when synced at least once) renders immediately to the left of the toggle icon. Exact pixel offsets are an implementation-time detail within this placement.
4. **FR-D adapter data access**: `CrossWorldStatsCloudSyncAdapter` uses `CrossWorldStatsConfigIO.load(path)`/`.save(path, filteredMap)` (typed, per spec Public API item 2) rather than raw bytes — confirmed sufficient, no `CrossWorldStatsConfigIO` API changes needed.
5. **FR-B/C/D lifecycle ordering across separate `ClientModInitializer`s**: `fabric.mod.json`'s existing client-entrypoint order already places `SteamCloudSyncClientInitializer` before `CrossWorldStatsClientInitializer`'s registration is independent (per its own class doc, "relative order... not load-bearing"). Because `CloudSyncCoordinator.reconcileAtStartup()` (called inside `SteamCloudSyncClientInitializer.onInitializeClient()`) runs synchronously and both `options.txt`/`servers.dat` are plain local files, ordering vs. vanilla's own options/server-list load is **not guaranteed** by entrypoint order alone. Adopt spec FR-B.5/FR-C.4's explicit fallback: do not attempt to force ordering before `Minecraft`'s `Options` construction; instead treat the pulled Cloud copy as taking effect on the *next* launch when a race is possible, and document this explicitly in the adapter's JavaDoc. FR-D.4's ordering (Cloud write-back after `CrossWorldStatsMergeHook.flush`) is achievable because `SteamCloudSyncClientInitializer` already registers its own `CLIENT_STOPPING`/`DISCONNECT` handlers separately from `CrossWorldStatsClientInitializer`'s; **verify at implementation time** that Fabric API's `ClientLifecycleEvents.CLIENT_STOPPING` invokes registered callbacks in registration order (i.e. registration order = the two initializers' entrypoint order in `fabric.mod.json`) so `CrossWorldStatsCloudSyncAdapter`'s in-memory read of the stats file happens after `CrossWorldStatsClientInitializer`'s own flush — if entrypoint order does not guarantee this, `CloudSyncCoordinator`'s shutdown write-back path (`syncOnShutdown()`) may need to move later in the entrypoint list, or `CrossWorldStatsCloudSyncAdapter.exportState()` may need to re-read the file fresh from disk at call time (already the plan, since it's file-backed) rather than relying on any in-memory cache — confirm `CrossWorldStatsCloudSyncAdapter` never caches file contents between calls.
6. **Cloud filenames** (Persistence section): `lazuli-options.txt`, `lazuli-servers.dat`, `lazuli-cross-world-stats.json`, following the existing lowercase/prefixed convention (`features/steam-cloud-sync/specification.md:135`).

## Risks

- **R1 — Deletion-gate false negative**: the reachability grep (Existing Implementation) could miss a dynamically-constructed reference (e.g. reflection by class name string) to `WorldSelectionList`/`SelectWorldScreen`. Mitigation: re-run the grep immediately before deleting, and additionally grep for the literal class name strings `"WorldSelectionList"`/`"SelectWorldScreen"` (not just import statements) to catch any string-based reflection use, though F8's own reflection helpers (being deleted) were the only known consumers of that pattern.
- **R2 — Lifecycle-ordering races** (Decision 5): `options.txt`/`servers.dat` Cloud-pull-before-vanilla-read ordering cannot be fully guaranteed without deeper Fabric loader/mixin-based interception (out of scope per spec Non-goals — "no change to where/how these files are read for their primary purpose"). Accepting spec's own fallback (apply on next launch) is correct per spec, but must be clearly documented so a future maintainer doesn't assume same-launch effect.
- **R3 — `CrossWorldStatsCloudSyncAdapter`'s Feature→Feature dependency**: this is a deliberate, spec-sanctioned (NFR1) exception; risk is scope creep if a future change tries to reuse this adapter's logic inside `features/steam-cloud-sync` itself, reintroducing a real architectural violation. Mitigation: JavaDoc callout on the adapter class, matching FR-B.2's own call for explicit code comments on its "always on" exception.
- **R4 — `WorldRestoreScreen` reuse (Decision 1) coupling to `owner` (`MainMenuScreen`)**: pushing `WorldRestoreScreen` as a full screen and returning to `MainMenuScreen` on completion requires threading an `owner`/callback reference through from `WorldsPanel` into a class (`WorldRestoreScreen`) that currently only knows about `SelectWorldScreen`. Risk of a small but real signature change to `WorldRestoreScreen`'s constructor/completion-callback. Mitigation: confirm `WorldRestoreScreen`'s existing constructor already accepts a generic `Runnable`/`Screen`-supplier for its "on complete, reopen X" behavior rather than hardcoding `new SelectWorldScreen(...)` — if hardcoded, this is a small, spec-sanctioned modification (FR-E.5 explicitly anticipates "adapted to reopen/refresh MainMenuScreen's Worlds tab instead"), not a violation of "reused verbatim."
- **R5 — Toggle-icon/expand-click precedence regression (FR-A.7)**: inserting a new hit-test into `WorldsPanel.mouseClicked` ahead of the existing whole-row expand fallthrough risks accidentally breaking the existing Play/Edit pill hit-tests (which already run first) if ordering is done carelessly. Mitigation: insert the new toggle hit-test between the existing pill checks and the final whole-row fallthrough, per FR-A.7's own precedence description.
- **R6 — Cross-module mixins.json accuracy**: this pass only read 26.2's `lazuli.mixins.json` in full; 1.21.11/26.1 must be individually confirmed to contain the equivalent mixin-class-name entry (and no invoker-mixin entries) before editing, since class names differ (Yarn vs. Mojmap naming) between 1.21.11 and the 26.x line.

## Test Strategy

- **Unit (plain JVM, per NFR4)**: direct test coverage for the FR-D.2 offline-bucket filter/merge pure function — (a) export excludes the `"offline"` key from an `AccountStats` map containing both offline and Steam-account-keyed entries; (b) import preserves whatever local `"offline"` entry currently exists, unconditionally, even when the incoming Cloud payload's `"offline"` entry (if any, which per FR-D.2 export it should never contain, but a test should also confirm defensive behavior if a malformed/legacy payload did contain one) differs or is newer. Lives as a plain-JVM test near wherever the filter logic is extracted (see Files to Create).
- **Unit**: `OptionsTxtCloudSyncAdapter`/`ServersDatCloudSyncAdapter`'s `exportState()`/`importState(byte[])` round-trip on a temp file (read bytes → write bytes → same bytes), verifying opaque-blob behavior with no format assumptions (FR-B.3/FR-C.2).
- **Regression**: run `features/steam-cloud-sync/src/test/**` unchanged (NFR3) — must stay green, confirming `WorldSyncPreferenceService`/`WorldSaveSyncService`/`CloudSyncCoordinator`/`CloudOnlyWorldDetector`/`WorldRestoreService` tests are unaffected by the UI-layer changes.
- **Manual/in-game verification** (platform modules are Minecraft-coupled, not amenable to plain-JVM tests):
  - FR-A: with Steam Cloud Sync enabled and a Steam session available, open the Worlds tab, confirm the toggle icon renders on both compact and expanded rows, click-toggles without triggering row expand/collapse, and reflects `SYNCED`/`SYNC_ERROR`/`SKIPPED_TOO_LARGE` status coloring/tooltips correctly (FR-A.3) after a save-sync cycle. With Steam Cloud Sync disabled/unavailable, confirm no icon renders at all (FR-A.6).
  - FR-E: seed a cloud-only world's fingerprint metadata (or reuse an existing test fixture from `features/steam-cloud-sync`'s own manual-test setup if one exists) with no matching local save folder; confirm it renders as a synthetic row in the Worlds tab, that the "play" trigger opens the restore flow (not a launch attempt), that progress/cancel/complete/failed states behave per FR-E.5, and that on success the row becomes a normal real-world row on tab refresh.
  - FR-B/C/D: verify `options.txt`/`servers.dat`/`config/cross-world-stats.json` each produce a corresponding `lazuli-*` Cloud file after a session (checkable via Steam's own Cloud file browser or `SteamRemoteStorage` debug logging, consistent with however `features/steam-cloud-sync`'s existing Groups were manually verified per its own plan/verification-report), and that a second device (or a wiped local `config`/`options.txt`/`servers.dat`) picks up the Cloud copy on next launch per FR-B.5/FR-C.4's "next launch" fallback.
  - Deletion gate: after deleting the FR-A.4/FR-E.6 classes, do a full mod build + smoke-test launch on all three target Minecraft versions (1.21.11, 26.1, 26.2) confirming no crash, no missing-mixin-target error, and that the vanilla Singleplayer screen is genuinely never reached from any menu path (Compatibility section's explicit gate).

## Acceptance Criteria

1. The Worlds tab (`MainMenuScreen`'s Worlds panel) shows a per-world Cloud Sync toggle icon on every real-world row (compact and expanded), driven by `WorldSyncToggleHookHolder`/`WorldSyncStatusHookHolder`, with FR-A.3's ported status coloring/tooltips and FR-A.6's no-icon-when-unavailable behavior, and FR-A.7's click precedence over row expand/collapse — verified in-game on all three platform modules.
2. A cloud-only world (present in Cloud fingerprint metadata, absent locally) renders as a synthetic row in the same Worlds tab list (FR-E.2/E.3), and invoking its trigger opens a working restore flow (FR-E.4/E.5) that, on success, results in the row becoming a normal real-world row after refresh, and on failure/cancel remains cloud-only and retryable.
3. `options.txt`, `servers.dat`, and `config/cross-world-stats.json` (minus the `"offline"` bucket) are each synced via a new `CloudSyncable` adapter, unconditionally registered (no config toggle), gated only by the existing master `enabled`/`isSteamAvailable()` check (FR-B.2/FR0.1).
4. The FR-D.2 offline-bucket exclusion is enforced in both directions and has direct, passing unit test coverage (NFR4).
5. `WorldListEntrySyncIconMixin`/`WorldEntrySyncIconMixin`, their reflection helpers, `FabricCloudOnlyWorldListInjector`, `CloudOnlyWorldListEntry`, `AbstractSelectionListReflection`, and any invoker-mixin-family accessor classes are deleted from all three platform modules, with corresponding `lazuli.mixins.json` entries removed, and the mod still builds and launches cleanly on all three target Minecraft versions with no dead-mixin-target errors.
6. `features/steam-cloud-sync`'s existing test suite (`features/steam-cloud-sync/src/test/**`) passes unchanged (NFR3).
7. No new Feature→Feature compile-time dependency is introduced except the single, explicitly-documented, spec-sanctioned exception (`CrossWorldStatsCloudSyncAdapter`'s platform-module-local reference to `features/cross-world-stats`'s public `CrossWorldStatsConfigIO`, per NFR1) — `features/steam-cloud-sync` itself gains no new dependency.
8. No new config field/file is introduced (Configuration section); `config/steam-cloud-sync.json`'s schema is byte-for-byte unchanged.
