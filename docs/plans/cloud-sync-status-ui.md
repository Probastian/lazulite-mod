## Planning decisions (resolving the spec's deferred naming/placement choices)

1. **FR-P1 placement: extend `WorldSyncStatusTracker`, not a sibling class.** Per FR-R.3's explicit recommendation (avoids a second object threaded through all three `SteamCloudSyncClientInitializer`s). Add `markUploadPending(String)`, `markUploadFinished(String)`, `isUploadInProgress(String)` directly to `WorldSyncStatusTracker`, backed by a new `Set<String> inProgress = ConcurrentHashMap.newKeySet()`.
2. **`WorldSyncStatusHook` interface: widen it** with `boolean isUploadInProgress(String worldSlug)` (default method returning `false`, so no other implementer — if any exist — breaks). Confirm via a repo-wide search for other `implements WorldSyncStatusHook` before finalizing the default; expected only `WorldSyncStatusTracker` implements it today (test-only fakes aside).
3. **FR-T.5 placement: option (b)** — inside `features/steam-cloud-sync`, platform-independent, keyed by `cloudSyncId()`. New package-private class `CloudSyncableUploadGate` (sibling to `CloudSyncableReconciler`, same package, same visibility level) owning the persisted map and `hasChangedSinceLastUpload`/`recordUploadedState`. `CloudSyncableReconciler.reconcileAtStartup`/`pushOnShutdown` gain an optional `CloudSyncableUploadGate` parameter (overloaded, mirroring the existing `infoLogger`-optional overload pattern at L50-57/L67-73) so `CloudSyncCoordinatorTest`'s existing no-gate call sites, if any, keep compiling — actually, since these are package-private static methods only called from `CloudSyncCoordinator`, prefer a single updated signature (add the gate as a new required parameter) and update `CloudSyncCoordinator`'s two call sites (L157-158, L175-176) plus `CloudSyncableReconcilerTest`'s call sites directly, rather than an overload — simpler, no dead API surface.
4. **FR-T.5 mechanism: mtime-based**, per spec's own steer ("simpler and consistent with FR-P3's own mtime-based approach") — `CloudSyncableUploadGate` stores `Map<String,Long> lastUploadedMillis`, gate check is `currentLocalTimestamp > lastUploadedMillis.getOrDefault(cloudSyncId, -1L)` treated as "changed" (mirrors FR-T.5's Compatibility-section first-run fallback: no entry → treat as changed → upload proceeds, matching today's behavior).
5. **Persistence for `CloudSyncableUploadGate`:** new file `featureConfigDir.resolve("cloudsyncable-upload-state.json")`, new IO class `CloudSyncableUploadStateIO` in `features/steam-cloud-sync/.../config/`, following `WorldFingerprintIO`'s existing `ParseResult(entries/warning)` shape (simple `Map<String,Long>` keyed by `cloudSyncId`, JSON object, no need for a richer record type).
6. **New mixin name:** `WorldSaveHookMixin`, one per platform module's `de.lazuli.mixin` package, `@Mixin(IntegratedServer.class)`, `@Inject(method = "<saveEverything-mapped-name>", at = @At("RETURN"))`. New static holder: `WorldSaveHookHolder` in `features/steam-cloud-sync/.../services/` (feature-side, not per-platform, since unlike `WorldHostingHookHolder` this bridges into an already-platform-independent service) — actually per the mixin's package constraints, the holder must be reachable from `de.lazuli.mixin` in each platform module, and `features/steam-cloud-sync` is already a dependency of each platform module (confirmed by existing imports in `SteamCloudSyncClientInitializer`), so placing `WorldSaveHookHolder` in `features/steam-cloud-sync/src/main/java/de/lazuli/features/steamcloudsync/services/WorldSaveHookHolder.java` is valid and keeps it single-sourced (published once by each module's `SteamCloudSyncClientInitializer`, same pattern as `WorldSyncToggleHookHolder`/`WorldSyncStatusHookHolder`, which are per-platform classes in `de.lazuli` publishing feature-side hooks — confirm during implementation whether the existing `*HookHolder` classes are per-platform-duplicated or already-shared; if per-platform-duplicated by precedent, follow that precedent instead and put three copies of `WorldSaveHookHolder` under each module's own package, mirroring `WorldHostingHookHolder`'s actual location at `platform/<module>/.../worldhosting/WorldHostingHookHolder.java`). **Resolved for planning purposes: mirror `WorldHostingHookHolder` exactly — one `WorldSaveHookHolder` class per platform module**, in a new `de.lazuli.cloudsync` or existing platform package, holding a static reference to `WorldSaveSyncService` (or a narrower functional interface over it) published by `SteamCloudSyncClientInitializer.onInitializeClient()`.
7. **New `WorldSaveSyncService` methods (Public API section, now finalized names):**
   - `static long computeFolderLastModifiedMillis(Path worldFolder) throws IOException`
   - `enum UpToDateStatus { UP_TO_DATE, STALE, UNKNOWN }`

   - `void onWorldSaved(String worldSlug, Path worldFolder, String displayName)` (FR-T.1 hook target; re-entrancy-guarded via `statusTracker.isUploadInProgress(worldSlug)`)

8. **`CloudSyncCoordinator.onReturnToMainMenu()`** (FR-T.4): wraps `worldSaveSyncService.pullFingerprintsAtStartup()` (renamed to `pullFingerprints()` per spec's own suggestion — update the one existing call site in `reconcileAtStartup()` too) + `cloudOnlyWorldsFacade`'s refresh (check `CloudOnlyWorldsFacade`'s actual API during implementation; expected a cheap re-derive method, not a Steam call, per F5's "cheap local set-difference" note — if no refresh method exists yet, it is a no-op wrapper today since `CloudOnlyWorldsFacade` already recomputes from the fingerprint cache lazily on each `listCloudOnlyWorlds` call per `WorldsPanel.refreshCloudOnlyWorlds()`'s existing per-reload pattern; confirm by reading `CloudOnlyWorldsFacade.java` at implementation time).

1. **Early, blocking step: `javap` verification of `IntegratedServer`'s (or `MinecraftServer`'s) save-everything method for all three modules' resolved jars** (FR-T.1, FR-R.4) — must happen before `WorldSaveHookMixin` is written for any module, since the mapped method name/overload may differ across `fabric-1.21.11`/`fabric-26.1`/`fabric-26.2` (confirmed real risk per FR-R.4, unlike `IntegratedServerWorldHostingMixin`'s `initServer`/`isPublished` which this repo has already verified are stable). Do this once per module, record the confirmed signature in the new mixin's doc comment (mirroring `IntegratedServerWorldHostingMixin`'s own javadoc pattern), before writing any mixin body.
2. Implement platform-independent `features/steam-cloud-sync` changes first (`WorldSyncStatusTracker`, `WorldSaveSyncService`, `CloudSyncCoordinator`, `CloudSyncableReconciler`, new `CloudSyncableUploadGate`/`CloudSyncableUploadStateIO`), with their tests, before touching any platform module — this is where nearly all new business logic lives (FR-R.2) and can be fully unit-tested standalone.
3. Only after step 2 compiles and its tests pass, implement the three platform modules' mixin + holder + `SteamCloudSyncClientInitializer` wiring + `lazuli.mixins.json` entries, one module at a time (suggest `fabric-26.2` first since it's the already-being-edited reference module per FR-R.1, then diff-port to `fabric-26.1`/`fabric-1.21.11`).
4. `WorldsPanel.java` FR-Q changes last, per module, once the backing hooks (`isUploadInProgress`, freshness status) are live and holder-published — do `fabric-26.2` first (reference, uncommitted edits already present per spec), then port the diff to the other two, re-diffing all three per FR-R.1 before considering this step done.
5. FR-T.5 (settings/stats-file gating) has no ordering dependency on FR-T.1-T.4/FR-P1-P3 — it can be implemented and tested in parallel with/independently of the rest, since it touches only `CloudSyncableReconciler`/`CloudSyncCoordinator`, not `WorldSaveSyncService`/`WorldsPanel`. Recommend doing it either first (simplest, most isolated, quick win) or last (lowest risk of merge conflict with the larger FR-P/FR-T.1-4 changes) — plan treats it as an independent workstream, sequenced at implementer's discretion relative to steps 1-4, but still before final acceptance testing (step 6).
6. Final: cross-module diff/consistency pass (FR-R.1, Compatibility section) confirming all three `WorldsPanel.java`, all three `SteamCloudSyncClientInitializer.java`, and all three `lazuli.mixins.json` carry the same shape, before manual/live verification.

## Risks

- **Mixin version skew (FR-R.4, confirmed real risk, not speculative):** `IntegratedServer`/`MinecraftServer`'s save-everything method signature may differ (name, overload, obfuscation) across the three targeted Minecraft versions. Mitigation: step 1's mandatory per-module `javap` check before any mixin code is written; if the method genuinely differs in shape (e.g. different boolean-arg count) across modules, each module's `WorldSaveHookMixin` may need a different `@Inject` signature — acceptable, already the norm for other per-module mixin pairs in this codebase (e.g. `SpriteContentsCaptureAnimatorMixin` vs. `SpriteContentsCaptureAnimationStateMixin`).
- **Steam Cloud quota/rate-limit impact of FR-T.1/FR-T.2 (Networking section):** on-save and on-stale-startup uploads increase upload frequency versus today's exactly-once-per-session model. Mitigation: FR-T.2 is scoped to stale-only (never every world unconditionally); FR-T.1 is guarded by the existing `isUploadInProgress` re-entrancy check (no double-queueing while an upload is in flight for that world) and by the unchanged size-threshold `decideStrategy` gate. No autosave-interval throttling beyond re-entrancy is specified — if live testing shows excessive upload frequency (e.g. a very short vanilla autosave interval), a debounce window is a plausible follow-up not currently in scope; flag to the user post-implementation per the spec's own Future Extensions framing.
- **First-run fallback for FR-T.5's new persisted state (Compatibility section):** an upgrade/fresh install with no `cloudsyncable-upload-state.json` must not silently skip an upload it should perform. Mitigation: Decision 4's "no entry → treated as changed" semantics already satisfies this; must be covered by an explicit `CloudSyncableUploadGateTest`/`CloudSyncableReconcilerTest` case (see Test strategy).
- **`WorldSyncStatusHook` interface widening could affect an out-of-tree implementer** — mitigated by the default-method approach (Decision 2); no other implementer found in-repo at planning time, but this is an `api` module interface, so a default method (not an abstract new method) is the safer compatibility choice regardless.
- **`WorldsPanel.java` row-geometry crowding (UI section, all three modules):** adding a progress bar/freshness icon to an already-compact 32px-high row risks visual crowding, especially on `fabric-1.21.11`'s slightly different 406-line layout. Mitigation: spec already specifies a spinner/8px-square fallback if a progress bar doesn't fit; implementer decides per-module, verified visually (manual test, not unit-testable) before considering FR-Q done for that module.
- **Fingerprint-cache/`CloudOnlyWorldsFacade` refresh-cost assumption in `onReturnToMainMenu()` (Decision 8):** plan assumes this is cheap (local-only), per F5/existing `WorldsPanel.refreshCloudOnlyWorlds()` precedent; if `CloudOnlyWorldsFacade`'s actual refresh path turns out to re-read from disk or Steam on every call, calling it from every disconnect could be more expensive than assumed — verify its actual implementation during implementation (not yet read in full during this planning pass) before wiring it into a now more-frequent trigger point.

## Test strategy

All new tests are plain-JVM (`@TempDir` where filesystem I/O is involved), matching existing style (`WorldSaveSyncServiceTest`, `CloudSyncableReconcilerTest`), added to `features/steam-cloud-sync/src/test/java/...`. No platform-module (`WorldsPanel.java`, mixin) automated tests — those remain manual/live-verification only, consistent with this codebase's existing practice (no existing tests touch `WorldsPanel.java`, `IntegratedServerWorldHostingMixin`, or any other mixin).

- **`WorldSyncStatusTrackerTest`** (extend): `markUploadPending` sets `isUploadInProgress` true immediately (before any `syncWorldNow`-equivalent call); `markUploadFinished` clears it; a fresh `worldSlug` defaults to `false`; existing `markSynced`/`markError`/`markSkippedTooLarge`/`statusFor`/`lastErrorFor` tests must still pass unmodified (Compatibility).
- **`WorldSaveSyncServiceTest`** (extend):
  - `onWorldUnload` calls `markUploadPending` synchronously before handing off to the worker (assert via a test double/spy on `statusTracker`, or by checking status immediately after `onWorldUnload` returns, before the background thread has necessarily run).
  - `syncWorldNow`'s all four terminal paths (skipped-too-large, success, tick-thread error, IOException-during-archive-build) each leave `isUploadInProgress` false afterward (`try/finally` correctness).
  - `computeFolderLastModifiedMillis`: empty dir, single file, nested files (returns the max mtime), non-existent path (throws `IOException`, mirroring `computeFolderSizeBytes`'s existing error-handling test shape).
  - `upToDateStatusFor`'s three branches: `UP_TO_DATE` (matching device label, local mtime ≤ fingerprint timestamp), `STALE` case (a) (local mtime newer than this device's own fingerprint timestamp), `STALE` case (b) (fingerprint exists, different device label), `UNKNOWN` (no fingerprint entry for this world).
  - `checkAndUploadStaleWorldsAtStartup`: correctly skips a world already `UP_TO_DATE`; correctly enqueues (calls through to the sync path, verifiable via a test double) only a `STALE`-case-(a) world; does not enqueue for `STALE`-case-(b)/`UNKNOWN` (FR-T.2's exact scoping — confirm against spec wording: FR-T.2 only fires on case (a), never case (b)/(unknown), during implementation, since case (b)/(unknown) aren't "this device's own upload is stale," they're a different-device-wrote-it-more-recently or no-data situation which re-uploading would not fix/could make worse).
- **`CloudSyncCoordinatorTest`** (extend): `onReturnToMainMenu()` refreshes fingerprint cache (verify via a test double `CloudFileStore`/`WorldSaveSyncService` collaborator) without side effects on unrelated state (bookmarked servers, notes, last-played pointer, world-sync preferences all untouched by this call) — mirrors the spec's explicit FR-T.4 test requirement.
- **New `CloudSyncableUploadGateTest`:** unchanged local timestamp vs. recorded state → `hasChangedSinceLastUpload` false; changed timestamp → true; no prior recorded state for a `cloudSyncId` → true (first-run fallback, Compatibility); `recordUploadedState` persists across a new `CloudSyncableUploadGate` instance constructed against the same file (round-trip persistence, since FR-T.5 explicitly requires cross-restart persistence unlike FR-P1's session-only flags).
- **New `CloudSyncableUploadStateIOTest`:** round-trip serialize/parse of a `Map<String,Long>`; malformed-JSON returns a `warning()` and an empty map (mirrors `WorldFingerprintIO`'s existing `ParseResult` contract/tests).
- **`CloudSyncableReconcilerTest`** (extend, per spec's own explicit list):
  - Unchanged local file (per the gate) → no upload at `reconcileAtStartup`'s upload branch and no upload at `pushOnShutdown`.
  - Changed local file → upload proceeds at both checkpoints and `recordUploadedState` is called with the new timestamp afterward.
  - First-ever run, no prior gate state for this `cloudSyncId` → upload proceeds (matches today's existing unconditional-upload behavior for that one first pass, per Compatibility's explicit fallback requirement).
  - Download/import branch (Cloud strictly newer than local) is completely unaffected by the gate — existing tests for that branch must still pass unmodified, plus a new explicit assertion that the gate is never consulted/mutated on that path.
- No changes required to `WorldRestoreServiceTest`, `WorldSyncPreferenceServiceTest`, `DeviceLabelResolverTest`, `CloudOnlyWorldDetectorTest`, or any `config/*IOTest` beyond the two new IO tests above.

## Acceptance criteria

Tied to spec's Goals/FR sections:

### Risks (addendum, additive to base plan's Risks)

- **Clock skew across devices (new):** F20e's comparisons are all `System.currentTimeMillis()`-based across potentially different physical machines with unsynchronized clocks. A device with a clock meaningfully behind another could see its own local changes look "older" than they are relative to a Cloud timestamp written by a clock-ahead device, producing a false `NONE`/missed conflict, or the reverse (false `CONFLICT`). Mitigation: no clock-sync mechanism is introduced (out of proportion for this pass); document this as an accepted limitation (consistent with F20a-e's whole model already being self-recorded-timestamp-based, not a Steam-side authoritative clock) and note it as a Future Extension only if it proves problematic in practice — not blocking for this pass since the base FR-P3 freshness feature already carries the identical clock-skew assumption today (F5/F8), so this isn't a new class of risk, only the same one extended to a second condition.
- **Migration/backfill for pre-existing worlds with no ancestor record (new, real):** any world synced before this addendum ships has no `WorldSyncAncestor` entry. Per Decision 8's explicit handling, `checkConflictFor` treats "no `ownAncestor` entry" as `ConflictStatus.NONE` (never retroactively flags a pre-existing world as conflicted) — the ancestor record only starts accumulating from the first post-upgrade successful sync on each device going forward. This means a world that already has a real, latent two-sided divergence at the moment of upgrade will not be detected as `CONFLICT` until at least one more successful sync from this device establishes a baseline ancestor — an accepted gap, not a bug, and should be called out to the user as a known limitation of shipping this addendum (no backfill mechanism is planned, since a synthetic "first observed state" ancestor would risk falsely suppressing a real, already-existing conflict rather than correctly deferring it one cycle).
- **New required constructor parameter on `WorldSaveSyncService`:** breaks every existing call site (production + test) that constructs it directly; mitigation is purely mechanical (compiler-enforced, will not silently miss a call site) but is flagged since the base plan's Decision claims "no signature change" for FR-P1 — this addendum is the one place in the whole feature that does change the constructor, so implementation must update `WorldSaveSyncServiceTest`'s existing setup helpers/`@BeforeEach` construction alongside `CloudSyncCoordinator`.
- **`ConflictStatus` as a new type vs. folding into `UpToDateStatus`:** kept separate per Decision 8's reasoning; risk is two separate hook calls (`upToDateStatusFor`/`upToDateStatusDetailFor` and `checkConflictFor`) being invoked at slightly different cadences in `WorldsPanel`, which could theoretically show a `STALE` icon and a `CONFLICT` icon that briefly disagree with each other if computed from cache snapshots taken at different moments — mitigation: compute both from the same `reload()`/checkpoint pass, not independently polled, consistent with the base plan's existing caching discipline (Performance section).
- **FR-V.5 boundary discipline:** risk of accidentally coupling `WorldConflictScreen`'s "Keep Cloud" path so tightly to `WorldRestoreService` that a future change to `WorldRestoreScreen` unintentionally affects it. Mitigation: only call `WorldRestoreService.beginRestore(...)` (already a stable, tested public method) — no shared UI state, no shared screen class, no modification to `WorldRestoreService`/`WorldRestoreScreen` themselves planned or needed.

### Dependencies (addendum)

No new external (non-Fabric, non-project) dependencies. `java.time.format.DateTimeFormatter`/`ZoneId` (Decision 4) are JDK standard library, already implicitly available (the codebase already uses `java.time.Instant` throughout `WorldSaveSyncService`, e.g. `checkFingerprintForConflict`'s existing `Instant.ofEpochMilli(...)` formatting at L469-471) — no Maven Central lookup required for this addendum.

### Acceptance criteria (addendum)

1. Every sync/freshness indicator's tooltip reflects the current concrete state per FR-U.1/FR-U.3 (fingerprint timestamps, device labels, `SYNCED` timestamp) rather than a fixed generic string, verified by the new `upToDateStatusDetailFor`/ancestor-write unit tests plus manual visual confirmation in at least one platform module; FR-U.2's elapsed-time enhancement and the exact-byte-count `SKIPPED_TOO_LARGE` enhancement are explicitly deferred (Decision 1) and must not block this criterion.
