## Decisions on the spec's Open Questions

1. **Hex colors for the four consolidated states** — reuse/rename existing constants to minimize churn, per FR-2's own suggestion, and keep all four visually distinct from `COLOR_SYNC_ENABLED` (`0xFF3399FF`) and `COLOR_SYNC_DISABLED` (`0xFF808080`) (the retained toggle square):
   - **Unsynced** → `0xFFCC3333` (reuse today's `COLOR_SYNC_ERROR` red — the collapsed bucket already privileges "something's not right" framing over neutral grey, and red is the most attention-grabbing of the deleted colors, appropriate since Unsynced is the state most likely to need player action).
   - **Syncing** → `0xFF3366CC` base / `0xFF66AAFF` highlight (reuse today's `COLOR_IN_PROGRESS_BASE`/`COLOR_IN_PROGRESS_HIGHLIGHT` verbatim, including the existing animated marquee at the same `IN_PROGRESS_ANIMATION_PERIOD_MS = 800L`).
   - **Synced** → `0xFF33CC33` (reuse today's `COLOR_SYNC_SYNCED` green).
   - **Conflict** → `0xFFCC33CC` (reuse today's `COLOR_CONFLICT` magenta, unchanged — already visually distinct from all others).
   - Deleted (no longer referenced anywhere): `COLOR_FRESH_UP_TO_DATE` (`0xFF33CCCC`), `COLOR_FRESH_STALE` (`0xFFCC7A33`), `COLOR_FRESH_UNKNOWN` (`0xFF5A5A5A`), `COLOR_SYNC_SKIPPED` (`0xFFCCAA33`). `COLOR_SYNC_ERROR` is kept but repurposed as the Unsynced-state color (no rename needed at the constant-declaration level, but its Javadoc comment should be updated to reflect the new meaning — implementation's call whether to rename the constant itself to e.g. `COLOR_STATUS_UNSYNCED`; the plan's recommendation is to rename all four kept constants to `COLOR_STATUS_UNSYNCED`/`COLOR_STATUS_SYNCING_BASE`/`COLOR_STATUS_SYNCING_HIGHLIGHT`/`COLOR_STATUS_SYNCED`/`COLOR_STATUS_CONFLICT` for clarity, since their old names (`COLOR_SYNC_ERROR`, `COLOR_IN_PROGRESS_*`, `COLOR_SYNC_SYNCED`) no longer describe a single narrow state).
2. **Placement of `isDownloadInProgress`** — on `WorldSyncStatusHook`, per the spec's own recommendation: `default boolean isDownloadInProgress(String worldSlug) { return false; }`, mirroring `isUploadInProgress`'s existing precedent exactly (same interface, same default-method backward-compat shape, same session-only in-memory backing in `WorldSyncStatusTracker` via a new `downloadInProgress` `ConcurrentHashMap.newKeySet()` field plus `markDownloadPending(String)`/`markDownloadFinished(String)` methods mirroring `markUploadPending`/`markUploadFinished` line-for-line).
3. **Extract FR-1's precedence computation into a testable pure function** — yes. New package-private static method in each platform's `WorldsPanel.java`:
   ```
   enum ConsolidatedStatus { UNSYNCED, SYNCING, SYNCED, CONFLICT }
   static ConsolidatedStatus computeConsolidatedStatus(
       ConflictStatus conflict, boolean uploadInProgress, boolean downloadInProgress,
       boolean syncEnabled, UpToDateStatus freshness)
   ```
   implementing FR-1's exact precedence (Conflict > Syncing > Synced > Unsynced). This is a plain function of five primitive/enum arguments (no hook lookups, no I/O), package-private static so a same-package test class can call it directly without reflection. Duplicated three times (once per platform module, same as every other per-module method in `WorldsPanel`) rather than factored into a shared module — consistent with the base feature's own established per-module-duplication practice (Compatibility section, `FR-R.1`) and this spec's Non-goals (no new shared service). Recommended test target: `platform/fabric-26.2/src/test/java/de/lazuli/mainmenu/WorldsPanelStatusTest.java` (the plan picks one module, 26.2, as the canonical test location since the precedence logic is identical across all three and duplicating the same test three times adds no coverage value; see Test strategy).

## Risks

- **Interface-vs-concrete-class ambiguity for `isDownloadInProgress`'s write side.** `WorldSyncStatusHook` (the interface `WorldsPanel`/`WorldConflictScreen` are meant to depend on) only exposes read accessors (`statusFor`, `lastErrorFor`, `isUploadInProgress`); the *write* side (`markUploadPending`/`markUploadFinished`) lives only on the concrete `WorldSyncStatusTracker`, called today only from `WorldSaveSyncService` (which presumably holds a concrete reference, not just the interface). `WorldConflictScreen` is constructed from `WorldsPanel`, which today only resolves `WorldSyncStatusHookHolder.getOrNull()` (the interface). Implementation must confirm (via `WorldSyncStatusHookHolder`'s own source, not yet read in this pass) whether the holder can also vend the concrete tracker type, or whether the plan's fallback (adding `markDownloadPending`/`markDownloadFinished` to the interface itself, defaulted to no-ops, mirroring how `isUploadInProgress` itself was added) is needed instead. This is a "confirm at implementation time" item flagged rather than pre-decided, since it depends on composition-root wiring not yet inspected.
- **Three-way platform duplication drift.** As with the base feature, hand-editing three near-identical files risks the same edit landing slightly differently in one module (e.g. the Yarn-mapped `fabric-1.21.11` file's different iteration shape over `WorldListWidget.WorldEntry` vs. `LevelSummary` directly makes a byte-for-byte diff impossible even when intentional). Mitigated by the Compatibility section's required end-of-implementation three-way diff pass (already established practice) and by keeping `fabric-1.21.11`'s pre-existing `getName()` bug untouched (do not let this pass accidentally "fix" it while touching nearby lines).
- **`WorldConflictScreen` behavior only verified in detail on `fabric-26.2`.** The `fabric-1.21.11`/`fabric-26.1` versions were not read in full for their `onKeepCloud`/`RestoreProgressListener` wiring in this planning pass (only confirmed to exist via grep matches on `beginRestore`/"Keep Cloud"). Implementation must re-read both before editing to confirm the same three-callback shape applies identically; if either diverges (e.g. different callback structure), the download-flag wiring must be adapted per-file rather than copy-pasted blind.
- **Precedence-function test duplication decision (picking `fabric-26.2` only) leaves `fabric-1.21.11`/`fabric-26.1`'s copies of `computeConsolidatedStatus` untested by an automated test**, relying instead on the three-way diff pass to catch drift. Acceptable per this being a UI-consolidation pass, not a full test-coverage initiative, but flagged as a real gap should the three modules' copies diverge silently in the future.
- **Play/Edit disabled-styling regression risk.** Today neither button has any disabled-state code path at all; introducing one touches the same block the base feature's own bug-fix history (`FX15`, `post-launch-fixes-3`) already patched carefully per-platform (e.g. `fabric-1.21.11`'s divergent `editWorld` note about `EditWorldScreen`'s navigation). Keep the new `rowSyncing`-gated styling purely additive (an `if (rowSyncing) {...} else {...normal path unchanged...}` branch) rather than restructuring the existing button-rendering/click logic, to avoid reintroducing any of those previously-fixed bugs.

## Test Strategy

1. **New unit test, `platform/fabric-26.2/src/test/java/de/lazuli/mainmenu/WorldsPanelStatusTest.java`** (package-private access to `WorldsPanel.computeConsolidatedStatus`/`ConsolidatedStatus`, no Minecraft-client bootstrapping needed since the function takes only plain enum/boolean arguments): cover FR-1's full precedence table —
   - Conflict present + upload in progress → CONFLICT (precedence over Syncing).
   - Conflict present + no upload/download → CONFLICT.
   - No conflict + upload in progress → SYNCING.
   - No conflict + download in progress (upload false) → SYNCING.
   - No conflict + both upload and download true → SYNCING (either sub-case, precedence between the two is display-text-only per FR-3.2, not state-relevant here).
   - No conflict, not syncing, sync enabled, freshness UP_TO_DATE → SYNCED.
   - No conflict, not syncing, sync enabled, freshness STALE → UNSYNCED.
   - No conflict, not syncing, sync enabled, freshness UNKNOWN → UNSYNCED.
   - No conflict, not syncing, sync disabled (regardless of freshness) → UNSYNCED.
   First test file for any `WorldsPanel.java` in the repo; if `fabric-26.2`'s Gradle module has no test source set wired up yet, this includes the one-time build-file change to add it (using whatever test framework `features/steam-cloud-sync` already uses, confirmed at implementation time by reading its `build.gradle`).
2. **New/extended test for `WorldSyncStatusTracker`'s download-tracking pair** (`markDownloadPending`/`markDownloadFinished`/`isDownloadInProgress`), placed either as new test methods in an existing `WorldSyncStatusTracker`-focused test file (search for one at implementation time — none was found by name in this pass, so this may be a new small file) or inline in `WorldSaveSyncServiceTest.java` if that's where upload-tracking's own equivalent behavior is already covered (implementation to confirm by reading that test file, not yet read in this pass) — mirroring whatever pattern already tests `markUploadPending`/`isUploadInProgress`, if one exists.
3. **Manual/live verification** (no headless-Minecraft-client automated coverage exists or is proposed for actual rendering/click-hit-testing, consistent with the base feature's own established test-strategy limits): confirm on a live client, per platform build, that (a) exactly two squares render per row, (b) each of the four consolidated states shows the correct color/tooltip per FR-5's table by manually forcing each backing condition, (c) Play and Edit are both visibly greyed, both tooltip identically, and both no-op on click while an upload is genuinely in progress (trigger via a real save/upload), (d) the "Keep Cloud" restore path shows Syncing/"Downloading from Steam Cloud..." for its duration and clears back to Unsynced/Synced afterward, (e) clicking the consolidated square while Conflict is active still opens `WorldConflictScreen`, and clicking it in any other state is a no-op, (f) the existing toggle square's new tooltips (FR-5) appear correctly for both enabled/disabled. This must be repeated on all three platform builds per the Compatibility section's existing three-way-verification practice.
4. Regression-check existing `WorldSaveSyncServiceTest.java`/`WorldRestoreServiceTest.java`/any `CloudSyncableReconciler`/`CloudSyncCoordinator` tests still pass unmodified (spec's Compatibility section asserts no backend logic changes here — this is a check, not new work).

## Acceptance Criteria

- Each of the three platform `WorldsPanel.java` files renders exactly two 8px squares per world row (toggle, then one consolidated status square immediately to its left) — `drawFreshnessIndicator` and `drawConflictIndicator` no longer exist as independently-drawn squares (FR-2, FR-6).
- The consolidated square's color/state is computed via `computeConsolidatedStatus` (or equivalently-named pure function) following FR-1's exact precedence (Conflict > Syncing > Synced > Unsynced), unit-tested per Test strategy item 1.
- Hovering the consolidated square shows the correct FR-5 tooltip text for whichever of the four states is active, including the Unsynced state's priority-ordered detail-reason fallback chain (SYNC_ERROR → SKIPPED_TOO_LARGE → sync-disabled → STALE → UNKNOWN) and the Syncing state's upstream/downstream text distinction (FR-3.1/FR-3.2).
- Hovering the toggle square shows the new FR-5 enabled/disabled tooltip text (previously absent).
- Clicking the consolidated square while its state is Conflict opens `WorldConflictScreen`; clicking it in any other state is a no-op; the toggle square's click-to-toggle behavior is unchanged.
- `WorldSyncStatusHook.isDownloadInProgress(String)` exists as a default method returning `false`, implemented by `WorldSyncStatusTracker` with matching `markDownloadPending`/`markDownloadFinished` methods; `WorldConflictScreen`'s `onKeepCloud()` sets the flag true before `beginRestore` and false in both `onComplete` and `onFailed`.
- While a given world's consolidated status is Syncing (upload or "Keep Cloud" download in progress), that row's Play and Edit buttons are both visually greyed (muted fill + dimmed label), both show the shared "Cannot play or edit while syncing with Steam Cloud." tooltip on hover, and both clicks are consumed as no-ops — verified for both buttons independently, not just one (FR-4).
- A pending Conflict with no active Syncing does **not** disable Play or Edit (FR-4.4) — verified as a distinct manual test case from the Syncing-disables-both case.
- All three platform modules' changes are diffed against each other at the end of implementation and confirmed to differ only in the already-known, pre-existing platform-API-shape ways (Compatibility section) — no new unintended divergence introduced by this pass.
- No changes made to `WorldSaveSyncService`, `CloudSyncCoordinator`, `CloudSyncableReconciler`, `WorldRestoreService`'s internal algorithms, `WorldFreshnessHook`/`WorldConflictHook` interfaces, `WorldConflictScreen`'s own conflict-detection/resolution logic (only its download-flag side-effect wiring), or any persisted file format (Non-goals, Compatibility, Persistence sections) — confirmed via `git diff` scope review at the end of implementation.
- Existing tests (`WorldSaveSyncServiceTest`, `WorldRestoreServiceTest`, and any others under `features/steam-cloud-sync/src/test`) still pass unmodified.
