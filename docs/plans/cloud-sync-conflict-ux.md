## Decisions on the spec's Open Questions

1. **`ConflictDetail` shape — nested `LocalDetail`/`CloudDetail`, per the spec's own recommendation.** Concrete shape:
   ```java
   record ConflictDetail(
       String worldSlug,
       LocalDetail local,
       CloudDetail cloud) {

     record LocalDetail(
         String displayName,
         long lastModifiedMillis,
         long folderSizeBytes,
         String deviceLabel,
         Long ancestorSyncedAtTimestamp,   // nullable: no prior sync recorded for this device
         String gameMode,                  // pre-formatted display string (LevelSummary.getGameMode() already resolved by the caller before this record is built -- see below)
         long lastPlayedMillis,
         boolean hardcore,
         boolean cheatsEnabled,            // nullable-by-sentinel: -1/false + a separate `boolean levelDatReadable` flag (below) distinguishes "false" from "unknown"
         String difficulty,                // null if the level.dat read failed
         Long seed,                        // null if the level.dat read failed
         String minecraftVersion,          // null if unavailable (LevelSummary or level.dat, whichever sourced it -- see F10 row 2)
         long dayCount,                    // -1 if the level.dat read failed
         int regionFileCount,              // -1 if the region directory could not be listed
         boolean levelDatReadable) {       // false if the batched LevelStorageAccess/NBT read failed entirely; screen renders "Unknown" for every level.dat-sourced field in that case rather than crashing (F8)
     }

     record CloudDetail(
         String displayName,
         long syncedAtTimestamp,
         long archiveSizeBytes,   // -1 if WorldArchiveCloudStore.fileSize returned -1 (not present / Steam unavailable)
         String deviceLabel) {
     }
   }
   ```
   Rationale: `LocalDetail`/`CloudDetail` map 1:1 onto FR-3.1's two boxes, so `WorldConflictScreen` can pass one record per box to a shared row-rendering helper instead of threading 14+ loose fields through method parameters. `WorldConflictScreen` does **not** additionally receive the raw `LevelSummary` (resolving the Public API section's open question) — `game mode`/`last played`/`hardcore` are already cheaply available to `WorldSaveSyncService.detailFor` today only if it is *given* the `LevelSummary`, which it currently is not (it only receives `worldSlug`/`worldFolderAbsolutePath`/`displayName`). Two options were weighed:
   - (a) widen `detailFor`'s parameter list to accept the `LevelSummary` (or just the three primitive values it needs: game mode string, last-played millis, hardcore boolean) from `WorldsPanel`, which already has it at the `openConflictScreen` call site; or
   - (b) have `WorldConflictScreen` read those three fields itself from a `LevelSummary` it is separately handed.
   **Decision: (a)** — `detailFor`'s signature grows to `detailFor(String worldSlug, String worldFolderAbsolutePath, String displayName, String gameModeDisplayName, long lastPlayedMillis, boolean hardcore)`, called from `WorldsPanel.openConflictScreen` with `summary.getGameMode().getLongDisplayName().getString()` (matching the row subtitle's own existing call, `WorldsPanel.java:330`), `summary.getLastPlayed()`, `summary.isHardcore()`. This keeps `WorldConflictScreen` a pure presentation layer over one `ConflictDetail` (consistent with its current single-`detail`-field shape) rather than also depending on `LevelSummary`, and keeps `WorldSaveSyncService` — not three duplicated per-platform screens — as the single place that assembles the record. This is a source-compatible-in-spirit but signature-breaking change to a hook interface method used only within this mod's module boundary (Compatibility section already establishes this is fine, no shim needed).
2. **Hex colors.** `0xFFFFD700` (gold/yellow) for mismatch, confirmed via repo-wide grep that no existing color constant in `WorldsPanel.java`/`WorldConflictScreen.java`/`StatisticsPanel.java` uses this or a near-duplicate hex — safe to introduce as a new constant `COLOR_MISMATCH` in each `WorldConflictScreen.java`. Match color reuses the existing `0xFF908C7F` muted constant (already used for disabled-button labels, `StatisticsPanel`'s empty-state text, etc.) — named `COLOR_MATCH` for local clarity at the new call site. Key text stays `0xFFEAE8E1` (existing default body-text constant, already used in `WorldConflictScreen` for the old two-line text).
3. **Third-pill layout mechanics.** Play/Edit's own bounds/order/width must not silently change for non-conflicted rows (FR-2.1's explicit constraint). Decision: append the resolve pill in previously-unused row width, to the **left of Play**, in the same right-to-left layout style `pillBounds` already uses, only when `showResolveButton` is true:
   ```java
   private static int[] pillBounds(Font font, int x, int width, boolean showResolveButton) {
       int playW = font.width("Play") + PILL_PADDING * 2;
       int editW = font.width("Edit") + PILL_PADDING * 2;
       int editX = x + width - 8 - editW;
       int playX = editX - PILL_GAP - playW;
       int resolveW = showResolveButton ? font.width("Resolve Cloud Conflict") + PILL_PADDING * 2 : 0;
       int resolveX = showResolveButton ? playX - PILL_GAP - resolveW : 0;
       return new int[] { playX, playW, editX, editW, resolveX, resolveW };
   }
   ```
   Returning a 6-element array (not a new record type) minimizes churn at both existing call sites (`render()`/`mouseClicked()` already destructure this array positionally) — both call sites add two more local variables (`resolveX`, `resolveW`) and an `if (showResolveButton) {...}` render/hit-test block, guarded so array indices 4/5 are simply unused (0) when the row isn't conflicted. `showResolveButton` is computed once per row (`conflictCache.getOrDefault(worldSlug, ConflictStatus.NONE) == ConflictStatus.CONFLICT`), passed into `pillBounds` at both call sites, mirroring `rowSyncing`'s existing "compute once, pass to both" pattern. Overlap risk: at narrow GUI scales the three pills plus their gaps could theoretically underflow past the row's icon/text area on the left — accepted as a known cosmetic edge case (spec's Non-goals don't require a wrap-to-second-row fallback; FR-2.1 only requires all three visible/non-overlapping at the existing expanded-row width, which this satisfies at all GUI scales the Worlds tab already supports today, since expanded rows are already sized to fit two pills comfortably and a third short-ish label fits within the same margin used elsewhere in this codebase).
4. **F11 unpaired-row scrolling.** Decision: no scrolling — fit the full field list unscrolled. At a typical default font (9px line height) and GUI scale, 4 paired rows + a sub-heading + 10 unpaired rows ≈ 15 lines × ~11px row pitch ≈ 165px per box, well within a typical `Screen`'s content height (`WorldConflictScreen` is a full screen, not a fixed-height panel like `WorldsPanel`'s rows) — confirmed by the fact the current screen already reserves `height/2 - 60` down to `height/2 + 70` (buttons) for far less content, meaning ample vertical room exists above/below `height/2` on any reasonably-sized game window. Implementation should compute box top/bottom from actual measured content height (row count × line height) rather than hardcoding `height/2`-relative magic numbers, and place "Keep Local"/"Keep Cloud" at `boxBottom + margin` (FR-3.6) rather than a literal `height/2 + 50`. If a genuinely tiny GUI scale (e.g. scale 1 at a small window) is found at implementation/verification time to clip content, the fallback is trimming to a smaller font/row-pitch before resorting to scrolling, per the spec's stated preference.
5. **`fabric-1.21.11` vs `fabric-26.1`/`fabric-26.2` API parity for the F10 `level.dat` NBT batch.** Real risk, not resolved by planning-time reading alone (no existing code path in this repo reads `level.dat` on any platform today). Plan: implement the batched read as a small private static helper *inside each platform's own `WorldSaveSyncService`*... **correction, see below** — actually inside a new small per-platform helper class colocated with each platform module (not `features/steam-cloud-sync`, which is platform-agnostic Java with no Minecraft-client/version-specific imports today — confirmed by `WorldSaveSyncService.java`'s import list containing no `net.minecraft.*` types). Concretely:
   - `WorldConflictResolutionHook.detailFor`'s new signature (Decision 1) needs the F10 fields, but `WorldSaveSyncService` (in `features/steam-cloud-sync`, version-agnostic) cannot itself open a `LevelStorageAccess` or read `PrimaryLevelData` without importing per-Minecraft-version classes it does not otherwise depend on.
   - Two structural options: (a) add a new small `LevelDatReader` interface to `api/src/main/java/de/lazuli/api/cloudsync/` (a new tiny hook, implemented per-platform, injected into `WorldSaveSyncService` at construction the same way `WorldArchiveCloudStore`/`WorldFingerprintCache` already are), or (b) have each platform's `WorldsPanel.openConflictScreen` read the F10 fields itself (it already runs on the client thread, already has `levelSource`/`LevelStorageSource` in scope) and pass them into `detailFor` as additional primitive parameters, mirroring Decision 1's `gameMode`/`lastPlayed`/`hardcore` treatment.
   - **Decision: (b)**, for the same reason as Decision 1's game-mode/last-played/hardcore call — it avoids a new cross-module hook interface for a screen-only, read-once, per-platform-varying concern, and `WorldsPanel` already imports `net.minecraft.world.level.storage.LevelStorageSource`/`LevelSummary` per platform, so it is the natural place to add a small `readLevelDatBatch(String worldSlug)`-shaped private helper per platform, returning a small local carrier (not `ConflictDetail` itself — a smaller intermediate record, e.g. `LevelDatBatch(Long seed, String difficulty, Boolean cheatsEnabled, long dayCount, String minecraftVersion, boolean readable)`) that `openConflictScreen` passes into the widened `detailFor(...)` call alongside the F9/game-mode/etc. primitives.
   - This makes `detailFor`'s final signature (all platforms call it identically): `detailFor(String worldSlug, String worldFolderAbsolutePath, String displayName, String gameModeDisplayName, long lastPlayedMillis, boolean hardcore, LevelDatBatch levelDatBatch)` — with `LevelDatBatch` itself declared in `api/src/main/java/de/lazuli/api/cloudsync/WorldConflictResolutionHook.java` alongside `ConflictDetail` (a plain data-carrier record with only primitive/boxed/String fields, no Minecraft-client types, so it is safe for the version-agnostic `WorldConflictResolutionHook` interface to reference), constructed identically in shape by all three platforms' `WorldsPanel.openConflictScreen`, but by three separately-written per-platform `readLevelDatBatch` implementations.
   - **Concrete per-platform read approach** (to be finalized/verified at implementation time, not guessed further here): open `LevelStorageSource.LevelStorageAccess access = levelSource.createAccess(worldSlug)` (already used identically in `editWorld`/`StatisticsPanel.accumulateSaveStats` on all three platforms, confirmed same call shape), then obtain the level data — `fabric-26.1`/`fabric-26.2` (Mojang-mapped, newer MC) likely expose `access.getSummary(...)`/a `PrimaryLevelData`-returning method or a `getDataTag()`-style raw-NBT accessor; `fabric-1.21.11` (Yarn-mapped, MC 1.21.11) needs its own equivalent (`LevelStorage.Session`-shaped, per Yarn naming). **Implementation must read the actual `LevelStorageSource.LevelStorageAccess`/equivalent class's method list on each platform's mapped Minecraft jar before writing this code** — this plan intentionally does not assert an exact method name it cannot verify from files already in this repo (none of the three platforms have ever called this accessor for NBT before). Batch all four fields (seed, difficulty, `allowCommands`, `Time`/`DayTime`) into the single open, matching F10's explicit "one open, not four" requirement; wrap the whole read in one try/catch, setting `readable = false` and leaving the other fields at their null/-1 sentinels on any exception (F8's crash-avoidance requirement), always `access.close()` in a `finally` (mirroring `editWorld`'s existing explicit-close discipline, `WorldsPanel.java:778-782`).
   - Region-file count (F10) is computed the same call site, via `Files.list(worldFolder.resolve("region")).filter(p -> p.toString().endsWith(".mca")).count()` wrapped in its own try/catch (`-1` sentinel on failure) — independent of the NBT batch, no `LevelStorageAccess` needed for this one field.

  - `detail == null`'s existing "Conflict detail is no longer available." fallback (F6/F8) is preserved as-is, rendered instead of the two boxes when null.

## Risks

- **`LevelStorageAccess`/`level.dat` NBT accessor names are unverified across `fabric-1.21.11` vs `fabric-26.1`/`fabric-26.2`** (Decision 5, spec's flagged risk, Compatibility section item, Open Question 5). No code in this repo has ever read `level.dat` NBT before; the exact method chain (`LevelStorageAccess.getSummary(...)`/`.getDataTag()`/a `PrimaryLevelData`-returning accessor, or Yarn's differently-named equivalent) must be discovered by reading each platform's actual mapped Minecraft jar/sources at implementation time, not assumed from this plan. Mitigation: implement and verify one platform first (recommend `fabric-26.2`, since it is Mojang-mapped and has the most other already-verified precedent in this codebase), get its F10 fields rendering correctly, then port to `fabric-26.1` (likely near-identical, same mapping) and finally `fabric-1.21.11` (expect real divergence, budget extra time). If any one platform's API genuinely cannot cheaply expose one of the four F10 batch fields, the correct fallback per this spec's own F8 crash-avoidance rule is `levelDatReadable = false` for that platform (screen shows "Unknown" for all four fields on that platform only), not blocking the whole feature — confirm with the user only if an entire platform's NBT access turns out to be infeasible, not for a single missing sub-field.
- **`showResolveButton`/FR-2.5 staleness window.** As noted in the WorldsPanel section above, `conflictCache` is only refreshed at `reload()`/upload-completion checkpoints, and `recordKeepCloudResolution`'s `clearPendingConflict` call only fires on restore *completion*, not restore *start* — there is a real risk that `conflictCache` still reads `CONFLICT` for the entire duration of an active Keep-Cloud restore, which would keep showing the resolve pill during the exact window FR-2.5 says it must not. This must be verified at implementation time (trace `refreshConflictFor`'s call sites against `isDownloadInProgress`'s own true/false transitions) and an explicit `&& !isDownloadInProgress` guard added to `showResolveButton`'s condition if confirmed stale.
- **Three-way platform duplication drift**, same standing risk this feature area always carries — mitigated by the same end-of-implementation three-way diff pass already established practice (Compatibility section), doubly important here since this spec's FR-3 layout redesign is the single largest hand-written block of new per-platform-duplicated code in this feature area so far.
- **`detailFor`'s signature widening from 3 to 7 parameters** is a larger call-site churn than a typical additive change — every one of the three `WorldsPanel.openConflictScreen`/`WorldConflictScreen` constructor call sites, plus the one production `detailFor` implementation and any existing `WorldSaveSyncServiceTest` mocks/fakes of `WorldConflictResolutionHook`, must be updated in lockstep. Mitigated by doing this as one atomic edit across all files in one implementation pass, not incrementally.
- **Row-count/vertical-fit assumption (Decision 4)** is a planning-time estimate (≈165px per box), not a rendered measurement — if implementation finds the estimate wrong at common GUI scales, the spec's own stated fallback order (smaller font/tighter row-pitch, then only as a last resort scrolling) applies; flagging here so implementation doesn't silently reach for scrolling as a first response.
- **`archiveStore.fileSize`'s real (non-stub) implementation** in `SteamRemoteStorageWorldArchiveStore` was not read line-by-line this pass — confirm at implementation time it actually calls Valve's `GetFileSize` and returns a real value (not a placeholder `-1`/`0`) before relying on it for the cloud archive size field; if it turns out to be a stub, F8's "Unknown" placeholder handles the `-1` case gracefully regardless, so this is a low-severity risk (worst case: the new field silently always shows "Unknown" until that store's own implementation is completed, not a crash or a blocking issue for this spec).

## Dependencies

No new external (non-Fabric) dependencies. This is entirely additive Java/Minecraft-client-API code plus one existing-hook-interface signature widening; no new Maven Central coordinate is introduced. If implementation discovers a genuine need for a helper library (not expected — NBT reading is standard vanilla API, JSON/duration formatting are already hand-rolled elsewhere in this codebase), it must be verified against `search.maven.org` before being added, per this project's dependency-verification rule.

## Acceptance Criteria

- While a world's consolidated status is Conflict (and not simultaneously Syncing), that row's Play and Edit buttons render muted/dimmed, are non-clickable, and show the tooltip "Cannot play or edit while this world has an unresolved Steam Cloud conflict. Resolve it first." — distinct from the existing Syncing tooltip text, which is unchanged and still shown when Syncing (with or without a simultaneous conflict) (FR-1, FR-1.1).
- A "Resolve Cloud Conflict" pill renders on an expanded row if and only if that row's world is in the Conflict state (and, per FR-2.5, not during an active Keep-Cloud-restore-triggered Syncing window even if `conflictCache` is stale) — absent entirely, not merely disabled, in every other state (FR-2).
- Clicking the resolve pill opens `WorldConflictScreen` via the existing `openConflictScreen` method, with no new method introduced for this purpose (FR-2.3).
- Both the resolve pill and the pre-existing small conflict-square click remain valid, independent entry points to the same screen (FR-2.4) — neither is removed.
- Play/Edit's own bounds/order/width are unchanged for non-conflicted rows after `pillBounds`'s signature widening (verified by a visual/pixel-position check, not just a compile-time check).
- `WorldConflictResolutionHook.ConflictDetail` is restructured into nested `LocalDetail`/`CloudDetail` records carrying every F11 field (rows 1-14), with the F9-tier fields backed by already-existing data (no new I/O beyond one `fileSize` call and one ancestor-cache lookup) and the F10-tier fields backed by exactly one batched `LevelStorageAccess`/NBT read per screen-open, per platform.
- `WorldConflictScreen` renders two bordered, titled, symmetric boxes with F11's exact field ordering identical in both boxes for rows 1-4, unpaired rows 5-14 rendered only in the Local box under a "Local-only details" sub-heading, correct grey/yellow value coloring per FR-3.4 (key text never colored), and "Keep Local"/"Keep Cloud" repositioned below both boxes without overlapping content, on all three platform modules.
- No change to `WorldSaveSyncService.checkConflictFor`, `WorldFingerprintCache`, `WorldSyncAncestor`/`world-sync-ancestor-cache.json` persistence, or the underlying effects of "Keep Local"/"Keep Cloud" (confirmed via `git diff` scope review at the end of implementation) (Non-goals).
- No cloud-side chunk/file count, content diffing, or persisted sync-history log is introduced (Non-goals) — confirmed via code review that no new Steam Cloud content-read (`beginAsyncRead`) call was added and no new persisted file format was introduced.
- Existing tests (`WorldSaveSyncServiceTest`, `CloudSyncCoordinatorTest`, `CloudSyncableReconcilerTest`, `WorldSyncStatusTrackerTest`) still pass, extended only additively for the new `detailFor` fields.
- All three platform modules' `WorldsPanel.java`/`WorldConflictScreen.java` changes are diffed against each other at the end of implementation and confirmed to differ only in the already-known, pre-existing platform-API-shape ways plus this spec's own newly-introduced (and expected) `level.dat`-accessor divergence (Compatibility section).
