# Server Browser — Feature Specification

## Overview
Adds `features/server-browser`, a new custom `Screen` reachable from the vanilla Multiplayer server-list screen (`net.minecraft.client.gui.screens.multiplayer.JoinMultiplayerScreen` on `platform/fabric-26.1`/`platform/fabric-26.2` (Mojang mappings) / `net.minecraft.client.gui.screen.multiplayer.MultiplayerScreen` on `platform/fabric-1.21.11` (Yarn mappings) — **confirmed**, see Compatibility) via a new button injected next to that screen's existing footer buttons (Pattern 1, `.claude/context/ui-guidelines.md:20-46` — no mixin needed for the button itself), placed at the **top right** of the screen (see UI). The new screen — the **Server Browser** — queries Steam's server-list matchmaking API (`ISteamMatchmakingServers`, exposed by this repo's already-vendored `steamworks4j` binding as `SteamMatchmakingServers`) for servers registered against the target Steam App ID, and renders them in a sortable, filterable, scrollable table, letting the player connect to a selected server the same way double-clicking a saved server entry does today — including servers that require a password (see Requirements, Connecting).

This is the first feature in this repo built on `ISteamMatchmakingServers`/`SteamMatchmakingServers` (distinct from `friends-sidebar`'s `SteamFriends`/`SteamUser` and `steam-cloud-sync`'s `SteamRemoteStorage`/`steam-world-hosting`'s legacy `SteamNetworking` P2P surface) and the first feature that opens a whole new custom `Screen` from a vanilla screen's button, rather than only overlaying a widget on an existing one (contrast `friends-sidebar`'s Pattern-1 overlay).

## Goals
- Add one new button to the vanilla Multiplayer screen's own button row, positioned at the top right of the screen, that opens `ServerBrowserScreen`.
- `ServerBrowserScreen` lists servers returned by a Steam Internet server-list query (`SteamMatchmakingServers.requestInternetServerList`), scoped to the target App ID (`SteamworksService.steamAppId()`, `SteamAppIdResolver` — same App ID already used for `SteamAPI.initEx()`/Steam Cloud/Friends). During this dev/testing phase, that App ID is **480 (Spacewar)**, per the current `SteamAppIdResolver`/dev `steam_appid.txt` configuration this repo already uses — this mod's own project developers and other test projects are all expected to register test servers against 480 so the Internet list has real entries to browse; when the mod ships against its own production App ID, `SteamAppIdResolver` is the single place that changes (Compatibility).
- Support LAN discovery as a second, switchable source (`requestLANServerList`) so the same screen also finds unlisted local servers, mirroring vanilla's own LAN-and-internet split.
- Sortable columns: server name, ping, players/max players, map (or game/mode string if `getMap()` is empty), password-protected indicator, VAC-secured indicator — clicking a column header toggles ascending/descending sort by that column, mirroring a conventional table-browser UX.
- Filterable: live name/text search box, "hide full servers" toggle, "hide password-protected servers" toggle, "hide servers with no password" (i.e. password-only) is out of scope (Non-goals), maximum-ping threshold (numeric input or slider), "hide empty servers" toggle. Filters apply client-side to the already-fetched/refreshing list — no re-query per keystroke.
- Connecting to a selected server (double-click a row, or select + a "Join Server" button) hands off to the exact same vanilla connect flow used elsewhere in this codebase's multiplayer join path (`ConnectScreen.connect`/`startConnecting`, per `minecraft.md`'s table row for the client-connect UI, or a `ServerInfo`/`ServerData` construction feeding `MultiplayerScreen`'s own selection, per planning's discretion) — this spec does not mandate bypassing vanilla's own connect screen/flow. Servers flagged password-protected are joinable in v1 via a password-prompt step before connecting (Requirements, Connecting) — this is not deferred to a future revision.
- Every list-population and query-lifecycle call happens off the Steamworks callback-pump/render thread coupling this repo already established (`SteamworksService.pumpCallbacks()` on the client tick loop) — this feature adds no new thread of its own; `SteamMatchmakingServerListResponse` callbacks fire synchronously during `SteamAPI.runCallbacks()`, i.e. on the client tick thread, same as every other Steamworks callback in this codebase.
- Steam-unavailable and no-Steamworks-App-ID states render a clear, non-crashing status message in place of the table, following the same status-vs-content branch precedent `friends-sidebar` v1.2 established (FR6.x in `features/friends-sidebar/specification.md`).

## Non-goals
- No Favorites/History/Spectator server-list request types (`requestFavoritesServerList`/`requestHistoryServerList`/`requestSpectatorServerList`) in v1 — Internet and LAN only (Future Extensions).
- No per-server rules/player-list drill-down (`serverRules`/`playerDetails`) in v1 — only the summary fields already present on `SteamMatchmakingGameServerItem` from the list query itself (Future Extensions).
- No favoriting/bookmarking a server from this screen into Steam's own favorites list or into this mod's own persisted server list (`ServerList`/saved servers) in v1 (Future Extensions) — connecting is one-shot, it does not add the server to the player's saved-servers list unless the player does that manually afterward via vanilla's own "Add to server list" flow (out of this feature's scope to trigger automatically).
- No server-tag/gametype filter UI beyond the generic name-search box in v1 (`SteamMatchmakingKeyValuePair` filters exist for this — Future Extensions), though the underlying request already accepts a filter array so this is a low-cost later addition, not an architecture change.
- No raw UDP ping/query fallback (`pingServer` outside Steam's own list-refresh ping) — pings shown are exactly what `SteamMatchmakingGameServerItem.getPing()` reports from Steam's own query, nothing hand-rolled.
- No dedicated `services/steamworks` extraction of a `SteamMatchmakingServersGateway` in v1 unless this feature genuinely needs to share it with a second consumer — per the graduate-on-second-use rule (`architecture.md:26`), the Steamworks calls stay local to `features/server-browser` first, exactly as `friends-sidebar`'s `SteamFriendsGateway` did before any second consumer existed (confirm at planning time whether a `services`-layer gateway already exists from a sibling feature; if not, don't build one speculatively here either).

## Requirements

**Steam matchmaking query lifecycle (business logic, `features/server-browser`)**
- **FR1.1** On opening `ServerBrowserScreen` (or switching source tabs, FR1.6), issue exactly one `SteamMatchmakingServers.requestInternetServerList(appId, filters, responseHandler)` (default source) using the App ID already resolved by this process's `SteamworksService`/`SteamAppIdResolver` — never a new/second App ID resolution path. During this dev/testing phase that App ID resolves to 480/Spacewar (Goals, Compatibility); this requirement does not hardcode 480 anywhere in `features/server-browser` itself, it only ever reads whatever `SteamAppIdResolver` already resolves.
- **FR1.2** Implement `SteamMatchmakingServerListResponse`'s three callback methods:
  - `serverResponded(request, server)` — fetch that server's row via `getServerDetails(request, server, gameServerItemBuffer)` and upsert it into the in-memory row list (keyed by server index or IP:port), then re-apply the current sort/filter.
  - `serverFailedToRespond(request, server)` — remove/mark that row as failed to respond (do not silently leave a stale row); this repo's convention for "not fatal, degrade the specific item" (compare `friends-sidebar`'s per-friend resolution failures) applies here at per-server granularity.
  - `refreshComplete(request, response)` — clear the "refreshing" spinner/indicator state; log (not surface as an error dialog) `NoServersListedOnMasterServer`/`ServerFailedToRespond` outcomes, matching this repo's existing warning-logger convention (`SteamworksService.create`'s `Consumer<String> warningLogger` pattern) rather than inventing a new error-surfacing mechanism.
- **FR1.3** `SteamMatchmakingServers.isRefreshing(request)` backs a visible "refreshing…" indicator; a manual "Refresh" button calls `refreshQuery(request)` on the existing request rather than releasing and re-issuing a brand-new one, when the same source/filter set is still selected.
- **FR1.4** `SteamMatchmakingServers.releaseRequest(request)` is called exactly once per issued request, on screen close (`Screen.removed()`/`onClose()`) and whenever a new request replaces an in-flight one (source-tab switch, FR1.6) — mirrors `SteamworksService.shutdown()`'s own idempotency discipline (never double-release, never leak).
- **FR1.5** No query is ever issued, and `SteamMatchmakingServers` is never referenced, when `SteamAvailability.isSteamAvailable()` is `false` at screen-open time — same no-op-when-unavailable discipline as every other Steamworks-touching feature in this repo (`steam-cloud-sync` FR0.1, `friends-sidebar` FR0.2). The screen still opens, but renders the FR6.x-equivalent status state instead of a table (see Requirements, Steam-unavailable below).
- **FR1.6** A simple two-way source toggle (Internet / LAN) switches between `requestInternetServerList` and `requestLANServerList`; switching sources releases the previous request (FR1.4) and issues a new one for the newly selected source. Favorites/History/Spectator sources are out of scope (Non-goals) but the toggle's shape should not preclude adding more source tabs later (Future Extensions).

**Table: columns, sorting**
- **FR2.1** Columns, in order: Name, Map/Mode, Players (`getPlayers()`/`getMaxPlayers()`, rendered as `"players/max"`), Ping (`getPing()`), Password (icon/glyph derived from `hasPassword()`), Secure/VAC (icon/glyph derived from `isSecure()`).
- **FR2.2** Every column header is clickable; clicking toggles that column's sort direction (ascending/descending), replacing any previous sort column — single-column sort only in v1 (no multi-column sort, Non-goals-adjacent simplification, not called out separately since it's the obvious default absent a stated multi-sort requirement).
- **FR2.3** Sorting is a pure, plain-JVM-testable function over the in-memory row list (a `Comparator<ServerBrowserRow>` per column) — kept outside the `Screen`/widget class per `ui-guidelines.md`'s Testing section ("keep any decision logic a UI class depends on in a plain, unit-tested class the UI layer merely reads from").
- **FR2.4** Default sort (before the player clicks any header): ascending ping — the same "nearest/most-responsive first" default a player would expect from a server browser, and a reasonable proxy for relevance before any row has been clicked.

**Filtering**
- **FR3.1** A text search box filters rows by case-insensitive substring match against `getServerName()`, applied live (every keystroke re-filters the already-fetched row list; it does not re-issue a Steam query).
- **FR3.2** "Hide full servers" toggle filters out rows where `getPlayers() >= getMaxPlayers()`.
- **FR3.3** "Hide password-protected servers" toggle filters out rows where `hasPassword() == true`. (This is purely a visibility/browsing filter; it is independent of the ability to actually join a password-protected server, FR4.3.)
- **FR3.4** A maximum-ping numeric filter (text field or slider, planning's choice) filters out rows where `getPing()` exceeds the configured threshold; a value of 0/empty means "no limit" (default).
- **FR3.5** "Hide empty servers" toggle filters out rows where `getPlayers() == 0`.
- **FR3.6** All filters (FR3.1-FR3.5) combine with logical AND, and are pure functions over the row list — same plain-JVM-testable requirement as FR2.3, ideally the same small business-logic class (e.g. `ServerBrowserRowFilter`/`ServerBrowserTableModel`) owning both sort and filter so `ServerBrowserScreen` itself stays a thin renderer.
- **FR3.7** Filters and sort persist for the lifetime of the open screen (not saved to config/disk in v1 — see Non-goals/Configuration) and reset to defaults each time the screen is freshly opened.

**Connecting**
- **FR4.1** Double-clicking a row, or selecting a row and pressing a "Join Server" button, initiates the vanilla connect flow for that server's resolved `IP:port` (`SteamMatchmakingServerNetAdr`, from `getNetAdr()`), constructing whatever vanilla `ServerInfo`/`ServerData` (per-version, `minecraft.md`'s naming table) the target connect entry point needs, exactly as an existing saved-server double-click already does elsewhere in this codebase's Multiplayer screen flow — this feature does not reimplement connection/handshake logic, it only launches it, in this respect no different from clicking an existing entry in the vanilla server list.
- **FR4.2** A row for a server that failed to respond (FR1.2) is visibly non-selectable/disabled for the purposes of FR4.1, rather than allowed to attempt a connect against known-stale data.
- **FR4.3** Password-protected servers are joinable in v1. When the player attempts to join a row whose `hasPassword()` is `true` (double-click or "Join Server", FR4.1), the connect attempt is intercepted before any connection is opened and a password-entry prompt is shown first:
  - If this repo/target Minecraft version already exposes a vanilla password-prompt screen/dialog as part of its own connect flow (server-required-password support in the base game's `ConnectScreen`/server-join path — confirm exact class per version during planning, since no prior feature in this repo has needed it and it was not `javap`-confirmed as part of this spec pass), this feature reuses that vanilla prompt rather than building a new one, consistent with FR4.1's "hand off to the exact same vanilla connect flow" principle.
  - If no such reusable vanilla prompt exists for a given target version (confirmed absent during planning), this feature provides its own minimal password-entry widget/screen (a single masked text field + Join/Cancel buttons) local to `features/server-browser`'s platform Version Adapter, following this repo's usual from-scratch custom-`Screen` precedent (`WorldRestoreScreen`, Compatibility) rather than inventing new shared UI infrastructure for a single caller.
  - Either way, the password the player enters is passed through to the same connect entry point FR4.1 already uses (e.g. as part of the constructed `ServerData`/connect call's credentials, per whatever the target vanilla connect API accepts for a password-protected join) — this feature does not implement its own password verification; Steam/the target server does that as part of the normal connect handshake.
  - Cancelling the password prompt returns the player to `ServerBrowserScreen` with no connect attempt made and no error state.

**Steam-unavailable / no-App-ID status state**
- **FR5.1** If `SteamAvailability.isSteamAvailable()` is `false` when `ServerBrowserScreen` opens, no query is issued (FR1.5) and the screen instead renders a single status message ("Steam not available — make sure Steam is running…", reusing the same generic wording precedent `friends-sidebar` FR6.1 already established and justified) in place of the table/filter controls.
- **FR5.2** The Multiplayer-screen button that opens `ServerBrowserScreen` remains visible and clickable even when Steam is unavailable (consistent with FR5.1's screen-level, not button-level, status handling) — the player should be able to open the screen and see *why* it's unavailable, rather than the button silently vanishing with no explanation (same non-technical-actionable-message principle as `friends-sidebar` FR6.1's justification, applied here at the screen level instead of a sidebar-row level).

**Non-functional**
- **NFR1** Row filtering/sorting logic (FR2.3, FR3.6) is unit-tested on a plain JVM, with zero `net.minecraft.*`/`com.codedisaster.steamworks.*` imports in the tested class, following this repo's established discipline (`friends-sidebar`'s `FriendSidebarStateMachineTest`, `steam-cloud-sync`'s own precedent).
- **NFR2** No uncaught exception from any `SteamMatchmakingServers`/`SteamMatchmakingServerListResponse` call reaches the client tick/render thread uncaught — every Steam call site is defensively guarded the same way `SteamworksService.create` guards `SteamAPI` calls.
- **NFR3** `SteamMatchmakingServers`/`SteamMatchmakingGameServerItem`/`SteamServerListRequest` imports stay confined to as few classes as practical within `features/server-browser` (mirrors `friends-sidebar` NFR5's "sole Steamworks-importing class" discipline) — ideally one gateway/service class, not scattered across the `Screen` and widget classes.
- **NFR4** Public types carry JavaDoc with a usage example, per this repo's established convention (every class read during research for this spec follows this pattern).
- **NFR5** Feature folder layout follows the established convention (`features/server-browser/{api,config,events,gui,mixins,services}` — `mixins/` stays an empty placeholder unless Pattern 2/3 turns out to be needed, which FR-level requirements above do not currently require: the new-screen-plus-button shape only needs Pattern 1 for the button and a brand-new `Screen` subclass, neither needs a mixin).

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision (same convention as `features/friends-sidebar/specification.md`'s Public API section).

1. **`api/src/main/java/de/lazuli/api/serverbrowser/ServerBrowserRow`** — a steamworks4j-free plain data record (`serverName`, `map`, `players`, `maxPlayers`, `ping`, `hasPassword`, `isSecure`, `address` (host:port string), `respondedSuccessfully`) that `features/server-browser`'s business logic and `platform`'s `Screen`/widget classes both depend on, without either needing a `com.codedisaster.steamworks.*` import for basic row data (only the gateway class translating `SteamMatchmakingGameServerItem` -> `ServerBrowserRow` needs that import, per NFR3).
2. **`features/server-browser/services/ServerBrowserTableModel`** (or `ServerBrowserRowFilter`/`ServerBrowserSort` split into two classes, planning's choice) — owns FR2.3/FR3.6's pure sort+filter logic over `List<ServerBrowserRow>`, unit-tested per NFR1.
3. **`features/server-browser/services/ServerBrowserQuery`** (or similarly named gateway) — the sole class wrapping `SteamMatchmakingServers`/`SteamMatchmakingServerListResponse`/`SteamServerListRequest` (NFR3), exposing a small callback-free-to-callers surface, e.g. `void start(Source source, Consumer<List<ServerBrowserRow>> onRowsChanged, Runnable onRefreshComplete)` / `void refresh()` / `void close()` (mirrors `SteamworksService`'s own `create`/`pumpCallbacks`/`shutdown` idempotent-lifecycle shape) — constructed with a `SteamAvailability` + resolved App ID, no-ops (never constructs `SteamMatchmakingServers`) when unavailable (FR1.5).
4. **`api/src/main/java/de/lazuli/api/serverbrowser/ServerBrowserHook`** (only if a second platform-facing hook interface is actually needed beyond the `Screen` itself — likely unnecessary here since, unlike `MainMenuHook`, this feature owns its entire new screen rather than extending an existing vanilla one persistently; the only cross-boundary hook needed is the button injection into the Multiplayer screen, which can reuse Pattern 1's shape directly without a new named interface if the button's only job is "open `ServerBrowserScreen`" — planning should confirm whether any `api`-layer interface is warranted at all, or whether the platform Version Adapter can construct `ServerBrowserScreen` and push it via `Minecraft.setScreen(...)` with zero new `api` surface, since the screen itself already only depends on `api`/`services`-layer types per the Dependency Rules).
5. **`platform/fabric-<version>/.../serverbrowser/FabricServerBrowserButtonInjector`** — Version Adapter, Pattern 1: `ScreenEvents.AFTER_INIT` filtered to the vanilla Multiplayer screen type (`JoinMultiplayerScreen` on `fabric-26.1`/`fabric-26.2` / `MultiplayerScreen` on `fabric-1.21.11` — confirmed, Compatibility), adds one new `Button`/`ButtonWidget` positioned at the top right of that screen (UI) via `Screens.getWidgets(screen)` (≥26.1) / `Screens.getButtons(screen)` (≤1.21.11, per `minecraft.md`'s existing table row) whose `onPress` opens `ServerBrowserScreen`.
6. **`platform/fabric-<version>/.../serverbrowser/ServerBrowserScreen`** — Version Adapter, a genuinely new `Screen` subclass (not an overlay widget) implementing the table/filter UI, backed by `ServerBrowserQuery` + `ServerBrowserTableModel`. Table rendering itself is very likely a Pattern-2-adjacent custom scrollable list (this feature's own synthetic rows, not a vanilla list being extended) — i.e. it can freely subclass a vanilla `AbstractSelectionList`/`ObjectSelectionList`-style base (or hand-roll a scrollable panel) since this is **this feature's own new list**, not an attempt to insert synthetic rows into an *existing* vanilla list widget (contrast Pattern 2's actual pain point, which is about extending someone else's already-populated list) — confirm the simplest viable base class per version during planning/implementation rather than assuming continuity from Pattern 2's `WorldListWidget`/`WorldSelectionList` findings, which solved a different problem (external rows into vanilla's own list).
7. **`platform/fabric-<version>/.../serverbrowser/ServerBrowserPasswordPromptScreen`** (only if planning confirms no reusable vanilla password prompt exists for a given target version, FR4.3) — Version Adapter, a minimal masked-text-field + Join/Cancel screen invoked before connecting to a password-protected row.

## Architecture
- Layering: `features/server-browser` depends on `api` and `services` only (never another feature), same Dependency Rules table as every other feature (`architecture.md:64-71`).
- `SteamworksService`/`SteamAvailability` dependency: obtained via the same `SteamworksServiceHandoff` static-holder hand-off pattern already established for every other Steamworks-dependent feature (`friends-sidebar` FR0.1, `steam-cloud-sync` FR0.1) — never re-initializes Steamworks itself, never constructs a second `SteamAPI` session.
- App ID: reused from `SteamworksService.steamAppId()`/`SteamAppIdResolver` — no new App-ID resolution path is introduced. During this dev/testing phase `SteamAppIdResolver` resolves to 480/Spacewar (Goals, Compatibility); this feature contains no App-ID literal of its own.
- New-screen injection is Pattern 1 for the *button* (adding one widget to an existing screen, no mixin) but the *screen itself* (`ServerBrowserScreen`) is a brand-new `Screen` subclass, not an overlay — this is architecturally simpler than `friends-sidebar`'s persistent-overlay-across-many-screens shape (Overview), since `ServerBrowserScreen` only ever needs to exist while it itself is the active screen, with a normal `Screen.onClose()`/back-button lifecycle releasing its Steam request (FR1.4) — no cross-screen state machine analogous to `FriendSidebarStateMachine` is needed.
- No second feature currently extends the vanilla Multiplayer screen, so `architecture.md`'s "Shared-screen extension point"/collision rule does not apply yet — if a future feature also wants to add a button to the same screen, that is the trigger to introduce a `services`-layer layout coordinator for it, not before.
- `ServerBrowserQuery` (Public API item 3) is the sole `com.codedisaster.steamworks.SteamMatchmaking*`-importing class (NFR3), living in `features/server-browser/services`, constructed by the platform composition root and handed to `ServerBrowserScreen` alongside `ServerBrowserTableModel`.

## UI
- **Entry point**: one new `Button`/`ButtonWidget` added to the vanilla Multiplayer screen, positioned at the **top right** of the screen (i.e. anchored to the screen's top-right corner/margin, not in the existing bottom footer button row alongside "Join Server"/"Direct Connect"/"Add Server"/"Cancel" — exact pixel offsets a planning/UX decision verified in-game per version, consistent with `ui-guidelines.md`'s Pattern-1 convention) — label "Server Browser" (or similar), opens `ServerBrowserScreen` via `Minecraft.setScreen(...)`/`MinecraftClient.setScreen(...)`.
- **Screen layout**: header row of clickable column labels (FR2.2) above a scrollable table body; each row shows the six columns (FR2.1) plus reflects failed/disabled state (FR4.2) with a visually muted/greyed treatment. A left-aligned or top toolbar holds the search box (FR3.1), the three toggle checkboxes (FR3.2/FR3.3/FR3.5), the max-ping field/slider (FR3.4), the Internet/LAN source toggle (FR1.6), a "Refresh" button (FR1.3), a "refreshing…" indicator (visible only while `isRefreshing(request)` is true), and a "Join Server"/"Back" button pair at the bottom, mirroring vanilla's own screen-footer convention.
- **Password prompt**: a single masked-input dialog (FR4.3) with "Join"/"Cancel" actions, shown modally over `ServerBrowserScreen` (or as a full-screen replacement, matching whatever convention the reused-or-new prompt follows) when the player attempts to join a password-protected row; on "Join" the entered password flows into the same connect call FR4.1 uses, on "Cancel" the player returns to the unmodified `ServerBrowserScreen`.
- Color literals for any status/disabled text must carry a full `0xFF` alpha byte, never a bare 3-byte RGB literal — this repo has already hit the exact "text silently renders nothing on 1.21.11" bug from this mistake once (`minecraft.md`'s alpha-zero-skip table row) and it applies identically to any new text this feature draws.
- Manual, per-supported-Minecraft-version in-game verification is required (UI code is not unit-testable, `ui-guidelines.md`'s Testing section) — verification should include: opening the screen with Steam unavailable (status state), with Steam available but zero servers returned (`NoServersListedOnMasterServer`, a real empty-content state distinct from the unavailable status state — same "don't conflate empty-but-valid with broken" caution `friends-sidebar` FR6.3(a) already called out for its own empty-friends-list case), sorting by every column, each filter individually and combined, and the password-prompt flow against an actual password-protected 480/Spacewar test server (FR4.3).

## Configuration
No new persisted config file in v1 (Non-goals: filters/sort are session-only, FR3.7) — unlike `friends-sidebar`'s `config/friends-sidebar.json`, this feature introduces no on-disk settings. If a future revision wants to persist the player's last-used filter/sort/source choice across sessions, that would follow the same flat-under-config-dir convention (`config/server-browser.json`) every other feature's own config already uses (Future Extensions).

## Events
No new cross-feature event/callback type. `ServerBrowserQuery`'s row-list/refresh callbacks (Public API item 3) are internal to this feature, consumed directly by `ServerBrowserScreen`/`ServerBrowserTableModel` — nothing published to a shared event bus (`services/` has no event-bus capability yet per the graduate-on-second-use rule, and this feature does not need one).

## Networking
No new client-server packet. `ISteamMatchmakingServers` queries are Steam-client-IPC (native Steamworks calls, not this mod's own network protocol) exactly like every other Steamworks surface already used in this repo. Connecting to a selected server (FR4.1), including the password-protected path (FR4.3), reuses vanilla's own existing client-connect networking path — no new protocol/handshake is introduced by this feature.

## Persistence
No new on-disk state in v1 (see Configuration) — everything (fetched rows, current sort/filter, current source) is in-memory for the lifetime of the open `ServerBrowserScreen` and discarded on close.

## Compatibility
- **Minecraft/Fabric versions**: this repo targets three platform modules — `platform/fabric-1.21.11` (Yarn, obfuscated, Java 21), `platform/fabric-26.1` and `platform/fabric-26.2` (Mojang mappings, unobfuscated, Java 25) — confirmed via `gradle.properties:16` (`minecraft_version=26.2`) and the three `platform/fabric-*` module directories. This feature needs a Version Adapter per module, same as every other UI-touching feature in this repo.
- **Vanilla Multiplayer screen class name — CONFIRMED**: `net.minecraft.client.gui.screens.multiplayer.JoinMultiplayerScreen` (Mojang mappings, `platform/fabric-26.1`/`platform/fabric-26.2`) and `net.minecraft.client.gui.screen.multiplayer.MultiplayerScreen` (Yarn mappings, `platform/fabric-1.21.11`). This spec's earlier guess is confirmed correct by direct evidence rather than a fresh `javap` pass in this session (this session's tool access had no shell/`javap` capability): both classes are already imported and referenced (`instanceof` checks in the screen allow-list) by this repo's own existing, compiling, committed production code — `platform/fabric-26.2/src/main/java/de/lazuli/friends/FabricFriendsSidebarInjector.java:19,77` and `platform/fabric-26.1/src/main/java/de/lazuli/friends/FabricFriendsSidebarInjector.java` (same import/usage) for `JoinMultiplayerScreen`, and `platform/fabric-1.21.11/src/main/java/de/lazuli/friends/FabricFriendsSidebarInjector.java:19,77` for `MultiplayerScreen`. Since that injector compiles against the exact same resolved Minecraft jars (`.gradle/loom-cache/minecraftMaven/...`) this feature will also compile against, this is equivalent-strength evidence to a `javap` pass for the class-name question specifically. The "unconfirmed" flag is removed. Exact footer/button-row layout members (button list field/getter, positioning) still need a quick per-version look during planning/implementation (not a naming risk, just normal per-screen layout work) — no `javap` risk remains, this is ordinary Version-Adapter implementation work.
- **`Screens.getWidgets`/`Screens.getButtons`**: already-documented divergence (`minecraft.md`'s Known Cross-Version API Differences table, row 1) — `Screens.getButtons(Screen)` on ≤1.21.11, `Screens.getWidgets(Screen)` on ≥26.1. Applies directly to this feature's button-injection Version Adapter.
- **`Button`/`ButtonWidget`, `Screen.render`/`extractRenderState`, `DrawContext`/`GuiGraphicsExtractor`**: already-documented divergence (`minecraft.md` row "Screen rendering entry point") — `ServerBrowserScreen`'s custom rendering must follow the same per-version drawing-primitive split already confirmed for `WorldRestoreScreen` (`platform/fabric-1.21.11/.../cloudsync/WorldRestoreScreen.java`, cited as this repo's own prior working example of a from-scratch custom `Screen`).
- **`SteamMatchmakingServers`/`SteamMatchmakingServerListResponse`/`SteamMatchmakingGameServerItem`/`SteamServerListRequest`**: sourced from steamworks4j `1.10.0` (`gradle.properties:47`, `services/build.gradle:8`, same shared Jar-in-Jar'd dependency every platform module already bundles). The resolved jar (`platform/fabric-*/build/processIncludeJars/steamworks4j-1.10.0.jar`) was located in each platform module's build output, but this session's tool access had no shell/`javap` capability to disassemble it directly, and fetching the library's own GitHub source (`code-disaster/steamworks4j`) for a text-level check also failed (repeated 404s against several plausible branch/tag/path combinations from this session's web-fetch tool). As a partial substitute, the underlying native `ISteamMatchmakingServers` signatures were confirmed against Valve's own partner documentation (`RequestInternetServerList(AppId_t, MatchMakingKeyValuePair_t**, uint32, ISteamMatchmakingServerListResponse*)`, `RequestLANServerList(AppId_t, ISteamMatchmakingServerListResponse*)`, `GetServerDetails(HServerListRequest, int) -> gameserveritem_t*`, `IsRefreshing`, `RefreshQuery`, `ReleaseRequest`, and the `ServerResponded`/`ServerFailedToRespond`/`RefreshComplete` callback triad), which match the method names and call shapes this spec already documents; steamworks4j's own established convention in this repo (every other wrapped interface — `SteamFriends`, `SteamUser`, `SteamRemoteStorage` — exposes a 1:1 Java method per native method, with pointer-out-params like `gameserveritem_t*` replaced by a caller-supplied Java buffer object) gives reasonable confidence the wrapper follows the same shape here. **This is not a full `javap`-against-resolved-jar confirmation** — unlike `friends-sidebar`'s already-`javap`-verified `SteamUser`/`SteamFriends` v1.1 surface — and remains the one item in this spec that should get a direct `javap -p` pass (or equivalent decompile) against `platform/fabric-26.2/build/processIncludeJars/steamworks4j-1.10.0.jar` as the literal first step of planning/implementation, before any code is written against it, using a session/environment that has shell access. This is flagged as a first-step verification task, not a spec gap — every requirement above is written against the documented/expected shape and should not need to change even if minor signature details (e.g. buffer-vs-return-value shape of `getServerDetails`) turn out to differ.
- **App ID resolution / dev-time testing**: `ISteamMatchmakingServers`'s Internet query only returns servers actually registered with Steam's master server list for the App ID it's queried against. During this dev/testing phase, `SteamAppIdResolver` resolves to **480 (Spacewar)** — the same publicly-usable Valve test App ID this mod's Steamworks integration already initializes against for other features — and this mod's own developers, plus other developers' test projects/servers, are expected to also register against 480, so the Internet server list realistically returns live entries during testing rather than staying empty. When this mod ships against its own production Steam App ID, `SteamAppIdResolver` is the sole place that changes (no code in `features/server-browser` references 480 or any App ID literal directly, per Architecture) — this is a configuration/deployment change, not a feature change. The empty-state UI (FR5.1's sibling "zero servers, Steam available" case, noted in UI's manual-verification list) must still be distinguishable from a genuine failure, since even against 480 a zero-result query is a legitimate outcome (e.g. no test server currently running).

## Performance
- One Steam matchmaking request in flight per open `ServerBrowserScreen` (FR1.4's release discipline prevents request leaks across repeated opens/closes or source-tab switches).
- Row upsert (`serverResponded`) is O(1) amortized per server (indexed map keyed by server index/address), not a full list rescan per callback; sort/filter re-application (FR2.3/FR3.6) can reasonably be O(n log n)/O(n) per triggering event (a new row, a filter/sort change) since server-browser row counts are typically small (tens to low hundreds), not a hot per-frame cost — no per-frame Steam call either way (Steam's own refresh cadence, not this feature's render loop, drives new callback ticks).
- No new per-client-tick cost beyond the render/callback-pump cost already paid: `SteamworksService.pumpCallbacks()` already runs every client tick regardless of this feature (`SteamworksService.java:120-124`); this feature adds no second callback pump.
