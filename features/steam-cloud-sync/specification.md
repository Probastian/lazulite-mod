# Steam Cloud Sync — Feature Specification

## Overview
Adds `features/steam-cloud-sync`, the first feature built on top of the already-implemented Steamworks bootstrap (`services/src/main/java/de/lazuli/services/steamworks/SteamworksService.java`, contract `api/src/main/java/de/lazuli/api/steamworks/SteamAvailability.java`). It syncs six categories of small-to-medium player data across a player's devices via `ISteamRemoteStorage` ("Steam Cloud"): (1) this mod's own feature settings/preferences, (2) UI/accessibility preferences, (3) a personal bookmarked-server list, (4) a "continue where you left off" pointer, (5) personal notes/waypoints, and (6) world-save sync with an explicit size-limiting strategy. It is one cohesive feature (`features/steam-cloud-sync`), not six, sharing one Cloud-availability check, one reconciliation rule, and — for groups 1–2 — one generic extensibility mechanism (`CloudSyncable`).

Steam Cloud's actual behavior, confirmed from primary sources rather than assumed: it is a per-user, per-file, flat logical namespace (`SteamRemoteStorage.fileWrite(String file, ByteBuffer data)` — source: github.com/code-disaster/steamworks4j `SteamRemoteStorage.java`); Valve does **not** merge concurrent writes to the same file — whichever device's `FileWrite` is seen last simply overwrites what was there; and the per-user quota is **developer-configured** (Steamworks App Admin "Steam Cloud Settings" page: "Byte quota per user" / "Number of files allowed per user", self-service, max 100,000,000,000 bytes ≈ 93 GiB) rather than a fixed small number Valve imposes and later raises on request — this project has not yet issued a real App ID (`services/specification.md:21,106`), so this spec treats the quota as an unknown, project-controlled variable and designs against a conservative reference budget instead of a hard Valve limit.

## Goals
- Sync all six data categories through one Cloud-availability check (`SteamAvailability.isSteamAvailable()`) and one reconciliation rule, degrading to fully-functional local-only operation with no crash when Steam/Cloud is unavailable (mirrors `services/specification.md:10`).
- Establish one reusable, api-layer `CloudSyncable` mechanism so this and future features can opt a small config blob into Cloud sync without a Feature→Feature dependency (forbidden per `.claude/context/architecture.md:74`).
- Design and justify a concrete size-limiting + degraded-fallback strategy for world-save sync given Steam Cloud's small, project-controlled quota and Valve's documented 100MB per-call write cap.
- Explicitly design around Steam Cloud's no-merge/last-write-wins model for every synced artifact (timestamp-based reconciliation) and add an advisory warning for the one artifact where silent overwrite would be most damaging (world saves), rather than only documenting the risk.
- Let a player **restore** a world that exists in this feature's own Steam Cloud fingerprint/metadata file (FR6.6) but has no matching save folder on this device yet — surfaced as a distinct, cloud-icon-marked synthetic entry on the vanilla Singleplayer world-select screen, restored on demand via an honestly-framed "restoring from Steam Cloud" progress screen (not "downloading" — the actual data transfer already happened silently before Minecraft launched, per Valve's own docs; see Requirements Group 6 and Architecture) before it becomes a normal, playable local world.
- Keep all business logic (data models, size-threshold decisions, JSON I/O, quota/`fileForget` bookkeeping, reconciliation, cloud-only-world detection, restore-progress math) unit-testable on a plain JVM with zero Minecraft/steamworks4j-native-call classes needed for the deterministic cases, consistent with `philosophy.md:9` and the existing precedent (`features/hello-world-main-menu/specification.md:47`).

## Non-goals
- True concurrent multi-device editing of the same world (both devices playing at literally the same time). Steam Cloud has no merge; only *sequential* multi-device play (finish on device A, then start on device B) is supported, mitigated by an advisory warning (Requirements, Group 6), not a distributed lock.
- Syncing vanilla Minecraft's own `options.txt` or `servers.dat` directly — this feature defines its own independent schemas for the settings/accessibility and bookmark categories rather than reading/writing Mojang's files (lower risk of corrupting a file Minecraft itself also writes; importing from `servers.dat` is a Future Extension).
- "Dynamic Cloud Sync" (near-live sync while a session is running on two machines) — Valve's own docs describe this as an app-level opt-in flag on top of classic launch/exit-timed Cloud sync (`partner.steamgames.com/doc/api/isteamremotestorage`, `RemoteStorageLocalFileChange_t` callback, "only applies to applications flagged as supporting dynamic Steam Cloud sync"); this is a Steamworks-partner-console setting this project cannot yet make (no real App ID) — Future Extension.
- In-game management screens beyond the Multiplayer-screen bookmark toggle, the Singleplayer-screen sync/cloud icons, and the new restore-progress screen described under UI. Notes/waypoints and the continue-pointer ship as data-sync-only in v1, same UI-scoping precedent already established (`features/hello-world-main-menu/specification.md:25`).
- Any server-side/dedicated-server behavior — Steam Cloud is a client-only capability requiring a locally-running Steam client, same constraint already established for the whole Steamworks bootstrap (`services/specification.md:18`).
- Actually requesting/raising Lazuli's Cloud quota — that is a Steamworks-partner-console action requiring a real, issued App ID, out of scope until that product question is resolved (`services/specification.md:21,106`; Future Extensions).
- Any additional client-side encryption of Cloud-stored data beyond whatever Steam itself provides.
- Compression/delta-sync of only-changed region files, or a merge-safe multi-device editing model — explicitly deferred (Future Extensions), consistent with the "whole-archive" decision under Architecture.
- **Syncing the per-world sync-preference list itself across devices (FR6.1) — still local-only in v1.** One narrow clarification given the restore flow: the non-goal is about *other* devices' preference entries for worlds this device has never seen — that list is still never pulled/merged wholesale. It does **not** mean a freshly-restored world's own single preference entry stays unset; per FR6.10, this device sets a sensible local default for that one world the moment it restores it, derived from the restore event itself, not from syncing anyone else's preference list.
- A richer conflict-resolution UI, or automatic handling, for the case where a same-named local world folder already exists at restore time beyond the single warn-and-abort behavior in FR6.13 — a fuller "merge/rename/pick one" UI is a Future Extension.

## Requirements

**Cross-cutting (all six groups)**
- **FR0.1** The feature depends on `SteamAvailability`/`SteamworksService` (handed in by the platform composition root, same pattern as `services/specification.md:60`). If `isSteamAvailable()` is `false`, every sync operation for every group is a no-op; all local read/write/CRUD operations continue to work normally (local-only mode), and no exception escapes.
- **FR0.2** A local JSON config (`config/steam-cloud-sync.json`, flat under `FabricLoader.getInstance().getConfigDir()`, mirroring the existing precedent at `platform/fabric-26.2/.../HelloWorldMainMenuClientInitializer.java:40`) carries one master `enabled` boolean plus one independent boolean per group (see Configuration). A group whose toggle is `false` performs no Cloud read/write for that group, but its local CRUD/data still works.
- **FR0.3** Cloud reads/writes happen only at defined checkpoints — client startup (reconcile), the group's own natural data-change checkpoint (e.g. world unload, note added, bookmark added), and client shutdown — never per-tick, never on the render/hot path.
- **FR0.4** For every group except Group 6, reconciliation between the local copy and the Cloud copy at startup compares `SteamRemoteStorage.getFileTimestamp(file)` (Cloud) against the local file's own last-modified time; whichever is newer is treated as authoritative and copied over the other side. This is this feature's own implementation of "closest we can get to last-write-wins reconciliation," since Valve's API itself has no merge (confirmed: no conflict-resolution guidance found in `partner.steamgames.com/doc/features/cloud` or `.../isteamremotestorage`).
- **FR0.5** The local copy is always written first and is the source of truth for a single-device session; Steam being unavailable never loses local data, only forfeits that session's cross-device sync (mirrors `services/specification.md:10`'s "degrade gracefully" goal, applied to data rather than availability).
- **FR0.6** No automatic/background code path ever calls `fileDelete` (which also removes Valve's Cloud copy and, per Steam's docs, propagates a delete) as part of routine sync or quota management; only an explicit user action (e.g. removing one bookmark/note) does so. Automatic quota management (Group 6) uses `fileForget` only (Requirements, Group 6, FR6.7).

**Group 1 — Settings/Preferences Sync**
- **FR1.1** Defines `CloudSyncable` in `api/` (see Public API): any feature's own service may implement it to export/import its config as bytes, without importing another feature's package (avoids the Feature→Feature edge forbidden at `architecture.md:74`).
- **FR1.2** The platform composition root constructs the list of every opted-in `CloudSyncable` (today: an adapter around `features/hello-world-main-menu`'s existing `HelloWorldMainMenuConfigIO`/`HelloWorldMainMenuConfig`, `features/hello-world-main-menu/src/main/java/de/lazuli/features/helloworldmainmenu/config/HelloWorldMainMenuConfigIO.java:38-122`) and hands it to this feature's own aggregator service — the same "platform wires a shared thing into a feature" pattern already established (`services/specification.md:60`; `docs/adr/0001-...md`, `docs/adr/0002-...md`).
- **FR1.3/FR1.4** Apply the FR0.4 reconciliation rule at startup per registered `CloudSyncable`, keyed by `cloudSyncId()`; re-export and write back at shutdown to capture in-session edits.

**Group 2 — UI/Accessibility Preferences Sync**
- **FR2.1** Defines no new UI/accessibility config schema itself — HUD layout, color-blind mode, UI scale, and mod-specific keybind overrides belong to whichever future feature owns Lazuli's own accessibility settings (not yet built; inventing that schema here would be speculative). Vanilla Minecraft's own `options.txt` is explicitly out of scope (Non-goals).
- **FR2.2** Once that future feature exists, it participates by implementing the same `CloudSyncable` contract from Group 1 and being added to the composition root's registration list — Group 2 requires zero additional design in this feature beyond Group 1's mechanism; this is stated explicitly so a future reader does not go looking for a second, bespoke sync path.

**Group 3 — Bookmarked Servers**
- **FR3.1** Data model, owned entirely by this feature (not another feature's schema, per explicit instruction): `BookmarkedServer { id: UUID-string, label: String, address: String, addedAt: epoch-millis }`, stored as `{ "schemaVersion": 1, "entries": [...] }` — a `schemaVersion` field from v1 (unlike hello-world's schema, `features/hello-world-main-menu/specification.md:134`, which explicitly deferred one), because this schema is expected to evolve once a future matchmaking/server-discovery feature exists (`README.md:11`; `.claude/context/feature-guidelines.md:28-30`).
- **FR3.2** CRUD (`add`/`remove`/`rename`) exposed by a pure `BookmarkedServersService`, independent of and never reading/writing vanilla's own `servers.dat` (Non-goals).
- **FR3.3** v1 in-game affordance: a bookmark-toggle widget injected into each entry of the vanilla Multiplayer server-list screen via the same non-mixin `ScreenEvents.AFTER_INIT` + widget-injection pattern already established (`features/hello-world-main-menu/specification.md:95`), subject to the same `Screens.getButtons`→`Screens.getWidgets` cross-version rename already logged (`.claude/context/minecraft.md:56`).
- **FR3.4** Synced per the FR0.4 rule, own Cloud file.

**Group 4 — "Continue Where You Left Off" Pointer**
- **FR4.1** Data model: a single record (not a list), `LastPlayedPointer { type: "world"|"server", name: String, identifier: String, timestamp: epoch-millis }` — metadata only, never the save itself (per explicit scope).
- **FR4.2** Updated locally on well-defined lifecycle checkpoints: entering/leaving a singleplayer world, joining/disconnecting a multiplayer server. Exact Fabric API event class/method names (e.g. a `ClientPlayConnectionEvents`-family event, and whatever signals singleplayer world entry/exit) are **not asserted here** and must be confirmed at planning time by compiling against each supported Fabric API version, the same caution already applied to `ClientTickEvents` in `services/specification.md:83` and to the `Screens` rename in `.claude/context/minecraft.md:56`.
- **FR4.3** At client startup, after pulling the Cloud copy, if it differs from this device's own last-recorded pointer and its timestamp is newer, log a notification (v1: log/toast only — no dedicated "Continue as..." screen, Future Extension). Never auto-launches a world/server.
- **FR4.4** Explicitly does not fetch or sync the referenced world/server's actual data (Group 6 is the separate, opt-in mechanism for that).

**Group 5 — Personal Notes/Waypoints**
- **FR5.1** Data model: `Note { id: UUID-string, text: String, context: String|null, x/y/z: Double|null, createdAt: epoch-millis }`. Decision: notes are **loosely tied** to a world/server — `context` (e.g. world folder name or server address) and coordinates are optional/nullable, populated only if the player attached a location when creating the note. This supports both pure text reminders (no context) and location-bound waypoints (with context+coordinates) without forcing every note into a world/server it may not have been created in (e.g. one added from the title screen).
- **FR5.2** CRUD via a pure `NotesService`; v1 ships no in-game HUD/waypoint-rendering or management screen (Future Extension), matching the same UI-scoping rationale as Group 4/hello-world's own precedent.
- **FR5.3** Synced per the FR0.4 rule, own Cloud file, same `schemaVersion`-wrapped shape as Group 3.

**Group 6 — World Save Sync, with Size-Limiting**
- **FR6.1** Opt-in only, **per world**, not a single global switch: a new icon widget is added to every *local* world's row in the vanilla Singleplayer world-select screen (same non-mixin `ScreenEvents.AFTER_INIT` + widget-injection technique as Group 3's per-server toggle, FR3.3), toggling that specific world's cloud-sync participation on/off. Every world defaults to sync-**disabled** (the conservative default is deliberate, given both the no-merge risk (FR6.6) and that world archives are the only category realistically able to blow through a small shared quota) — **except** a world this device just restored from Cloud-only status, which defaults to sync-**enabled** immediately, per the one explicit exception in FR6.10. The icon itself is always present (gated only by the feature's master `enabled` switch and `SteamAvailability.isSteamAvailable()`, Configuration), so a player discovers and opts in per-world rather than needing to first find a separate global setting. The per-world preference is tracked by a new `WorldSyncPreferenceService` (Public API), persisted **locally only** — it is not itself synced to Cloud in v1, since the toggle only has meaning for a world that already exists on this specific device (see Non-goals).
- **FR6.2** Trigger: on world unload/exit, **only if that world's per-world preference (FR6.1) is enabled** — deliberately chosen to piggy-back on vanilla's own existing "Saving world" pause the player already expects, rather than mid-gameplay (also load-bearing for Performance).
- **FR6.3** Size check: compute the world folder's total on-disk size. If it is `<= maxWorldArchiveSizeMb` (config, default below), build one compressed zip of the entire world folder (`java.util.zip`, already in the JDK — no new dependency, matching this repo's existing "hand-roll rather than add a JSON library" precedent, `HelloWorldMainMenuConfigIO.java:20-26`) and write it as one Cloud file via steamworks4j's **streamed** write path — `fileWriteStreamOpen`/`fileWriteStreamWriteChunk`/`fileWriteStreamClose` (confirmed method set: github.com/code-disaster/steamworks4j `SteamRemoteStorage.java`) — chunked under Valve's documented 100MB-per-call cap on `FileWrite`/`FileWriteStreamWriteChunk` (`partner.steamgames.com/doc/api/isteamremotestorage`), regardless of the archive's total size.
- **FR6.4** If over threshold: log a clear, player-visible message naming the world, its size, and the threshold, then — if `allowSelectiveFallback` (config, default `true`) — fall back to a small "critical files" archive containing `level.dat` (which embeds the singleplayer local player's own state in vanilla Minecraft) plus, if present, `playerdata/`, `stats/`, `advancements/`, and `icon.png`; explicitly **excluding** `region/`, `entities/`, `poi/`, and any `DIM*/` per-dimension chunk data (the actual terrain — by far the largest, unbounded component). This restores the player's own identity/progress/game-rules context on another device but never restores full terrain; the same log message must state this limitation, never sync silently in degraded mode.
- **FR6.5** Approach decision (evaluated explicitly): **whole-archive zip is the default/primary strategy**, not "selective sync for every world." Rationale: Steam Cloud's file-level, no-merge, all-or-nothing write semantics (`FileWrite`'s own documented "creates a new file, writes the bytes, then closes the file") make a *partial*, region-file-granularity sync actively more dangerous than a single archive — syncing some chunk files but not others produces a silently inconsistent world on the receiving device (terrain/entity data that doesn't match player state), whereas one zip is at least internally self-consistent as a single atomic Cloud file. Selective-critical-files mode is a clearly-labeled degraded fallback used only when a world is too large for the whole-archive path, never an alternative "mode" chosen for a normal-size world.
- **FR6.6 (amended)** Conflict/data-loss mitigation: a small companion Cloud metadata file (e.g. one file listing every synced world's fingerprint: `{ worldSlug, displayName, deviceLabel, syncedAtTimestamp }` — `displayName` added so a **cloud-only** entry (FR6.8) has something player-facing to render, since it has no local `level.dat` to read a display name from) is checked before overwriting a world's Cloud archive. If the Cloud-side fingerprint this device last pulled doesn't match what's currently on Cloud (i.e. some other device wrote a newer copy this device never downloaded), warn the player explicitly before proceeding ("this world was last synced from `<device>` at `<time>`; continuing will overwrite that copy") instead of silently overwriting. This is an advisory warning, not a lock — true simultaneous editing remains a Non-goal. This same file is now also the source of truth for detecting cloud-only worlds (FR6.8).
- **FR6.7** Quota-exceeded handling: before writing/updating a world archive, call `getQuota(long[] totalBytes, long[] availableBytes)`. If the pending write would not fit, `fileForget` the least-recently-synced previously-tracked world archive(s) — Valve's own documented behavior: "deletes the file from remote storage, but leaves it on the local disk" (`partner.steamgames.com/doc/api/isteamremotestorage`) — repeating until enough quota is freed or no more forgettable archives remain, and notify the player which world(s) are no longer Cloud-backed (still fully playable locally). `fileDelete` is never used for this (FR0.6).
- **FR6.8 (new)** Cloud-only world detection: each time the Singleplayer world-select screen is populated (initial open and any vanilla refresh), cross-reference the local saves directory's world-folder names against the `worldSlug` list in FR6.6's fingerprint metadata file (pulled at the FR0.3 startup checkpoint like every other Cloud file). Any `worldSlug` present in the fingerprint file with no matching local save folder is a **cloud-only world**; produce a plain-JVM-testable `List<CloudOnlyWorldSummary>` (Public API) from this comparison — this detection step itself does no Steam I/O beyond the metadata file already pulled at startup, so it stays cheap and synchronous on the render/client thread.
- **FR6.9 (new)** Rendering: each cloud-only world (FR6.8) is rendered as a **distinct synthetic entry** on the Singleplayer world-select screen, visually marked with a cloud icon that is clearly different from FR6.1's on/off sync-toggle icon (a local world's icon means "is this device keeping this world in sync"; a cloud entry's icon means "this world isn't downloaded here yet"), showing at minimum the world's `displayName` and, if present, `deviceLabel`/`syncedAtTimestamp` from the fingerprint file — no folder-size/last-played detail is shown, since none exists locally to read. Exact list ordering/interleaving of synthetic entries alongside real ones (matching vanilla's own sort, vs. a separate grouped section) is **not decided here** — left to planning, contingent on which of the two injection approaches under Architecture is chosen, since the constraints differ (true interleaving requires inserting into vanilla's own sorted collection; a separate section is simpler but a bigger visual departure from vanilla).
- **FR6.10 (new)** Restore trigger: attempting to "play" a cloud-only entry (double-click, or selecting it and pressing Play) does **not** attempt to launch a world — it opens the new `WorldRestoreScreen` (Public API), which drives `WorldRestoreService.beginRestore(worldSlug, listener)`: read the archive's Cloud file named per FR6.6/Persistence conventions, decompress, and extract into a new folder under the local saves directory (see FR6.12 for the atomicity/failure discipline). On successful completion, this device's local `WorldSyncPreference` entry (FR6.1) for that `worldSlug` is created with `enabled = true` — the one deliberate exception to FR6.1's otherwise-conservative default — since the world's mere presence in the Cloud fingerprint file is itself proof a previous device already opted it in; this is a local decision triggered by the restore event, not a sync of the preference list itself (Non-goals).
- **FR6.11 (new)** Progress computation and honest framing: because Steam Cloud fully downloads all of a user's Cloud files to the local machine automatically **before** the game launches (Valve's own doc, `partner.steamgames.com/doc/features/cloud`: "the files are automatically downloaded to the new computer prior to the game launching"), every steamworks4j read call reached from `WorldRestoreScreen` (`fileRead`/`fileReadAsync`+`fileReadAsyncComplete`) is always a fast **local** read — there is no real network-transfer-progress signal available to hook at this point. Accordingly:
  - All player-visible copy uses "**Restoring** world from Steam Cloud..." / "Extracting world files..." framing — never "Downloading..." — to avoid falsely implying a live network transfer is happening.
  - The progress bar is synthesized from two local phases: **Phase 1 (read)** — cumulative bytes read via repeated chunked `fileReadAsync`/`fileReadAsyncComplete` calls against the total from `getFileSize(file)`; **Phase 2 (extract)** — cumulative bytes or entries written via `java.util.zip.ZipInputStream`/`ZipFile` against the archive's total uncompressed size (obtainable from the zip's own central directory, or optionally recorded in the FR6.6 fingerprint metadata at upload time to skip a pre-scan). The two phases are weighted by their relative expected wall-clock cost rather than a naive 50/50 split, so the bar does not appear to stall on whichever phase is actually slower for a given archive — exact weighting is illustrative only, a planning/playtesting decision.
- **FR6.12 (new)** Failure handling / atomicity: extraction writes into a **temporary staging directory** (e.g. a `.tmp`-prefixed sibling under the saves directory), never directly into the final world folder name. Only once every archive entry has been extracted without an I/O exception is the staging directory atomically renamed/moved into place as the new, real world folder. If extraction fails partway (I/O error, corrupt/truncated archive, disk full, or the player cancels via `WorldRestoreScreen`), the staging directory is deleted in full and the real saves folder is left exactly as it was before the attempt — a half-extracted, corrupt world folder must never become visible as a normal local world. The failure is logged with the reason, `WorldRestoreScreen` shows a clear, retryable error, and control returns to the Singleplayer world-select screen with the world still shown as a cloud-only entry (FR6.9).
- **FR6.13 (new)** Same-slug collision handling: if, at the moment restore is attempted, a local world folder already exists for that `worldSlug` (e.g. created independently on this device, or left over from an earlier partial attempt outside the FR6.12 staging discipline), the restore is **aborted before any extraction begins** with a clear conflict message naming the existing local world — mirroring FR6.6's own warn-rather-than-silently-overwrite spirit — rather than merging or overwriting it automatically. Resolving this collision (rename, pick one, merge) beyond "abort and tell the player" is a Future Extension.

**Non-functional**
- **NFR1.** All group-specific business logic (data models, JSON I/O, size-threshold and quota-math decisions, reconciliation-timestamp comparison) is a plain-JVM-testable class with no `net.minecraft.*`/steamworks4j-native-call dependency, mirroring `services`'s own NFR5 (`services/specification.md:39`) and hello-world's NFR3 (`features/hello-world-main-menu/specification.md:47`).
- **NFR2.** No uncaught exception from any Cloud operation reaches Minecraft's tick/render thread or crashes client startup/shutdown — every steamworks4j call site catches and logs, same discipline as `SteamworksService.create(...)` (`services/.../SteamworksService.java:84-112`).
- **NFR3.** Public classes/interfaces carry JavaDoc with a usage example (`philosophy.md:19`).
- **NFR4.** Follows the required feature folder layout (`api/`, `config/`, `events/`, `gui/`, `mixins/`, `resources/`, `services/`, `tests/`, `README.md`, `.claude/context/feature-guidelines.md:5-16`).

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision (same convention as `features/hello-world-main-menu/specification.md:53`).

1. **`api` module** — new package `de.lazuli.api.cloudsync`, zero external/Minecraft dependencies, same "zero-dependency, safe for any layer" rationale as `SteamAvailability` (`api/.../SteamAvailability.java:14-17`):
   - `CloudSyncable` (interface): `String cloudSyncId();` `byte[] exportState();` `void importState(byte[] data);` — the mechanism Requirement Groups 1–2 share. This is a genuinely new pattern for this repo (a Feature-authored contract other Features implement, aggregated by a third Feature via the Platform composition root) — not simply another instance of `MainMenuHook`'s Platform→Feature shape. Flagged under Architecture as likely needing its own ADR during planning, the same way the services spec flagged its own Platform/Services generalization (`services/specification.md:60`, resolved as `docs/adr/0002-...md`).

2. **`features/steam-cloud-sync/api/`**:
   - `BookmarkedServer`, `LastPlayedPointer`, `Note`, `WorldSyncPreference { worldSlug: String, enabled: Boolean }` — immutable data records for Groups 3–6.
   - `SteamCloudSyncConfig` — this feature's own local settings (master + per-group toggles for Groups 1–5, `maxWorldArchiveSizeMb`, `allowSelectiveFallback`; no global Group 6 on/off — see FR6.1/Configuration).
   - `WorldFingerprint { worldSlug: String, displayName: String, deviceLabel: String, syncedAtTimestamp: Long }` — plain data mirror of one entry in FR6.6's Cloud metadata file.
   - `CloudOnlyWorldSummary { worldSlug: String, displayName: String, deviceLabel: String, syncedAtTimestamp: Long }` (FR6.8/FR6.9) — this feature's own stand-in for a row that has no real `LevelSummary` backing it; deliberately **not** any Minecraft type, so it stays constructible/testable on a plain JVM.
   - `RestoreProgress { phase: Phase, processedBytes: Long, totalBytes: Long }` where `Phase` is `{ READING_FROM_CLOUD, EXTRACTING }` (FR6.11) — a plain, immutable snapshot handed to a listener, never a Minecraft-facing type itself.
   - `RestoreProgressListener` (interface): `void onProgress(RestoreProgress progress);` `void onComplete(String worldSlug);` `void onFailed(String worldSlug, String reason);` (FR6.10–FR6.12).

3. **`features/steam-cloud-sync/services/`**:
   - `CloudSyncCoordinator` — owns the shared `SteamRemoteStorage` instance (constructed only if `SteamAvailability.isSteamAvailable()`) and the FR0.4 reconciliation routine; exposes `void syncNow()`/lifecycle-hook methods for each group.
   - `BookmarkedServersService`, `NotesService`, `LastPlayedPointerService` — pure CRUD + (de)serialization.
   - `WorldSyncPreferenceService` — pure CRUD over the local-only, per-world `WorldSyncPreference` list (FR6.1); never touches Cloud itself; gains one new method shape for FR6.10's post-restore default (e.g. `void markEnabledAfterRestore(String worldSlug)`).
   - `WorldSaveSyncService` — size check (FR6.3), archive-building, selective-fallback file set (FR6.4), fingerprint/warning logic (FR6.6), quota/`fileForget` bookkeeping (FR6.7); consults `WorldSyncPreferenceService` before acting on a given world (FR6.2).
   - `CloudOnlyWorldDetector` (new) — pure, plain-JVM-testable: given the local saves-directory listing and the parsed `List<WorldFingerprint>`, returns `List<CloudOnlyWorldSummary>` (FR6.8). Deliberately split out from anything Steam/Minecraft-touching so its set-difference logic is unit-testable with no native call.
   - `WorldRestoreService` (new) — the Steam-calling half of restore: `RestoreHandle beginRestore(String worldSlug, RestoreProgressListener listener)` (chunked `fileReadAsync`/`fileReadAsyncComplete` against `getFileSize`, off the render thread, per Architecture — Threading), staging-directory extraction and atomic move-into-place (FR6.12), same-slug collision check (FR6.13) before starting; `void cancelRestore(RestoreHandle handle)` aborts and cleans up the staging directory.
   - `CloudSyncableRegistry`-shaped constructor parameter (a `List<CloudSyncable>`), populated by the platform composition root (Requirements, FR1.2).

4. **`platform/fabric-<version>/...`**: a new client entrypoint constructing `CloudSyncCoordinator` with the shared `SteamworksService`/`SteamAvailability` and the `CloudSyncable` list, registering the FR0.3 lifecycle checkpoints, and the Version Adapters for the Multiplayer-screen bookmark-toggle (Group 3), the Singleplayer-screen world-sync-toggle icon (Group 6, FR6.1), and — new, and the heavier item — whatever entry-injection mechanism Architecture's flagged subsection resolves to for the FR6.9 synthetic cloud-only rows (very likely an `@Mixin`-based class living in this module's own `mixin/` package, e.g. alongside `platform/fabric-1.21.11/src/main/java/de/lazuli/mixin/ExampleMixin.java`, per this repo's own rule that Mixins targeting `net.minecraft.*` can never live inside a `features/*` module — `features/hello-world-main-menu/src/main/java/de/lazuli/features/helloworldmainmenu/mixins/package-info.java:1-16`).
   - `WorldRestoreScreen` (new, one per platform module, a thin `Screen` subclass): displays the current world's `displayName`, a status line reflecting `RestoreProgress.phase` with the FR6.11 honest copy, a manually-drawn progress bar (a filled rectangle sized to `processedBytes/totalBytes`, drawn via `DrawContext` primitives rather than any per-version reusable progress-bar widget class — deliberately sidesteps needing yet another cross-version widget-class lookup on top of the one already flagged under Architecture), and a Cancel button wired to `WorldRestoreService.cancelRestore`. On `onComplete`, returns to a refreshed Singleplayer world-select screen (the illustrative default — auto-launching directly into the newly-restored world instead is a reasonable alternative left open for planning/playtesting). On `onFailed`, shows the FR6.12 error and also returns to the world-select screen.

## Architecture
Layering: `features/steam-cloud-sync` depends on `api` (`CloudSyncable`, `SteamAvailability`, its own `api/` data records) and `services` (the shared `SteamworksService`), per the Dependency Rules table (`architecture.md:64-71`, "Features: API, Services"). It never depends on `features/hello-world-main-menu` or any other feature directly (`architecture.md:74`) — Group 1's cross-feature settings sync is bridged exclusively through the `api`-layer `CloudSyncable` contract plus platform-composition-root wiring (FR1.2), not a direct import.

```
features/hello-world-main-menu/services/HelloWorldMainMenuService  (implements/adapts to CloudSyncable)
features/<future-ui-accessibility>/services/...Service              (implements CloudSyncable, later)
        |  registered into, by
        v
platform/fabric-<version>/.../SteamCloudSyncClientInitializer   (composition root; constructs List<CloudSyncable>)
        |  constructs, passing SteamworksService + List<CloudSyncable>
        v
features/steam-cloud-sync/services/CloudSyncCoordinator          (reconciliation, checkpoints)
        |  constructs (only if isSteamAvailable())
        v
com.codedisaster.steamworks.SteamRemoteStorage                    (steamworks4j; requires a SteamRemoteStorageCallback)
        |
        v
Steam client (local IPC) -> Valve Cloud backend (classic launch/exit-timed sync, per Steamworks docs)
```

**Storage model — two independent locations per sync target, not one:** each target has (a) a "real" local file, owned by whichever feature/service normally reads/writes it for single-device operation (e.g. hello-world's own `config/hello-world-main-menu.json`, `platform/.../HelloWorldMainMenuClientInitializer.java:40`; or this feature's own `config/steam-cloud-sync/*.json`), and (b) a logically separate Steam Cloud file addressed only by a string name via `SteamRemoteStorage.fileWrite`/`fileRead` — Steam itself manages the physical on-disk cache location for (b), opaque to this mod. `CloudSyncCoordinator` reconciles between the two (FR0.4), it does not treat Cloud storage as "the" filesystem location for these files.

**Cloud filename convention:** Valve's docs confirm filenames are lowercased/case-insensitive (`partner.steamgames.com/doc/api/isteamremotestorage`); whether `/` in a filename creates a real pseudo-subdirectory is **not conclusively confirmed** by this research (no definitive documentation found) — flagged, not assumed, the same way the services spec flagged its own "two-binary distinction" for empirical confirmation (`services/specification.md:87-91`). Default to a flat, lowercase, prefixed naming convention (e.g. `lazuli-bookmarked-servers.json`, `lazuli-world-<slug>.zip`) rather than assuming `/` works.

**Threading:** small-target `fileRead`/`fileWrite` calls are cheap and run at the FR0.3 checkpoints on the client thread. For Group 6, archive **compression** (potentially seconds of CPU/I/O work) must happen off the render/client thread first, producing a ready `ByteBuffer`; only the final `fileWriteStreamOpen`/`WriteChunk`/`Close` calls hop back onto the same thread `SteamAPI.init()` ran on, consistent with the single-thread convention already documented for this project's Steamworks integration (`services/specification.md:85`). The restore path is symmetric: `WorldRestoreService`'s chunked `fileReadAsync`/`fileReadAsyncComplete` loop, subsequent `java.util.zip` decompression, and staging-directory extraction all run off the render/client thread (confirmed steamworks4j read-side shape: `SteamRemoteStorage.fileRead`, `fileReadAsync`/`fileReadAsyncComplete`, `getFileSize` — github.com/code-disaster/steamworks4j `SteamRemoteStorage.java`; completion delivered via `SteamRemoteStorageCallback.onFileReadAsyncComplete`, itself only fired while the tick-thread pump keeps running per `services/specification.md:83-85`); `WorldRestoreScreen` (Public API) only reads the latest `RestoreProgress` snapshot on the render thread to draw the bar, never blocks it.

**Two open architectural items inherited from the Steamworks bootstrap, now squarely this feature's problem:**
1. `services/implementation-plan.md:266-275` (Risk 3) explicitly left unresolved "how does a *second* client entrypoint obtain the same already-constructed `SteamworksService` instance rather than double-`init()`ing." This feature *is* that second entrypoint and must resolve the hand-off during its own planning phase (e.g. entrypoint-ordering discipline, or a small non-global holder passed between composition roots) — not re-solved speculatively here.
2. The `CloudSyncable` aggregation pattern (Public API, item 1) is a new shape of composition-root wiring beyond what `docs/adr/0001-...md`/`docs/adr/0002-...md` cover (Platform constructing one Feature or one Services class); planning should determine whether it needs its own ADR (e.g. `docs/adr/0003-...md`) generalizing "Platform bridges Feature A's exported state to Feature B via an api-layer contract."

**Quota math (reference budget, not a Valve-imposed number — see Overview):** absent a real, issued App ID and its own configured quota, this spec designs against an illustrative conservative reference of ~100MB total, split roughly: settings/accessibility (tens of KB each), bookmarks/notes/pointer (tens of KB to a few hundred KB depending on entry counts) leaving the large majority of the reference budget for Group 6 world archives — meaning, at this reference size, comfortably one to a few modest world archives fit at once. This is why `maxWorldArchiveSizeMb` (default below) is deliberately conservative rather than set anywhere near Valve's 100MB-per-call/256MB-soft-warn ceiling, and why FR6.7's `fileForget` housekeeping exists at all.

**Third open architectural item — Singleplayer-screen synthetic-entry injection (clearly flagged, materially bigger than the rest of this spec):** every other in-game widget injection in this spec (Group 3's bookmark toggle, Group 6's own FR6.1 sync icon) uses Fabric API's documented, non-mixin `ScreenEvents.AFTER_INIT` + `Screens.getButtons`/`Screens.getWidgets` mechanism (`features/hello-world-main-menu/specification.md:91-95`, `.claude/context/minecraft.md:56`), because that mechanism only needs to append an independent, always-visible overlay widget positioned near an existing row — it never needs to become part of the row list itself. FR6.9's requirement — a fully synthetic row that scrolls, is keyboard-navigable, is selectable, and responds to double-click-to-play exactly like a real world entry — is a different, harder problem:
- **Confirmed** (Yarn 1.21.11 API docs, `maven.fabricmc.net/docs/yarn-1.21.11+build.1/...`): `SelectWorldScreen` exposes no public accessor to its `WorldListWidget levelList` field; `WorldListWidget` populates entries through a **private** async pipeline (`loadLevels()`/`show()`/`showSummaries()`), and its inherited `EntryListWidget.addEntry(E)`/`clearEntries()` methods are **protected**, not public. A real row is a `WorldListWidget.WorldEntry` built from a genuine `LevelSummary`, which itself expects a real on-disk save (icon path, save-version info) to make sense.
- **Confirmed, non-mixin insufficiency:** the existing `Screens.getWidgets`/`getButtons` technique operates on the *Screen's* own top-level widget list, not on `WorldListWidget`'s internal entry collection — it cannot be used to insert a real scrolling/selectable row, only an overlay on top of the screen.
- **Not confirmed here, left to planning verification** (same discipline as the already-logged `Screens.getButtons`→`getWidgets` rename): (a) whether `WorldListWidget.children()` returns the actual live, externally-appendable backing list (which would allow a non-mixin insertion once a reference to the `WorldListWidget` instance is obtained by filtering the Screen's own children for `instanceof WorldListWidget`) or a defensive copy; (b) whether `WorldEntry`'s constructor is even accessible outside its own package, or whether a bespoke `WorldListWidget.Entry` subclass (re-implementing render/click/keyboard-nav/narration itself, without reusing `WorldEntry`) is required instead; (c) whether the equivalent classes/method visibilities still hold for 26.1/26.2 — no compiled Mojang-mapped jar for either version was reachable during this research pass, so this is genuinely unconfirmed, not just an assumed rename.
- **Working assumption for planning:** treat this as very likely requiring a real `@Mixin` (at minimum `@Accessor`/`@Invoker` mixins onto `WorldListWidget`'s population methods and/or entry-add methods) per supported Minecraft version, living in each `platform/fabric-<version>/.../mixin/` package — never in `features/steam-cloud-sync/mixins/`, which stays permanently empty for the same reason `features/hello-world-main-menu`'s does (`features/hello-world-main-menu/src/main/java/de/lazuli/features/helloworldmainmenu/mixins/package-info.java:1-16`). This is the first genuine Mixin need in this spec (versus every other injection point's documented non-mixin Fabric API mechanism) and should get its own Risk entry in the implementation plan, the same way `services/implementation-plan.md:266-275` tracks its own open risks.

## UI
Deliberately minimal for v1, following this repo's own precedent of shipping data/sync plumbing before an in-game editor (`features/hello-world-main-menu/specification.md:25`, "No in-game config-editing screen for v1"), with these toggle/screen exceptions:
- **Group 3**: a bookmark-toggle widget added to each entry on the vanilla Multiplayer server-list screen, via the same non-mixin `ScreenEvents.AFTER_INIT` widget-injection technique already used by `features/hello-world-main-menu` (`features/hello-world-main-menu/specification.md:91-95`).
- **Group 6**: two related but distinct pieces of Singleplayer-screen UI:
  - A **sync-toggle icon** added to each *local* world's row, same widget-injection technique as Group 3, gating that world's sync participation per FR6.1 — shows on/off at a glance, no additional detail screen (size, last-sync time, etc.) in v1, that detail stays log-only (FR6.4/FR6.6/FR6.7).
  - A **distinct cloud icon** marking each *synthetic, cloud-only* entry (FR6.8/FR6.9) for a world that exists in this device's Cloud fingerprint metadata but has no local save folder yet — visually different from the sync-toggle icon so a player can immediately tell "world I have, sync on/off" apart from "world I don't have yet." Selecting one and pressing Play does not launch a world; it opens the new **`WorldRestoreScreen`** (Public API), which shows the world's name, a status line using the honest "**Restoring** world from Steam Cloud..." / "Extracting world files..." framing (never "Downloading...", since the real transfer already happened silently before Minecraft launched — FR6.11), a progress bar synthesized from local read + decompression/extraction work (FR6.11), and a Cancel button. On success, the world becomes a normal local entry (its cloud-only synthetic row is replaced by a real one) and its sync preference defaults to enabled (FR6.10); on failure, a clear retryable error is shown and the world remains cloud-only (FR6.12).
- Groups 1, 2, 4, 5: no dedicated screen in v1 — log/toast notifications only for the events that matter to a player (FR4.3). Full management screens, a HUD waypoint overlay, and a "Continue as..." title-screen prompt are Future Extensions.

## Configuration
`config/steam-cloud-sync.json`, same flat-under-config-dir convention as `hello-world-main-menu.json` (`platform/.../HelloWorldMainMenuClientInitializer.java:40`):
```json
{
  "schemaVersion": 1,
  "enabled": true,
  "syncSettings": true,
  "syncAccessibility": true,
  "syncBookmarkedServers": true,
  "syncContinuePointer": true,
  "syncNotes": true,
  "maxWorldArchiveSizeMb": 50,
  "allowSelectiveFallback": true
}
```
- `enabled`: master switch; even when `true`, has no effect unless `SteamAvailability.isSteamAvailable()`. This also gates whether the Group 6 Singleplayer-screen toggle icon appears at all (FR6.1) — there is no separate global Group 6 on/off, since that live per-world (FR6.1).
- Per-group booleans for Groups 1–5: default `true` for these small/low-risk categories. Group 6 has no entry here by design — its opt-in state lives entirely in the per-world `WorldSyncPreference` list (FR6.1), not in this shared config file.
- `maxWorldArchiveSizeMb` default `50`: chosen well under Valve's 100MB-per-call cap and 256MB soft-warn threshold, and conservative relative to the ~100MB reference budget (Architecture — Quota math), so a synced world leaves headroom for the other five categories under a modest configured quota.
- `allowSelectiveFallback` default `true`: prefer the degraded critical-files-only fallback (FR6.4) over doing nothing when a world exceeds the threshold.
- `schemaVersion` included from v1 (unlike hello-world's initial schema, `features/hello-world-main-menu/specification.md:134`) because this schema is expected to grow (per-world overrides, etc., Future Extensions).
- Malformed/missing file falls back to these defaults with a logged warning, same pattern as `HelloWorldMainMenuConfigIO.load(...)` (`HelloWorldMainMenuConfigIO.java:71-88`).
- A separate, local-only file (e.g. `config/steam-cloud-sync/world-sync-preferences.json`, `{ "schemaVersion": 1, "worlds": [ { "worldSlug": "...", "enabled": true } ] }`) holds the per-world Group 6 toggle state (FR6.1) — deliberately not merged into the shared config above, since it is per-world data, not a feature-level setting, and is never itself Cloud-synced (Non-goals).

## Events
- Consumes, does not define, Fabric API events: `ScreenEvents.AFTER_INIT` (Group 3 widget), `ClientLifecycleEvents.CLIENT_STOPPING` (shutdown sync checkpoint, same event `SteamworksClientInitializer` already registers on per `services/implementation-plan.md:253`), and a world-unload/join/disconnect event family for Groups 4 and 6 whose exact class/method name is **not asserted** here (see FR4.2) — must be confirmed per supported Fabric API version during planning, the same caution already exercised for `ClientTickEvents` (`services/specification.md:83`) and the `Screens` rename (`.claude/context/minecraft.md:56`).
- Defines no new cross-feature event bus type — none exists yet in this repo (`architecture.md:26`), and this feature has no second-feature reason to build one; internal group-to-group signaling (e.g. "a note was added, sync it") is plain in-process method calls within `features/steam-cloud-sync`.

## Networking
No new client-server packets; entirely client-only (mirrors `services/specification.md:18`, `features/hello-world-main-menu/specification.md:22,142`). The only "networking" involved is Steam's own client↔Valve-backend Cloud transfer, opaque to this mod and not directly controllable — classic launch/exit-timed sync applies by default; "Dynamic Cloud Sync" (near-live, mid-session sync) requires a separate Steamworks-partner-console opt-in flag this project has not requested (Non-goals; Future Extensions).

## Persistence
- Six Cloud-tracked logical files (flat, lowercase naming convention, Architecture): settings/accessibility (via `CloudSyncable.cloudSyncId()`, one per registered feature), `lazuli-bookmarked-servers.json`, `lazuli-continue-pointer.json`, `lazuli-notes.json`, `lazuli-world-<slug>.zip` (one per synced world) plus its fingerprint metadata file (FR6.6).
- Each has an independent local "real" file as source of truth (Architecture — Storage model); Cloud is a mirror, never the sole copy.
- This feature's own settings (`config/steam-cloud-sync.json`) and the per-world sync-preference list (`config/steam-cloud-sync/world-sync-preferences.json`, FR6.1/Configuration) are both local-only and never themselves Cloud-synced (they are this device's own sync preferences, not player data).
- World archives are built via `java.util.zip` (JDK-provided, no new dependency, mirrors the hand-rolled-parser precedent at `HelloWorldMainMenuConfigIO.java:20-26`).

## Compatibility
- Minecraft/Fabric versions: business logic (data models, JSON I/O, size/quota math, reconciliation) is plain Java, Minecraft-version-agnostic, same as the Steamworks bootstrap itself (`services/specification.md:123`). Version-specific Version Adapters are needed only for: (a) resolving the world-saves directory and the world-unload/join/disconnect lifecycle hooks (FR4.2/FR6.2), (b) the Multiplayer-screen bookmark-toggle widget injection (subject to the already-logged `Screens.getButtons`→`Screens.getWidgets` rename, `.claude/context/minecraft.md:56`), and (c) obtaining the shared `SteamworksService` instance from the composition root (Architecture, inherited item 1).
- Steamworks/steamworks4j: same version pin as the bootstrap (`steamworks4j 1.10.0`, `gradle.properties:41`); no additional native/Gradle wiring beyond what `services/build.gradle` already provides transitively (`services/specification.md:95`).
- Java/OS/architecture: inherits the bootstrap's constraints (`services/specification.md:124-126`) — no additional restriction introduced by this feature.

## Performance
- Groups 1–5: sub-millisecond to low-millisecond synchronous `fileWrite`/`fileRead` calls, triggered only at FR0.3 checkpoints (startup/shutdown/data-change), never per-tick — negligible.
- Group 6: archive-building cost scales with world size up to `maxWorldArchiveSizeMb` (bounded by design); deliberately piggy-backed onto vanilla's own existing "Saving world" wait (FR6.2) so added latency is perceived as part of an already-expected pause rather than new jank; compression runs off the render/client thread, only the final streamed-write calls touch the client thread (Architecture — Threading).
- `getQuota`/`fileForget` housekeeping (FR6.7) is cheap and runs only around a Group 6 sync checkpoint, not per-tick.
- No retained per-tick allocation or polling anywhere in this feature.

## Future Extensions
- Dynamic Cloud Sync (near-live, mid-session sync) once a real App ID exists and the Steamworks-partner-console flag is enabled.
- Additional Group 6 per-world granularity beyond a plain on/off toggle (e.g. a per-world size override).
- In-game management screens: bookmarks beyond the v1 toggle, notes/waypoints (including a HUD overlay), and a "Continue as..." title-screen prompt for Group 4.

- A richer conflict-resolution UI for Group 6 (e.g. showing both devices' world metadata and letting the player choose) instead of the current warn-then-overwrite flow for uploads, and beyond the simple abort-and-tell-the-player behavior in FR6.13 for a same-slug local collision at restore time.

- Resolving whether the `CloudSyncable` aggregation pattern (Public API item 1) needs its own ADR, and whether it should ever be promoted further given the graduate-on-second-use spirit (`architecture.md:26`) if a third feature needs an analogous cross-feature-bridging mechanism outside Cloud sync specifically.
