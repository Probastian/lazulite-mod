# Implementation Plan — DropdownWidget UI Polish + Overlay Split

## Implements
- `platform/ui/specification.md` — v2 Amendment ("Polish pass"), requirements UI-FR8-UI-FR18 and the corresponding Public API / Architecture / UI / Compatibility deltas.
- `features/friends-sidebar/specification.md` — v1.5 Amendment ("Join-policy control polish"), requirements v1.5-FR7.16 through v1.5-FR7.20 and the corresponding Public API / Architecture / UI / Compatibility deltas.

This plan is **cross-cutting**: it touches a shared, non-feature-owned Platform component (`de.lazuli.ui.DropdownWidget`, one copy per platform module) and that component's one real consumer (`features/friends-sidebar`'s `FriendSidebarWidget`/`FabricFriendsSidebarInjector`/`FriendsSidebarZOrder`). It is filed under `features/friends-sidebar/` (rather than `platform/ui/`) because every concrete file changed lives either in a platform module under a `friends/`-named consumer package, or in `api/friends/`, and the friends-sidebar spec's v1.5 amendment is what pins down the exact wiring decisions (label copy, ordinal placement, mutual-exclusivity rationale) that make the generic `platform/ui/specification.md` v2 requirements concrete. No `features/server-browser` file is touched or referenced anywhere in this plan.

## Existing Implementation (research, this plan)

**`DropdownWidget.java`** — confirmed byte-for-byte structural twin across all three platform modules (`platform/fabric-26.2`, `platform/fabric-26.1`, `platform/fabric-1.21.11`, all at `src/main/java/de/lazuli/ui/DropdownWidget.java`), differing only in the existing `GuiGraphicsExtractor`/`Minecraft.getInstance().font`/`guiGraphics.text(...)` (Mojang, 26.1/26.2) vs. `DrawContext`/`MinecraftClient.getInstance().textRenderer`/`context.drawTextWithShadow(...)` (Yarn, 1.21.11) idiom. Current shape (identical across modules apart from that idiom):
- `record Option(String label, String description)`
- Constructor: `DropdownWidget(List<Option> options, int initialSelectedIndex, IntConsumer onSelectionChanged)` — no label parameter today.
- `boolean isOpen()`, `void close()`, `int selectedIndex()`.
- `int render(<GuiGraphicsExtractor|DrawContext>, int x, int y, int width, int rowHeight, int mouseX, int mouseY)` — single method, draws closed row **and**, inline, every open-state option row (with inline wrapped hover-description text beneath the hovered row via the private `wrapMessage(...)` helper). Returns `rowHeight` when closed, `rowHeight * (1 + options.size())` when open — the returned height already excludes the inline description text (the undercount defect the spec's Problem 3 describes).
- `boolean mouseClicked(double mouseX, double mouseY, int x, int y, int width, int rowHeight)` — single method covering closed-row toggle, option selection, and elsewhere-while-open close.
- No tooltip API call anywhere in the class today (confirmed, both modules).
- `private static List<String> wrapMessage(ToIntFunction<String> widthOf, String message, int maxWidth)` — only consumer today is the inline description block inside `render()`.

**`FriendSidebarWidget.java`** (`platform/fabric-26.2/.../friends/FriendSidebarWidget.java`, structural twin on `fabric-26.1` and `fabric-1.21.11` — confirmed same field/method names, only the Mojang `GuiGraphicsExtractor` vs. Yarn `DrawContext` idiom differs, e.g. `renderNow(GuiGraphicsExtractor, int, int, float)` vs. `renderNow(DrawContext, int, int, float)`):
- `joinPolicyDropdown` field, constructed once at `new DropdownWidget(options, initialSelectedIndex, onSelectionChanged)` (26.2 line 176; options built at line 171 via `joinPolicyShortLabel(policy)`/`joinPolicyDescription(policy)`).
- `dropdownX`, `dropdownY`, `dropdownWidth`, `dropdownVisible`, `lastDropdownHeight` fields, all mutated inside `renderNow()`'s render pass (26.2 lines 385-395) — `dropdownVisible = expanded && showText`; when visible, `lastDropdownHeight = joinPolicyDropdown.render(guiGraphics, dropdownX, dropdownY, dropdownWidth, DROPDOWN_HEIGHT, mouseX, mouseY)` (26.2 lines 386-391).
- `listTopOffset()` (26.2 lines 204-210, both the instance method and the `static int listTopOffset(boolean expanded, int dropdownHeight)` overload used both in the constructor's `super(...)` height call and at runtime) is the sole consumer of `lastDropdownHeight`, per v1.4-FR7.14's existing "read the height back from `render()`" mechanism.
- `mouseClicked` forwards to `joinPolicyDropdown.mouseClicked(event.x(), event.y(), dropdownX, dropdownY, dropdownWidth, DROPDOWN_HEIGHT)` (26.2 lines 539-540), gated by `dropdownVisible`.
- `renderNow(...)` is the single public entry point `FabricFriendsSidebarInjector.onAfterExtract`/`onAfterRender` calls once per frame; it currently draws the whole sidebar including the dropdown's closed row and (today) its open-state rows, all within the `SIDEBAR`-ordinal pass.
- No existing `renderDropdownOverlay(...)` method on any platform (confirmed via grep — only `renderNow` and `render` matches).

**`FriendsSidebarZOrder.java`** (`api/src/main/java/de/lazuli/api/friends/FriendsSidebarZOrder.java`, single copy, no per-platform duplication): today a two-value enum, `SIDEBAR, CONTEXT_MENU`, with a Javadoc describing exactly those two manually-drawn layers and stating ordinal order determines draw order (ascending, lowest first).

**`FabricFriendsSidebarInjector.java`** — **confirmed real per-platform discrepancy, not called out by either spec, that implementers must handle:**
- On `fabric-26.2` and `fabric-26.1` (Mojang mapping): the hook is `ScreenEvents.afterExtract(screen).register(this::onAfterExtract)`, and the handler signature is `private void onAfterExtract(Screen screen, net.minecraft.client.gui.GuiGraphicsExtractor guiGraphics, int mouseX, int mouseY, float delta)` (confirmed identical on both, 26.2 lines 111/121-129). Body: `if (screen == activeSidebarScreen && activeSidebar != null) { activeSidebar.renderNow(guiGraphics, mouseX, mouseY, delta); }` then the equivalent `openMenu != null && screen == openMenuScreen` guard calling `openMenu.renderNow(...)`.
- On `fabric-1.21.11` (Yarn mapping): the hook is `ScreenEvents.afterRender(screen).register(this::onAfterRender)` (not `afterExtract`/`onAfterExtract`), and the handler signature is `private void onAfterRender(Screen screen, net.minecraft.client.gui.DrawContext context, int mouseX, int mouseY, float delta)` (line 120-123). Both specs (`platform/ui/specification.md` v2 Architecture, `features/friends-sidebar/specification.md` v1.5-FR7.20) refer to this hook uniformly as `onAfterExtract`/`afterExtract`, matching the Mojang modules' actual naming but **not** the Yarn module's actual method/event name. This plan's file-level task list (below) uses the correct per-module name for each module; implementers must not literally search-and-replace `onAfterExtract` into the Yarn file.
- Guard structure (the `screen == activeSidebarScreen && activeSidebar != null` check) is otherwise identical across all three modules.

**Tests.** No existing test file for `DropdownWidget` or `FriendSidebarWidget` on any platform (`Glob` for `**/ui/**Test*.java` and `**/friends/**Test*.java` returns zero matches). This is consistent with this repo's established convention (confirmed via `platform/ui/specification.md`'s own UI section: "Manual, per-supported-version in-game verification is required (not unit-testable, consistent with every other rendering concern in this repo's only existing custom widgets)") — the only automated tests in this feature area today are for the plain-JVM `services`/`config` layer (`FriendsSidebarConfigIOTest`, `FriendSidebarStateMachineTest`, `FriendsSidebarFacadeTest`, all under `features/friends-sidebar/src/test/java/...`), none of which touch `DropdownWidget`/`FriendSidebarWidget`/the injector, all of which remain untouched by this plan (Non-goals/Persistence sections of both specs confirm this work has zero config/services-layer surface).

## Files to Modify

Per platform module (`fabric-26.2`, `fabric-26.1`, `fabric-1.21.11`), identical logical change, differing only in the pre-existing per-module rendering idiom:

1. **`platform/<module>/src/main/java/de/lazuli/ui/DropdownWidget.java`** (all three)
   - Add optional `String label` field + constructor parameter. Recommended shape (per spec's illustrative Public API item 3, planning finalizes): retain a no-label convenience constructor delegating to a new primary constructor, e.g.:
     - `public DropdownWidget(List<Option> options, int initialSelectedIndex, IntConsumer onSelectionChanged)` — existing signature, now delegates with `label = null`.
     - `public DropdownWidget(String label, List<Option> options, int initialSelectedIndex, IntConsumer onSelectionChanged)` — new primary constructor (UI-FR10, Public API item 3).
   - Add internal cached-bounds state for the overlay split (UI-FR16): fields to hold `x, y, width, rowHeight` and the options/open-state needed by `renderOpenOverlay`, populated at the end of the closed-row `render(...)` call.
   - Split `render(...)`:
     - Keep method name/signature `int render(<GuiGraphicsExtractor|DrawContext>, int x, int y, int width, int rowHeight, int mouseX, int mouseY[, float delta if adopted — see Risks])` (UI-FR15 item 1) — draws only: label row (if present), closed row (background/text), border/hover chrome (UI-FR8/UI-FR9), and — if the closed row is hovered and has a description — queues the native tooltip (UI-FR12). No longer draws open-state rows regardless of `isOpen()`. Returns closed-row-plus-label height only (UI-FR11). Caches `(x, y, width, rowHeight)` + current `options`/`selectedIndex` for `renderOpenOverlay()` (UI-FR16) before returning.
     - Add new method `void renderOpenOverlay(<GuiGraphicsExtractor|DrawContext>, int mouseX, int mouseY, float delta)` (UI-FR15 item 2, Public API item 4) — no-op (zero draw calls) when `!open`; otherwise draws every option row (chrome, hover highlight, tooltip for the hovered row) at the cached bounds, directly below the cached closed-row `y + rowHeight`.
   - Add button chrome (UI-FR8): a border/outline `fill`/rectangle pass in a lighter shade than `BACKGROUND`, applied to both the closed row (in `render`) and every option row (in `renderOpenOverlay`). New constant(s), e.g. `BORDER_COLOR`.
   - Add hover-highlight (UI-FR9): a second, brighter background fill color used instead of `BACKGROUND` when `mouseX`/`mouseY` is over the row currently being drawn (closed row in `render`, whichever option row in `renderOpenOverlay`). New constant, e.g. `BACKGROUND_HOVER`.
   - Replace inline hover-description rendering with native tooltip calls (UI-FR12/UI-FR13/UI-FR14):
     - `fabric-1.21.11` (Yarn): `context.drawTooltip(Text.literal(option.description()), mouseX, mouseY)` (exact `Text` construction for multi-line — see Risks).
     - `fabric-26.1`/`fabric-26.2` (Mojang): `guiGraphics.setTooltipForNextFrame(Component.literal(option.description()), mouseX, mouseY)` — confirm exact class/package (`net.minecraft.client.gui.GuiGraphicsExtractor` per spec; verify at implementation time whether this is a static/instance method and its exact import, since `GuiGraphicsExtractor` is this repo's own extractor type, not vanilla `GuiGraphics` — cross-check against `.claude/context/minecraft.md`'s API-difference table cited by the spec before writing the call).
   - Retire or leave dead the `wrapMessage(...)` private helper (UI-FR14 — planning discretion per spec; **recommendation: delete it**, since its sole caller is removed by this change and leaving dead code in a `final` utility-like class has no benefit here).
   - No change to `mouseClicked(...)`'s signature or hit-testing logic (UI-FR17) — it continues to use caller-supplied `(x, y, width, rowHeight)` args exactly as today; only its Javadoc may be updated to note it hit-tests the same bounds `render`/`renderOpenOverlay` last cached.

2. **`platform/<module>/src/main/java/de/lazuli/friends/FriendSidebarWidget.java`** (all three)
   - Constructor call site (26.2 line 176 and structural equivalents): add `"Who can join:"` as the new first argument, switching to the new `DropdownWidget(String label, ...)` constructor (v1.5-FR7.16, Public API item 12).
   - `renderNow(...)`'s existing `joinPolicyDropdown.render(guiGraphics, dropdownX, dropdownY, dropdownWidth, DROPDOWN_HEIGHT, mouseX, mouseY)` call (26.2 lines 390-391) stays as-is structurally (same call, now only drawing the closed row/label thanks to `DropdownWidget`'s internal split) — `lastDropdownHeight` continues to be set from its return value unchanged (v1.5-FR7.17, no new branch needed).
   - Add new public method `renderDropdownOverlay(<GuiGraphicsExtractor|DrawContext> guiGraphics, int mouseX, int mouseY, float delta)` (v1.5-FR7.19, Public API item 13): no-op when `!joinPolicyDropdown.isOpen()`, else forwards to `joinPolicyDropdown.renderOpenOverlay(guiGraphics, mouseX, mouseY, delta)`.
   - No change to the existing `mouseClicked` forwarding call (v1.5-FR7.19's last sentence, UI-FR17) or to `dropdownVisible`/`dropdownX`/`dropdownY`/`dropdownWidth` field usage.

3. **`api/src/main/java/de/lazuli/api/friends/FriendsSidebarZOrder.java`** (single copy)
   - Add new ordinal `DROPDOWN_OVERLAY`, declared between `SIDEBAR` and `CONTEXT_MENU` (enum declaration order: `SIDEBAR, DROPDOWN_OVERLAY, CONTEXT_MENU`) per v1.5-FR7.20/Public API item 14.
   - Update the class Javadoc to describe three manually-drawn layers instead of two, and explicitly state that `DROPDOWN_OVERLAY` and `CONTEXT_MENU` are the same topmost-overlay tier (both above `SIDEBAR`), with their relative declaration order carrying no priority meaning because the two states are mutually exclusive at runtime (v1.5 Compatibility delta — this exact wording requirement is spec-mandated, not just recommended).

4. **`platform/<module>/src/main/java/de/lazuli/friends/FabricFriendsSidebarInjector.java`** (all three — note the per-module hook-name discrepancy from Existing Implementation, above)
   - `fabric-26.2` / `fabric-26.1`: inside `onAfterExtract(Screen screen, GuiGraphicsExtractor guiGraphics, int mouseX, int mouseY, float delta)`, insert one new guarded call between the existing `activeSidebar.renderNow(...)` call and the existing `openMenu.renderNow(...)` call:
     ```
     if (screen == activeSidebarScreen && activeSidebar != null) {
         activeSidebar.renderDropdownOverlay(guiGraphics, mouseX, mouseY, delta);
     }
     ```
   - `fabric-1.21.11`: same logical insertion, but inside the actually-named `onAfterRender(Screen screen, DrawContext context, int mouseX, int mouseY, float delta)` method (not `onAfterExtract` — confirmed discrepancy above), using `context` in place of `guiGraphics`.
   - No change to the existing `activeSidebar.renderNow(...)` or `openMenu.renderNow(...)` calls or their guards on any module.

## Order / Dependencies of Changes
1. `DropdownWidget.java` on all three platforms first (label param, render split, chrome, tooltip) — self-contained, no dependency on the other files; can be done per-module in any order, but all three should land together in the same change (Compatibility risk, below).
2. `FriendsSidebarZOrder.java` (single `api/` file) — independent of `DropdownWidget`, can be done in parallel with step 1, but must land before step 4 (compile dependency).
3. `FriendSidebarWidget.java` on all three platforms — depends on step 1 (new constructor shape, `renderOpenOverlay` method existing on `DropdownWidget`) being complete on that same platform first.
4. `FabricFriendsSidebarInjector.java` on all three platforms — depends on step 2 (new ordinal, if the ordinal itself is referenced directly by name in a comment/guard — functionally the ordinal isn't referenced by value in the injector's `if` logic itself, only documented) and step 3 (`renderDropdownOverlay(...)` must exist on `FriendSidebarWidget` before the injector can call it).

Recommended sequencing per module: `DropdownWidget.java` -> `FriendSidebarWidget.java` -> `FabricFriendsSidebarInjector.java`, repeated across all three modules; `FriendsSidebarZOrder.java` done once, anywhere in that sequence (no compile-order dependency on the platform files, only a documentation-consistency one).

## Risks
1. **Tooltip API exact shape unresolved at planning time.** The spec cites `DrawContext.drawTooltip(Text, int, int)` (Yarn) and `GuiGraphicsExtractor.setTooltipForNextFrame(Component, int, int)` (Mojang) from `.claude/context/minecraft.md`'s cross-version API table, but does not resolve (a) whether these are instance or static methods, (b) the exact `Text`/`Component` construction call for multi-line content (`Text.literal("a\nb")` vs. explicit multi-line builder), or (c) whether `GuiGraphicsExtractor` (this repo's own extractor type, distinct from vanilla `GuiGraphics`) exposes `setTooltipForNextFrame` directly or requires unwrapping to a vanilla `GuiGraphics` first. Implementers must re-read `.claude/context/minecraft.md`'s table and, if needed, the actual `GuiGraphicsExtractor` source before writing the call — this is a compile-time-verifiable risk, not a design one.
2. **Per-module injector hook-name discrepancy (confirmed, documented above).** Both specs describe the injector hook uniformly as `onAfterExtract`/`afterExtract`; the Yarn module (`fabric-1.21.11`) actually names it `onAfterRender`/`ScreenEvents.afterRender`. An implementer following the spec text literally (rather than this plan's per-file task list) risks either mis-naming the new call site or missing it entirely on that module. Mitigated by this plan spelling out the correct name per module.
3. **Width-matching / bounds-caching correctness (UI-FR16).** `renderOpenOverlay()` relies on `render()` having been called earlier in the *same frame* to populate cached bounds. Today's call order (`FriendSidebarWidget.renderNow()` at `SIDEBAR` ordinal, then `renderDropdownOverlay()` at the new `DROPDOWN_OVERLAY` ordinal, both from the same `onAfterExtract`/`onAfterRender` invocation) already satisfies this per both specs' analysis — but if `dropdownVisible` is `false` this frame (e.g. sidebar collapsed), `render()` is never called, so cached bounds are stale from whenever it was last visible. Per UI-FR16 this is spec-blessed as "stale-but-harmless single-frame lag at worst," but implementers should confirm `renderDropdownOverlay()`'s own no-op guard (`!joinPolicyDropdown.isOpen()`) is sufficient in practice — if a user could somehow leave the dropdown "open" internally while the sidebar collapses (spec's v1.4-FR7.6a says `close()` is called precisely to prevent this — 26.2 line 370, `joinPolicyDropdown.close()` inside the `!steamAvailable` branch), verify collapse/steam-unavailable paths all still call `close()` so this scenario can't surface a stale overlay.
4. **Chrome color/contrast is a design decision with no UX sign-off captured in either spec.** Both specs explicitly leave exact pixel/color values to planning/implementation discretion (UI-FR8/UI-FR9). Recommend picking values with clear contrast against the existing `BACKGROUND = 0xCC202020` (e.g. a border a few shades lighter, a hover fill blended toward white) and validating visually during manual in-game verification rather than guessing "correct" hex values now — no further planning action needed, flagged so implementation doesn't block on it.
5. **Z-order Javadoc wording is spec-mandated, easy to under-deliver.** The v1.5 Compatibility delta requires the updated `FriendsSidebarZOrder` Javadoc to explicitly state `DROPDOWN_OVERLAY`/`CONTEXT_MENU` are equal-topmost-tier, not that one outranks the other — a generic "add DROPDOWN_OVERLAY" edit that doesn't include this specific claim would technically satisfy the enum-value requirement but fail the spec's Javadoc requirement. Call out explicitly in verification.
6. **`FriendSidebarWidget.java` and `FabricFriendsSidebarInjector.java` are actively-evolving shared files** (both specs' own Compatibility sections flag this) — re-run `git status`/`git diff` before editing either, per both specs' own stated discipline, since uncommitted changes already show these files as modified in the working tree (per the session's git status).

## Test Strategy
- **No new automated/unit tests planned for `DropdownWidget.java` or `FriendSidebarWidget.java`**, on any platform, consistent with this repo's existing convention: neither class has any test today (confirmed, zero matches for `**/ui/**Test*.java` and `**/friends/**Test*.java`), and both specs' own UI sections explicitly classify this as "not unit-testable... consistent with every other rendering concern in this repo's only existing custom widgets," requiring manual, per-platform in-game verification instead. This plan does not deviate from that established precedent.
- **No change to existing automated tests.** `FriendsSidebarConfigIOTest`, `FriendSidebarStateMachineTest`, `FriendsSidebarFacadeTest` (`features/friends-sidebar/src/test/java/...`) are all plain-JVM `services`/`config` tests with zero coupling to `DropdownWidget`/`FriendSidebarWidget`/the injector/`FriendsSidebarZOrder` — this plan's changes have no config/services-layer surface (both specs' Configuration/Persistence sections confirm "None" / "unchanged"), so these tests require no update and should be re-run only as a regression sanity check (no code path they cover is touched).
- **Manual in-game verification required, per platform module (`fabric-1.21.11`, `fabric-26.1`, `fabric-26.2`), covering:**
  1. Closed-row chrome: border/outline visible at rest (not merely on hover) on the join-policy control.
  2. Hover highlight: closed row and each open option row visibly brighten when moused over, at rest state unaffected.
  3. `"Who can join:"` label renders directly above the closed row, closed-row's own `"Join: <value>"` text unchanged.
  4. Native tooltip: hovering the closed row or an open option row with a non-empty description shows vanilla's dark rounded tooltip box (not the old inline wrapped text) — confirm on all three modules given the tooltip API's per-module divergence and its frame-timing sensitivity (`setTooltipForNextFrame` must be called during that frame's render pass).
  5. Open-state overlay draws on top of the friend-row list: open the join-policy dropdown with enough online friends that the friend list extends into the same screen region the open option list occupies; confirm no clipping/covering, on all three modules (the concrete symptom that motivated Problem 5/UI-FR15-UI-FR18).
  6. Height/layout: confirm no visual gap or overlap in `listTopOffset()`'s reserved space now that the label adds a row and the open-state rows no longer participate in that height at all.
  7. Click behavior unchanged: opening/closing via closed-row click, selecting an option, closing via outside click — all pre-existing v1.4 behaviors regression-checked, since `mouseClicked`'s contract is unchanged.
  8. Mutual-exclusivity assumption holds: confirm the context menu and the open dropdown are never both visible in the same frame in practice (per the spec's construction-based rationale, this should already be guaranteed by existing click-handling code, not by this change — verify it hasn't regressed).
  9. Steam-unavailable / sidebar-collapse paths: confirm the dropdown overlay never renders stale content when the sidebar collapses or Steam becomes unavailable mid-open (Risk 3, above).

## Acceptance Criteria
Per `platform/ui/specification.md` v2:
- UI-FR8: closed row and every open-state row render visible border/outline chrome at rest, on all three platforms.
- UI-FR9: hovered row (closed or open-state) renders a visibly different background fill than non-hovered rows, on all three platforms, consistent within a single frame across both render calls.
- UI-FR10/UI-FR11: `DropdownWidget` accepts an optional `label`; when set, it renders above the closed row and is included in `render()`'s returned height; when unset/empty, no visual/height change from today.
- UI-FR12/UI-FR13/UI-FR14: per-row descriptions render via the platform-correct native tooltip API, hover-gated, no longer as inline body text; `render()`'s returned height never includes any variable/hover-conditional or open-state amount.
- UI-FR15/UI-FR16/UI-FR17/UI-FR18: `render(...)` (closed-row/label only) and `renderOpenOverlay(...)` (open-state rows only, using bounds cached from the same frame's `render()` call) exist as two distinct public methods on `DropdownWidget`, on all three platforms; `mouseClicked(...)`'s external signature/contract is unchanged; `DropdownWidget` has zero import of `FriendsSidebarZOrder` or any other friends-sidebar-specific type.
- Structural twin requirement (UI-FR7) holds across all three platform copies of `DropdownWidget.java` after this change, differing only in the already-established per-module rendering/tooltip idiom.

Per `features/friends-sidebar/specification.md` v1.5:
- v1.5-FR7.16: `FriendSidebarWidget` constructs `joinPolicyDropdown` with label `"Who can join:"`.
- v1.5-FR7.17: `listTopOffset()` continues to derive solely from `DropdownWidget.render()`'s returned height, now correctly reflecting the label row when present and never the open-state rows.
- v1.5-FR7.18: no inline per-row description text remains anywhere in `FriendSidebarWidget`'s own rendering; `joinPolicyDescription(...)` text still flows into `DropdownWidget.Option.description` unchanged.
- v1.5-FR7.19: `FriendSidebarWidget` exposes `renderDropdownOverlay(...)`, forwarding to `DropdownWidget.renderOpenOverlay(...)` when open, no-op otherwise; the existing `joinPolicyDropdown.render(...)` call site now only draws the closed row/label.
- v1.5-FR7.20: `FriendsSidebarZOrder` gains `DROPDOWN_OVERLAY` between `SIDEBAR` and `CONTEXT_MENU`, with Javadoc explicitly describing the two as equal topmost tier; each platform's injector (using the correct per-module hook name, per Risk 2) gains exactly one new guarded call to `renderDropdownOverlay(...)`, positioned between the existing `activeSidebar.renderNow(...)` and `openMenu.renderNow(...)` calls.
- Manual in-game verification (Test Strategy, above) passes on all three platform modules, with particular attention to the open-state overlay never being clipped/covered by the friend-row list.
