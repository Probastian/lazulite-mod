## v1.7 Amendment — Keep sidebar expanded while a context menu or dropdown is open

### Overview
Today, `FriendSidebarWidget.renderNow(...)` (all three platform modules: `fabric-1.21.11`, `fabric-26.1`, `fabric-26.2`) collapses the sidebar back to its collapsed/handle footprint a short "coyote time" grace period after the mouse stops satisfying `FriendSidebarStateMachine.isExpanded(...)` (`features/friends-sidebar/src/main/java/de/lazuli/features/friendssidebar/services/FriendSidebarStateMachine.java:36-39`), regardless of whether a friend row's right-click context menu (`FriendContextMenuWidget`) or the join-policy dropdown (`DropdownWidget`, via `FriendSidebarWidget.joinPolicyDropdown`) is currently open. Both of those overlays can render/be interacted with outside the sidebar's own hover-bounds footprint (the context menu is explicitly positioned "opening below-left of the cursor," `FabricFriendsSidebarInjector.java:197-201`; the dropdown's open-state option list, per the in-flight v1.5 polish work, now draws in a separate `DROPDOWN_OVERLAY` pass and is only bounded by the sidebar's own width, not guaranteed to stay within the collapsed/expanded hover-test rectangle at every row count/animation frame). Moving the mouse onto either overlay is enough to let the coyote timer expire and collapse the sidebar out from under the very menu/dropdown the user is interacting with.

This amendment fixes that: the sidebar must not collapse while a context menu or the join-policy dropdown is open, resuming normal hover-driven collapse behavior only once that menu/dropdown is dismissed.

**Relationship to the in-flight v1.5 "DropdownWidget polish" work** (`features/friends-sidebar/implementation-plan-dropdown-polish.md`, uncommitted as of this writing per `git status`: `api/friends/FriendsSidebarZOrder.java`, all three platforms' `FabricFriendsSidebarInjector.java`/`FriendSidebarWidget.java`/`DropdownWidget.java`): that work is what introduces the separate `DROPDOWN_OVERLAY` render pass and `renderDropdownOverlay(...)`/`joinPolicyDropdown.isOpen()` surface this amendment depends on and reuses (see Requirements, Public API below). **This amendment must land after the v1.5 polish work is committed**, not before and not interleaved with it — it reads/depends on the post-polish shape of `FriendSidebarWidget.java` (`renderNow`'s current coyote-time block at lines 330-347, `joinPolicyDropdown.isOpen()` already present at line 458) and `FabricFriendsSidebarInjector.java` (the `openMenu`/`openMenuScreen` fields and `closeMenu()`/`onBeforeMouseClick` dismissal logic, lines 56-57, 195-222). All file/line references below are against the current uncommitted working tree (i.e. the post-v1.5-polish shape), confirmed via `git diff`/`git status` at time of writing; re-verify against HEAD before implementation in case v1.5 lands with further changes first. This amendment does **not** touch `DropdownWidget.java`'s render-split/chrome/tooltip work, `FriendsSidebarZOrder`'s ordinal values, or any UI-FR8-UI-FR18 requirement from `platform/ui/specification.md` v2 — it only adds a new "stay expanded" input to the existing hover/coyote state machine.

This amendment is unrelated to, and does not touch any file touched by, the separately in-flight "Invite to Game" feature (`specification-invite-to-game.md`, already implemented per recent commits) or the "status recolor + In Game tier" spec (`specification-status-recolor-ingame.md`, still in spec phase, touches `FriendSidebarStateMachine.statusColorArgb`/`statusLabel`/`FriendSummary`/`FriendsService` — no overlap with this amendment's `isExpanded`/coyote-time/menu-tracking surface).

### Goals
- The sidebar (`expanded` state in `FriendSidebarWidget`) must never collapse while the friend-row context menu (`FriendContextMenuWidget`) is open, on any of the three platform modules.
- The sidebar must never collapse while the join-policy dropdown (`DropdownWidget`/`joinPolicyDropdown`) is open, on any of the three platform modules.
- Once the context menu is dismissed (any existing dismissal path: outside click, Escape, opening a different friend's menu, selecting an action that closes it) or the dropdown is dismissed (outside click, selecting an option, Steam becoming unavailable), normal hover/coyote-time collapse behavior resumes immediately (no special extra grace period beyond the existing coyote time).
- A single, reusable notion of "an overlay that should suppress collapse is open" that both the context menu and the dropdown feed into, so a future third overlay (if any) has an obvious place to plug in.

### Non-goals
- No change to the coyote-time duration (`COYOTE_NANOS = 250_000_000L`), the hover-bounds test itself (`FriendSidebarStateMachine.isExpanded`'s signature/logic), the handle-open-on-hover behavior, or the width-animation logic (`animatedWidth`/`moveTowards`) — this amendment only adds one more condition that counts as "hovering" for the purposes of resetting `lastHoverNanos`/skipping collapse.
- No change to where or how the context menu or dropdown themselves render, their own click-outside/Escape dismissal logic, or `DropdownWidget`'s internal open/close state — this amendment only *reads* that existing/soon-to-exist open state, it does not change how it is set.
- No change to `FriendsSidebarZOrder`, `DROPDOWN_OVERLAY`, or any v1.5-polish-specific render-split detail.
- No new persisted config, no new user-facing setting to disable this behavior.
- Does not address the (separate, already-acceptable-per-spec) case of the mouse being simply *inactive* over the menu/dropdown with no collapse concern today when the sidebar itself is still hovered — this amendment is specifically about the case where the mouse has left the sidebar's own footprint while an overlay it opened is still open.

### Requirements

**Root cause (precise):**
- FR1. `FriendSidebarStateMachine.isExpanded(...)` (`FriendSidebarStateMachine.java:36-39`) is, and must remain, a pure hover-bounds check with no knowledge of menus/dropdowns — it is not the fix point.
- FR2. The actual collapse decision is made per-platform in `FriendSidebarWidget.renderNow(...)`'s coyote-time block (`fabric-26.2` lines 330-347, structurally identical on `fabric-26.1` and `fabric-1.21.11`): `boolean hovering = overPanel || overHandle;` followed by `if (hovering) { lastHoverNanos = now; }` and, once `(now - lastHoverNanos) >= COYOTE_NANOS`, `expanded = false` (and `panelOpen = false` when `handleOnly`). Neither `overPanel` nor `overHandle` accounts for an open context menu or dropdown, so `hovering` can go and stay `false` while either overlay is open and the mouse is on it (or anywhere off the sidebar's own footprint), and after `COYOTE_NANOS` the sidebar collapses out from under the open overlay.
- FR3. The join-policy dropdown's open/closed state is already tracked, per-instance, inside `FriendSidebarWidget` itself via `joinPolicyDropdown.isOpen()` (confirmed live use at `FriendSidebarWidget.java:458`, part of the in-flight v1.5 polish work) — this is directly reusable with no new field needed on `FriendSidebarWidget`.
- FR4. The context menu's open/closed state, by contrast, is **not** known to `FriendSidebarWidget` at all today — it is tracked one level up, in `FabricFriendsSidebarInjector` (`openMenu`/`openMenuScreen` fields, `FabricFriendsSidebarInjector.java:56-57`), which constructs `FriendSidebarWidget` and separately constructs/tracks `FriendContextMenuWidget` instances via `openContextMenu(...)`/`closeMenu()` (lines 195-216). `FriendSidebarWidget` has no visibility into whether the menu it caused to open (via the `friend, mouseX, mouseY, button, isOwnProfile -> openContextMenu(...)` callback passed into its constructor, line 114-116) is still open. This is the one piece of genuinely new state/plumbing this amendment requires.

**Desired behavior:**
- FR5. While `joinPolicyDropdown.isOpen()` is `true`, `FriendSidebarWidget.renderNow(...)`'s `hovering` computation must additionally be considered `true` regardless of `overPanel`/`overHandle` — i.e. `lastHoverNanos` keeps resetting every frame, so the coyote timer never expires and `expanded` never flips to `false`, for as long as the dropdown stays open.
- FR6. While the context menu associated with this sidebar is open (see FR7/FR8 for how that's communicated), the same must hold: `hovering` is forced `true`, coyote timer never expires, `expanded` stays `true`.
- FR7. `FabricFriendsSidebarInjector` must inform the currently-active `FriendSidebarWidget` (`activeSidebar`) whenever the context menu it manages opens or closes, so `FriendSidebarWidget.renderNow(...)` can fold that into its own `hovering` computation on every frame — see Public API for the concrete shape.
- FR8. The mechanism must be robust to a context menu opening for **any** friend row (own-profile or any friend), not just a specific one — the sidebar cares only about "is *a* context menu currently open that this sidebar caused to open," not which friend it's for.
- FR9. When both the dropdown and the context menu happen to close in the same frame the mouse is also off the sidebar's footprint, normal coyote-time collapse resumes exactly as it does today when hover is simply lost — no new grace period is added on top of the existing `COYOTE_NANOS`.
- FR10. This behavior must be implemented identically (same field/method shape, same logic) across all three platform modules (`fabric-1.21.11`, `fabric-26.1`, `fabric-26.2`), consistent with this repo's established structural-twin convention for these files.

**Edge cases (explicit):**
- FR11. Menu dismissed (any path: outside click, Escape, selecting an action) while the mouse is still off the sidebar's own hover bounds: the very next frame after dismissal, `hovering` reverts to being driven solely by `overPanel`/`overHandle` again; since the mouse is off-bounds, `lastHoverNanos` stops refreshing from that frame onward and the existing coyote timer (unchanged duration) begins counting down toward collapse from that point — i.e. the user gets exactly one more coyote-time window after dismissal before it collapses, same as today's ordinary "moved mouse away" behavior, no more and no less.
- FR12. Menu dismissed while the mouse is back over the sidebar's own hover bounds: `overPanel` is already `true` that frame, so `hovering` is `true` via the pre-existing path regardless of this amendment — no special handling needed, sidebar simply stays expanded.
- FR13. Switching from context menu to dropdown or vice versa without ever re-entering the sidebar's hover bounds in between (e.g. user right-clicks a friend row to open the context menu, then somehow triggers the dropdown to open while the context menu is still up, or dismisses the context menu and immediately opens the dropdown): since FR5/FR6 are independent `||`-combined conditions (not a single toggle), the sidebar stays expanded continuously as long as *either* is `true` at any given frame, with no gap even during a one-frame transition where both happen to be true or where one becomes false right as the other becomes true. (In practice the context menu and dropdown are already mutually exclusive at runtime per the v1.5 polish plan's own Compatibility rationale, but this amendment's logic does not depend on that assumption — it degrades gracefully either way.)
- FR14. Multiple friend rows: opening a context menu for a different friend row (while one is already open) goes through the existing `openContextMenu(...)` -> `closeMenu()` -> reconstruct flow (`FabricFriendsSidebarInjector.java:195-196`, `closeMenu()` called unconditionally at the top of `openContextMenu`), so from this amendment's perspective it is a continuous "menu open" state with no false collapse-triggering gap between the old menu closing and the new one opening (both happen synchronously within the same click handler, same frame).
- FR15. Screen changes while a menu/dropdown is open (e.g. the allow-listed screen the sidebar is attached to closes/changes, per `onScreenInit`'s existing widget-removal logic, `FabricFriendsSidebarInjector.java:106-108`): out of scope beyond noting that the existing `activeSidebarScreen`/`openMenuScreen` guards already prevent any stale cross-screen interaction; this amendment adds no new cross-screen state.
- FR16. Steam becoming unavailable mid-open (`!steamAvailable` branch, `FriendSidebarWidget.java:392-393`, which already force-calls `joinPolicyDropdown.close()`): once closed, `joinPolicyDropdown.isOpen()` correctly returns `false` again that same frame, so this amendment's FR5 condition naturally stops forcing `hovering = true` from that point on — no additional handling needed, this existing force-close path is sufficient.

### Public API
1. `FriendSidebarWidget` (all three platform modules) — new public method: `void notifyContextMenuOpenChanged(boolean open)`. Called by `FabricFriendsSidebarInjector` whenever it opens or closes the context menu associated with this sidebar's screen (FR7). Stores the value in a new private field (e.g. `private boolean contextMenuOpen;`) read by `renderNow(...)`'s `hovering` computation (FR6). No other public surface change on `FriendSidebarWidget`.
2. `FriendSidebarWidget.renderNow(...)` — unchanged signature; internal `hovering` computation changes from `boolean hovering = overPanel || overHandle;` to `boolean hovering = overPanel || overHandle || contextMenuOpen || joinPolicyDropdown.isOpen();` (exact boolean composition; planning may choose a differently-named local/helper, but the four-way `||` semantics per FR5/FR6/FR13 must hold).
3. `FabricFriendsSidebarInjector` (all three platform modules) — no new public method (it has none today); internal `openContextMenu(...)` and `closeMenu()` are each updated to call `activeSidebar.notifyContextMenuOpenChanged(true)` / `activeSidebar.notifyContextMenuOpenChanged(false)` respectively (guarded by `activeSidebar != null`, matching this class's existing null-guard convention elsewhere, e.g. line 154/157). No change to `openMenu`/`openMenuScreen`/`activeSidebar`/`activeSidebarScreen` field semantics.
4. No change to `FriendSidebarStateMachine`'s public surface (`isExpanded(...)` stays a pure hover-bounds check per FR1/Non-goals) — this amendment's logic lives entirely in `FriendSidebarWidget`/`FabricFriendsSidebarInjector`, not in the plain-JVM-testable services layer.

### Architecture
No new classes, packages, or cross-module edges. Confined entirely to the existing Platform-module pair (`FriendSidebarWidget` + `FabricFriendsSidebarInjector`, one copy of each per platform module) that already collaborate via the constructor-supplied context-menu-open callback (`FriendSidebarWidget.java:114-116`) — this amendment adds the missing *reverse* direction of that same collaboration (injector -> widget, "menu is open/closed now") alongside the existing widget -> injector direction ("please open a menu for this friend"). `FriendSidebarStateMachine` (the `services` layer, plain-JVM-testable, `features/friends-sidebar`) is untouched — this is deliberately a Platform-only fix since the state it depends on (`FriendContextMenuWidget`/`DropdownWidget` open/closed) is itself Platform-only state with no plain-JVM equivalent.

### UI
- No new visible UI element. The only observable behavior change: the sidebar visibly stays in its expanded (not collapsed/handle) footprint while a context menu or the join-policy dropdown is open and the mouse is off the sidebar's own hover bounds — where today it would shrink back after the coyote-time grace period.
- Once the menu/dropdown closes, the sidebar's existing hover-driven collapse animation (unchanged `WIDTH_ANIM_PX_PER_SECOND` easing) resumes normally.

### Configuration
None. No new persisted field, no new user-facing toggle.

### Events
No new Fabric/Screen event registration. This amendment only adds two new call sites (`notifyContextMenuOpenChanged(true/false)`) into `FabricFriendsSidebarInjector`'s **existing** `openContextMenu(...)`/`closeMenu()` methods — it does not hook any additional `ScreenEvents`/`ScreenMouseEvents`/`ScreenKeyboardEvents` registration beyond what's already wired for context-menu dismissal (`onBeforeMouseClick`, `onAllowKeyPress`'s Escape handling, both already call `closeMenu()` today, `FabricFriendsSidebarInjector.java:218-222`, `224-230`).

### Networking
None. Purely client-local render-loop state.

### Persistence
None. `contextMenuOpen` (new field) and `joinPolicyDropdown.isOpen()` (existing) are both per-frame, non-persisted, in-memory state, exactly like every other field `renderNow(...)` already reads (`expanded`, `panelOpen`, `lastHoverNanos`, `animatedWidth`).

### Compatibility
- Same three-platform-module structural-twin requirement already established by every prior amendment in this directory (v1.4/v1.5 Compatibility sections) — FR5-FR10/Public API items 1-3 must land identically across `platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`.
- **Sequencing dependency (hard requirement, not just a suggestion):** this amendment must be implemented and merged **after** the in-flight v1.5 "DropdownWidget polish" work (`implementation-plan-dropdown-polish.md`) is committed, since it depends on that work's `joinPolicyDropdown.isOpen()` call site already existing at the location cited in FR3/Requirements. Attempting to implement this amendment concurrently with or before that work risks either merge conflicts in the same `renderNow(...)` method body (the coyote-time block, `FriendSidebarWidget.java:330-347`, sits a few lines above the v1.5 polish's own `dropdownVisible`/`joinPolicyDropdown.render(...)` edits at lines 400-425) or building against a pre-polish shape of the file that no longer matches HEAD by the time this amendment lands.
- `FriendSidebarWidget.java` and `FabricFriendsSidebarInjector.java` are confirmed (this session's `git status`) to be actively-evolving, shared files with in-flight, unrelated (well, sequenced-dependent, per above) changes — re-run `git status`/`git diff` immediately before editing either, per this repo's own established discipline (see the dropdown-polish plan's own Compatibility/Risks notes), and confirm no line-number drift from what's cited here before making these edits.
- No change to any existing public method signature (`isExpanded`, `renderNow`, `mouseClicked`, etc.) — only one new method added (`notifyContextMenuOpenChanged`) and one new private field (`contextMenuOpen`) per platform's `FriendSidebarWidget`. Fully additive; no existing caller of any touched class needs updating beyond the two new call sites inside `FabricFriendsSidebarInjector` itself.
- No existing automated test covers this path (`FriendSidebarStateMachineTest` tests `isExpanded`'s pure hover-bounds logic only, unchanged by this amendment, per FR1/Non-goals) — this remains a manual, per-platform in-game verification concern, consistent with this repo's established convention for all `FriendSidebarWidget`/injector rendering-and-input logic (no `net.minecraft.*`-free unit test is feasible for `FabricFriendsSidebarInjector`'s Fabric-Screen-API-coupled callback wiring).

### Performance
Negligible. One additional boolean field read (`contextMenuOpen`) and one already-existing method call (`joinPolicyDropdown.isOpen()`, already invoked elsewhere in the same method today) added to an existing per-frame boolean expression — no additional allocation, no additional per-friend/per-row cost.

### Future Extensions
- If a future overlay type is added to the sidebar beyond the context menu and join-policy dropdown, the same pattern (an explicit "is this overlay open" boolean, `||`-folded into `renderNow(...)`'s `hovering` computation) is the established extension point — no refactor to a more general "overlay stack" is proposed here, since exactly two overlay types exist today and a third is speculative.
- Should the context-menu-open/closed notification prove useful for something beyond collapse-suppression in the future (e.g. suppressing the coyote-time-driven `panelOpen` reset for handle-only mode too, which this amendment does not separately address since `panelOpen = false` only happens inside the `coyoteExpired` branch that this amendment's `hovering` fix already prevents from being entered), no new mechanism should be needed — `contextMenuOpen`/`joinPolicyDropdown.isOpen()` already gate that same branch.
