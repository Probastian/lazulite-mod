## Risks
1. **`FriendSummary` constructor arity change is source-breaking at every construction call site.** Confirmed exactly two call sites in the whole repo (`FriendsService.resolveFriend` line 119-120, `FriendsService.localProfile` line 147) plus zero in `NoopFriendsService` (verified by full-file read — it never constructs one). Both must be updated in the same change or the `features/friends-sidebar` module fails to compile. No other module constructs a `FriendSummary` (confirmed by targeted reads of `FriendsService.java`/`NoopFriendsService.java`; the three platform widgets only read accessors, never construct).
2. **`statusSortRank`'s new overload must not simply delegate with `+1`.** FR-I3's mapping is not a uniform shift of the bare-`int` overload's output (`0,1,2,3` -> `1,2,3,4`) plus a new `0` for in-game — it happens to be exactly that in this specific case, but implementing it as `inGame ? 0 : statusSortRank(personaState) + 1` is fragile if the bare overload's ranks ever change independently later (they're documented as intentionally decoupled elsewhere in this class). This plan specifies an explicit standalone `switch` (see Files to Modify, item 6) to avoid relying on that coincidental arithmetic relationship — flagging so implementation doesn't take the shorter-looking but more fragile shortcut.
3. **Platform `FriendSidebarWidget.java` is an actively-evolving, shared file with in-flight, unrelated changes** (dropdown-polish work, confirmed via git status: all three copies show as modified in the working tree). Re-run `git status`/`git diff` immediately before editing each of the three files and confirm the specific line numbers cited in this plan (`drawRow`, `personaColor`, the status-label ternary) haven't drifted, before making the FR-P1/FR-P2/FR-P3 edits — same discipline the dropdown-polish plan itself establishes for this file.
4. **Existing widget behavior for the in-game label is being *moved*, not newly added.** The three widgets already implement the exact FR-L1/FR-L2/FR-L3 fallback order inline today (`friend.inGame() ? "In Game" : statusLabel(personaState)`), a fact the spec's own "Existing Implementation"-adjacent Non-goals section did not call out explicitly (it frames Rich-Presence-first labeling as "already implemented" but does not mention the in-game ternary specifically). This plan's FR-P2 step is therefore a refactor (extract-method into the state machine) rather than new behavior — the risk is an implementer mistakenly treating this as net-new logic and introducing a subtly different fallback order (e.g. swapping the ternary branches) during the extraction; mitigated by this plan spelling out the exact before/after call-site text.
5. **Recolor does not break any existing test assertion (confirmed, narrower than the dropdown-polish plan's generic warning about this test file).** `FriendSidebarStateMachineTest` only asserts grouping/alpha/non-null properties for the bare-`int` overloads, never a hardcoded hex literal for the recolored branches — verified via direct read/grep of the test file. No test update is strictly required for FR-R1/FR-R2 to keep passing, though new tests are still expected for the new overloads per Test Strategy below.
6. **`SteamworksSteamFriendsGateway`'s three near-identical `getFriendGamePlayed` call sites (`friendInGame`, `friendGameConnectHint`, new `friendGameAppId`) remain independent, unconsolidated.** This is an explicit spec decision (FR-G2/Future Extensions), not an oversight — flagged only so implementation doesn't "improve" this into a shared private helper unprompted, which would be a scope-creep change beyond this amendment's stated minimal-diff intent.
