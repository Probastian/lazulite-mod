## v1.6 Amendment — Status-color recolor + "In Game" tier

### Overview
This amendment changes the friends sidebar's persona-state status-color palette and introduces a new, cross-cutting "In Game" status tier that outranks a friend's raw `SteamFriends.PersonaState`. It also reconciles a duplicated, cruder avatar-placeholder color helper (`personaColor(FriendSummary)`) present in all three platform copies of `FriendSidebarWidget.java` with the richer color logic already centralized in `FriendSidebarStateMachine`.

This is filed as a v1.6 amendment to `features/friends-sidebar/specification.md`, following the existing convention in this directory (see the v1.5 amendment in that file, and the standalone `specification-invite-to-game.md` precedent for a topically-scoped file living alongside the main spec). It does not touch, and is not touched by, the in-flight v1.5 "DropdownWidget polish" work described in `features/friends-sidebar/implementation-plan-dropdown-polish.md` (that work is confined to `DropdownWidget.java`/the join-policy control/`FriendsSidebarZOrder`; this amendment touches `FriendSidebarStateMachine.java`, `FriendSummary.java`, `SteamFriendsGateway`/`SteamworksSteamFriendsGateway`/`NoopSteamFriendsGateway`, `FriendsService.java`, and the status-color/label/placeholder-color call sites in the three `FriendSidebarWidget.java` copies — no file overlap). Verified against the working tree at the time of writing (git status showed `FriendsSidebarZOrder.java`, the three `FabricFriendsSidebarInjector.java`/`FriendSidebarWidget.java`/`DropdownWidget.java` copies as modified, all part of that unrelated in-flight dropdown-polish work) — none of those in-flight diffs touch `statusColorArgb`/`statusLabel`/`statusSortRank`/`personaColor`/`FriendSummary`, so this amendment's line-number references below (current as of this writing) should be re-checked against HEAD at implementation time only for possible drift from that other change landing first, not for any logical conflict.

### Goals
- Recolor the existing persona-state status palette (`FriendSidebarStateMachine.statusColorArgb`) so Online-ish states read as blue and Away/Snooze reads as a greyed-blue, freeing up the old Online green for a new, higher-priority "In Game" tier.
- Add an "In Game" status tier: green, outranking every persona-state color/label/sort-order for any friend currently in a game, regardless of their underlying `PersonaState`.
- Give the in-game label real content when available: prefer the friend's Steam Rich Presence status string (already plumbed, unchanged); otherwise show a generic "In Game" label. (A real "Playing `<game name>`" string is confirmed not achievable in v1.6 — see Non-goals and Networking below — so there is no numeric-App-ID middle tier.)
- Reconcile the three duplicated, cruder `personaColor(FriendSummary)` avatar-placeholder-color helpers (one per platform module) so the placeholder box always matches the same status color the row's own text/dot already uses.

### Non-goals
- No change to `FriendSidebarStateMachine.statusLabel`'s existing plain-persona-state word set ("Online", "Busy", "Away", "Snooze", "Looking to Trade", "Looking to Play", "Invisible", "Offline") — those remain exactly as-is and are still used verbatim whenever a friend is not in-game.
- No change to the existing Rich Presence plumbing (`FriendsDataSource.richPresenceStatus`/`FriendsService.richPresenceById`/`FriendsSidebarFacade.richPresenceStatus`) — it is already implemented, already the highest-priority label source at each `FriendSidebarWidget`'s render call site, and is reused as-is by this amendment (see Requirements, below). This amendment adds a new field to `FriendSummary` and a new gateway accessor, it does not change how Rich Presence text itself is requested/cached/read.
- **No real game-name resolution — decided, not merely deferred.** This was investigated and confirmed not achievable in v1.6: steamworks4j 1.10.0 (this repo's pinned version) exposes no app-ID-to-display-name lookup anywhere in its public surface. This was independently re-verified directly against the pinned `steamworks4j-1.10.0` jar via `javap` (not just against upstream source) — `SteamFriends`, `SteamApps`, and `SteamUtils` have no such method, and `ISteamApps`/`ISteamAppList`'s native app-metadata queries are not bound in this jar version at all (see Networking, below, for the full verified method inventory). Consequently, the in-game label fallback has exactly two tiers (Rich Presence text, then a generic "In Game" label) — there is no "Playing App `<id>`"/numeric-ID middle tier in this amendment. Real name resolution (a static app-ID-to-name table shipped with the mod, a Steam Web API call, or local `appmanifest_*.acf` parsing) is captured as a Future Extension for a possible later, separately-scoped feature request — explicitly out of scope here.
- No change to `isInviteEnabled`/`isJoinEnabled` (both remain hard-`false` per the existing v1 decision) or to `joinable`/`connectHint` semantics on `FriendSummary`.
- No change to the `DropdownWidget`/join-policy control, `FriendsSidebarZOrder`, or any file exclusively touched by the in-flight dropdown-polish work.
- No change to avatar texture loading/caching itself — this amendment only changes what color the *placeholder* (no-avatar-yet) box uses.

### Requirements

**Color palette (delta over `FriendSidebarStateMachine.statusColorArgb`, current lines 127-134):**
- FR-R1. `Online` (1) / `LookingToTrade` (5) / `LookingToPlay` (6): change from `0xFF5BA32F` (green) to `0xFF4A90D9` (blue).
- FR-R2. `Away` (3) / `Snooze` (4): change from `0xFF4A90D9` (blue) to `0xFF2D5683` (greyed-blue).
- FR-R3. `Busy` (2): unchanged, `0xFFE3A008` (yellow).
- FR-R4. `Offline` (0) / `Invisible` (7): unchanged, `0xFF898989` (grey).
- FR-R5. New "In Game" tier color: `0xFF5BA32F` (the exact green value `Online` previously used).

**"In Game" priority (cross-cutting, not a `personaState` ordinal):**
- FR-I1. A friend is "in-game" for the purposes of this amendment iff `FriendSummary.inGame()` is `true`. This flag's own resolution (`SteamFriendsGateway.friendInGame`/`getFriendGamePlayed`) is unchanged.
- FR-I2. `statusColorArgb` gains an in-game-aware entry point that returns `0xFF5BA32F` whenever `inGame` is `true`, **regardless of `personaState`** — this takes priority over every case in FR-R1 through FR-R4. The existing `statusColorArgb(int personaState)` overload is retained unchanged (still used wherever only a bare ordinal is available, e.g. any existing call site not yet touched by this amendment) but every call site that also has a `FriendSummary`/`inGame` value available must switch to the new in-game-aware overload (Public API, below).
- FR-I3. `statusSortRank` gains the same priority rule: an in-game friend sorts into a new rank `0` (ahead of the existing `Online`-tier rank `0`), i.e. the existing four ranks (`0` online-ish, `1` away/snooze, `2` busy, `3` offline) all shift down by one when in-game is not the case, and in-game friends occupy the new top rank `0`. Concretely: `inGame == true` -> rank `0`; else `personaState` 1/5/6 -> rank `1`; else 3/4 -> rank `2`; else 2 -> rank `3`; else -> rank `4`. (Ties within the in-game rank are still broken alphabetically by `sortForDisplay`, unchanged.)
- FR-I4. `statusLabel` gains the same priority rule via a new in-game-aware overload: when `inGame` is `true`, it returns the in-game label per the fallback order in FR-L1/FR-L2 below **instead of** the plain persona-state word, regardless of `personaState`. The existing bare-`int` `statusLabel(int personaState)` overload is retained unchanged for any call site that has no `FriendSummary`/Rich-Presence context.
- FR-I5. `sortForDisplay` is updated to call the new in-game-aware `statusSortRank` overload (passing each `FriendSummary`'s own `inGame()`), so friend-list ordering reflects FR-I3 automatically; no caller-visible signature change (still `List<FriendSummary> sortForDisplay(List<FriendSummary>)`).

**In-game label fallback order** (two tiers, evaluated in this exact order; matches the existing Rich-Presence-first pattern already live at each `FriendSidebarWidget` render call site, `FriendSidebarWidget.java:560-561` on `fabric-26.2`, mirrored on the other two platforms) — **decided (see Non-goals): no numeric App-ID tier.**
- FR-L1. If `FriendsDataSource.richPresenceStatus(steamId64)` returns a non-empty value (existing mechanism, unchanged), use it verbatim. This is unconditional on `inGame` today (the existing code already prefers it over everything) and remains so — a friend can in principle have a Rich-Presence "status" string set without `inGame` being true (e.g. a game that sets Rich Presence but whose `GetFriendGamePlayed` semantics didn't register it as "playing" — steamworks4j's own doc does not guarantee the two are perfectly correlated); this amendment does not change that existing precedence, it only changes what happens in tier 2 below, which is new.
- FR-L2. Else, if `inGame` is `true`, use a generic fallback string, `"In Game"`. (No numeric App-ID tier — a human game title is not resolvable at all in v1.6, and a bare numeric ID was judged not worth showing to the user; see Non-goals/Future Extensions.)
- FR-L3. Else (`inGame` is `false`), fall back to the existing plain persona-state word (`statusLabel(personaState)`, unchanged, FR1.8/FR4.8).

**`FriendSummary` data-plumbing delta:**
- FR-D1. `FriendSummary` (`api/src/main/java/de/lazuli/api/friends/FriendSummary.java`) gains one new component: `long gameAppId` — the numeric Steam App ID the friend is currently playing, or `0` if not in a game / unresolved. Placed immediately after the existing `boolean inGame` component (record component order: `steamId64, personaName, personaState, avatarHandle, inGame, gameAppId, joinable, connectHint`). This is an additive, source-incompatible-only-at-the-constructor-call-site change (a Java record's canonical constructor gains one parameter) — every existing construction call site must be updated (two in `FriendsService.java`: `resolveFriend` and `localProfile`; one in `NoopFriendsService.java` if it constructs any `FriendSummary` directly — verify at implementation time).
  - **Rationale (confirmed, not tied to the removed numeric-label fallback):** `gameAppId` is *not* needed by, and is not read by, `statusLabel`/`statusColorArgb`/`statusSortRank` in this amendment — the two-tier label fallback (FR-L1/FR-L2) and the in-game color/sort rank (FR-I2/FR-I3) depend only on `inGame`, never on `gameAppId`. It is not used as a sort tie-breaker either (ties are broken alphabetically by persona name, unchanged). The field is kept solely because `SteamFriendsGateway.friendGameAppId` (FR-G1) already resolves it as a side effect of the existing `getFriendGamePlayed` call (no extra API cost to capture it, see Performance), and because plumbing it into `FriendSummary` now makes the Future Extensions name-resolution work (see below) a small, additive change later — only `statusLabel` would need to change, not any data-plumbing. If this reasoning changes at implementation time (e.g. gateway/service wiring is judged not worth the extra field yet), dropping `gameAppId` from `FriendSummary` entirely and inlining the app-ID read only where `SteamFriendsGateway` needs it is an acceptable alternative; this spec's default is to keep it for the forward-compatibility reason stated above.
- FR-D2. `localProfile()`'s constructed `FriendSummary` always passes `gameAppId = 0L` (the own-profile row never shows an in-game tier, matching its existing `inGame = false`/`joinable = false` convention, FR1.6).

**`SteamFriendsGateway` delta:**
- FR-G1. `SteamFriendsGateway` (`services/src/main/java/de/lazuli/services/steamworks/SteamFriendsGateway.java`) gains one new method: `long friendGameAppId(long steamId64)` — returns the friend's current `FriendGameInfo.getGameID()` value if `getFriendGamePlayed` returns `true`, else `0L`. Never throws (same fail-closed convention as every other method on this interface).
- FR-G2. `SteamworksSteamFriendsGateway` implements FR-G1 by calling `steamFriends.getFriendGamePlayed(SteamID.createFromNativeHandle(steamId64), info)` (the same call `friendInGame`/`friendGameConnectHint` already make, each with their own local `FriendGameInfo` instance — this amendment does not consolidate those three call sites into one, to keep the change minimal and each method independently fail-closed; a future refactor could combine them, out of scope here) and, if `true`, returning `info.getGameID()`, else `0L`.
- FR-G3. `NoopSteamFriendsGateway.friendGameAppId` returns `0L` unconditionally (matching this class's existing all-zero/all-empty convention).

**`FriendsService` delta:**
- FR-S1. `resolveFriend(long steamId64)` (`FriendsService.java:97-124`) additionally calls `gateway.friendGameAppId(steamId64)` and passes the result as the new `gameAppId` argument when constructing the `FriendSummary` (alongside the existing `inGame`/`connectHint`/`joinable` computation, which is otherwise unchanged).

**Platform `FriendSidebarWidget.java` delta (all three modules, structurally identical change):**
- FR-P1. The existing `int statusColor = facade.stateMachine().statusColorArgb(friend.personaState());` call site is updated to pass `friend.inGame()` as well, using the new in-game-aware overload (FR-I2).
- FR-P2. The existing status-label call site (`FriendSidebarWidget.java:560-561` on `fabric-26.2`, mirrored on the other two) is updated to match the new fallback order (FR-L1/FR-L2/FR-L3) exactly: `facade.richPresenceStatus(friend.steamId64()).orElseGet(() -> facade.stateMachine().statusLabel(friend.personaState(), friend.inGame()))` (or equivalent — exact lambda shape is planning/implementation discretion, but the two-tier fallback order inside the state machine, not the widget, must be FR-L2/FR-L3, so all three platforms share one implementation of "what does the in-game label say," not three copies).
- FR-P3. The duplicated `personaColor(FriendSummary)` helper (`FriendSidebarWidget.java:567-571` on `fabric-26.2`, mirrored on the other two, current body: `friend.personaState() == 0 ? 0xFF808080 : 0xFF33AA33`) is **removed** and every call site that used it (the avatar-placeholder-box fill, `FriendSidebarWidget.java:554`) is updated to call `facade.stateMachine().statusColorArgb(friend.personaState(), friend.inGame())` instead — i.e. reuse the exact same color the row's status dot/text already uses (FR-P1), rather than maintaining a second, cruder color mapping. This is the specific reconciliation direction for Goal 4: not "keep `personaColor` as a separate simplified mapping," but "delete it and point its one call site at the shared, richer logic."

### Public API
1. `FriendSidebarStateMachine#statusColorArgb(int personaState, boolean inGame)` — new overload; returns `0xFF5BA32F` if `inGame`, else delegates to the existing per-`personaState` logic (FR-R1-FR-R4). The existing `statusColorArgb(int personaState)` overload is retained, unchanged in behavior (recolored per FR-R1/FR-R2, but still ignorant of `inGame`).
2. `FriendSidebarStateMachine#statusSortRank(int personaState, boolean inGame)` — new overload implementing FR-I3. The existing `statusSortRank(int personaState)` overload is retained unchanged (still usable by any caller without an `inGame` value, though `sortForDisplay` itself switches to the new overload per FR-I5).
3. `FriendSidebarStateMachine#statusLabel(int personaState, boolean inGame)` — new overload implementing FR-I4/FR-L2/FR-L3 (does **not** itself consult Rich Presence — that remains the caller's own first-tier check per FR-L1, exactly as today). Takes no `gameAppId` parameter — there is no numeric-ID tier (decided, see Non-goals). The existing `statusLabel(int personaState)` overload is retained unchanged.
4. `FriendSidebarStateMachine#sortForDisplay(List<FriendSummary>)` — unchanged signature; internal comparator now keys on `statusSortRank(f.personaState(), f.inGame())` (FR-I5).
5. `FriendSummary` — record gains new component `long gameAppId` (FR-D1), inserted after `inGame`, before `joinable`. New canonical-constructor arity: `(long steamId64, String personaName, int personaState, int avatarHandle, boolean inGame, long gameAppId, boolean joinable, String connectHint)`. Kept for forward-compatibility (Future Extensions), not consulted by any label/color/sort logic in this amendment (see FR-D1 rationale).
6. `SteamFriendsGateway#friendGameAppId(long steamId64) -> long` — new method (FR-G1), implemented on both `SteamworksSteamFriendsGateway` (FR-G2) and `NoopSteamFriendsGateway` (FR-G3).
7. Platform `FriendSidebarWidget` (all three modules) — updated call sites only (FR-P1/FR-P2/FR-P3); no new public method. `personaColor(FriendSummary)` (currently `private static`) is deleted.

### Architecture
No new classes, packages, or cross-module edges. This is an additive-field/additive-overload change confined to the existing `api` <-> `services` <-> `features/friends-sidebar` <-> `platform/*` layering already established:
- `api/friends/FriendSummary` gains a field (data-shape change only, no new dependency).
- `services/steamworks/SteamFriendsGateway` + its two implementations gain one method each, following the exact same fail-closed/plain-Java-typed convention every other method on that interface already uses (no new steamworks4j type crosses the interface boundary — `friendGameAppId` returns a plain `long`, matching `FriendGameInfo.getGameID()`'s own plain-`long` return type, so no wrapping/unwrapping is needed).
- `features/friends-sidebar/services/FriendsService` gains one new gateway call inside its existing `resolveFriend` sweep (no new field/state on `FriendsService` itself beyond what it already passes into `FriendSummary`).
- `features/friends-sidebar/services/FriendSidebarStateMachine` gains three new overloads, each delegating to (and not duplicating) the corresponding existing bare-`personaState` overload — plain-JVM-testable, zero `net.minecraft.*`/steamworks4j import, consistent with this class's existing NFR1 constraint (see its own class Javadoc).
- Platform `FriendSidebarWidget` (three structurally-identical copies) update three call sites and delete one private helper; no new fields, no new per-platform divergence beyond the pre-existing `GuiGraphicsExtractor`/`DrawContext` idiom split already present.

### UI
- Status dot/text color for any in-game friend renders green (`0xFF5BA32F`) regardless of their underlying persona state (Online/Away/Busy/etc.), both in the main row text (FR-P1) and the avatar-placeholder box (FR-P3) — the two are now guaranteed to match by construction.
- Non-in-game friends render blue for Online/LookingToTrade/LookingToPlay, greyed-blue for Away/Snooze, yellow for Busy, grey for Offline/Invisible (FR-R1-FR-R4) — a straight recolor, no layout/size change.
- Status label text for an in-game friend prefers Rich Presence text (unchanged visual behavior from today), then a generic `"In Game"` label (FR-L1/FR-L2) — never blank, matching the existing "never rendered blank" invariant (FR1.7/FR4.8 comment in `FriendsService.java:116`). There is no numeric App-ID text shown to the user.
- Friend-list ordering: in-game friends sort as a group ahead of Online-ish friends (FR-I3); within that group, alphabetical by persona name (unchanged tie-break rule).
- No change to row height, hover/expand behavior, context menu, or the join-policy dropdown control.

### Configuration
None. No new config field, no persisted value changes.

### Events
None. No new callback/event registration — `friendGameAppId` is resolved via the exact same per-sweep, poll-driven `getFriendGamePlayed` call `friendInGame`/`friendGameConnectHint` already make (no new steamworks4j callback subscription).

### Networking — verified Steamworks4j API facts (steamworks4j 1.10.0, this repo's pinned version, `gradle.properties:47`)
Verified against the actual pinned `steamworks4j-1.10.0` jar directly (via `javap` against the jar's class files, not merely against upstream source), cross-checked against this repo's own existing usage in `SteamworksSteamFriendsGateway.java:150-173` (which already calls every method below) and the upstream steamworks4j GitHub source for the same classes:
- `boolean getFriendGamePlayed(SteamID steamIDFriend, SteamFriends.FriendGameInfo friendGameInfo)` — returns `true` iff the friend is currently in a game; when `true`, populates the caller-supplied, mutable `FriendGameInfo` out-parameter. Returns `false` (and, per this repo's own existing defensive coding at `SteamworksSteamFriendsGateway.java:150-158`, does not guarantee `friendGameInfo`'s fields are left unmodified) when the friend isn't in a game.
- `SteamFriends.FriendGameInfo` fields/getters (verified, upstream source and jar `javap` output agree): `long getGameID()` (the app ID the friend is playing — a raw numeric Steam App ID, **not** a display name), `int getGameIP()`, `short getGamePort()`, `short getQueryPort()`, `SteamID getSteamIDLobby()`. This repo's existing `friendGameConnectHint` already reads `getGameIP()`/`getGamePort()`; this amendment's new `friendGameAppId` is the first call site to read `getGameID()`.
- **No app-name/title resolution exists anywhere in this jar's public surface — confirmed decision basis.** `javap` against the pinned jar confirms `SteamFriends`, `SteamApps`, and `SteamUtils` expose no app-ID-to-display-name method. `SteamApps`'s full method set (verified via `javap` and cross-checked against upstream source): `isSubscribed()`, `isLowViolence()`, `isCybercafe()`, `isVACBanned()`, `getCurrentGameLanguage()`, `getAvailableGameLanguages()`, `isSubscribedApp(int)`, `isDlcInstalled(int)`, `getEarliestPurchaseUnixTime(int)`, `isSubscribedFromFreeWeekend()`, `getDLCCount()`, `installDLC(int)`, `uninstallDLC(int)`, `getAppOwner()`, `getAppBuildId()`, `setDlcContext(int)` — none of these return an app's display name/title given an app ID. Valve's native `ISteamApps`/`ISteamAppList` interfaces do expose app-metadata queries in some SDK versions, but this jar (1.10.0) does not bind `ISteamAppList` at all, and `ISteamApps`'s binding in this jar (per the method list above) omits any name-lookup call. This is the concrete, verified, jar-level basis for this amendment's decided Non-goals entry ruling out a real "Playing `<game name>`" string — this is a hard platform constraint for this dependency version, not a scoping choice.
- `String getFriendRichPresence(SteamID steamIDFriend, String key)` / `void requestFriendRichPresence(SteamID steamIDFriend)` — already in use, unchanged by this amendment (`SteamworksSteamFriendsGateway.java:176-196`, `FriendsService.java:117-123`). Per this repo's own existing comment (`FriendsService.java:113-116`), Rich Presence values are Steam-side cached and only refresh on explicit request per sweep; a friend's Rich Presence "status" key being unset/empty is a normal, common case (not every game sets it), which is exactly why the FR-L2 generic-fallback tier exists.
- Threading/callback considerations: both `getFriendGamePlayed` and `getFriendRichPresence` are synchronous, poll-style calls (no callback registration, no async result) — consistent with every other per-sweep accessor `FriendsService.resolveFriend` already calls in the same method body; `friendGameAppId`'s addition introduces no new threading concern.

### Persistence
None. `gameAppId` is a transient, per-refresh-sweep value (like `inGame`/`connectHint` today) — never written to `FriendsSidebarConfig` or any other persisted store.

### Compatibility
- `FriendSummary` is a public record in `api/`, consumed across the Platform/Feature boundary (its own class Javadoc, `FriendSummary.java:4-9`) — adding a record component is a binary/source-breaking change for every existing construction call site (not for read-only consumers, who gain a new accessor for free). All known construction call sites in this repo (`FriendsService.resolveFriend`, `FriendsService.localProfile`, and `NoopFriendsService` if it constructs one directly — verify at implementation time via a repo-wide search for `new FriendSummary(`) must be updated together, in the same change, or the module will not compile.
- Same three-platform-module structural-twin requirement already established by every prior amendment in this file (v1.4/v1.5 Compatibility sections) — FR-P1/FR-P2/FR-P3 must land identically across `platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`.
- `FriendSidebarWidget.java` is confirmed (git status, this session) to be an actively-evolving, shared file with in-flight, unrelated changes from the dropdown-polish work — re-run `git status`/`git diff` immediately before editing it, per this repo's own established discipline (see the dropdown-polish plan's own Compatibility/Risks notes), and confirm no line-number drift from what's cited here before making the FR-P1/FR-P2/FR-P3 edits.
- The recolor (FR-R1/FR-R2) is a pure visual change with no compatibility impact on any consumer of `statusColorArgb(int)` — the bare-`int` overload's *signature* is unchanged, only its returned color values for two of the four `switch` branches.
- Existing automated tests: `FriendSidebarStateMachineTest` (`features/friends-sidebar/src/test/java/...`) almost certainly asserts today's `statusColorArgb`/`statusSortRank`/`statusLabel` return values for the bare-`int` overloads — implementers must update any assertion pinned to the old `Online = green`/`Away = blue` values (FR-R1/FR-R2) and add new test cases for the three new overloads (FR-I2/FR-I3/FR-I4) and the FR-L1/FR-L2/FR-L3 fallback order. This spec does not enumerate exact test names/assertions (planning/implementation discretion) but flags that the existing recolor **will** break at least one existing assertion if left unupdated.

### Performance
No measurable impact. `friendGameAppId` is one additional synchronous, already-in-flight-pattern call per friend per refresh sweep (same call shape/cost as the existing `friendInGame`/`friendGameConnectHint` calls, each already invoking `getFriendGamePlayed` once per friend per sweep) — the sweep is already rate-limited by `refreshIntervalSeconds` (`FriendsService.tick()`, unchanged). No new per-frame (render-loop) cost: the three new `FriendSidebarStateMachine` overloads are the same O(1) `switch`/ternary work as their existing bare-`int` counterparts.

### Future Extensions
- Real game-name resolution — decided out of scope for this amendment (see Non-goals/Networking: steamworks4j 1.10.0 has no app-ID-to-name API). If requested as a separate, later feature, three concrete approaches were identified and are left for that future scoping pass to choose between:
  1. A static app-ID-to-name table shipped with/updated alongside the mod (no network dependency, but requires maintaining the table).
  2. A Steam Web API call (e.g. `ISteamApps/GetAppList` or the Store API) to resolve names on demand (requires network access and, likely, an API key/rate-limit handling).
  3. Local parsing of the user's own `steamapps/appmanifest_*.acf` files (works offline for games the local user owns, but cannot resolve a friend's game the local user doesn't own).
  `FriendSummary.gameAppId` is added now specifically so that whichever approach is chosen later is a small, additive change (only `statusLabel`'s in-game-label formatting would need to change, not any data-plumbing — see FR-D1 rationale).
- Consolidating the three independent `getFriendGamePlayed` call sites in `SteamworksSteamFriendsGateway` (`friendInGame`, `friendGameConnectHint`, and this amendment's new `friendGameAppId`) into a single per-sweep call whose result is reused for all three — noted as a minor efficiency opportunity in FR-G2, explicitly deferred as out of scope for this amendment to keep the diff minimal and each method's fail-closed behavior independently verifiable.
- Reusing the same in-game-priority pattern (FR-I1-FR-I5) for any other cross-cutting status flag this feature might add in the future (e.g. "recently played together," "in the same lobby") — no such flag exists today; this amendment establishes the precedent (a boolean flag that outranks `personaState` in color/label/sort, expressed as a new overload rather than folding into the `personaState` `switch` itself) for whoever adds the next one.
