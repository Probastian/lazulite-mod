# Friends Sidebar — Feature Specification

## Overview
Adds `features/friends-sidebar`, a persistent overlay showing the player's Steam friends list, visible on every main-menu screen and on the in-game ESC/pause menu (`GameMenuScreen` / `PauseScreen`). Collapsed by default (avatars only), it expands on hover to show names, and every friend row is clickable (either mouse button) to open a small context menu (Open chat, Show profile, Invite to game, Join game). It is the first feature in this repo built directly on `SteamFriends` (`ISteamFriends`) rather than `ISteamRemoteStorage`, and — because it must render identically on many different vanilla screens rather than one specific screen — it is also the first feature whose injection shape is closer to a persistent screen-agnostic layer than a single Pattern-1 widget addition (see Architecture).

Everything below treats concrete Minecraft/steamworks4j class and method names exactly as confident as their citation allows: names confirmed via this repo's own prior `javap`-verified findings (`.claude/context/minecraft.md`'s Known Cross-Version API Differences table) are stated as fact; names sourced only from web documentation/javadoc mirrors (not yet verified against this repo's actual resolved jars) are explicitly flagged **"unconfirmed — verify via `javap` before implementation"**, per this repo's own stated research discipline (`.claude/context/minecraft.md:19-30`, `92-96`).

## Goals
- Render one persistent friends sidebar, present on: `TitleScreen` and every other screen reachable from the main menu while no world/server session is active (e.g. `SelectWorldScreen`, `MultiplayerScreen`, `RealmsMainScreen`, `OptionsScreen`, and any other screen shown before a game session starts), and on the in-game pause menu (`GameMenuScreen` (Yarn) / `PauseScreen` (Mojang)).
- Default state: collapsed, showing only each friend's avatar image (smallest/32px Steam avatar), stacked vertically.
- Hover state: hovering anywhere on the collapsed sidebar expands the **whole sidebar** (not per-row) to show every friend's persona name next to their avatar.
- Every rendered friend row responds to both left-click and right-click by opening one context menu, positioned at the current mouse cursor location, with exactly four options: **Open chat**, **Show profile**, **Invite to game**, **Join game**.
- Populate the sidebar from `SteamFriends`'s live friend list (Steam-account friends, matching the flag scope decided in Requirements), refreshed periodically rather than once at startup, since presence/online-status/joinability change during a session.
- Keep all business logic (which friends to show, row layout/ordering, context-menu option availability given a friend's current state, hover/expand state machine) unit-testable on a plain JVM wherever this repo's own precedent shows it is feasible (`philosophy.md:9`; `features/steam-cloud-sync/specification.md:14`) — the concrete Steam/Minecraft calls stay confined to `services`/`platform` per the Dependency Rules.

## Non-goals
- Full in-game chat window/conversation UI behind "Open chat" — v1 opens Steam's own overlay chat dialog for that friend (`ISteamFriends::ActivateGameOverlayToUser(steamID, "chat")`) rather than building a native in-mod chat UI. A custom in-mod chat window is a Future Extension.
- A custom in-mod profile viewer behind "Show profile" — v1 opens Steam's own overlay profile dialog (`ActivateGameOverlayToUser(steamID, "steamid")`) rather than rendering profile data (bio, level, games) inside a Minecraft screen.
- Friend-list management (add/remove/block friends) — Steam's own overlay already owns this; this feature is read-only against the friends list.
- Voice chat, party/lobby systems, or any matchmaking beyond a single "invite"/"join" action per friend.
- Any server-side or dedicated-server behavior — Steam Friends, like Steam Cloud, is a purely client-side, locally-running-Steam-client capability (mirrors `services/specification.md:18`); this feature never loads on a dedicated server.
- Rendering the sidebar during actual gameplay (HUD-visible while playing, not paused) — v1 scope is explicitly "main menu screens AND the pause menu" only, per the stated goal; an always-on HUD variant is a Future Extension.
- Rendering the sidebar over any main-menu-family screen this project cannot cheaply hook via `ScreenEvents.AFTER_INIT` — if a given screen turns out unreachable by that mechanism, exclusion from v1 is acceptable and should be logged, not force-fitted with a screen-specific mixin (see Requirements/Architecture for the "all main-menu screens" scoping decision). `RealmsMainScreen` is in v1 scope (Requirements, FR2.2); this Non-goal covers only a screen unexpectedly turning out unreachable.
- Any new steamworks4j dependency/version change — reuses the exact pinned `steamworks4j` version and Jar-in-Jar wiring the Steam Cloud Sync / bootstrap work already established (`services/specification.md:64-71,95`).
- Rich presence key/value design (`SteamFriends.setRichPresence`) — "joinable" state is read from `GetFriendGamePlayed`'s own connect-string field (see Requirements/Architecture), not a custom rich-presence schema; defining this mod's own rich-presence keys for richer status text is a Future Extension.
- Persisting any friends-sidebar-specific data to Steam Cloud — this feature has no save state of its own; it is a live, read-only view over Steamworks' own friend list (see Persistence).
- An actual invite/join connection mechanism behind "Invite to game"/"Join game" — v1 ships both options as visible, but disabled/greyed-out placeholder buttons only (see Requirements FR2.6, FR3.3, FR3.4). No connect-string, rich-presence-driven join, or real Minecraft auto-connect flow is implemented in v1; that mechanism is deferred to a Future Extension.

## Requirements

**Cross-cutting**
- **FR0.1** The feature depends on the same shared `SteamworksService`/`SteamAvailability` bootstrap the Steam Cloud Sync feature already depends on (`services/src/main/java/de/lazuli/services/steamworks/SteamworksService.java`), obtained via the same `SteamworksServiceHandoff` static-holder hand-off pattern already established between composition roots (`platform/fabric-*/.../SteamCloudSyncClientInitializer.java:51`, referencing `SteamworksServiceHandoff.require()`). It never re-initializes Steamworks itself.
- **FR0.2** If `SteamAvailability.isSteamAvailable()` is `false` at the point this feature's composition-root wiring runs, the sidebar is never constructed/attached to any screen, and no `SteamFriends` object is ever constructed — mirrors `features/steam-cloud-sync/specification.md:FR0.1`'s no-op-when-unavailable discipline. No exception escapes either way.
- **FR0.3** A local JSON config (`config/friends-sidebar.json`) carries at minimum a master `enabled` boolean (default `true`), following the same flat-under-config-dir convention as every other feature's own config (`features/hello-world-main-menu/specification.md:122-123`; `features/steam-cloud-sync/specification.md:159-160`). If `enabled` is `false`, behaves identically to `isSteamAvailable() == false` (FR0.2).

**Friend data (business logic, `services`/`api`)**
- **FR1.1** Enumerates the caller's friend list via `SteamFriends.getFriendCount(FriendFlags)` / `getFriendByIndex(int, FriendFlags)` (confirmed method shapes: `com.codedisaster.steamworks.SteamFriends`, github.com/code-disaster/steamworks4j) using `FriendFlags.Immediate` (Valve's own documented flag for "users the current user is a friend of" — `partner.steamgames.com/doc/api/ISteamFriends`, `k_EFriendFlagImmediate`) as the default scope; a broader/narrower flag set is a planning-level decision, not fixed here.
- **FR1.2** For each friend `SteamID`, resolves: persona name (`getFriendPersonaName`), persona/online state (`getFriendPersonaState`) — used only to decide row ordering/graying, not to gate visibility (offline friends still show, per no stated exclusion), and joinability/game-played info (`getFriendGamePlayed(SteamID, FriendGameInfo)`) — populates a `FriendGameInfo`-shaped record whose fields determine (a) whether "Join game" is enabled/actionable for that friend and (b) what connect-string, if any, is later passed to `inviteUserToGame`.
- **FR1.3** Resolves each friend's small avatar via `getSmallFriendAvatar(SteamID)` (returns an opaque image handle, `int`), then reads pixel data via `SteamUtils.getImageSize(image, int[] size)` / `getImageSize`+`getImageRGBA(image, ByteBuffer dest)` (confirmed shapes, `com.codedisaster.steamworks.SteamUtils`) into an RGBA byte buffer this feature's Version Adapter turns into a renderable Minecraft texture (see Architecture — Avatar Rendering). A friend whose avatar handle/image data isn't yet available (Valve's documented `AvatarImageLoaded_t` callback fires asynchronously the first time a given avatar is requested) renders a placeholder (e.g. a plain colored square or a generic vanilla icon) until the callback delivers real data, never blocking or throwing.
- **FR1.4** The friend list + per-friend state is refreshed on a bounded interval (not per-tick, not per-render-frame; e.g. every N seconds, exact value a planning decision) rather than only once at feature startup — presence/joinability meaningfully changes during a session, and a stale sidebar showing a friend as offline/not-joinable after they've logged in would defeat the feature's purpose. Refresh work (the `getFriendCount`/`getFriendByIndex`/`getFriendPersonaName`/`getFriendGamePlayed` call sequence) is cheap, local IPC-backed calls per Valve's own docs, not network I/O — safe to run on the client thread at this cadence, consistent with this repo's existing "Steam calls are local IPC" understanding (`services/specification.md:115`).
- **FR1.5** Registers a `SteamFriendsCallback` (steamworks4j's own callback-object requirement, `SteamFriends(SteamFriendsCallback callback)` constructor) to receive `onPersonaStateChange`/`onAvatarImageLoaded`-shaped callback events (Valve: `PersonaStateChange_t`, `AvatarImageLoaded_t`) — delivered only while `SteamworksService`'s existing per-tick `SteamAPI.runCallbacks()` pump keeps running (already registered by the Steam Cloud Sync composition root's `ClientTickEvents.END_CLIENT_TICK`, and this feature's own composition root must confirm that same pump is already active rather than assuming/duplicating it — see Architecture).

**Rendering / overlay presence**
- **FR2.1** The sidebar renders as a fixed-position overlay (e.g. anchored to one screen edge — exact edge/position a planning/UI decision) on every currently-open instance of: `TitleScreen`, and every other screen this project classifies as "main menu family" (Requirements scoping list below), plus `GameMenuScreen`/`PauseScreen`. It must not consume click/hover input intended for the underlying vanilla screen's own widgets when the pointer is outside the sidebar's own bounds.
- **FR2.2** "Main menu family" screens in scope for v1: `TitleScreen`, `SelectWorldScreen`, `MultiplayerScreen`, `RealmsMainScreen`, `OptionsScreen` (opened from the title screen), and any screen reached by drilling into those (e.g. a server-edit screen) — a closed, enumerable set of `instanceof` checks per platform module's own screen classes, not an open-ended "every screen" rule (mirrors the existing per-screen `instanceof` filtering pattern already used, `FabricCloudOnlyWorldListInjector.java:54`). `RealmsMainScreen` is in v1 scope; its exact injection mechanics (whether it is cleanly reachable via `ScreenEvents.AFTER_INIT` the same way as the other allow-listed screens, given it is driven by third-party-library internals) still need confirmation during implementation — this is an implementation-time verification detail, not open scope. World-generation/loading screens and any screen shown *during* an active session (in-world HUD, non-pause in-game screens) are out of scope (Non-goals).
- **FR2.3** Collapsed state (default): renders each friend's avatar only, stacked vertically, no name text, minimal footprint.
- **FR2.4** Hover state: while the mouse is within the sidebar's overall bounds, the **entire sidebar** expands horizontally to render every friend's persona name text next to their avatar — this is whole-sidebar hover, not per-row hover; hovering anywhere on the collapsed sidebar expands all rows together, not just the row under the cursor. Returns to collapsed the instant the mouse leaves the sidebar's bounds — no click needed to collapse.
- **FR2.5** Every rendered friend row is clickable via either the left or right mouse button; either button opens the same context menu (no left/right distinction in behavior, unlike vanilla's own left-click-vs-right-click-context-menu convention elsewhere) — this is an explicit, deliberate simplification per the stated requirement, not an oversight.
- **FR2.6** The context menu renders at the screen-space position of the mouse cursor at the moment of the click (not anchored to the row), listing exactly: **Open chat**, **Show profile**, **Invite to game**, **Join game** — in that order, unless planning finds a strong reason to reorder. **Open chat** and **Show profile** are enabled per FR3.1/FR3.2. **Invite to game** and **Join game** are v1 **disabled/greyed-out placeholders** for every friend, regardless of that friend's actual state — no connect-string/rich-presence/actual invite-join mechanism exists yet in v1 (see Non-goals, FR3.3, FR3.4); the options are visible so the menu's shape is stable and forward-compatible, but always non-actionable in this version. A menu option that cannot currently apply is disabled/grayed rather than hidden, so the option set is visually stable regardless of a given friend's state — exact disabled-vs-hidden choice is a planning/UX decision but must be stated and applied consistently.
- **FR2.7** Clicking outside the open context menu, or pressing Escape, closes it without action — must not also trigger whatever `Escape` normally does on the host screen (e.g. must not simultaneously close the pause menu itself) while the context menu is open.

**Context menu actions**
- **FR3.1** "Open chat" calls `ActivateGameOverlayToUser(SteamID, "chat")` (Valve-documented dialog name for opening Steam's own overlay chat with that friend) — requires the Steam overlay to be enabled; if the overlay is unavailable/disabled, this is a no-op with a logged warning, never a crash (mirrors the graceful-degradation discipline already established, `services/specification.md:NFR2`).
- **FR3.2** "Show profile" calls `ActivateGameOverlayToUser(SteamID, "steamid")` (Valve-documented dialog name for opening that friend's profile) — same overlay-unavailable degradation as FR3.1.
- **FR3.3** "Invite to game" is a v1 **disabled placeholder menu option** — it renders greyed-out and is not clickable/actionable for any friend in v1 (FR2.6). No `inviteUserToGame(SteamID, connectString)` call is wired up and no connect-string is designed or supplied in this version. The real invite mechanism (connect-string design, wiring `inviteUserToGame`, and enabling this option once the local player is in an invitable session) is explicitly deferred to a Future Extension.
- **FR3.4** "Join game" is a v1 **disabled placeholder menu option** — it renders greyed-out and is not clickable/actionable for any friend in v1 (FR2.6), regardless of what a friend's `FriendGameInfo` (FR1.2) reports. No join flow (auto-connect, `GameRichPresenceJoinRequested_t`-driven join, or otherwise) is implemented in this version. The real join mechanism is explicitly deferred to a Future Extension, and — since it is the receiving end of the same connect-string/rich-presence design as "Invite to game" — must be planned together with FR3.3 whenever that future work is taken up.
- **FR3.5** No context-menu action ever blocks the render/client thread; all are simple, fast steamworks4j calls (per Valve's docs, local IPC), consistent with FR1.4's own "local IPC, not network I/O" reasoning. This applies to FR3.1/FR3.2's real calls; FR3.3/FR3.4 make no Steamworks call at all in v1 since they are inert placeholders.

**Non-functional**
- **NFR1.** Friend-list/state resolution logic (which flags to query, how to compute joinability/disabled-menu-option state from a `FriendGameInfo`-shaped record, hover/expand state transitions) lives in a plain-JVM-testable class with no `net.minecraft.*`/steamworks4j-native-call dependency wherever feasible, mirroring `features/steam-cloud-sync/specification.md:NFR1`. The actual `SteamFriends`/`SteamUtils` calls and all Minecraft rendering/input code cannot be unit-tested per this repo's own stated constraint (`ui-guidelines.md`'s Testing section: "UI code that touches Screen/widget classes is not unit-testable... verify manually in-game") and must instead be manually verified per supported Minecraft version.
- **NFR2.** No uncaught exception from any Steamworks call (`SteamFriends`/`SteamUtils` construction or method calls) reaches Minecraft's tick/render thread or crashes any screen's `init()`/`render()` — every call site catches and logs, same discipline as `SteamworksService.create(...)` (`services/specification.md:83`) and `features/steam-cloud-sync/specification.md:NFR2`.
- **NFR3.** Public classes/interfaces carry JavaDoc with a usage example (`philosophy.md:19`).
- **NFR4.** Follows the required feature folder layout (`api/`, `config/`, `events/`, `gui/`, `mixins/`, `resources/`, `services/`, `tests/`, `README.md`, `.claude/context/feature-guidelines.md:5-16`) — `mixins/` stays a permanent empty placeholder per that same doc (`feature-guidelines.md:18`), since any real mixin work must live in `platform/fabric-<version>/.../mixin/` instead (see Architecture).

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision (same convention as `features/hello-world-main-menu/specification.md:53`).

1. **`api` module** — new package `de.lazuli.api.friends`, zero external/Minecraft dependencies, same rationale as `SteamAvailability` (`api/.../SteamAvailability.java:14-17`) and `CloudSyncable` (`features/steam-cloud-sync/specification.md:90`):
   - `FriendSummary { steamId64: long, personaName: String, personaState: int-or-enum, avatarHandle: int, inGame: boolean, joinable: boolean, connectHint: String|null }` — an immutable, plain-JVM data record; `steamId64` (the raw 64-bit Steam ID) rather than any steamworks4j `SteamID` type, so `api` never depends on the Steamworks binding library, mirroring `SteamAvailability`'s own "zero-dependency, safe for any layer" property (`services/specification.md:45-49`).
   - `FriendSidebarHook` (interface) — the "Platform API" this feature calls into, following the exact `MainMenuHook` shape/precedent (`api/.../mainmenu/MainMenuHook.java`, `features/hello-world-main-menu/specification.md:56-62`): `void updateFriends(List<FriendSummary> friends);`, `void setEnabled(boolean enabled);` — Minecraft-agnostic surface a Version Adapter implements per platform module.
   - `FriendActionListener` (interface), handed to the Version Adapter so a click on a row/context-menu option calls back into feature logic without the platform layer needing to know about `SteamFriends` itself: `void onOpenChat(long steamId64); void onShowProfile(long steamId64); void onInvite(long steamId64); void onJoin(long steamId64);`. In v1, `onInvite`/`onJoin` are unreachable from the UI since their menu options are disabled placeholders (FR3.3, FR3.4), but the interface still declares all four methods for forward compatibility.

2. **`features/friends-sidebar/api/`**:
   - `FriendsSidebarConfig { boolean enabled }` — this feature's own local settings (Configuration).

3. **`features/friends-sidebar/services/`**:
   - `FriendsService` — owns the `SteamFriends`/`SteamUtils` instances (constructed only if `SteamAvailability.isSteamAvailable()`, mirroring `CloudSyncCoordinator`'s own `SteamRemoteStorage`-ownership pattern, `features/steam-cloud-sync/specification.md:102`), the `SteamFriendsCallback` registration (FR1.5), the refresh-interval loop (FR1.4), and translation of raw `SteamFriends`/`SteamUtils` calls into `FriendSummary` records plus decoded avatar RGBA byte buffers; exposes `List<FriendSummary> currentFriends()` and `byte[] avatarRgba(long steamId64)`-shaped accessors, plus the four action methods (`openChat`, `showProfile`, `invite`, `join` — the concrete implementations of `FriendActionListener`) that call the corresponding `SteamFriends` method. In v1, `invite`/`join` are not wired to any real `SteamFriends` call (FR3.3, FR3.4) and are effectively unreachable given the disabled menu options.
   - `FriendSidebarStateMachine` (or similarly named) — the plain-JVM-testable hover/expand/context-menu-option-availability logic (NFR1): given a `FriendSummary` list plus current mouse position, computes collapsed-vs-expanded state for the whole sidebar (FR2.4) and which context-menu options are enabled for a given friend (always disabling Invite/Join in v1 per FR2.6), without touching Minecraft/steamworks4j types itself.

4. **`platform/fabric-<version>/...`**: one new client entrypoint (or an addition to the existing per-platform composition root pattern) constructing `FriendsService` with the shared `SteamworksService`, and a `FabricFriendsSidebarHook` Version Adapter (implements `FriendSidebarHook`) per platform module rendering the actual overlay + context menu using that version's real `Screen`/`GuiGraphics`(-extractor)/texture APIs (Architecture).

## Architecture
Layering: `features/friends-sidebar` depends on `api` (`FriendSummary`, `FriendSidebarHook`, `FriendActionListener`, `SteamAvailability`) and `services` (`SteamworksService`), per the Dependency Rules table (`architecture.md:64-71`). It never depends on `features/steam-cloud-sync` or any other feature (`architecture.md:74`); the two features share only the `services`-layer `SteamworksService` bootstrap, not each other.

```
platform/fabric-<version>/.../FriendsSidebarClientInitializer  (composition root)
        |  obtains via SteamworksServiceHandoff.require() (same pattern as SteamCloudSyncClientInitializer)
        v
services/steamworks/SteamworksService  (shared bootstrap; already ticking via ClientTickEvents.END_CLIENT_TICK)
        |  constructs (only if isSteamAvailable())
        v
features/friends-sidebar/services/FriendsService
        |  wraps
        v
com.codedisaster.steamworks.SteamFriends (+ SteamFriendsCallback)  /  SteamUtils
        |
        v
Steam client (local IPC) -> friend list, persona/game state, avatar image handles
```

Rendering flow: `FriendsService.currentFriends()` -> `FriendSidebarHook.updateFriends(...)` (api-layer, Minecraft-agnostic) -> `FabricFriendsSidebarHook` (platform Version Adapter) draws the sidebar/rows/context-menu using real `Screen`/`GuiGraphics` calls, and forwards row/menu clicks back through `FriendActionListener` -> `FriendsService`'s action methods -> `SteamFriends`.

**Injection shape — the central open architectural question for this feature, materially different from every screen-injection precedent already in this repo:** every existing injection this project has done extends exactly one specific screen (`FabricMainMenuHook` on `TitleScreen`; `FabricBookmarkToggleInjector` on the multiplayer server list; `FabricCloudOnlyWorldListInjector`/`WorldSyncToggleHookHolder` on `SelectWorldScreen`), so a single `ScreenEvents.AFTER_INIT` + `instanceof` filter (Pattern 1, `ui-guidelines.md`) suffices per screen. This feature instead needs the **same** persistent overlay + input-handling logic active across an entire *family* of otherwise-unrelated vanilla screen classes (Requirements, FR2.2) plus one more (the pause menu) that no feature has touched before. Two design shapes, to be resolved during planning:
1. **One `ScreenEvents.AFTER_INIT` registration whose handler runs against every screen**, `instanceof`-checking against the FR2.2 allow-list (a closed set of concrete screen classes, mirroring the existing per-screen `instanceof` filter idiom, `FabricCloudOnlyWorldListInjector.java:54`) and adding the same sidebar-drawing overlay widget via `Screens.getWidgets(screen)` (`Screens.getButtons(screen)` pre-1.21.11) each time one of those screens (re-)initializes — a pure Pattern 1 approach repeated across many screen types, no mixin. This is the default/preferred shape unless a concrete problem with it is found.
2. If Pattern 1's widget-list mechanism turns out insufficient for a fixed, screen-independent overlay (e.g. z-ordering/input-priority problems drawing "on top of" every other widget consistently, or needing to intercept clicks before the underlying screen's own widgets consume them) — a small, narrowly-scoped `@Mixin` (Pattern 3-shaped: hooking an existing screen's own `render`/`mouseClicked` at `TAIL`/`HEAD` respectively to draw the overlay last and intercept clicks first) applied once per allow-listed screen class, per platform module's `mixin/` package (never `features/friends-sidebar/mixins/`, per `feature-guidelines.md:18`). Given the number of distinct target screen classes in the FR2.2 allow-list (potentially five or more per platform module, each independently named across the Yarn/Mojang mapping boundary), this is a materially bigger mixin surface than any prior feature in this repo and should get its own explicit Risk entry in the implementation plan.
- Whichever shape is chosen, `GameMenuScreen` (Yarn, `net.minecraft.client.gui.screen.GameMenuScreen`) / `PauseScreen` (Mojang, `net.minecraft.client.gui.screens.PauseScreen` — **unconfirmed by `javap` against this repo's own resolved jars, sourced only from a NeoForge Mojang-mapped javadoc mirror**, `nekoyue.github.io/ForgeJavaDocs-NG`; verify before implementation, per this repo's own "confirm by compiling, don't assume across the obfuscation boundary" discipline, `.claude/context/minecraft.md:19-30,92-96`) is simply one more entry in the same allow-list/mixin-target set as the main-menu-family screens — no separate mechanism is needed just because it's an in-game rather than title-flow screen, since `ScreenEvents.AFTER_INIT` fires identically for any `Screen` subclass regardless of when it's shown. `RealmsMainScreen` is likewise one more allow-list entry (FR2.2); whether it is reachable via the same `ScreenEvents.AFTER_INIT` mechanism given its third-party-library-driven internals still needs confirmation during planning/implementation.
- This "one overlay across many otherwise-independent vanilla screens" shape is also a new pattern relative to `architecture.md`'s existing "Shared-screen extension point" note (`architecture.md:76`, which is about *two features* colliding on *one* screen) — here it is *one* feature deliberately targeting *many* screens. Not itself a collision case, but flagged since it stretches that section's original framing; no ADR is obviously required (this is still one feature, one hook, no cross-feature coordination), but planning should confirm that reading holds.

**Avatar rendering:** `SteamUtils.getImageSize`/`getImageRGBA` (FR1.3) yield raw RGBA bytes, not a Minecraft `Identifier`/`ResourceLocation`-addressable texture. Each platform Version Adapter must convert this into a dynamically-registered/uploadable texture (Minecraft's own dynamic-texture APIs — exact class, e.g. `NativeImage`/`DynamicTexture`-shaped, differs in name only, not concept, across the mapping boundary and is **not asserted here**; confirm via `javap` during planning/implementation, same discipline as every other cross-version fact in this spec) rather than a pre-baked PNG resource (unlike this repo's existing texture-asset convention for static icons, `ui-guidelines.md`'s Textures section, which doesn't apply here since avatar pixels are only known at runtime). This upload must happen off the hot render path where possible (cache the uploaded texture per Steam ID, re-upload only when `AvatarImageLoaded_t`/`onAvatarImageLoaded` fires for that friend, not every frame) — mirrors this repo's own "no per-frame allocation" performance discipline (`features/steam-cloud-sync/specification.md:204`).

**Threading:** all `SteamFriends`/`SteamUtils` calls happen on the same thread `SteamAPI.init()` ran on (Minecraft's client/tick/render thread in this repo's setup), consistent with the existing documented Steamworks threading constraint (`services/specification.md:85`, `features/steam-cloud-sync/specification.md:137`). FR1.4's periodic refresh is cheap enough (Valve: local IPC) to run directly on that thread at its chosen interval rather than needing a background executor — unlike Steam Cloud Sync's archive-compression work, there is no CPU-heavy step here to offload.

**Composition-root ordering:** this feature's client entrypoint must run after whichever entrypoint first establishes the `SteamworksService`/`SteamworksServiceHandoff` publication (today, `SteamworksClientInitializer`, per `services/implementation-plan.md`'s own flagged hand-off risk, also referenced at `features/steam-cloud-sync/specification.md:140`) — this feature inherits that same already-flagged ordering dependency, it does not introduce a new one.

## Existing Implementation
Summarized for the planner so this doesn't need re-discovery:
- **Shared Steamworks bootstrap** (reusable as-is): `services/src/main/java/de/lazuli/services/steamworks/SteamworksService.java` (+ `SteamNativeLibraryNames.java`, `ClasspathSteamLibraryLoader.java`, `SteamAppIdResolver.java`) and `api/src/main/java/de/lazuli/api/steamworks/SteamAvailability.java` — already handles native library loading, `SteamAPI.init()`/`initEx()`, the per-tick `runCallbacks()` pump (registered via `ClientTickEvents.END_CLIENT_TICK` by whichever composition root runs first), and graceful unavailable-degradation. This feature must reuse this, not reinitialize Steamworks.
- **Cross-composition-root hand-off pattern**: each platform module's `SteamCloudSyncClientInitializer.onInitializeClient()` (e.g. `platform/fabric-1.21.11/src/main/java/de/lazuli/SteamCloudSyncClientInitializer.java:51`) obtains the already-constructed `SteamworksService` via `SteamworksServiceHandoff.require()` — a small static holder class (`platform/fabric-<version>/.../WorldSyncToggleHookHolder.java` is an analogous, unrelated-purpose static holder in the same codebase, `publish(...)`/`require()`-shaped) bridging two independently-registered client entrypoints, since Fabric doesn't otherwise let one entrypoint directly hand an object to another. This feature should follow the identical hand-off shape for obtaining `SteamworksService`.
- **Pattern 1 precedent (`ui-guidelines.md`)**: `FabricBookmarkToggleInjector` and (for its per-row-icon variant) `WorldSyncToggleHookHolder`'s associated `@Inject`-mixin — `ScreenEvents.AFTER_INIT` + `Screens.getWidgets`/`Screens.getButtons`, no mixin, is this repo's default, cheapest overlay-widget mechanism and should be the starting design for this feature's sidebar per screen, per the Architecture section's default preference.
- **Pattern 2/3 precedent and its hard-won lessons** (`FabricCloudOnlyWorldListInjector.java`, `EntryListWidgetReflection.java`, `WorldEntryReflection.java`, and the corresponding 26.x-side `AbstractSelectionListReflection.java`/`WorldListEntryReflection.java`): three consecutive `@Mixin`/`@Invoker`-based designs to reach a vanilla list's protected `addEntry`/entry-accessor methods each failed differently (wrong compiled descriptor for a generic-erased parameter; Sponge Mixin's hierarchy validator rejecting a mixin `extends` its own target; Sponge Mixin's package-ownership rule breaking an unrelated same-package vanilla class) — the design that actually survived in-game testing abandons `@Mixin`/`@Invoker` for reaching protected members entirely and uses plain reflection (`getDeclaredMethods()` + `setAccessible(true)` + `invoke(...)`, with an untyped `Object` parameter so there is no descriptor to get wrong). Full narrative: `.claude/context/minecraft.md`'s Known Cross-Version API Differences table (rows on `WorldListWidget`/`WorldSelectionList`) and `.claude/context/ui-guidelines.md`'s Pattern 2/"duck-interface trap" sections. This feature is not expected to need Pattern 2 (no synthetic list *row* is being inserted), but if Architecture's mixin fallback (option 2) is chosen for click-interception, this reflection-over-mixin lesson is directly relevant precedent for any similarly protected member it needs to reach.
- **Pattern 3 precedent** (`ui-guidelines.md`'s Pattern 3 section, "rendering/click-handling inside an existing real list entry"): confirms `render`/`extractContent` and `mouseClicked` method shapes (`(graphics, mouseX, mouseY, hovering, partialTick)` and `(clickEvent-record, doubleClick)` respectively) are consistent across both mapping sides for at least the world-list-entry case — useful reference if this feature's own mixin fallback needs to hook a screen's top-level `render`/`mouseClicked` rather than a list entry's.
- **Cross-version screen/rendering divergences already logged** (`minecraft.md`'s table): `Screens.getButtons` -> `Screens.getWidgets` rename; `Screen.render(DrawContext,...)` -> `Screen.extractRenderState(GuiGraphicsExtractor,...)` render-state-extraction model change; `Text`/`Component` text-type rename; `MinecraftClient`/`Minecraft` client-singleton rename — all directly relevant to building this feature's own overlay/context-menu rendering and must be re-verified (not assumed identical) for whichever new screen classes and widget/text APIs this feature's sidebar code touches that no prior feature has touched yet.
- **Config-file convention**: `HelloWorldMainMenuConfigIO`-shaped hand-rolled JSON load/save with warn-and-default-on-malformed behavior (`features/hello-world-main-menu/specification.md:122-135`; `platform/.../HelloWorldMainMenuClientInitializer.java:40`) is the established pattern this feature's own `config/friends-sidebar.json` should follow.

## UI
- **Position/anchor**: fixed to one edge of the screen (e.g. right edge, vertically centered or top-anchored) — exact placement is a planning/UX decision; must not overlap vanilla's own title-screen logo/splash text or button rows on any of the allow-listed screens, at common resolutions/GUI scales (same verification discipline as the hello-world label, `features/hello-world-main-menu/specification.md:113`).
- **Collapsed row**: one small avatar image per friend, stacked vertically, fixed width.
- **Expanded state** (whole-sidebar hover, FR2.4): the entire sidebar expands together — every row shows avatar plus persona name text to one side, wider footprint; must not push/resize other on-screen vanilla widgets. Hovering a single row does not expand that row alone; the sidebar has exactly two states, collapsed and expanded, driven by whether the mouse is anywhere within the sidebar's bounds.
- **Context menu** (FR2.5-2.7): a small vertical list of exactly four text options at the mouse's click position, rendered above/overlapping whatever screen is currently open (including, when open on the pause menu, above the pause menu's own buttons); **Invite to game** and **Join game** always render visually distinguished as disabled/greyed-out placeholders in v1 (FR2.6, FR3.3, FR3.4); **Open chat**/**Show profile** render enabled.
- **No dedicated settings/management screen in v1** — only the `enabled` config toggle (Configuration); a Mod-Menu-integrated or in-game settings screen for sidebar position/behavior is a Future Extension, following this repo's own established "ship plumbing before an in-game editor" precedent (`features/hello-world-main-menu/specification.md:25`; `features/steam-cloud-sync/specification.md:152`).
- Manual, per-supported-version in-game verification is required (not unit-testable), per `ui-guidelines.md`'s Testing section.

## Configuration
`config/friends-sidebar.json`, same flat-under-config-dir convention as every other feature (`platform/.../HelloWorldMainMenuClientInitializer.java:40`):
```json
{
  "enabled": true
}
```
- `enabled`: master switch (default `true`); even when `true`, has no effect unless `SteamAvailability.isSteamAvailable()` (FR0.2).
- Malformed/missing file falls back to defaults with a logged warning, same pattern as `HelloWorldMainMenuConfigIO.load(...)` (`HelloWorldMainMenuConfigIO.java:71-88`).
- Additional fields (refresh interval, sidebar edge/position, avatar size) are plausible planning-time additions to this same file; not fixed here since exact defaults are a UX decision.

## Events
- Consumes, does not define, Fabric API's `ScreenEvents.AFTER_INIT` (module `fabric-screen-api-v1`) for the FR2.2 allow-listed screens, and `ClientTickEvents.END_CLIENT_TICK` only insofar as it must confirm the shared Steamworks callback pump is already running (it does not register its own second pump — see Architecture).
- Consumes steamworks4j's own `SteamFriendsCallback`-delivered events (`PersonaStateChange_t`/`onPersonaStateChange`, `AvatarImageLoaded_t`/`onAvatarImageLoaded`) to know when to re-query a friend's state or re-fetch/re-upload an avatar, rather than polling every possible field every refresh tick.
- Defines no new cross-feature event bus type — none exists yet in this repo (`architecture.md:26`), and this feature has no cross-feature signaling need.

## Networking
No new client-server packets; entirely client-only (mirrors `services/specification.md:18`). The only "networking" is Steam's own client-to-Valve-backend and client-to-client communication via the local Steam client process, opaque to this mod, same framing already established for Steam Cloud Sync (`features/steam-cloud-sync/specification.md:187`). v1 ships no invite/join networking at all — "Invite to game"/"Join game" are disabled placeholders (FR3.3, FR3.4) with no `inviteUserToGame` call and no Minecraft-server-connect step wired up. Whatever "Join game"'s actual Minecraft-server-connect step ends up using, if it involves this mod initiating a real Minecraft multiplayer connection to a friend's server, is a Future Extension design question, not resolved here.

## Persistence
None. This feature holds no on-disk state of its own beyond its one small `enabled`-flag config file (Configuration) — the friend list, persona data, and avatar images are all live, in-memory, Steamworks-sourced state, re-fetched/refreshed per session and never written to disk by this feature.

## Compatibility
- **Minecraft/Fabric versions**: per `features/hello-world-main-menu/specification.md:154-159`'s already-established table — `platform/fabric-26.2` (MC 26.2, Mojang mappings, unobfuscated), `platform/fabric-26.1` (MC 26.1, Mojang mappings, unobfuscated), `platform/fabric-1.21.11` (MC 1.21.11, Yarn `1.21.11+build.6`, obfuscated, `fabric-loom-remap`). This feature's business logic (`FriendsService`'s data-shaping, `FriendSidebarStateMachine`) is Minecraft-version-agnostic, same as the Steamworks bootstrap itself (`services/specification.md:123`); only the Version Adapter (screen hooking, avatar texture upload, context-menu rendering) needs per-platform-module work.
- **Steamworks/steamworks4j**: same version pin as the bootstrap and Steam Cloud Sync (`steamworks4j 1.10.0`, `gradle.properties:41`; `features/steam-cloud-sync/specification.md:197`); no new Gradle/native wiring beyond what already exists.
- **Cross-version screen classes this feature newly touches** (none previously touched by this repo, all needing fresh `javap` confirmation during planning/implementation, per this repo's own research discipline):
  - `SelectWorldScreen`/`MultiplayerScreen`/`RealmsMainScreen`/`OptionsScreen` (Yarn, `net.minecraft.client.gui.screen.*`) vs. their Mojang-mapped equivalents (`net.minecraft.client.gui.screens.*` package, exact simple names to be confirmed — likely unchanged simple names given the existing `SelectWorldScreen` reference already used unqualified in `FabricCloudOnlyWorldListInjector.java:11`, but the *package* prefix and any render-model differences must still be reconfirmed for each new screen this feature touches). `RealmsMainScreen`'s reachability via `ScreenEvents.AFTER_INIT` given its third-party-library-driven internals is specifically flagged for confirmation during implementation (Architecture).
  - `GameMenuScreen` (Yarn, `net.minecraft.client.gui.screen.GameMenuScreen`, confirmed present at least as of Yarn 1.20/1.21.4 per Fabric's own maven-hosted javadoc, `maven.fabricmc.net/docs/yarn-1.21.4+build.8/...`) vs. `PauseScreen` (Mojang, `net.minecraft.client.gui.screens.PauseScreen` — **sourced only from a third-party Mojang-mapped javadoc mirror, not yet confirmed via `javap` against this repo's own resolved 26.1/26.2 jars; treat as unconfirmed until verified**).
- **Java/OS/architecture**: inherits the bootstrap's constraints (`services/specification.md:124-126`) — no additional restriction introduced by this feature.

## Performance
- Friend-list/state refresh (FR1.4): bounded-interval, not per-tick; each refresh is a small number of cheap local-IPC `SteamFriends` calls proportional to friend-list size, not proportional to render-frame rate.
- Avatar texture upload: performed once per friend per `AvatarImageLoaded_t` event (or on first request), cached thereafter — never re-uploaded every frame (Architecture — Avatar Rendering).
- Sidebar/context-menu rendering itself: ordinary per-frame Minecraft widget drawing, no heavier than any other overlay widget already in this codebase; no per-tick allocation beyond what a normal `Screen`/widget render pass already does.
- No blocking I/O or network calls on the render/client thread at any point (Architecture — Threading).
