## v1.5 Amendment — Join-policy control polish (button chrome, label, native tooltip)

### Background / trigger
Live in-game testing of the v1.4 `DropdownWidget`-based join-policy control found four problems, fully researched and specified generically at the component level in `platform/ui/specification.md`'s own v2 amendment (that document's Overview, "v2 Amendment — Polish pass"): (1) no button chrome — the control reads as plain text, not a clickable control; (2) an easy-to-miss label — today's only "label" is the leading `"Join: "` prefix baked into the closed-state row's own selection text (`joinPolicyShortLabel`), with no visually distinct labeling element; (3) a description-text sizing/overlap defect, whose real root cause (confirmed by re-reading the current code this pass) is that the old inline hover-description text was never counted in `DropdownWidget.render()`'s returned height, not a horizontal width/alignment bug (the horizontal alignment was already correct); (4) the per-row description is plain inline body text, not Minecraft's native tooltip box. All four are fixed once, generically, inside `DropdownWidget` itself (`platform/ui/specification.md` v2's UI-FR8-UI-FR14) — this amendment covers only what changes on this feature's own side: the label design decision and this feature's construction call site. The persisted value, its meaning, its default, its enforcement (FR7.1/FR7.2/FR7.8-FR7.13), and its config schema (Configuration, above) remain **entirely unchanged**.

**(this revision, correction)** A fifth problem was found during specification review, before implementation started: the v1.4 control renders its open-state option list **inline**, inside `FriendSidebarWidget.renderNow()`'s single `SIDEBAR`-layer draw call (`FriendSidebarWidget.java:390-391`), the same manually-driven layer that also draws the scrollable friend-row list beneath it — so content drawn later in that same `renderNow()` call can clip or cover the open option list, unlike `FriendContextMenuWidget`, which always draws on top of `SIDEBAR` via its own dedicated `FriendsSidebarZOrder.CONTEXT_MENU` ordinal (`platform/ui/specification.md` v2's Overview, "Existing Implementation" and Problem 5). `platform/ui/specification.md` v2 now fixes this generically by splitting `DropdownWidget`'s single `render()` method into a closed-row render call plus a separate `renderOpenOverlay()` overlay call (that document's UI-FR15-UI-FR18); this amendment's own delta (below) covers only how `FriendSidebarWidget`/`FabricFriendsSidebarInjector` wire that new overlay call into their own existing `FriendsSidebarZOrder`-driven `afterExtract` hook, the same way they already wire `FriendContextMenuWidget.renderNow()`.

### Label design decision (this revision)
**Decision: adopt `DropdownWidget`'s new optional, generic `label` constructor parameter (`platform/ui/specification.md` v2's UI-FR10)** rather than have `FriendSidebarWidget` draw a separate `"Who can join:"` string alongside the control itself.

**Tradeoff considered.** The alternative — `FriendSidebarWidget` renders its own label text at a position it chooses next to/above the `DropdownWidget` instance, with `DropdownWidget` itself unchanged — keeps `DropdownWidget`'s height contract exactly as it is today and keeps 100% of the label's presentation caller-owned, matching this document's own pre-existing "layout constants are the embedding widget's own choice" framing (v1.4 UI section). It was not chosen because it does not actually solve the generic-component goal driving this whole effort (`platform/ui/specification.md`'s Goals, "avoid a second, independently-invented [control] the next time a feature needs one") — a caller-drawn label is exactly the kind of per-consumer reinvention a shared component exists to prevent, and this feature is not expected to be `DropdownWidget`'s last consumer. Adopting the generic `label` parameter costs this feature only a one-line constructor-call change (supplying `"Who can join:"` as the new argument, Public API delta below) and one small layout adjustment (`listTopOffset()`'s height math must account for `DropdownWidget.render()`'s now-taller returned height when a label is present, mirroring the exact same "read the height back from `render()`" mechanism v1.4-FR7.14 already established for the open-state height, so no new layout mechanism is needed here either — only a wider input range for the one that already exists).

### Open-state overlay / z-order wiring decision (this revision, correction)
**Decision: give the join-policy dropdown's open-state option list its own new `FriendsSidebarZOrder` ordinal, `DROPDOWN_OVERLAY`, declared adjacent to the existing `CONTEXT_MENU` ordinal, both above `SIDEBAR`**, and drive it from `FabricFriendsSidebarInjector`'s existing `onAfterExtract` hook exactly the way `CONTEXT_MENU` (`FriendContextMenuWidget.renderNow()`) is already driven — no new hook, no new event registration, only one new ordinal and one new conditional call inserted into the existing `onAfterExtract` method body.

**Ordinal placement rationale (finalized, this revision — supersedes an earlier draft of this same amendment).** An earlier draft of this decision placed `DROPDOWN_OVERLAY` strictly beneath `CONTEXT_MENU` in ordinal order, on the reasoning that `CONTEXT_MENU` is this feature's "existing highest-priority, modal-like popup" and should stay topmost as a fixed rule. Explicit product direction for this revision rejects that framing: the open-state dropdown overlay must get the **same** topmost-overlay treatment `CONTEXT_MENU` already has, not a fixed lesser layer beneath it — there is no product reason an open dropdown should ever be understood to lose to the context menu, or vice versa.

Re-confirming the interaction model directly against `FriendSidebarWidget.java`/`FriendSidebarStateMachine.java`/`FabricFriendsSidebarInjector.java` for this revision settles the mechanism: **the dropdown-open and context-menu-open states are mutually exclusive in practice — the two overlays are never both open in the same rendered frame under today's interaction model**, for two independently-enforced reasons:
- **Opening the dropdown while the context menu is open.** `FabricFriendsSidebarInjector.onBeforeMouseClick` (`FabricFriendsSidebarInjector.java:183-187`) closes any open `FriendContextMenuWidget` *before* `onAllowMouseClick` (`FabricFriendsSidebarInjector.java:150-158`) runs, whenever the click lands outside the menu's own bounds. `onAllowMouseClick` then dispatches to `activeSidebar.mouseClicked(...)` only after that closure has already happened (`openMenu` is `null` by the time it checks it), so a click that opens the join-policy dropdown's closed row (`FriendSidebarWidget.mouseClicked`, `FriendSidebarWidget.java:539-542`) always sees the context menu already closed within that same click event — the two can never both be showing on the very next rendered frame either.
- **Opening the context menu while the dropdown is open.** `FriendSidebarWidget.mouseClicked` (`FriendSidebarWidget.java:539-542`) checks `dropdownVisible && joinPolicyDropdown.mouseClicked(...)` first, before any friend-row click-handling that could invoke `rowClickListener.onRowClicked(...)` (which is what opens the context menu, `FabricFriendsSidebarInjector.java:101,160-173`). `DropdownWidget.mouseClicked` (`DropdownWidget.java:109-133`) always returns `true` and consumes the click whenever the dropdown is currently open — including a click that lands on a friend row rather than an option row (the "elsewhere while open" branch, `DropdownWidget.java:129-132`, closes the dropdown without forwarding). So a click intended to right-click a friend row while the dropdown is open instead only closes the dropdown on that click; opening the context menu requires a second, subsequent click, by which point the dropdown is already closed.

Because the two states are mutually exclusive by construction (not merely by observed behavior), which of `DROPDOWN_OVERLAY`/`CONTEXT_MENU` is declared first in the enum is inconsequential at runtime — `FabricFriendsSidebarInjector.onAfterExtract` only ever has at most one of the two overlay `renderNow(...)`/`renderDropdownOverlay(...)` calls actually draw anything in a given frame (the other is a no-op guard, e.g. `!joinPolicyDropdown.isOpen()` or `openMenu == null`), so there is no frame in which their relative draw order is ever observable. This revision therefore does **not** introduce any dynamic "whichever is open draws last" mechanism (that would be solving a problem that cannot occur, given the guarantee above) — a fixed enum ordinal remains correct and sufficient, chosen here purely for documentation clarity (`SIDEBAR` → `DROPDOWN_OVERLAY` → `CONTEXT_MENU`, matching the existing Public API/Requirements delta below), not because `CONTEXT_MENU` outranks `DROPDOWN_OVERLAY` in priority. Both ordinals are drawn above `SIDEBAR` and are documented as the same topmost-overlay tier (Compatibility, below) — neither is ever "below" the other in any observable, rendered sense.

**Why not skip the enum and just call `renderOpenOverlay()` unconditionally from inside `activeSidebar.renderNow()` itself (i.e. keep it a `SIDEBAR`-layer call)?** That was the orchestrator's explicit correction to reject for this amendment — it does not fix Problem 5 at all, since it is exactly the current (broken) mechanism: a call made from *within* the same `SIDEBAR`-layer `renderNow()` invocation is still subject to whatever else that same invocation draws afterward. The fix requires a call made from a **separate, later-ordinal, top-level** `onAfterExtract`-driven pass, which is what `FriendsSidebarZOrder`'s ordinal-ordering guarantee exists to provide (`platform/ui/specification.md` v2's Overview, "Existing Implementation").

### Requirements (delta over v1.4; all v1.4/v1.3 requirements not named here are unchanged, see above)
- **v1.5-FR7.16 (new).** `FriendSidebarWidget` constructs its `DropdownWidget` instance with a non-null `label` (Public API delta below) reading `"Who can join:"` (or equivalent planning/UX-decided copy, matching FR7.4's "never ambiguous" requirement) — rendered by `DropdownWidget` itself directly above the closed-state row (`platform/ui/specification.md` v2's UI-FR10), in addition to (not instead of) the closed-state row's own existing `"Join: <value>"`-shaped selection text (FR7.4, unchanged).
- **v1.5-FR7.17 (new, supersedes the height-only portion of v1.4-FR7.14 where the label is concerned).** `listTopOffset()`'s reservation of vertical space for the join-policy control (v1.4-FR7.14's existing mechanism) continues to read `DropdownWidget.render()`'s returned total-height-this-frame as its sole source of truth (unchanged) — after this revision that returned height additionally includes the label row (`platform/ui/specification.md` v2's UI-FR11) whenever `expanded` is true, and, per that same v2 amendment's Problem 5 fix, **no longer** includes the open-state option rows at all (they were already excluded from height accounting before this correction, and remain excluded now — only the *mechanism* by which they're excluded changed, from "not counted despite being drawn inline" to "not drawn by this call at all, drawn by a separate overlay call instead"); no new branch/field is needed on `FriendSidebarWidget`'s own side beyond continuing to consume the one returned `int` it already consumes today (v1.4-Architecture item 2, unchanged).
- **v1.5-FR7.18 (new).** No inline per-row description text remains in `FriendSidebarWidget`'s own rendering after this revision — the description copy currently supplied via `joinPolicyDescription(...)` (`FriendSidebarWidget.java:435-449`, retained verbatim as a text source, FR7.4/v1.4-Architecture item 1, unchanged) is still passed to `DropdownWidget.Option`'s `description` field exactly as today, but `DropdownWidget` itself now delivers it as a native tooltip (`platform/ui/specification.md` v2's UI-FR12) rather than inline body text — `FriendSidebarWidget` makes no separate tooltip call of its own; this is entirely internal to `DropdownWidget`'s own rendering.
- **v1.5-FR7.19 (new, correction).** `FriendSidebarWidget`'s existing call to `joinPolicyDropdown.render(...)` (`FriendSidebarWidget.java:390-391`, within `renderNow()`, `SIDEBAR`-layer) is updated to call only the closed-row render method (`platform/ui/specification.md` v2's UI-FR15 item 1 — the same method name/signature, now scoped to just the closed row/label) — it no longer draws the open-state option list, regardless of `joinPolicyDropdown.isOpen()`. `FriendSidebarWidget` gains one new method, e.g. `renderDropdownOverlay(GuiGraphicsExtractor guiGraphics, int mouseX, int mouseY, float delta)` (Mojang modules) / the Yarn-mapped equivalent on `fabric-1.21.11`, that does nothing when `!joinPolicyDropdown.isOpen()` and otherwise forwards directly to `joinPolicyDropdown.renderOpenOverlay(...)` (`platform/ui/specification.md` v2's UI-FR15 item 2) using the same `guiGraphics`/`mouseX`/`mouseY`/`delta` it is given. This new method is called once per frame by `FabricFriendsSidebarInjector.onAfterExtract` (v1.5-FR7.20).
- **v1.5-FR7.20 (new, correction).** `de.lazuli.api.friends.FriendsSidebarZOrder` (`api/src/main/java/de/lazuli/api/friends/FriendsSidebarZOrder.java`) gains one new ordinal, `DROPDOWN_OVERLAY`, declared between the existing `SIDEBAR` and `CONTEXT_MENU` ordinals (enum declaration order: `SIDEBAR`, `DROPDOWN_OVERLAY`, `CONTEXT_MENU`) — both `DROPDOWN_OVERLAY` and `CONTEXT_MENU` are the same topmost-overlay tier, above `SIDEBAR`; their relative declaration order carries no priority meaning, since the two are mutually exclusive at runtime and never both render in the same frame (rationale above). Each platform module's `FabricFriendsSidebarInjector.onAfterExtract` (`platform/fabric-26.2/.../friends/FabricFriendsSidebarInjector.java:121-129`, structurally mirrored on `fabric-26.1`/`fabric-1.21.11`) gains one new call, inserted between the existing `activeSidebar.renderNow(...)` call and the existing `openMenu.renderNow(...)` call: `if (screen == activeSidebarScreen && activeSidebar != null) { activeSidebar.renderDropdownOverlay(guiGraphics, mouseX, mouseY, delta); }` (guarded the same way the existing `activeSidebar.renderNow(...)` call above it already is, since the dropdown only exists on the same screen the sidebar itself is attached to). No other line of `onAfterExtract` changes; the existing `activeSidebar.renderNow(...)` and `openMenu.renderNow(...)` calls, and their own existing guards, are unmodified.

13. **(new, correction)** **`platform/fabric-<version>/.../friends/FriendSidebarWidget#renderDropdownOverlay(...)`** — new public method (v1.5-FR7.19), one structurally-identical copy per platform module (differing only in the existing `GuiGraphicsExtractor` vs. `DrawContext` idiom, same as every other per-module render method on this class), forwarding to `joinPolicyDropdown.renderOpenOverlay(...)` (`platform/ui/specification.md` v2's Public API delta item 4) when open.
14. **(new, correction)** **`api/src/main/java/de/lazuli/api/friends/FriendsSidebarZOrder`** — gains the new `DROPDOWN_OVERLAY` ordinal (v1.5-FR7.20), declared between `SIDEBAR` and `CONTEXT_MENU` as an equal-priority topmost tier with `CONTEXT_MENU` (rationale above) — not a lesser layer beneath it.

### Architecture (v1.5 delta)
The same-layer, same-module `FriendSidebarWidget` -> `DropdownWidget` composition v1.4's Architecture section already established is unchanged in kind — this revision widens the one existing construction call (Public API item 12) and continues consuming the closed-row `render()`'s returned height exactly as v1.4-Architecture item 2 already does (v1.5-FR7.17). **(correction, new this revision)** What *is* new is a second, parallel wiring path alongside that existing one: `FriendSidebarWidget` now also composes `DropdownWidget.renderOpenOverlay(...)` via its own new `renderDropdownOverlay(...)` method (Public API item 13), and `FabricFriendsSidebarInjector` now calls that new method from its existing `onAfterExtract` hook at the new `FriendsSidebarZOrder.DROPDOWN_OVERLAY` ordinal (Public API items 14-15), positioned above the pre-existing `SIDEBAR` ordinal (the sidebar itself, including the dropdown's closed row/label) and at the same topmost tier as the pre-existing `CONTEXT_MENU` ordinal (the friend-row context menu) — not beneath it (Open-state overlay / z-order wiring decision, above). This is structurally identical to how `FriendContextMenuWidget` is already wired into the same hook (`FriendContextMenuWidget.renderNow()`, called from the same `onAfterExtract` method, at the pre-existing `CONTEXT_MENU` ordinal) — no new hook type, no new event source, one new enum ordinal and one new forwarding method. No new bridge point, no new cross-feature edge, no change to the `JoinPolicy` -> `HostGateway` composition-root bridge (unchanged, entirely orthogonal to this rendering-only revision).

### UI (v1.5 delta)
- **Closed state**: now additionally shows a `"Who can join:"` label row directly above the existing single row (v1.5-FR7.16), plus border/hover chrome (`platform/ui/specification.md` v2's UI-FR8/UI-FR9, entirely internal to `DropdownWidget`, no `FriendSidebarWidget`-side change needed). Rendered as part of `FriendSidebarWidget.renderNow()`'s existing `SIDEBAR`-layer call, unchanged in *which layer* it draws on from v1.4 (only the label/chrome content is new).
- **Open state**: unchanged in row count/order (Nobody, Friends, Everyone) from v1.4-UI; per-row description text is now a native tooltip (v1.5-FR7.18) rather than inline text drawn beneath the hovered row. **(correction, new this revision)** The open-state option list itself now renders as a genuine top-level overlay, drawn by `FriendSidebarWidget.renderDropdownOverlay(...)` at the new `FriendsSidebarZOrder.DROPDOWN_OVERLAY` ordinal (v1.5-FR7.19/FR7.20) — after the sidebar's own `SIDEBAR`-layer content (including the friend-row list beneath the join-policy control), and at the same topmost tier as the friend-row `CONTEXT_MENU`, if one happens to be open (in practice never simultaneously — see the mutual-exclusivity rationale above). This guarantees the open option list is never clipped or covered by the friend-row list or any other `SIDEBAR`-layer content, closing the gap the orchestrator's correction identified.
- **Interaction**: unchanged from v1.4-UI (click closed-state row to open; click an option row to select and close; click elsewhere while open to close without changing the selection). The overlay split (above) is rendering-only and does not change `mouseClicked` dispatch — `FriendSidebarWidget`'s existing `joinPolicyDropdown.mouseClicked(...)` forwarding call (`FriendSidebarWidget.java:539`) is unmodified.
- **Disabled/status-state behavior**: unchanged from v1.4-UI/v1.4-FR7.6a.

### Compatibility (v1.5 delta)
- Same three-platform-module structural-twin requirement as NFR9/v1.4-Compatibility (unchanged) — the label-argument addition (Public API item 12) and the new overlay-wiring addition (Public API items 13-15) must both be added identically across `platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`, mirroring the exact discipline v1.4's own Compatibility section already established for that same call site. `FriendsSidebarZOrder` itself (`api/` module, one copy, Public API item 14) needs no per-module duplication — only its three per-module *consumers* (`FabricFriendsSidebarInjector`) do.
- Shared-file risk: `FriendSidebarWidget` and `FabricFriendsSidebarInjector` remain actively-evolving, shared Platform-layer files (v1.4-Compatibility, carried forward unmodified; the injector is newly touched by this amendment for the first time) — re-run the same `git status`/`git diff` discipline before editing either again for this amendment, especially since `platform/ui/specification.md` v2's own polish-and-overlay-split pass and this amendment are expected to land together (`DropdownWidget`'s new constructor shape, its new `renderOpenOverlay(...)` method, and this feature's two call sites for both must be consistent within the same change).
- **(correction, new this revision)** `FriendsSidebarZOrder`'s existing two-ordinal Javadoc ("Both `FriendSidebarWidget` and `FriendContextMenuWidget` are drawn manually... this enum's ordinal order... is what determines what's on top") must be updated to describe three ordinals/three manually-drawn layers instead of two, since it is a repo-wide-visible `api/` type whose doc comment other future consumers may read as documentation of the pattern. **(finalized, this revision)** That updated Javadoc must also state explicitly that `DROPDOWN_OVERLAY` and `CONTEXT_MENU` are the same topmost-overlay tier, both drawn above `SIDEBAR`, and that their relative declaration order carries no priority meaning because the two states are mutually exclusive at runtime (Open-state overlay / z-order wiring decision, above) — it must not describe `CONTEXT_MENU` as outranking or sitting "above" `DROPDOWN_OVERLAY` in any priority sense.

### Future Extensions (v1.5 delta)
- **(v1.5, new)** A horizontal (left-of-control) label layout, if `"Who can join:"` stacked above the control ever proves too tall for a future, more vertically-constrained sidebar layout (mirrors `platform/ui/specification.md` v2's own Future Extensions item on this).
- **(v1.5, new)** Reusing this same label pattern for any future `DropdownWidget` consumer this or another feature adds, now that the generic component itself supports it (no specific future consumer is committed to by this amendment).
- **(v1.5, new, correction)** Reusing the `DROPDOWN_OVERLAY` ordinal/wiring pattern for any future `DropdownWidget` instance this feature might embed elsewhere in the sidebar (no specific future consumer is committed to by this amendment) — today `FriendsSidebarZOrder` gains exactly one new ordinal for exactly one `DropdownWidget` instance (the join-policy control); a second simultaneous `DropdownWidget` instance in this same sidebar, if one is ever added, would need its own planning-phase decision on whether it shares `DROPDOWN_OVERLAY` or needs its own ordinal, and — if that second instance's own open state is not itself mutually exclusive with `CONTEXT_MENU`/the first `DropdownWidget` the way this one is — a fresh mutual-exclusivity analysis rather than assuming this amendment's "order is inconsequential" conclusion still holds (out of scope today, no such second instance exists).
