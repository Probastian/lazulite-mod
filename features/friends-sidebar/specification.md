# Friends Sidebar — Feature Specification

## Overview
Adds `features/friends-sidebar`, a persistent overlay showing the player's Steam friends list, visible on every main-menu screen and on the in-game ESC/pause menu (`GameMenuScreen` / `PauseScreen`). Collapsed by default (avatars only), it expands on hover to show names, and every friend row is clickable (either mouse button) to open a small context menu (Open chat, Show profile, Invite to game, Join game). It is the first feature in this repo built directly on `SteamFriends` (`ISteamFriends`) rather than `ISteamRemoteStorage`, and — because it must render identically on many different vanilla screens rather than one specific screen — it is also the first feature whose injection shape is closer to a persistent screen-agnostic layer than a single Pattern-1 widget addition (see Architecture).

**v1.1 amendment (this revision):** the feature has since shipped (`70733ca`) and is being revised in place based on live-testing feedback: full corner-flush right-side docking, a heavily scaled-down row size, a pinned/sticky own-profile row above a scrollable friends list, status text (persona state or Rich Presence), and Steam-status-colored borders/text. These are additive requirement groups (`FR4.x`, `FR5.x` below) layered onto the same architecture already described in this document — no existing requirement is renumbered or removed; superseded specifics (e.g. the original `x=6,y=6` left-edge anchor) are called out explicitly where they are revised rather than silently dropped.

Everything below treats concrete Minecraft/steamworks4j class and method names exactly as confident as their citation allows: names confirmed via this repo's own prior `javap`-verified findings (`.claude/context/minecraft.md`'s Known Cross-Version API Differences table) are stated as fact; names sourced only from web documentation/javadoc mirrors (not yet verified against this repo's actual resolved jars) are explicitly flagged **"unconfirmed — verify via `javap` before implementation"**, per this repo's own stated research discipline (`.claude/context/minecraft.md:19-30`, `92-96`). This revision's own research pass had **no shell/`javap` tool available** (spec-authoring ran with `Read`/`Glob`/`Grep`/`Write`/`WebFetch`/`WebSearch` only) — every new steamworks4j citation below (`SteamUser.getSteamID()`, `getFriendRichPresence`) is sourced from a direct `WebFetch` of the pinned-tag (`1.10.0`) GitHub source at `code-disaster/steamworks4j`, the same technique (and the same level of confidence) the existing `implementation-plan.md`'s own "Existing Implementation" section already used and flagged for `SteamFriends`/`SteamUtils`/`OverlayToUserDialog` — **not** independently `javap`-confirmed against this repo's own resolved `steamworks4j-1.10.0.jar` (present at `platform/fabric-*/build/processIncludeJars/steamworks4j-1.10.0.jar`); planning/implementation should do that confirmation as its first concrete step for any new `SteamUser`/rich-presence code, exactly as prior work already did for the original `SteamFriends`/`SteamUtils` surface.

## Goals
- Render one persistent friends sidebar, present on: `TitleScreen` and every other screen reachable from the main menu while no world/server session is active (e.g. `SelectWorldScreen`, `MultiplayerScreen`, `RealmsMainScreen`, `OptionsScreen`, and any other screen shown before a game session starts), and on the in-game pause menu (`GameMenuScreen` (Yarn) / `PauseScreen` (Mojang)).
- Default state: collapsed, showing only each friend's avatar image (smallest/32px Steam avatar), stacked vertically.
- Hover state: hovering anywhere on the collapsed sidebar expands the **whole sidebar** (not per-row) to show every friend's persona name next to their avatar.
- Every rendered friend row responds to both left-click and right-click by opening one context menu, positioned at the current mouse cursor location, with exactly four options: **Open chat**, **Show profile**, **Invite to game**, **Join game**.
- Populate the sidebar from `SteamFriends`'s live friend list (Steam-account friends, matching the flag scope decided in Requirements), refreshed periodically rather than once at startup, since presence/online-status/joinability change during a session.
- Keep all business logic (which friends to show, row layout/ordering, context-menu option availability given a friend's current state, hover/expand state machine) unit-testable on a plain JVM wherever this repo's own precedent shows it is feasible (`philosophy.md:9`; `features/steam-cloud-sync/specification.md:14`) — the concrete Steam/Minecraft calls stay confined to `services`/`platform` per the Dependency Rules.
- **(v1.1)** Dock the sidebar fully flush into the corner of the screen it occupies (no visible gap to the screen edge), on the **right** edge of the screen rather than the left, at every allow-listed screen's current width (screen-width-dependent, not a fixed pixel offset).
- **(v1.1)** Shrink the sidebar's visual footprint substantially (row/avatar size roughly halved) so it reads as a compact always-on presence indicator rather than a prominent panel, while keeping name/status text legible (a smaller, but less drastic, text-size reduction than the avatar's).
- **(v1.1)** Always show the local player's own Steam identity (avatar, name, status) as a permanently-visible first row, pinned above a separately scrollable list of friends — the sidebar is no longer "friends only."
- **(v1.1)** Give every row (own profile and friends) a status-colored border and a status text line, using Steam's real current online-status color convention, with Rich Presence text preferred over the raw persona-state word when available for a given friend.

## Non-goals
- Full in-game chat window/conversation UI behind "Open chat" — v1 opens Steam's own overlay chat dialog for that friend (`ISteamFriends::ActivateGameOverlayToUser(steamID, "chat")`) rather than building a native in-mod chat UI. A custom in-mod chat window is a Future Extension.
- A custom in-mod profile viewer behind "Show profile" — v1 opens Steam's own overlay profile dialog (`ActivateGameOverlayToUser(steamID, "steamid")`) rather than rendering profile data (bio, level, games) inside a Minecraft screen.
- Friend-list management (add/remove/block friends) — Steam's own overlay already owns this; this feature is read-only against the friends list.
- Voice chat, party/lobby systems, or any matchmaking beyond a single "invite"/"join" action per friend.
- Any server-side or dedicated-server behavior — Steam Friends, like Steam Cloud, is a purely client-side, locally-running-Steam-client capability (mirrors `services/specification.md:18`); this feature never loads on a dedicated server.
- Rendering the sidebar during actual gameplay (HUD-visible while playing, not paused) — v1 scope is explicitly "main menu screens AND the pause menu" only, per the stated goal; an always-on HUD variant is a Future Extension.
- Rendering the sidebar over any main-menu-family screen this project cannot cheaply hook via `ScreenEvents.AFTER_INIT` — if a given screen turns out unreachable by that mechanism, exclusion from v1 is acceptable and should be logged, not force-fitted with a screen-specific mixin (see Requirements/Architecture for the "all main-menu screens" scoping decision). `RealmsMainScreen` is in v1 scope (Requirements, FR2.2); this Non-goal covers only a screen unexpectedly turning out unreachable.
- Any new steamworks4j dependency/version change — reuses the exact pinned `steamworks4j` version and Jar-in-Jar wiring the Steam Cloud Sync / bootstrap work already established (`services/specification.md:64-71,95`).
- Rich presence key/value **design** (`SteamFriends.setRichPresence`) remains out of scope — **v1.1 reads** `getFriendRichPresence` (a friend's own game/other-application-set values), it does not define or set this mod's own rich-presence keys; a Lazuli-specific rich-presence schema (this mod calling `setRichPresence` for its own sessions) is unchanged as a Future Extension. "Joinable" state (Invite/Join enablement) is still not derived from rich presence in this version — that remains `FriendGameInfo`-based per FR1.2/FR3.3/FR3.4, unaffected by v1.1.
- Persisting any friends-sidebar-specific data to Steam Cloud — this feature has no save state of its own; it is a live, read-only view over Steamworks' own friend list (see Persistence).
- An actual invite/join connection mechanism behind "Invite to game"/"Join game" — v1 ships both options as visible, but disabled/greyed-out placeholder buttons only (see Requirements FR2.6, FR3.3, FR3.4). No connect-string, rich-presence-driven join, or real Minecraft auto-connect flow is implemented in v1; that mechanism is deferred to a Future Extension.
- **(v1.1)** Per-row expand/collapse, drag-to-reposition, or any other new interaction mode beyond what's listed in Goals — the sidebar's existing collapsed/expanded and click/context-menu model is otherwise unchanged; v1.1 only touches position, size, own-profile row, scrolling, and status color/text.
- **(v1.1)** A user-configurable status-color palette or a settings screen for row size/position — the values this revision specifies are fixed constants (Configuration), matching this feature's existing "no in-game editor yet" precedent.

## Requirements

**Cross-cutting**
- **FR0.1** The feature depends on the same shared `SteamworksService`/`SteamAvailability` bootstrap the Steam Cloud Sync feature already depends on (`services/src/main/java/de/lazuli/services/steamworks/SteamworksService.java`), obtained via the same `SteamworksServiceHandoff` static-holder hand-off pattern already established between composition roots (`platform/fabric-*/.../SteamCloudSyncClientInitializer.java:51`, referencing `SteamworksServiceHandoff.require()`). It never re-initializes Steamworks itself.
- **FR0.2** If `SteamAvailability.isSteamAvailable()` is `false` at the point this feature's composition-root wiring runs, the sidebar is never constructed/attached to any screen, and no `SteamFriends` object is ever constructed — mirrors `features/steam-cloud-sync/specification.md:FR0.1`'s no-op-when-unavailable discipline. No exception escapes either way. **(v1.1)** This now also covers `SteamUser` (FR1.6) — neither `SteamFriends` nor `SteamUser` is constructed when Steam/the feature is unavailable.
- **FR0.3** A local JSON config (`config/friends-sidebar.json`) carries at minimum a master `enabled` boolean (default `true`), following the same flat-under-config-dir convention as every other feature's own config (`features/hello-world-main-menu/specification.md:122-123`; `features/steam-cloud-sync/specification.md:159-160`). If `enabled` is `false`, behaves identically to `isSteamAvailable() == false` (FR0.2).

**Friend data (business logic, `services`/`api`)**
- **FR1.1** Enumerates the caller's friend list via `SteamFriends.getFriendCount(FriendFlags)` / `getFriendByIndex(int, FriendFlags)` (confirmed method shapes: `com.codedisaster.steamworks.SteamFriends`, github.com/code-disaster/steamworks4j) using `FriendFlags.Immediate` (Valve's own documented flag for "users the current user is a friend of" — `partner.steamgames.com/doc/api/ISteamFriends`, `k_EFriendFlagImmediate`) as the default scope; a broader/narrower flag set is a planning-level decision, not fixed here.
- **FR1.2** For each friend `SteamID`, resolves: persona name (`getFriendPersonaName`), persona/online state (`getFriendPersonaState`) — used only to decide row ordering/graying, not to gate visibility (offline friends still show, per no stated exclusion), and joinability/game-played info (`getFriendGamePlayed(SteamID, FriendGameInfo)`) — populates a `FriendGameInfo`-shaped record whose fields determine (a) whether "Join game" is enabled/actionable for that friend and (b) what connect-string, if any, is later passed to `inviteUserToGame`.
- **FR1.3** Resolves each friend's avatar via `SteamFriends.getLargeFriendAvatar(SteamID)` (returns an opaque image handle, `int`; the shipped implementation uses the 184×184 "large" avatar rather than the small one, downscaled at draw time — see FR4.3/Architecture), then reads pixel data via `SteamUtils.getImageSize(image, int[] size)` / `getImageRGBA(image, ByteBuffer dest)` (confirmed shapes, `com.codedisaster.steamworks.SteamUtils`) into an RGBA byte buffer this feature's Version Adapter turns into a renderable Minecraft texture (see Architecture — Avatar Rendering). A friend whose avatar handle/image data isn't yet available (Valve's documented `AvatarImageLoaded_t` callback fires asynchronously the first time a given avatar is requested) renders a placeholder (e.g. a plain colored square or a generic vanilla icon) until the callback delivers real data, never blocking or throwing. **Confirmed hard-won rendering fact (do not re-derive):** Steam serves a placeholder image immediately, before the real avatar is delivered by `onAvatarImageLoaded` — the texture cache must treat the underlying `byte[]` reference as the cache key's freshness signal and re-upload whenever `FriendsService` hands it a *new* array instance for the same `steamId64`, never caching "first upload wins" forever (`AvatarTextureCache.getOrUpload`, `uploadedSource` reference-equality check — already implemented this way in the shipped code, `platform/fabric-26.2/.../AvatarTextureCache.java:56-68`; this must be preserved for any new avatar-adjacent code this revision adds, notably FR4.4's own-profile avatar).
- **FR1.4** The friend list + per-friend state is refreshed on a bounded interval (not per-tick, not per-render-frame; e.g. every N seconds, exact value a planning decision) rather than only once at feature startup — presence/joinability meaningfully changes during a session, and a stale sidebar showing a friend as offline/not-joinable after they've logged in would defeat the feature's purpose. Refresh work (the `getFriendCount`/`getFriendByIndex`/`getFriendPersonaName`/`getFriendGamePlayed` call sequence) is cheap, local IPC-backed calls per Valve's own docs, not network I/O — safe to run on the client thread at this cadence, consistent with this repo's existing "Steam calls are local IPC" understanding (`services/specification.md:115`).
- **FR1.5** Registers a `SteamFriendsCallback` (steamworks4j's own callback-object requirement, `SteamFriends(SteamFriendsCallback callback)` constructor) to receive `onPersonaStateChange`/`onAvatarImageLoaded`-shaped callback events (Valve: `PersonaStateChange_t`, `AvatarImageLoaded_t`) — delivered only while `SteamworksService`'s existing per-tick `SteamAPI.runCallbacks()` pump keeps running (already registered by the Steam Cloud Sync composition root's `ClientTickEvents.END_CLIENT_TICK`, and this feature's own composition root must confirm that same pump is already active rather than assuming/duplicating it — see Architecture).
- **FR1.6 (new, v1.1)** Resolves the **local player's own** Steam identity for the sidebar's permanent first row (FR4.4): `SteamUser.getSteamID()` (steamworks4j `com.codedisaster.steamworks.SteamUser`, constructor `SteamUser(SteamUserCallback)`; `getSteamID()` returns a `SteamID` — **sourced from a direct `WebFetch` of the pinned-tag `1.10.0` GitHub source, `java-wrapper/src/main/java/com/codedisaster/steamworks/SteamUser.java`; not independently `javap`-confirmed against this repo's own resolved jar this pass — flagged for implementation-time confirmation**), then reuses the **same** `SteamFriends` persona/avatar accessors already used for friends (FR1.2/FR1.3) — `getFriendPersonaName(SteamID)`, `getFriendPersonaState(SteamID)`, `getLargeFriendAvatar(SteamID)` — passed the local player's own `SteamID`. Valve's own `ISteamFriends` documentation states these "GetFriend*" accessors are also valid for the local user's own `SteamID` (there is no separate `GetPersonaName`/`GetLargeAvatar`-for-self call needed in the modern API — `ISteamFriends::GetPersonaName()`/`GetLargeFriendAvatar(SteamID)` with the local ID both exist and Valve's docs note `GetFriendPersonaName`/`GetFriendAvatar`-family calls also work when passed the local Steam ID), so no separate steamworks4j method beyond `SteamUser.getSteamID()` is needed to satisfy FR4.4 — **this exact behavior (that `getFriendPersonaName`/`getLargeFriendAvatar` accept the local user's own `SteamID` and return valid data unconditionally, i.e. without requiring `k_EFriendFlagImmediate`/a friend-list cache entry) is Valve-documentation-sourced only, not independently `javap`- or live-tested this pass; if it does not hold in practice, the fallback is `SteamFriends.getPersonaName()`/`getPersonaState()`(no-arg, self-only overloads, confirmed present in steamworks4j's `SteamFriends` per the existing implementation plan's own method inventory) plus `SteamUtils`' existing image-decode path applied to whatever avatar handle the self-only accessor yields — implementation's first concrete step for FR1.6 should confirm which path is actually needed via a real compile/`javap` pass, not assume the friend-accessor path works unconditionally.** No local-user Rich Presence is read (Rich Presence is a per-friend concept, FR1.7); the own-profile row's status text is always its persona-state word (FR4.8), never Rich Presence.
- **FR1.7 (new, v1.1)** For each **friend** (not the local user, FR1.6), attempts to resolve a Rich Presence status string via `SteamFriends.getFriendRichPresence(SteamID steamIDFriend, String key)` (steamworks4j — **sourced from the same `1.10.0`-tag `WebFetch` of `SteamFriends.java`; not independently `javap`-confirmed this pass**), using Valve's own documented `"status"` key (`partner.steamgames.com/doc/api/ISteamFriends` — Rich Presence's `"status"` key is Valve's own reserved, documented key specifically for "text that will show up in the 'View Game Info' dialog," i.e. a human-readable status string a game/application may set for that friend; confirmed via `WebSearch` of Valve's public docs page, not independently re-verified by a second direct fetch of the raw doc HTML this pass — flag as **Valve-documentation-sourced, not steamworks4j-jar-verified**, same citation-discipline tier as the rest of this key's usage). `getFriendRichPresence` returns an empty string `""` when no value is set for that key (Valve-documented, confirmed via `WebSearch`) — an empty result is treated as "no Rich Presence available for this friend," falling back to FR4.8's plain persona-state text, never rendered as blank/empty status text. Because Rich Presence values are cached locally and only refresh when explicitly requested, resolving this per friend also requires `SteamFriends.requestFriendRichPresence(SteamID)` (steamworks4j, same source tier) to be called at least once per friend (e.g. once per FR1.4 refresh sweep, or once per friend the first time it's seen) before `getFriendRichPresence` is trusted to return a non-stale value — exact call cadence (every refresh vs. only-once-then-callback-driven) is a planning decision; whichever is chosen must not add per-tick/per-frame Steam calls (Performance).
- **FR1.8 (new, v1.1)** `FriendSummary` (Public API) gains a `richPresenceStatus: String|null` field (or equivalent) populated by FR1.7, and `personaStateLabel()`-shaped derivation of the plain-text persona-state word (Offline/Online/Busy/Away/Snooze/Looking to Trade/Looking to Play — Valve's `PersonaState` enum constants, `com.codedisaster.steamworks.SteamFriends.PersonaState`, confirmed via the same `WebFetch` of `SteamFriends.java`: `Offline`, `Online`, `Busy`, `Away`, `Snooze`, `LookingToTrade`, `LookingToPlay`, `Invisible`) used whenever `richPresenceStatus` is null/empty (FR4.8).

**Rendering / overlay presence**
- **FR2.1** The sidebar renders as a fixed-position overlay (e.g. anchored to one screen edge — exact edge/position a planning/UI decision) on every currently-open instance of: `TitleScreen`, and every other screen this project classifies as "main menu family" (Requirements scoping list below), plus `GameMenuScreen`/`PauseScreen`. It must not consume click/hover input intended for the underlying vanilla screen's own widgets when the pointer is outside the sidebar's own bounds. **(v1.1 — superseded specifics, not the requirement itself)** The "which edge" question is no longer open: FR4.1/FR4.2 fix it to the screen's right edge, flush to the corner (`x=0, y=0` relative to that edge), superseding the shipped `x=6, y=6` left-edge anchor (`FabricFriendsSidebarInjector.java:71`, `new FriendSidebarWidget(6, 6, ...)`).
- **FR2.2** "Main menu family" screens in scope for v1: `TitleScreen`, `SelectWorldScreen`, `MultiplayerScreen`, `RealmsMainScreen`, `OptionsScreen` (opened from the title screen), and any screen reached by drilling into those (e.g. a server-edit screen) — a closed, enumerable set of `instanceof` checks per platform module's own screen classes, not an open-ended "every screen" rule (mirrors the existing per-screen `instanceof` filtering pattern already used, `FabricCloudOnlyWorldListInjector.java:54`). `RealmsMainScreen` is in v1 scope; its exact injection mechanics are now **confirmed** working per the shipped `FabricFriendsSidebarInjector` allow-lists (`.claude/context/minecraft.md`'s table row on `OptionsScreen`/`RealmsMainScreen` package names, confirmed via real compile) — unchanged by v1.1, all six screens named in the task's own allow-list (`TitleScreen`, `SelectWorldScreen`, `JoinMultiplayerScreen`, `OptionsScreen`, `PauseScreen`, `RealmsMainScreen`) already match the shipped `isAllowListed(Screen)` check (`FabricFriendsSidebarInjector.java:57-64`) on the 26.x side; the 1.21.11 module's own allow-list (Yarn class names) must be re-confirmed unchanged by this revision's own new rendering work (position/scroll/border), not assumed identical just because the screen-reachability question itself was already settled.
- **FR2.3** Collapsed state (default): renders each friend's avatar only, stacked vertically, no name text, minimal footprint. **(v1.1)** Now additionally always includes the pinned own-profile row (FR4.4) even in collapsed state — collapsed state has never meant "no rows," only "avatar-only, no name/status text"; this is unchanged in spirit, the own-profile row simply participates in collapsed/expanded the same way a friend row does.
- **FR2.4** Hover state: while the mouse is within the sidebar's overall bounds, the **entire sidebar** expands horizontally to render every friend's persona name text next to their avatar — this is whole-sidebar hover, not per-row hover; hovering anywhere on the collapsed sidebar expands all rows together, not just the row under the cursor. Returns to collapsed the instant the mouse leaves the sidebar's bounds — no click needed to collapse. **(v1.1)** Expanded state also now shows status text (FR4.8) under each row's name, own-profile row included; collapsed state shows neither name nor status text, consistent with FR2.3.
- **FR2.5** Every rendered friend row is clickable via either the left or right mouse button; either button opens the same context menu (no left/right distinction in behavior, unlike vanilla's own left-click-vs-right-click-context-menu convention elsewhere) — this is an explicit, deliberate simplification per the stated requirement, not an oversight.
- **FR2.6** The context menu renders at the screen-space position of the mouse cursor at the moment of the click (not anchored to the row), listing exactly: **Open chat**, **Show profile**, **Invite to game**, **Join game** — in that order, unless planning finds a strong reason to reorder. **Open chat** and **Show profile** are enabled per FR3.1/FR3.2. **Invite to game** and **Join game** are v1 **disabled/greyed-out placeholders** for every friend, regardless of that friend's actual state — no connect-string/rich-presence/actual invite-join mechanism exists yet in v1 (see Non-goals, FR3.3, FR3.4); the options are visible so the menu's shape is stable and forward-compatible, but always non-actionable in this version. A menu option that cannot currently apply is disabled/grayed rather than hidden, so the option set is visually stable regardless of a given friend's state — exact disabled-vs-hidden choice is a planning/UX decision but must be stated and applied consistently.
- **FR2.7** Clicking outside the open context menu, or pressing Escape, closes it without action — must not also trigger whatever `Escape` normally does on the host screen (e.g. must not simultaneously close the pause menu itself) while the context menu is open.
- **FR2.8 (new, v1.1)** Clicking the own-profile row (FR4.4) opens the **same** context menu shape as a friend row (FR2.6), but scoped to the local player's own identity: **Open chat** and **Invite to game**/**Join game** are meaningless for one's own account and must be disabled (never actionable, same visual convention as FR2.6's existing Invite/Join placeholders); **Show profile** remains enabled and calls `ActivateGameOverlayToUser(SteamID, "steamid")` with the local player's own `SteamID`, opening the player's own Steam overlay profile (Valve confirms this dialog works for the local user's own ID, same call shape as FR3.2). This is the smallest option-set change that keeps one context-menu widget/shape for both row kinds rather than introducing a second menu variant — planning may instead choose to suppress the context menu entirely for the own-profile row (no menu on click) if that's judged simpler; either choice must be stated and is not fixed further here.

**Layout, position & sizing (new, v1.1)**
- **FR4.1** The sidebar's outer bounds are flush to the screen corner it docks against: **zero** pixel gap between the sidebar's outer edge and the screen edges it touches (top and the edge it's anchored to — see FR4.2), i.e. `y = 0` and (per FR4.2) `x` computed against the live screen edge, not a fixed inset — supersedes the shipped `x=6, y=6` constant (`FabricFriendsSidebarInjector.java:71`).
- **FR4.2** The sidebar anchors to the **right** edge of the screen (previously the left), computed from each allow-listed screen's own current width at the time it's added (`ScreenEvents.AFTER_INIT`'s own `scaledWidth` parameter, already passed into `onScreenInit(Minecraft, Screen, int scaledWidth, int scaledHeight)` today, `FabricFriendsSidebarInjector.java:66` — simply unused for `x` positioning today and must be wired in), i.e. `x = scaledWidth - sidebarWidth`. Because the sidebar's width itself changes between collapsed and expanded (FR2.3/FR2.4), the **expanded** width must be used for this calculation so the sidebar's right edge stays pinned to the true screen edge in both states (expanding leftward into the screen, not rightward off-screen) — this is a behavior change from the shipped widget, whose `getX()` is currently a fixed left-anchor origin that the same value works for both states from (`FriendSidebarWidget.java:78`, `int width = expanded ? EXPANDED_WIDTH : COLLAPSED_WIDTH;` drawn from the same fixed `getX()`). Must be re-verified correct on every allow-listed screen at common resolutions/GUI scales (mirrors the existing UI section's own verification discipline).
- **FR4.3** Row/avatar size is reduced to roughly half the shipped size: the shipped `DISPLAY_SIZE = 32` (px, avatar/icon square) and derived `ROW_HEIGHT = DISPLAY_SIZE + ROW_PADDING * 2 = 40` (`FriendSidebarWidget.java:39-43`) should become roughly `DISPLAY_SIZE ≈ 16` and a correspondingly smaller `ROW_HEIGHT` (exact final pixel values are a planning/UX decision, "almost half" is the stated target, not an exact spec'd number) — the underlying 184×184 `getLargeFriendAvatar` source texture (FR1.3, `AvatarTextureCache.SIZE = 184`) is unaffected, only the on-screen draw size changes (the existing 12-arg `blit` call already separates sample-region size from draw size, `FriendSidebarWidget.java:96-99` — this is a pure constant/parameter change, not a new rendering mechanism). Name/status text (FR4.8) shrinks by a **smaller** factor than the avatar — e.g. rendering at a fractional GUI scale (`guiGraphics`'s pose-scale/`matrixStack.scale(...)`-equivalent around the text draw call) rather than switching to a genuinely smaller font resource, since Minecraft's default font has no smaller bitmap variant to switch to; exact scale factor a planning decision, but must remain legibly readable (not scaled down as aggressively as the icon) per the task's own explicit instruction.
- **FR4.4** The sidebar's first row is **always** the local player's own Steam profile (FR1.6's resolved `FriendSummary`-shaped self-record, or a small dedicated `OwnProfileSummary`-shaped type — a Public API/planning decision, see Public API below), regardless of friend-list contents — even with zero friends, the sidebar shows exactly one row (the player's own). This row is visually distinguished only by its fixed pinned position (FR4.6/FR4.7), not by different row chrome otherwise (same avatar/name/status/border rendering path as a friend row, parameterized by whichever `FriendSummary`-shaped record represents "self").
- **FR4.5** The sidebar has a thin border along its **left** edge — the edge facing into the screen's interior, which is the **left** edge now that the sidebar docks on the right (FR4.2; this is the edge that was previously the *right* edge back when the sidebar docked on the left, i.e. "the edge facing into the screen" is the stable concept the task specifies, not a fixed left/right literal — call this out explicitly since FR4.2's side-swap makes the literal edge flip). Border is a thin (1–2px) solid-color rectangle drawn via `guiGraphics.fill(...)` (the same primitive already used for the sidebar's background scrim, `FriendSidebarWidget.java:80` — no new rendering mechanism/texture needed for a flat-color border). Exact border color for the sidebar's *own* outer edge (as opposed to a per-row status border, FR4.10) is a plain neutral/UI-consistent color (e.g. the same semi-transparent dark tone already used for the background, or a slightly lighter shade of it) — not status-colored; only per-row borders (FR4.10) carry status color.
- **FR4.6** A border of the same thin style as FR4.5 separates the pinned own-profile row (FR4.4) from the scrollable friends list below it — a single 1–2px horizontal rule spanning the sidebar's width, drawn once between the own-profile row and the first friend row, present in both collapsed and expanded state.
- **FR4.7** The friends list **below** the own-profile row is scrollable via the mouse scroll wheel while the cursor is within the sidebar's bounds; the own-profile row (FR4.4) never scrolls — it stays visually pinned at the top of the sidebar at all times. This requires: (a) a scroll-offset concept — `FriendSidebarStateMachine` (the existing plain-JVM-testable class, NFR1) gains a bounded scroll-offset field/method (e.g. `int scroll(int currentOffset, double scrollDeltaY, int totalFriendRows, int visibleRows)` clamped to `[0, max(0, totalFriendRows - visibleRows)]`), kept free of `net.minecraft.*`/steamworks4j per its existing zero-Minecraft-import discipline (`FriendSidebarStateMachine.java`, confirmed today via direct read: no such imports present) — this is a pure, unit-testable clamp/accumulate function, the same shape as the class's existing `isExpanded(...)` method; (b) the platform Version Adapter (`FriendSidebarWidget`) wires the real mouse-scroll input event (that version's own `mouseScrolled`-shaped widget callback — exact signature not `javap`-confirmed this pass, a small/low-risk item since every `AbstractWidget`/equivalent already has *some* scroll-handling hook point) into that state-machine method, and offsets only the friend-row draw/click-hit-testing loop by the resulting scroll amount, never the own-profile row's fixed position. A scroll indicator (e.g. a simple truncation/fade at the bottom edge, or no visual indicator beyond the scroll itself working) is a planning/UX-level detail, not fixed here.
- **FR4.8** Each row (own profile and every friend) renders one line of status text directly below its name (only in expanded state, per FR2.4), using: (a) if `FriendSummary.richPresenceStatus` (FR1.7/FR1.8) is present and non-empty for that friend, that text; else (b) the plain persona-state word (Offline/Online/Busy/Away/Snooze/Looking to Trade/Looking to Play — FR1.8's `personaStateLabel()`). The own-profile row (FR4.4) always uses (b) — Rich Presence is a friend-relative concept in this version (FR1.7 explicitly friend-only), never resolved for the local player (FR1.6).
- **FR4.9** Status text (FR4.8) is colored per Steam's own real, current friends-list status-color convention — **researched, not guessed, but not independently pixel-sampled from a live Steam client this pass** (flagged below): modern Steam (the redesigned Friends UI, live as of this research date) uses a **blue/cyan** family of colors for every "online-but-not-in-a-game" persona state (`Online`, `Away`, `Busy`, `Snooze`, `LookingToTrade`, `LookingToPlay` all render as the same blue-ish "online" indicator color in the current Steam client — Steam's modern UI does **not** give each of these six states its own distinct hue; historical/pre-redesign Steam clients did distinguish some of these, which is why this needed active re-confirmation rather than assuming the old green-for-online convention still applies), a **green** color specifically for "in a game" (derived from `FriendGameInfo`/`inGame`, FR1.2 — **not** the same signal as `PersonaState`; a friend can be `PersonaState.Online` yet not `inGame`, in which case blue applies, not green), and a **grey** color for `Offline`/`Invisible`. Sourced via `WebSearch` (no official Valve-published hex/ARGB value exists for these UI colors — Steam does not document its own client's exact color constants the way it documents API behavior) — community-reverse-engineered approximate values found: online/away/busy/snooze/LTT/LTP ≈ `#57CBDE` (a cyan-blue), in-game ≈ `#90BA3C` (green), offline/invisible ≈ a neutral grey (no single confirmed hex found this pass, commonly rendered around `#898989`–`#8F98A0` range in various third-party Steam-badge tools; **treat as an approximate placeholder, confirm by live color-sampling an actual Steam client's Friends panel during implementation/verification**, this is the single most important "verify, don't just implement" item this revision introduces). Final ARGB constants (full 8-hex `0xFFxxxxxx`, alpha byte set — **the shipped `AvatarTextureCache`/text-rendering code already learned the hard way that a zero-alpha color silently no-ops `GuiGraphicsExtractor.text(...)`, e.g. `0xFFFFFF` draws nothing because its alpha byte is `0x00` — every new color constant this revision introduces, status text and status border alike, must be a full 4-byte ARGB literal with `0xFF` alpha, never a bare 3-byte RGB literal**) are a planning-time decision informed by this research, not fixed as exact hex here beyond the approximate values above.
- **FR4.10** Each row's border (own profile and every friend, a thin 1–2px rectangle around that row's own bounds, same drawing primitive as FR4.5/FR4.6) is colored using the **same** status-color convention as FR4.9 (blue-ish for online-not-in-game, green for in-game, grey for offline/invisible) — i.e. the row border communicates the same information the status text's color already does, redundantly-but-consistently (a friend's row border and their status text are always the same color for a given render). This border is separate from, and drawn in addition to, the sidebar's own outer-edge border (FR4.5) and the own-profile/friends-list separator (FR4.6), which are both non-status-colored per FR4.5.

**Rendering — cross-version fact base (new, v1.1, informational — not itself a numbered requirement, referenced by FR4.x above)**
The following facts, already learned the hard way during this feature's initial implementation and confirmed via real compiles against this repo's own resolved jars, apply to **all** new v1.1 rendering work (borders, scroll, resized rows, own-profile row) on the two Mojang-mapped (26.1/26.2) modules, and must be positively re-confirmed (not assumed) for any genuinely new call shape introduced on the Yarn-mapped 1.21.11 module:
- `GuiGraphicsExtractor.blit(Identifier, ...)`'s fractional-UV convenience overload silently draws **nothing** on 26.1/26.2 — the explicit 12-argument overload, `blit(RenderPipeline, Identifier, x, y, u, v, width, height, regionWidth, regionHeight, textureWidth, textureHeight)` with `RenderPipelines.GUI_TEXTURED` as the pipeline, is the one that actually renders (already the shipped call shape, `FriendSidebarWidget.java:98-99` — any new blit call this revision adds, e.g. for a resized/repositioned avatar, must keep using this exact overload, not the shorter one).
- `GuiGraphicsExtractor.text(...)` silently no-ops if the supplied color's alpha byte is `0` (e.g. `0xFFFFFF` has zero alpha and draws nothing) — colors must be full ARGB with a non-zero alpha byte (`0xFFFFFFFF`, not `0xFFFFFF`) — directly relevant to FR4.9's new status-text colors and FR4.5/FR4.6/FR4.10's new border colors if any border ever needs to be drawn via a text-adjacent API rather than `fill(...)` (borders drawn via `fill(...)` are unaffected by this specific bug, since `fill` already takes a full ARGB int and the shipped code already passes one, `FriendSidebarWidget.java:80`, `0x99000000` — but any new color constant introduced anywhere in this revision should still be written as a full 8-hex literal defensively, consistent with this lesson).
- Avatars are fetched via `SteamFriends.getLargeFriendAvatar` (184×184), downscaled at draw time via the 12-arg `blit`'s region-vs-display-size parameters (FR1.3/FR4.3) — already the shipped approach, unaffected by this revision beyond changing the display-size constant.
- `AvatarTextureCache` must re-upload whenever the underlying `byte[]` reference changes (Steam serves a placeholder before `onAvatarImageLoaded` delivers the real image) — never cache forever on first upload (FR1.3's cross-reference above; already the shipped behavior, must be preserved for the own-profile row's avatar too, FR4.4).
- **1.21.11 (Yarn) is confirmed unaffected by the three 26.x-specific bugs above** (its `DrawContext`-based `drawTexturedQuad`/`drawTextWithShadow`-equivalents don't share `GuiGraphicsExtractor`'s fractional-blit or zero-alpha-text quirks) — this was true for the feature's *original* rendering surface. **For the new v1.1 surface specifically (bordered rows, scroll-offset-adjusted drawing, the own-profile row, any new blit/fill/text call shape)**: this spec does **not** assume 1.21.11 remains unaffected just because its prior, narrower surface was — implementation must positively re-verify each new call this revision adds compiles and renders correctly on 1.21.11's own `DrawContext`/`Screen.render(...)` model (`.claude/context/minecraft.md`'s table row on this exact divergence, `Screen.render(DrawContext,...)` vs. `extractRenderState(GuiGraphicsExtractor,...)`) rather than porting the 26.x fix blindly; if in doubt, flag as needing implementation-time verification (mirrors this document's own existing citation discipline, `.claude/context/minecraft.md:19-30`).

## Architecture
Layering: `features/friends-sidebar` depends on `api` (`FriendSummary`, `FriendSidebarHook`, `FriendActionListener`, `SteamAvailability`) and `services` (`SteamworksService`), per the Dependency Rules table (`architecture.md:64-71`). It never depends on `features/steam-cloud-sync` or any other feature (`architecture.md:74`); the two features share only the `services`-layer `SteamworksService` bootstrap, not each other. Unchanged by v1.1.

```
platform/fabric-<version>/.../FriendsSidebarClientInitializer  (composition root)
        |  obtains via SteamworksServiceHandoff.require() (same pattern as SteamCloudSyncClientInitializer)
        v
services/steamworks/SteamworksService  (shared bootstrap; already ticking via ClientTickEvents.END_CLIENT_TICK)
        |  constructs (only if isSteamAvailable())
        v
features/friends-sidebar/services/FriendsService
        |  wraps
        v
com.codedisaster.steamworks.SteamFriends (+ SteamFriendsCallback)  /  SteamUtils  /  SteamUser (v1.1, FR1.6)
        |
        v
Steam client (local IPC) -> friend list, persona/game state, avatar image handles, local SteamID, friend rich presence (v1.1)
```

Rendering flow: `FriendsService.currentFriends()` (+ v1.1's own-profile accessor) -> `FriendSidebarHook.updateFriends(...)` (api-layer, Minecraft-agnostic) -> `FabricFriendsSidebarInjector`/`FriendSidebarWidget` (platform Version Adapter) draws the sidebar/rows/context-menu using real `Screen`/`GuiGraphics` calls, and forwards row/menu clicks back through `FriendActionListener` -> `FriendsService`'s action methods -> `SteamFriends`. Unchanged in shape by v1.1; only the widget's own drawing constants/logic (position, size, borders, scroll, status text) change.

**Injection shape:** resolved (Architecture's original central open question) — Pattern 1 (`ScreenEvents.AFTER_INIT` + `Screens.getWidgets`), one `FabricFriendsSidebarInjector` per module, no mixin for the sidebar's own presence/rendering (confirmed sufficient, shipped). v1.1 introduces no new injection-shape question — it only changes what the same already-injected `FriendSidebarWidget` draws and how it computes its own `x`/scroll offset, not how or where it's attached to a screen. The context-menu Escape/outside-click interception (`ScreenMouseEvents.beforeMouseClick`/`ScreenKeyboardEvents.allowKeyPress`, `FabricFriendsSidebarInjector.java:75-76,96-108`) is confirmed working via Pattern 1 alone (no mixin fallback was needed) and is unaffected by v1.1's own-profile-row addition (FR2.8 reuses the exact same menu-open/close plumbing).

**Avatar rendering:** unchanged mechanism from the original spec/plan (`SteamUtils.getImageSize`/`getImageRGBA` -> RGBA bytes -> `AvatarTextureCache`'s per-`steamId64` dynamic-texture upload, `NativeImage`/`DynamicTexture` on 26.x per `.claude/context/minecraft.md`'s now-confirmed table row) — v1.1 reuses this identical mechanism for the own-profile row's avatar (FR4.4), keyed by the local player's own `steamId64` the same way a friend's is, no new upload code path needed beyond calling the existing `AvatarTextureCache.getOrUpload(steamId64, rgba)` with the local player's own values.

**Threading:** unchanged — all `SteamFriends`/`SteamUtils`/`SteamUser` calls happen on the same thread `SteamAPI.init()` ran on, per the existing documented Steamworks threading constraint (`services/specification.md:85`). v1.1's new `SteamUser`/rich-presence calls are folded into the same existing tick-driven refresh sweep (FR1.4/FR1.6/FR1.7), no new thread or executor.

**Composition-root ordering:** unchanged, inherits the same already-flagged `SteamworksServiceHandoff` ordering dependency as before.

## UI
- **Position/anchor**: **(v1.1, supersedes)** flush to the **right** edge of the screen (`x = scaledWidth - expandedWidth`), `y = 0` — zero gap to either the top or right screen edge (FR4.1/FR4.2). Must not overlap vanilla's own title-screen logo/splash text or button rows on any of the allow-listed screens, at common resolutions/GUI scales, same as before — but now re-verified against the **right** edge specifically (the original left-edge verification does not automatically transfer; e.g. `JoinMultiplayerScreen`'s server-list scrollbar or `OptionsScreen`'s right-column buttons may sit closer to the right edge than the left edge's own vanilla content did).
- **Collapsed row**: one small avatar image per row (own profile pinned first, then friends), stacked vertically, fixed width — width and avatar size both roughly halved per FR4.3.
- **Expanded state** (whole-sidebar hover, FR2.4): the entire sidebar expands together — every row shows avatar plus persona name **and now a status text line** (FR4.8) to one side, wider footprint; must not push/resize other on-screen vanilla widgets. Hovering a single row does not expand that row alone; the sidebar has exactly two states, collapsed and expanded, driven by whether the mouse is anywhere within the sidebar's bounds.
- **Own-profile row (v1.1)**: always the first row, pinned/sticky, separated from the friends list below by a thin non-status-colored rule (FR4.6); never scrolls (FR4.7).
- **Friends list (v1.1)**: scrollable via mouse wheel, offset accumulated/clamped by `FriendSidebarStateMachine` (FR4.7); no page/scrollbar-thumb widget is specified as required, a simple wheel-driven offset is sufficient per the stated requirement.
- **Borders (v1.1)**: sidebar's own left-facing outer edge (FR4.5, neutral color), own-profile/friends separator (FR4.6, neutral color), and per-row status-colored border (FR4.10, blue/green/grey per FR4.9) — three visually distinct border concepts, not to be conflated into one color/meaning.
- **Status text (v1.1)**: one line below each row's name in expanded state, Rich-Presence-preferred-else-persona-state text (FR4.8), colored per FR4.9.
- **Context menu** (FR2.5-2.7, FR2.8): a small vertical list of exactly four text options at the mouse's click position, rendered above/overlapping whatever screen is currently open (including, when open on the pause menu, above the pause menu's own buttons); **Invite to game** and **Join game** always render visually distinguished as disabled/greyed-out placeholders in v1 (FR2.6, FR3.3, FR3.4); **Open chat**/**Show profile** render enabled for a friend row. **(v1.1)** For the own-profile row (FR2.8), **Open chat**/**Invite to game**/**Join game** all render disabled, only **Show profile** enabled.
- **No dedicated settings/management screen in v1/v1.1** — only the `enabled` config toggle (Configuration); row size/position/status colors are fixed constants, not user-configurable (Non-goals) — a Mod-Menu-integrated or in-game settings screen remains a Future Extension.
- Manual, per-supported-version in-game verification is required (not unit-testable), per `ui-guidelines.md`'s Testing section — **v1.1 adds** right-edge-overlap-per-screen, own-profile-row-always-present (including the zero-friends case), scroll-wheel behavior, and status-color accuracy (against a live Steam client, since no exact hex value is Valve-documented) to the existing manual verification matrix.

## Configuration
`config/friends-sidebar.json`, same flat-under-config-dir convention as every other feature:
```json
{
  "enabled": true,
  "refreshIntervalSeconds": 5
}
```
- `enabled`: master switch (default `true`); even when `true`, has no effect unless `SteamAvailability.isSteamAvailable()` (FR0.2).
- `refreshIntervalSeconds`: already-shipped field (implementation plan Decision 7), rate-limits `FriendsService.tick()`'s refresh sweep (FR1.4) — v1.1's new rich-presence resolution (FR1.7) is folded into this same sweep, not a new interval.
- Malformed/missing file falls back to defaults with a logged warning, same pattern as `HelloWorldMainMenuConfigIO.load(...)`.
- **(v1.1)** No new config field is introduced by this revision's own requirements — row size, border thickness/colors, and the status-color palette are fixed implementation constants (Non-goals), not exposed here.

## Events
- Consumes, does not define, Fabric API's `ScreenEvents.AFTER_INIT` (module `fabric-screen-api-v1`) for the FR2.2 allow-listed screens, and `ClientTickEvents.END_CLIENT_TICK` only insofar as it must confirm the shared Steamworks callback pump is already running (it does not register its own second pump — see Architecture).
- Also already consumes `ScreenMouseEvents.beforeMouseClick`/`ScreenKeyboardEvents.allowKeyPress` (per-screen, registered once per allow-listed screen's own `onScreenInit`, `FabricFriendsSidebarInjector.java:75-76`) for context-menu dismissal (FR2.7) — this was left as an open architecture question in the original spec and is now confirmed-shipped, no mixin needed.
- Consumes steamworks4j's own `SteamFriendsCallback`-delivered events (`PersonaStateChange_t`/`onPersonaStateChange`, `AvatarImageLoaded_t`/`onAvatarImageLoaded`) to know when to re-query a friend's state or re-fetch/re-upload an avatar, rather than polling every possible field every refresh tick.
- **(v1.1)** No new callback/event type is introduced by FR1.6/FR1.7 — the local player's identity and friends' rich presence are both resolved synchronously within the existing tick-driven `refresh()` sweep, not via a new asynchronous callback registration (Rich Presence's own Valve-documented async delivery mechanism, `FriendRichPresenceUpdate_t`, is **not** used here — this spec's FR1.7 relies on `requestFriendRichPresence` + polling `getFriendRichPresence` within the existing sweep cadence instead, the simpler of the two available approaches; if implementation finds the polling approach yields stale/empty results too often, switching to consuming `FriendRichPresenceUpdate_t` via the same `SteamFriendsCallback` class already used for FR1.5 is the natural escalation, flagged here as a plausible implementation-time adjustment, not committed to now).
- Defines no new cross-feature event bus type — none exists yet in this repo (`architecture.md:26`), and this feature has no cross-feature signaling need.

## Networking
No new client-server packets; entirely client-only (mirrors `services/specification.md:18`). The only "networking" is Steam's own client-to-Valve-backend and client-to-client communication via the local Steam client process, opaque to this mod, same framing already established for Steam Cloud Sync. v1 ships no invite/join networking at all — "Invite to game"/"Join game" are disabled placeholders (FR3.3, FR3.4) with no `inviteUserToGame` call and no Minecraft-server-connect step wired up. **(v1.1)** Reading a friend's Rich Presence (FR1.7) does not change this — it's the same local-IPC-to-Steam-client channel every other `SteamFriends` call already uses, not a new networking surface, and it still feeds only *display text* (FR4.8), never a connect/join decision (Non-goals). Whatever "Join game"'s actual Minecraft-server-connect step ends up using is unchanged, still a Future Extension design question.

## Persistence
None. This feature holds no on-disk state of its own beyond its one small config file (Configuration) — the friend list, persona data, local-user identity (v1.1), rich presence text (v1.1), and avatar images are all live, in-memory, Steamworks-sourced state, re-fetched/refreshed per session and never written to disk by this feature.

## Performance
- Friend-list/state refresh (FR1.4): bounded-interval, not per-tick; each refresh is a small number of cheap local-IPC `SteamFriends` calls proportional to friend-list size, not proportional to render-frame rate. **(v1.1)** The new local-user resolution (FR1.6) and per-friend rich-presence resolution (FR1.7, `requestFriendRichPresence` + `getFriendRichPresence`) are folded into this same bounded sweep — FR1.7 in particular adds up to two extra calls per friend per sweep (`requestFriendRichPresence` + `getFriendRichPresence("status")`), still small-number-of-cheap-local-IPC-calls-proportional-to-friend-count, not a new performance class.
- Avatar texture upload: performed once per friend per `AvatarImageLoaded_t` event (or on first request), cached thereafter — never re-uploaded every frame. **(v1.1)** The own-profile row's avatar (FR4.4) follows the identical cache/re-upload discipline, keyed by the local player's own `steamId64` — no special-casing that adds per-frame cost.
- Sidebar/context-menu rendering itself: ordinary per-frame Minecraft widget drawing, no heavier than any other overlay widget already in this codebase. **(v1.1)** The new per-row border draws (FR4.10) and the sidebar/separator border draws (FR4.5/FR4.6) are additional `fill(...)` calls per frame, proportional to visible row count (already bounded by `MAX_ROWS`/the viewport, FR4.7) — negligible relative to the existing avatar-blit-per-row cost; the scroll-offset computation itself (FR4.7) is an O(1) clamp per scroll event, not per frame.
- No blocking I/O or network calls on the render/client thread at any point.
