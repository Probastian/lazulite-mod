# Friends Sidebar — Feature Specification

## Overview
Adds `features/friends-sidebar`, a persistent overlay showing the player's Steam friends list, visible on every main-menu screen and on the in-game ESC/pause menu (`GameMenuScreen` / `PauseScreen`). Collapsed by default (avatars only), it expands on hover to show names, and every friend row is clickable (either mouse button) to open a small context menu (Open chat, Show profile, Invite to game, Join game). It is the first feature in this repo built directly on `SteamFriends` (`ISteamFriends`) rather than `ISteamRemoteStorage`, and — because it must render identically on many different vanilla screens rather than one specific screen — it is also the first feature whose injection shape is closer to a persistent screen-agnostic layer than a single Pattern-1 widget addition (see Architecture).

**v1.1 amendment (prior revision):** the feature has since shipped (`70733ca`) and was revised in place based on live-testing feedback: full corner-flush right-side docking, a heavily scaled-down row size, a pinned/sticky own-profile row above a scrollable friends list, status text (persona state or Rich Presence), and Steam-status-colored borders/text. These are additive requirement groups (`FR4.x`, `FR5.x` below) layered onto the same architecture already described in this document — no existing requirement is renumbered or removed; superseded specifics (e.g. the original `x=6,y=6` left-edge anchor) are called out explicitly where they are revised rather than silently dropped.

**v1.2 amendment (this revision):** today, whenever Steam is unavailable (Steam not running, not launched through Steam / missing `steam_appid.txt`, or a native-library load failure) the sidebar is **fully hidden** — driven by `facade.setEnabled(steamworksService.isSteamAvailable() && config.enabled())` in each platform module's `FriendsSidebarClientInitializer` (confirmed byte-for-byte identical across `platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2` — see Existing Implementation), and `FriendSidebarWidget.renderNow()`'s early-return on `!facade.isEnabled()`. This gives the user no visible signal that anything is wrong: the sidebar simply never appears, indistinguishable from the user having disabled it themselves via `config.enabled()`. This revision separates those two cases: **user-disabled** (`config.enabled() == false`) still fully hides the sidebar exactly as today; **Steam-unavailable-but-feature-enabled** (`config.enabled() == true && !steamworksService.isSteamAvailable()`) now renders the sidebar in a compact **status** state — a single-line, right-docked message in place of the own-profile row and friends list — rather than hiding it. No new Steamworks call, callback, or native surface is introduced; this is a presentation/state-plumbing change confined to `features/friends-sidebar` (`FriendsSidebarFacade`, `FriendsDataSource`) and the platform Version Adapters (`FriendSidebarWidget`), following the same interleaved-amendment convention v1.1 already established in this document (existing FR/NFR IDs are never renumbered; new ones are added).

Everything below treats concrete Minecraft/steamworks4j class and method names exactly as confident as their citation allows: names confirmed via this repo's own prior `javap`-verified findings (`.claude/context/minecraft.md`'s Known Cross-Version API Differences table) are stated as fact; names sourced only from web documentation/javadoc mirrors (not yet verified against this repo's actual resolved jars) are explicitly flagged **"unconfirmed — verify via `javap` before implementation"**, per this repo's own stated research discipline (`.claude/context/minecraft.md:19-30`, `92-96`). This revision's own research pass had **no shell/`javap` tool available** — every claim below about `SteamworksService`/`FriendsSidebarClientInitializer`/`FriendSidebarWidget`/`FriendsSidebarFacade`/`NoopFriendsService`/`FriendsSidebarConfig` behavior is sourced from a direct `Read` of this repo's own current source files (cited by `file:line` throughout), not from external documentation — no new Steamworks API surface is introduced by v1.2, so no new `javap`-unconfirmed citation is added by this revision.

## Goals
(v1/v1.1 goals unchanged — see below; this revision's own goal is additive.)
- Render one persistent friends sidebar, present on: `TitleScreen` and every other screen reachable from the main menu while no world/server session is active (e.g. `SelectWorldScreen`, `MultiplayerScreen`, `RealmsMainScreen`, `OptionsScreen`, and any other screen shown before a game session starts), and on the in-game pause menu (`GameMenuScreen` (Yarn) / `PauseScreen` (Mojang)).
- Default state: collapsed, showing only each friend's avatar image (smallest/32px Steam avatar), stacked vertically.
- Hover state: hovering anywhere on the collapsed sidebar expands the **whole sidebar** (not per-row) to show every friend's persona name next to their avatar.
- Every rendered friend row responds to both left-click and right-click by opening one context menu, positioned at the current mouse cursor location, with exactly four options: **Open chat**, **Show profile**, **Invite to game**, **Join game**.
- Populate the sidebar from `SteamFriends`'s live friend list (Steam-account friends, matching the flag scope decided in Requirements), refreshed periodically rather than once at startup, since presence/online-status/joinability change during a session.
- Keep all business logic (which friends to show, row layout/ordering, context-menu option availability given a friend's current state, hover/expand state machine) unit-testable on a plain JVM wherever this repo's own precedent shows it is feasible (`philosophy.md:9`; `features/steam-cloud-sync/specification.md:14`) — the concrete Steam/Minecraft calls stay confined to `services`/`platform` per the Dependency Rules.
- **(v1.1)** Dock the sidebar fully flush into the corner of the screen it occupies (no visible gap to the screen edge), on the **right** edge of the screen rather than the left, at every allow-listed screen's current width (screen-width-dependent, not a fixed pixel offset).
- **(v1.1)** Shrink the sidebar's visual footprint substantially (row/avatar size roughly halved) so it reads as a compact always-on presence indicator rather than a prominent panel, while keeping name/status text legible (a smaller, but less drastic, text-size reduction than the avatar's).
- **(v1.1)** Always show the local player's own Steam identity (avatar, name, status) as a permanently-visible first row, pinned above a separately scrollable list of friends — the sidebar is no longer "friends only."
- **(v1.1)** Give every row (own profile and friends) a status-colored border and a status text line, using Steam's real current online-status color convention, with Rich Presence text preferred over the raw persona-state word when available for a given friend.
- **(v1.2, new)** When the feature is enabled by config but Steam itself is unavailable, the sidebar must still render *something* visible (a status line), so a user is never left wondering whether the feature silently vanished, crashed, or was never enabled — distinct from the deliberate, user-chosen full-hide when `config.enabled() == false`.
- **(v1.2, new)** The status message must be understandable and (at least minimally) actionable by a non-technical player — e.g. "Steam not available" rather than a raw `InitResult` enum name or stack trace — while remaining a single generic message rather than Steamworks-internal failure-mode detail (see Requirements FR6.1 for the collapse-vs-distinguish decision and its justification).

## Non-goals
(v1/v1.1 non-goals unchanged — see prior revision for the full list, e.g. no custom in-mod chat/profile UI, no friend-list management, no HUD-during-gameplay variant, no new steamworks4j version. This revision adds:)
- **(v1.2)** Surfacing distinct, per-failure-reason status messages (e.g. "native library load failed" vs. "Steam not running" vs. "no `steam_appid.txt`") is explicitly **not** in scope for this revision — see FR6.1's justification. A single generic "Steam unavailable" status message is what ships; richer diagnostics remain a Future Extension.
- **(v1.2)** No retry/reconnect button or automatic re-check of Steam availability after startup — `SteamworksService.create(...)` runs once, at composition-root time, and its result is immutable for the process lifetime (`SteamworksService.java:44-59`, no re-`create` path exists); this revision does not add one. The status message is static for the session once shown.
- **(v1.2)** No change to `SteamworksService`'s public surface (`isSteamAvailable()`, `steamAppId()`, `pumpCallbacks()`, `shutdown()`) or to any other feature that depends on `SteamAvailability` (e.g. Steam Cloud Sync) — this revision is scoped entirely to `features/friends-sidebar` and its platform Version Adapters.
- **(v1.2)** No change to the own-profile row's or friends list's rendering, layout constants, borders, scroll behavior, or status-color convention (FR4.x, unchanged) — those only continue to apply when Steam *is* available; the status state (FR6.x) is a distinct, simpler render path that replaces them, not a variant of them.
- **(v1.2)** No localization/translatable-text system is introduced for the new status string — it is a plain literal `Text`/string, consistent with this feature's existing UI text (row labels, menu options) which are likewise not yet localized.

## Requirements

**Cross-cutting**
- **FR0.1** The feature depends on the same shared `SteamworksService`/`SteamAvailability` bootstrap the Steam Cloud Sync feature already depends on (`services/src/main/java/de/lazuli/services/steamworks/SteamworksService.java`), obtained via the same `SteamworksServiceHandoff` static-holder hand-off pattern already established between composition roots (`platform/fabric-*/.../SteamCloudSyncClientInitializer.java:51`, referencing `SteamworksServiceHandoff.require()`). It never re-initializes Steamworks itself.
- **FR0.2** If `SteamAvailability.isSteamAvailable()` is `false` at the point this feature's composition-root wiring runs, no `SteamFriends` object is ever constructed — mirrors `features/steam-cloud-sync/specification.md:FR0.1`'s no-op-when-unavailable discipline. No exception escapes either way. **(v1.1)** This now also covers `SteamUser` (FR1.6) — neither `SteamFriends` nor `SteamUser` is constructed when Steam/the feature is unavailable. **(v1.2, superseded specifics, not the requirement itself)** Previously, `isSteamAvailable() == false` also meant the sidebar was never attached/rendered at all (`facade.setEnabled(false)`); this is superseded by FR6.2/FR6.3 below — the `FriendsDataSource` construction behavior (never constructing a real `FriendsService`/`SteamFriends` when unavailable) is unchanged, only the sidebar's *visibility* decision changes.
- **FR0.3** A local JSON config (`config/friends-sidebar.json`) carries at minimum a master `enabled` boolean (default `true`), following the same flat-under-config-dir convention as every other feature's own config (`features/hello-world-main-menu/specification.md:122-123`; `features/steam-cloud-sync/specification.md:159-160`). **(v1.2, superseded specifics)** Previously, "If `enabled` is `false`, behaves identically to `isSteamAvailable() == false` (FR0.2)" — i.e. both cases fully hid the sidebar identically. This is superseded by FR6.2: `config.enabled() == false` still fully hides the sidebar (unchanged, user's deliberate choice is still honored as a full hide), but `isSteamAvailable() == false` with `config.enabled() == true` no longer behaves identically to the user-disabled case — see FR6.2/FR6.3.

**Friend data (business logic, `services`/`api`)** — FR1.1 through FR1.8 unchanged by v1.2 (friend enumeration, persona/avatar/game-info resolution, refresh cadence, callback registration, own-profile resolution, Rich Presence — see prior revision's text above `## Public API` for full detail; none of this logic runs when Steam is unavailable, in v1.2 exactly as before).

**Rendering / overlay presence** — FR2.1 through FR2.8 unchanged by v1.2 (screen allow-list, collapsed/expanded states, click/context-menu behavior) — these all describe behavior that only applies once the sidebar is actually showing friend-list content (FR6.3's "content" branch); the status branch (FR6.4-FR6.7) is additive, not a modification of these.

**Layout, position & sizing** — FR4.1 through FR4.10 unchanged by v1.2 (right-edge docking, row/avatar sizing, own-profile row, borders, scroll, status-color text) — again, these govern the "content" branch only.

**Context menu actions** — FR3.1 through FR3.5 unchanged by v1.2 — the status branch has no rows and therefore no context menu (FR6.6).

**Steam availability status display (new, v1.2)**
- **FR6.1** `SteamworksService.create(...)`'s failure modes are collapsed into a **single, generic** "Steam unavailable" status for display purposes, rather than being surfaced with distinct per-cause messages. Justification, based on direct reading of `SteamworksService.java:84-112`:
  - `SteamworksService` only exposes `isSteamAvailable(): boolean` (`SteamworksService.java:138-141`) and `steamAppId(): long` to any caller; the specific failure branch (native-library load failure, `SteamAPI.initEx()` returning a non-`OK` `InitResult`, a caught `SteamException`, or a caught `RuntimeException`/`UnsatisfiedLinkError`) is only ever passed to the **constructor-time** `warningLogger` callback (`create`'s own `Consumer<String> warningLogger` parameter, `SteamworksService.java:84`) and is never retained on the object itself — there is no field, enum, or accessor carrying that reason forward past the `create(...)` call.
  - Distinguishing these reasons for on-screen display would therefore require a **new public field/accessor on `SteamworksService`** (e.g. an `Optional<String> unavailableReason()` or a `enum UnavailableReason` set alongside the existing boolean in each of the four failure-branch returns, `SteamworksService.java:90,98,104,110`) — a change to a `services`-layer class shared by every feature that depends on `SteamAvailability` (currently at least Steam Cloud Sync, per `services/specification.md`'s own cross-feature framing), not something scoped to `features/friends-sidebar` alone. That is a materially larger blast radius than this revision's stated goal (make the sidebar visible when Steam is unavailable), and is explicitly deferred (Future Extensions).
  - A single generic message can still be reasonably actionable without per-cause detail — e.g. "Steam not available — make sure Steam is running and this game was either launched through Steam or has a valid `steam_appid.txt`" already mirrors the wording `SteamworksService.create` itself logs for the most common cause (`SteamworksService.java:95-97`), giving the player the same practical guidance without this feature needing to know *which* specific branch fired.
  - If a future revision wants distinct messages (e.g. "native library failed to load" vs. "not signed into Steam"), FR6.1 explicitly does not preclude that — it only states v1.2 does not attempt it, given today's `SteamworksService` API surface.
- **FR6.2** The sidebar's visibility now has **three** possible outcomes at composition-root time, computed from the same two inputs already read today (`steamworksService.isSteamAvailable()`, `config.enabled()`, `FriendsSidebarClientInitializer.java:54,59` on every platform module) — no new input is introduced:
  1. `config.enabled() == false` -> sidebar **fully hidden** (unchanged from today's behavior for this specific case) — a user's own deliberate opt-out is still honored exactly as before, regardless of Steam's availability. This is a deliberate design choice reaffirmed by this revision: disabling the feature is a stronger, user-initiated signal than an unavailable-Steam condition, and should not be second-guessed into showing a status message the user didn't ask to see.
  2. `config.enabled() == true && steamworksService.isSteamAvailable() == false` -> sidebar renders in the new **status** state (FR6.4-FR6.7) — this is the behavior change this revision introduces.
  3. `config.enabled() == true && steamworksService.isSteamAvailable() == true` -> sidebar renders exactly as it does today (own-profile row + friends list, FR1.x-FR4.x) — the **content** state, unchanged.
- **FR6.3** `FriendsSidebarFacade` (`features/friends-sidebar/services/FriendsSidebarFacade.java`) is the single place this three-way decision is threaded from composition root to Version Adapter, replacing today's single `setEnabled(boolean)` call (`FriendsSidebarFacade.java:62-65`, currently just stores one `enabled` boolean consumed by `isEnabled()`) with a shape that can express all three outcomes above. Exact shape is a planning decision (Public API below sketches the smallest viable option), but must satisfy: (a) a Version Adapter (`FriendSidebarWidget`) must be able to distinguish "don't render at all" from "render, but show status instead of content" from "render content normally" without inferring it indirectly from `facade.friends().isEmpty()` (an empty friend list is a normal, valid content-state outcome — e.g. a player with zero Steam friends — and must never be misread as the Steam-unavailable status state); (b) the composition root (`FriendsSidebarClientInitializer`, all three platform modules) computes outcome 1 vs. 2 vs. 3 using only `config.enabled()` and `steamworksService.isSteamAvailable()`, exactly as today's two booleans already allow, with no new Steamworks call.
- **FR6.4** In the status state (FR6.2 outcome 2), the sidebar still docks at the same right-edge, flush-to-corner position as the content state (FR4.1/FR4.2, unchanged reference point) so its presence is spatially consistent regardless of which state is showing — a user who has learned "the sidebar lives in the top-right corner" should find it there whether it's showing friends or a status message.
- **FR6.5** In the status state, the sidebar renders a single-line (or short, wrapped 2-3 line) text message in place of **both** the pinned own-profile row (FR4.4) and the scrollable friends list (FR4.7) — neither section renders at all in this state, since neither `FriendsService` (nor any `SteamFriends`/`SteamUser` instance) exists to source them from (FR0.2, unchanged: no real `FriendsDataSource` is constructed when Steam is unavailable, only `NoopFriendsService`, `FriendsSidebarClientInitializer.java:54-56`). The status message text is the single generic string described in FR6.1.
- **FR6.6** The status state has no clickable rows and therefore no context menu (FR2.5-FR2.8 do not apply — there is nothing to click). Mouse-scroll (FR4.7) is likewise inert in this state — there is no scrollable content. The sidebar in this state does not intercept clicks/scroll intended for the underlying screen outside its own (now much smaller) bounds, same non-interference guarantee as the content state already provides (FR2.1).
- **FR6.7** The status state still supports the same collapsed/expanded (hover) sizing model as the content state where practical (FR2.3/FR2.4) — e.g. collapsed shows a small indicator (an icon, a compact glyph, or a narrow colored bar — exact visual a planning/UX decision), and hovering expands the sidebar's width enough to show the full status text, mirroring the existing hover-to-reveal-detail interaction users already learn from the content state — **or**, if planning judges a single always-expanded-width status bar simpler and no worse for a message this rare, that is an acceptable alternative; either choice must be stated and applied consistently. This is the only FR6.x item left genuinely open for planning to resolve either way.
- **FR6.8** No new Steamworks/`steamworks4j` call, callback registration, or native surface is introduced anywhere by FR6.1-FR6.7 — this revision only threads the two already-read booleans (`isSteamAvailable()`, `config.enabled()`) differently through `FriendsSidebarFacade`/`FriendSidebarWidget`; it does not query `SteamworksService`/`SteamFriends` any more or less often than today.
- **FR6.9** Applies identically across all three platform modules (`platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`) — confirmed via direct read that `FriendsSidebarClientInitializer.java` is byte-for-byte identical logic in all three today (differing only in the 26.2 copy's one extra explanatory comment line, `platform/fabric-26.2/.../FriendsSidebarClientInitializer.java:66-67`; 1.21.11 and 26.1 have no such comment) — see Architecture for how this revision avoids re-introducing a fourth divergence point.

**Non-functional**
- **NFR1-NFR5** unchanged by v1.2 (plain-JVM-testable business logic where feasible; no uncaught Steamworks exception reaches the render/tick thread; JavaDoc-with-usage-example on public types; feature folder layout; `FriendsService` remains the sole `com.codedisaster.steamworks.*`-importing class — v1.2 adds no new Steamworks import anywhere, consistent with NFR5).
- **NFR6 (new, v1.2).** The three-way visibility decision (FR6.2/FR6.3) and the status-vs-content branch selection in `FriendSidebarWidget.renderNow()` (FR6.4-FR6.7) must each be expressible as, or delegate to, a plain-JVM-testable function wherever feasible (mirrors NFR1) — e.g. a small pure method on `FriendsSidebarFacade` or `FriendSidebarStateMachine` such as `visibilityState(): SidebarVisibility` (or equivalent) that a unit test can exercise directly with constructed booleans, without touching `net.minecraft.*`/steamworks4j, rather than the decision living only inline inside `FriendSidebarWidget.renderNow()`'s Minecraft-rendering method where it cannot be unit-tested.
- **NFR7 (new, v1.2).** Consistency across platform modules for this specific change is an explicit acceptance criterion, not just a stylistic preference — given `FriendsSidebarClientInitializer.java`'s confirmed-identical logic across all three modules today (FR6.9), planning/implementation must either (a) apply the composition-root change identically to all three files, verified by a direct diff showing only the pre-existing comment divergence remains, or (b) extract the shared decision into a single non-platform-specific location (Architecture's `FriendsSidebarComposer` suggestion below) so there is only one place to get it right instead of three. Either approach is acceptable; leaving any one of the three modules on the old two-outcome (`enabled`/fully-hidden) behavior while the others move to three-outcome behavior is not.

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision (same convention as `features/hello-world-main-menu/specification.md:53`). v1.2 additions only — v1/v1.1's `FriendSummary`, `FriendSidebarHook`, `FriendActionListener`, `FriendsSidebarConfig`, `FriendsService`, `FriendSidebarStateMachine` are unchanged in shape (see prior revision's text above for their full description).

5. **`features/friends-sidebar/services/FriendsSidebarFacade`** (`features/friends-sidebar/services/FriendsSidebarFacade.java`) — **(v1.2)** its existing `setEnabled(boolean)`/`isEnabled()` pair (currently the *only* signal a Version Adapter reads to decide whether to render anything at all, `FriendSidebarWidget.java:181-183,314-316,348`) is extended, not replaced, to carry the three-way outcome from FR6.2:
   - Smallest viable option (suggested default): keep `setEnabled(boolean)`/`isEnabled()` meaning exactly what they mean today — "should the sidebar attach/render at all" (`true` unless `config.enabled() == false`) — and add a second, independent setter/getter pair, e.g. `void setSteamAvailable(boolean available)` / `boolean isSteamAvailable()` (name deliberately mirroring `SteamAvailability.isSteamAvailable()` so a reader immediately recognizes what it reflects), defaulting to `true` (matching the facade's existing `enabled = true` default field, `FriendsSidebarFacade.java:40`) until the composition root calls it. `FriendSidebarWidget.renderNow()` then becomes: return early if `!facade.isEnabled()` (outcome 1, unchanged early-return shape); else if `!facade.isSteamAvailable()`, render the FR6.4-FR6.7 status branch; else render content exactly as today.
   - Alternative (also acceptable, a planning decision): a single tri-state accessor, e.g. `enum SidebarVisibility { HIDDEN, STEAM_UNAVAILABLE, ACTIVE }` plus `SidebarVisibility visibility()`, computed once by the composition root and passed via one setter — marginally more type-safe (impossible to construct the nonsensical "not enabled but steam available" combination that the two-boolean option technically allows, even though the composition root would never actually produce it) at the cost of touching more call sites that currently call `isEnabled()` directly (`FriendSidebarWidget.java:181,314,348`).
   - Either shape must expose a status-message accessor for the widget to render, e.g. `String steamUnavailableMessage()` (or the message could simply be a widget-side constant, since FR6.1 fixes it to one generic string not sourced from `SteamworksService` — a planning decision whether the string lives in the facade, the widget, or a shared constant in `api`/`features/friends-sidebar/api`).
6. **`platform/fabric-<version>/.../FriendsSidebarClientInitializer`** — **(v1.2)** the two identical lines `FriendsDataSource dataSource = (steamworksService.isSteamAvailable() && config.enabled()) ? ... : new NoopFriendsService();` and `facade.setEnabled(steamworksService.isSteamAvailable() && config.enabled());` (`FriendsSidebarClientInitializer.java:54-59`, all three modules) are replaced with the FR6.2 three-way computation — `dataSource` selection (real `FriendsService` vs. `NoopFriendsService`) keeps its existing two-input condition unchanged (FR0.2 is unaffected: a real `FriendsService`/`SteamFriends` is still only constructed when both are true), while the facade is now told about `config.enabled()` and `steamworksService.isSteamAvailable()` **separately** rather than pre-ANDed into one boolean, per item 5 above.

## Architecture
Layering unchanged from v1/v1.1 (`features/friends-sidebar` depends on `api` and `services` only, never another feature — `architecture.md:64-71,74`). **(v1.2)** This revision's only architectural addition is optional, addressing NFR7/FR6.9's cross-platform-consistency requirement:

- **Recommended: a small shared composition helper.** Rather than editing the same few lines identically in `platform/fabric-1.21.11`, `platform/fabric-26.1`, and `platform/fabric-26.2`'s `FriendsSidebarClientInitializer.java` (a triplication this feature has carried since it first shipped, `FR6.9`'s confirmed-identical-logic finding), this revision is a natural point to introduce a single factory method — e.g. a static `FriendsSidebarComposer.create(SteamworksService steamworksService, SteamFriendsGateway gateway, FriendsSidebarConfig config, Consumer<String> warningLogger)` returning a small record/holder of the already-wired `FriendsDataSource` + `FriendsSidebarFacade` — living in `features/friends-sidebar/services` (a location every platform module already depends on and imports from, `FriendsSidebarClientInitializer.java:5-9`), so all three composition roots call one shared method instead of duplicating the same conditional three times. This does not change the Dependency Rules (`features/friends-sidebar` already depends on `services`-layer `SteamworksService`/`SteamFriendsGateway` types, `FriendsSidebarClientInitializer.java:13-14`; a factory method taking those same types as parameters introduces no new dependency direction) — it only moves already-duplicated logic to a single owning location, the same kind of consolidation this repo's own `SteamworksServiceHandoff`/`SteamFriendsGatewayHandoff` static-holder pattern already demonstrates a preference for (shared, single-owner wiring helpers in a neutral layer, rather than copy-pasted platform-module logic) — though those two specific handoffs are hand-off/registry patterns solving a different problem (crossing a composition-root boundary), not a precedent for *this exact* factory-method shape; they are cited here only as evidence this codebase already reaches for a shared-helper-over-triplication solution when the same problem (three platform modules needing the same wiring) has come up before.
- **Acceptable alternative: edit all three files identically.** If planning judges a new shared factory class disproportionate for a two-line behavior change, editing all three `FriendsSidebarClientInitializer.java` files identically (verified by direct diff) satisfies NFR7 equally well — this spec does not mandate the extraction, only that *one* of these two paths is taken deliberately, rather than the change silently landing on only one or two of the three modules.
- No change to the existing composition-root ordering dependency (`SteamworksServiceHandoff`/`SteamFriendsGatewayHandoff`/`WorldHostingBridgeHandoff`, all unchanged, `FriendsSidebarClientInitializer.java:42-43,66-67`).
- No change to the `FabricFriendsSidebarInjector`/Pattern-1 (`ScreenEvents.AFTER_INIT`) injection shape — the status branch is drawn by the same already-injected `FriendSidebarWidget.renderNow()`, just taking a different internal branch (Public API item 5) instead of early-returning.

Rendering flow (status branch, new): `FriendsSidebarClientInitializer` reads `steamworksService.isSteamAvailable()` + `config.enabled()` -> `FriendsSidebarFacade.setEnabled(config.enabled())` / `.setSteamAvailable(steamworksService.isSteamAvailable())` (or the tri-state equivalent) -> `FriendSidebarWidget.renderNow()` branches on `facade.isEnabled()` (early-return if `false`, unchanged) then on `facade.isSteamAvailable()` (status branch if `false`, content branch if `true`, both newly explicit instead of today's single combined early-return). No `FriendsDataSource`/`FriendsService`/`SteamFriends` involvement in the status branch — it renders directly off the two facade flags, never off `facade.friends()`/`facade.localProfile()` (FR6.3(a)'s explicit "don't infer from empty friend list" guard).

## UI
**(v1.2, new — status state; v1/v1.1's content-state UI, FR4.x, is unchanged, see prior revision's UI section above)**
- **Position/anchor**: identical reference point to the content state — flush to the screen's right edge, `y = 0` (FR6.4, reusing FR4.1/FR4.2's existing `x = scaledWidth - width` computation, just with a smaller/status-appropriate `width`).
- **Collapsed status indicator**: a small, low-visual-weight indicator (icon/glyph/colored bar — exact treatment a planning/UX decision, FR6.7) rather than the friends-list collapsed avatar strip (FR2.3) — there are no avatars to show in this state.
- **Expanded status message**: on hover (or always, if planning takes FR6.7's simpler always-expanded alternative), a short, plain-language message — e.g. "Steam not available" plus the slightly longer guidance sentence from FR6.1's suggested wording — rendered with the same text-drawing primitives/pitfalls already documented for the content state (full-alpha `0xFFxxxxxx` color literals, never a bare 3-byte RGB literal — the same zero-alpha-no-op lesson recorded for FR4.9/FR4.10 applies to any new color this status text introduces).
- **No rows, no borders-per-row, no scroll, no context menu** in this state (FR6.5/FR6.6) — visually much simpler than the content state; a plain rectangle/scrim (reusing the same `context.fill(...)` background-scrim primitive already used today, `FriendSidebarWidget.java:255` on the 1.21.11 side) plus one text draw call is sufficient.
