# Main Menu — Bug-Fix Specification (Post-Launch Fixes 3)

## Overview
This is a **bug-fix spec**, not a redesign: it root-causes and specifies the corrected behavior for three defects found in the "Stonebound" main menu after commits `0d71821` (3D-scaffolded rework) and `6fb32ec` (post-launch fixes), across all three platform modules (`platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`, package `de.lazuli`). All three modules mirror the same class shapes; this spec cites the `fabric-26.2` copies as the reference (confirmed structurally identical entry points/method names across the three per the existing `features/main-menu/specification.md` Compatibility section) — planning/implementation must apply each fix to all three copies.

1. **Bug 1** — the right-hand friends sidebar (`FriendSidebarWidget`) does not reliably process clicks on its rows/dropdown, while its own footer (Options/Quit) buttons and `MainMenuScreen`'s tab bar do.
2. **Bug 2** — the center content panel's vertical margins (`MainMenuScreen.panelY()`/panel height) are asymmetric relative to the tab bar's full-height span.
3. **Bug 3** — several panels (`WorldsPanel`, `ServersPanel`, `StorePanel`, `WardrobePanel`) render content that diverges from `design_handoff_main_menu/README.md` in concrete, fixable ways (missing elements, wrong data format, undersized swatches, no proportional scaling).

## Goals
- Root-cause Bug 1's click-dispatch failure precisely (which code path is broken, under what conditions) and specify the exact fix so clicks on sidebar rows/dropdown are as reliable as clicks on the sidebar's own footer buttons and the tab bar.
- Specify a symmetric-margin formula for the center panel (Bug 2) derived from the *existing* top gap, requiring only a formula change, not new layout architecture.
- Enumerate concrete, file/line-referenced discrepancies between the four tab panels and the design handoff (Bug 3), each described as (current position/value) vs (design-specified position/value), so planning can scope fixes without re-deriving root cause.

## Non-goals
- No new widget architecture, no rewrite of `FriendSidebarWidget`'s state machine, no change to `friends-sidebar`'s reuse contract (`features/main-menu/specification.md` FR7.6) — Bug 1's fix is a hit-testing correction inside the existing class shape.
- No re-litigating the panel's overall flex-row layout (spacer / center panel / tab bar / sidebar) — Bug 2 is a formula fix within `MainMenuScreen`'s existing `panelX()`/`panelY()`/panel-height call sites, not a new layout model.
- No pixel-identical reproduction of the HTML prototype's CSS effects (blur, box-shadow) — Bug 3 only covers layout/positioning/data-format discrepancies that are reproducible with Minecraft-native primitives already in use, not new rendering techniques.
- No full proportional GUI-scale rescaling system is designed here in detail — Bug 3 flags the absence of one (every panel uses fixed pixel literals against the panel's actual pixel width/height, never against a canonical 1920×1080 reference), but the concrete scaling mechanism (if planning decides to add one) is left to planning; this spec only documents where fixed literals currently diverge from the README's stated proportions at the reference size.

## Requirements

### Bug 1 — Friends sidebar rows/dropdown not interactable

**Confirmed structure (not a hypothesis):** `MainMenuScreen.init()` (`platform/fabric-26.2/src/main/java/de/lazuli/mainmenu/MainMenuScreen.java:89`) adds `sidebar` via `addRenderableWidget(sidebar)`; `MainMenuScreen.mouseClicked()` (`MainMenuScreen.java:212-213`) calls `super.mouseClicked(event, doubleClick)` first, which (via `Screen`'s `ContainerEventHandler`-style child dispatch) calls `sidebar.mouseClicked(...)` directly — top-level dispatch is structurally sound, `FriendSidebarWidget` receives every click event routed to it.

**Root cause, confirmed by reading `FriendSidebarWidget.java` in full (`platform/fabric-26.2/src/main/java/de/lazuli/friends/FriendSidebarWidget.java`):**

`FriendSidebarWidget.mouseClicked()` (lines 681-732) gates **every** sub-region (own-profile row, footer Options/Quit, join-policy dropdown, friend rows) behind a single top-of-method call: `if (!isMouseOver(event.x(), event.y())) return false;` (line 693). `isMouseOver()` (lines 756-764) is the sole gate for the entire widget's input, so any discrepancy in its bounds affects footer, dropdown, and row clicks identically at the gate level — but two distinct, independently-confirmed bugs inside it produce the asymmetric symptom the report observed (footer registers, rows/dropdown don't):

1. **Width bug (animation-window mismatch).** `isMouseOver()` line 762 computes hit-test width as `int width = expanded ? EXPANDED_WIDTH : COLLAPSED_WIDTH;` — the animation's **target** width — whereas the actually-drawn width for the current frame is `Math.round(animatedWidth)` (set in `renderNow()`, lines 407-410, and used to position `getX()`/`getY()` at line 433 and to draw the footer/rows at their real screen coordinates). `animatedWidth` only reaches `EXPANDED_WIDTH`/`COLLAPSED_WIDTH` after the ~120ms width-transition completes (`WIDTH_ANIM_PX_PER_SECOND`, line 97, ≈1366px/s over a (180-16)px = 164px span). During that transition — and specifically during the **coyote-time collapse** (lines 384-401: `expanded` flips to `false` the instant `coyoteExpired` is true, line 394-395, which can happen on a frame where `animatedWidth` is still near `EXPANDED_WIDTH` because the width anim hasn't caught up yet) — `isMouseOver()` immediately narrows its hit-test box to `COLLAPSED_WIDTH` while the widget is still visually drawn near its expanded width for one or more subsequent frames. A click landing in that still-visually-wide-but-now-narrow-hit-tested region (which is exactly where rows/dropdown live, since they only render once `showText` is true near full expansion, `line 431`) fails the `isMouseOver` gate and the whole `mouseClicked` call returns `false` before reaching the row/dropdown logic further down.
2. **Height bug (overflow-branch mismatch, not animation-dependent — reproducible any time the friend list is long enough to fill the visible rows).** `renderNow()` computes the drawn `height` at lines 358-364: `height = totalHeight(friends.size())`, **but then overrides it** to `screenHeight - topInset` whenever `friends.size() >= maxRows` (the list fills/overflows the available rows, extending flush to the window edge rather than leaving a rounding remainder). `isMouseOver()` (line 761) **only ever calls `totalHeight(facade.friends().size())`** — it never replicates that overflow branch. Whenever a player has enough friends to fill `maxRows`, the widget is drawn taller (flush to the window bottom) than `isMouseOver()`'s computed box, so `isMouseOver()`'s box is **shorter** than the real drawn rect. Depending on exactly how much shorter (a function of `ROW_HEIGHT`/`maxRows` rounding), this can leave part of the *bottom* of the drawn widget — where the footer sits — outside `isMouseOver()`'s box while rows nearer the top remain inside it, or vice versa, meaning footer and row/dropdown click reliability diverge based on friend-list length and window size, independent of any animation state.

Both of these are the same class of defect: **`isMouseOver()` recomputes width/height independently from constants and a snapshotted `expanded` flag, instead of reusing the exact width/height `renderNow()` actually drew for the current frame.** The footer's own hit-test (lines 699-708) is comparatively more forgiving in casual testing only because `footerOptionsY`/`footerQuitY`/`footerWidth` are cached from the *same* `renderNow()` call that drew them (lines 559-561), so once a click passes the outer `isMouseOver()` gate, the footer's own internal bounds are always self-consistent with what's on screen that frame — but the footer is still just as capable of failing the outer gate as rows/dropdown are; the report's observation that it "always" works is consistent with footer clicks more often landing during idle (non-transitioning, non-overflowing) frames where `isMouseOver()`'s independently-computed box happens to coincide with the real one, not because footer has a separate, correct hit-test path.

**Desired behavior (fix target):**
- **FR-B1.1** `isMouseOver()` must use the exact same width and height values that were actually drawn for the current frame — not independently recomputed target/animation-unaware constants. Concretely: cache the frame's actual drawn `width` (the `Math.round(animatedWidth)` value used in `renderNow()`) and actual drawn `height` (the value after the `friends.size() >= maxRows` overflow branch is applied) into instance fields at the end of `renderNow()` (mirroring the existing `footerOptionsY`/`footerQuitY`/`footerWidth`/`dropdownX`/`dropdownY`/`dropdownWidth` "cache what was actually drawn" pattern already used elsewhere in this class), and have `isMouseOver()` read those cached fields instead of recomputing `expanded ? EXPANDED_WIDTH : COLLAPSED_WIDTH` and `totalHeight(...)`.
- **FR-B1.2** The handle-only collapsed state's `isMouseOver()` branch (line 758-759, `isOverHandle`) is unaffected by this bug (fixed `HANDLE_WIDTH`/`HANDLE_HEIGHT`, no animation-dependent sizing) and needs no change.
- **FR-B1.3** After the fix, a click on any part of the sidebar that is actually visibly drawn that frame (footer, dropdown when open, own-profile row, any visible friend row) must be accepted by the `isMouseOver()` gate; a click outside the actually-drawn rect must be rejected — verified specifically: (a) clicking a row/dropdown immediately after triggering the hover-expand (still mid-animation), (b) clicking anywhere on the sidebar within the ~250ms coyote window after the mouse leaves the hover zone (`COYOTE_NANOS`, line 92) while `animatedWidth` is still shrinking, and (c) clicking the footer/rows with a friends list long enough to trigger the `friends.size() >= maxRows` overflow-height branch.
- **FR-B1.4** No change to `mouseScrolled()`'s own independent width/height computation (lines 734-754) is required by this bug report, but planning should note it has the same latent "recomputed target width, not actual drawn width" pattern (line 740: `int width = expanded ? EXPANDED_WIDTH : COLLAPSED_WIDTH;`) and may want to apply the identical fix there for consistency, even though it wasn't explicitly reported as broken.

### Bug 2 — Panel margin/height asymmetry

**Confirmed in `MainMenuScreen.java`:**
- `panelY()` (line 123-125): `return (int) (height * 0.22);` — top gap between the tab bar's top (`barY = 0`, line 181) and the panel's top.
- Panel height is computed independently, inline, at **two** call sites rather than via a shared method: `extractRenderState()` line 152 and `mouseClicked()` line 232, both: `int h = (int) (height * 0.62);`
- Tab bar spans the full window height: `barHeight = height` (line 182), `barY = 0` (line 181).
- Resulting bottom gap: `height - panelY() - h = height - 0.22·height - 0.62·height = 0.16·height` — asymmetric vs. the `0.22·height` top gap, confirmed by direct arithmetic on the two literals above.

**Desired behavior (fix target):**
- **FR-B2.1** The panel must use its full available height between the tab bar's top and bottom edges, split into a top margin and a bottom margin of **equal size**, both equal to the *current* top-gap value (`panelY()`, unchanged at `height * 0.22`) — i.e., do not change what the top margin *is*, only make the bottom margin match it and let the panel height absorb the difference.
- **FR-B2.2** Concrete formula: replace both hardcoded `(int) (height * 0.62)` literals with a single shared computation `panelHeight() = height - 2 * panelY()`. With `panelY() = 0.22 * height`, this yields `panelHeight() = height * (1 - 0.44) = height * 0.56` (down from the current `0.62`), which by construction leaves a bottom gap of `height - panelY() - panelHeight() = height - 0.22·height - 0.56·height = 0.22·height`, exactly matching the top gap.
- **FR-B2.3** Introduce a single `panelHeight()` method (mirroring the existing `panelX()`/`panelY()`/`panelWidth()` accessor pattern already in this class, lines 119-129) and replace both inline `(int) (height * 0.62)` occurrences (`extractRenderState()` line 152, `mouseClicked()` line 232) with calls to it, so the two call sites can never drift out of sync with each other again (the current duplication is itself a latent bug risk independent of the margin math, worth fixing at the same time since it's the same lines).
- **FR-B2.4** No other panel-content layout code needs to change to satisfy this bug fix — panels already receive `x, y, w, h` as parameters and lay out their own content relative to those bounds (`WorldsPanel.render`, `ServersPanel.render`, etc.), so a smaller/repositioned `h` and unchanged `y` automatically propagates; planning should verify no panel's internal content (e.g. `ServersPanel`'s per-row `if (rowY + rowHeight > y + height) break;` truncation logic) assumed the old `0.62` ratio in a way that would clip content it didn't clip before (visual regression risk to flag in verification, not a design change to make now).

### Bug 3 — Panel content positioning vs. design handoff

Reference: `design_handoff_main_menu/README.md` (canvas reference 1920×1080, values below quoted from it directly). Current code: `platform/fabric-26.2/src/main/java/de/lazuli/mainmenu/{WorldsPanel,ServersPanel,StorePanel,WardrobePanel}.java` (mirrored in the other two platform modules).

**Systemic issue — no proportional scaling.** The design doc explicitly states its values are "against a 1920×1080 reference canvas" and must scale "proportionally to the real `scaledWidth`/`scaledHeight`" (`features/main-menu/specification.md:148`). None of the four panels do this: every literal in `WorldsPanel`/`ServersPanel`/`StorePanel`/`WardrobePanel` (`CARD_SIZE = 96`, `ROW_HEIGHT_EXPANDED = 72`, `bannerHeight = 72`, button widths `160`/`140`/`100`/`110`, etc.) is a fixed pixel constant applied directly against the panel's actual on-screen pixel width/height, with no reference-canvas conversion factor anywhere in these four files. This is the root cause underlying several of the per-panel discrepancies below (elements are sized/spaced as if the panel is always the same absolute pixel size, when `panelWidth()`/`panelHeight()` actually vary with window size and GUI scale). Flagged here as the umbrella finding; per-panel items below are its concrete symptoms plus a few independent data/element-presence gaps.

**WorldsPanel** (`WorldsPanel.java`):
- **FR-B3.1** Design: expanded row shows a "96×96px 2×2 thumbnail grid (4 colored tiles representing a world preview)" (`README.md:43`). Current: `render()` (lines 104-140) draws a **single** icon at `iconSize = (rowHeight - IMAGE_MARGIN*2) * 2/3` (line 118) — for the expanded row (`ROW_HEIGHT_EXPANDED = 72`), that's a ~46px single square, not a 2×2 four-tile grid at any size. The compact-row single-icon rendering is correct per design ("Unselected row: single thumbnail," `README.md:44`), but the expanded state's distinct 4-tile grid is entirely absent — both states currently share the same one-icon code path.
- **FR-B3.2** Design: "Last played X" is explicitly a **relative** time string (`README.md:43`, and `features/main-menu/specification.md` FR3.4: "relative time from the world's own last-played timestamp"). Current: `LAST_PLAYED_FORMAT` (line 35-36) is `DateTimeFormatter.ofPattern("MMM d, yyyy HH:mm")` — an absolute calendar timestamp, used directly in the subtitle (`WorldsPanel.java:127-129`), not a relative "X ago" computation. This is a direct violation of the feature's own already-approved FR3.4, not just a design nit.
- **FR-B3.3** Design: Play + Edit buttons are pills with "10px/18px padding" and read as two visually separated pill buttons. Current: Play spans `x+width-140` to `x+width-74` (66px) and Edit spans `x+width-70` to `x+width-8` (62px) — a 4px gap between them (`WorldsPanel.java:133-138`), which reads as adjoining blocks rather than two separated pills at the design's implied spacing; not sized as flexible-width "pill" buttons (fixed 66px/62px regardless of label length).

**ServersPanel** (`ServersPanel.java`):
- **FR-B3.4** Design: Saved-view expanded row uses "same card pattern as Worlds" (`README.md:52`), i.e. should also show the 2×2 thumbnail grid once Worlds' FR-B3.1 is fixed. Current: `renderSaved()` (lines 273-338) uses the same single-icon-with-colored-border pattern (lines 295-303) as the compact row — same gap as Worlds, not independently introduced here but inherited from the same missing-grid pattern.
- **FR-B3.5** Design: Browser sub-view filter bar includes a latency `<select>` dropdown (Any / <50ms / <100ms / <200ms, `README.md:55`) mapping onto `ServerBrowserFilterState.maxPing` (already confirmed present in the model, `features/main-menu/specification.md:70`). Current: `init()` (lines 96-141) wires a search `EditBox`, an `hideFullToggle` `Button`, and a `hidePasswordToggle` `Button` — **no latency dropdown/select control exists anywhere in `ServersPanel.java`**; `filter.maxPing` is never set from any UI control in this panel. This is a missing element, not merely a positioning discrepancy.
- **FR-B3.6** Design: sortable column header row shows a Lock/Name/Players/Latency four-column header, each independently clickable/sortable (`README.md:56`). Current: `drawColumnHeader()` calls exist only for `Name`, `Players`, `Latency` (`ServersPanel.java:361-363`); the lock/password-protected glyph is drawn per-row (`line 384`) but has no corresponding sortable column header, so the header row is a 3-column, not 4-column, layout vs. design.

**StorePanel** (`StorePanel.java`):
- **FR-B3.7** Design: featured banner shows a "large item swatch (130×130px, diagonal-stripe placeholder texture)" alongside the name/description/price/Buy-Now text (`README.md:63`) — i.e. swatch-left, text-right layout. Current: `render()`'s featured-banner block (lines 43-55) draws **no swatch/image element at all** — only a solid-fill background (`0xFF251F17`), a left accent stripe (`0xFF528A54`, 6px), and stacked text (FEATURED label, name, description, price) all starting at the same `x+16`, with the Buy pill positioned at the right (`x+width-120`). The swatch is missing entirely, and the banner height (`bannerHeight = 72`, line 46) is far shorter than the design's 130px swatch would require to sit inline with it.
- **FR-B3.8** Design: "All Cosmetics" grid cards each show a "square swatch (aspect-ratio 1:1)" filling most of the card, with name/category/price/Buy below it (`README.md:64`). Current: the placeholder swatch fill in the grid-card loop is only `cardTop+8` to `cardTop+48` (40px tall) inside a `CARD_SIZE = 96` card (`StorePanel.java:74`) — roughly 40/96 ≈ 42% of the card height, not a near-full-card square swatch; the remaining ~56px is used for name/category/price/Buy pill stacked below, materially smaller/differently-proportioned than the design's swatch-dominant card.

**WardrobePanel** (`WardrobePanel.java`):
- **FR-B3.9** Design: each of the four slot-selector buttons shows "a small swatch of the currently equipped item + slot label + equipped item name (truncated)" (`README.md:68`) — three distinct elements per slot button. Current: the slot-selector loop (`WardrobePanel.java:44-53`) draws only a background fill and a centered slot label (`slotLabel(slot)`) — **no equipped-item swatch and no equipped item name are rendered in the slot button at all**, even though `state.equippedItemId(slot)` is already available elsewhere in this same class (line 67, used only for the grid-card "Equipped" state, not surfaced in the slot selector).
- **FR-B3.10** Design: item-grid cards, same "square swatch (1:1)" sizing convention as the Store grid (`README.md:69`). Current: same undersized swatch pattern as StorePanel's grid (`WardrobePanel.java:74`, `rowY+8` to `rowY+48`, 40px tall in a 96px card) — same root cause as FR-B3.8, one shared fix should address both panels' grid-card swatch sizing consistently.

## Public API
No public API additions. All three bugs are internal fixes within existing classes' method bodies:
- `FriendSidebarWidget.isMouseOver(double, double)` (signature unchanged) — implementation reads newly-cached actual-drawn-width/height instance fields instead of recomputing them.
- `MainMenuScreen` gains one new private method `panelHeight()` (mirrors existing `panelX()`/`panelY()`/`panelWidth()` — same file, no interface change visible outside the class).
- `WorldsPanel`/`ServersPanel`/`StorePanel`/`WardrobePanel` render/mouseClicked method signatures are unchanged; only their internal drawing/layout math changes.

## Architecture
No architectural change. All three bugs are confined to the existing `platform/fabric-<version>/.../mainmenu/` and `platform/fabric-<version>/.../friends/FriendSidebarWidget.java` Version Adapter classes (per `features/main-menu/specification.md`'s existing layering) — no `services`/`api` module changes, no new cross-feature integration point. The Bug 1 fix stays entirely inside `FriendSidebarWidget`'s own per-frame render/hit-test state (the same "cache what was actually drawn this frame" pattern the class already uses for `dropdownX/Y/Width`, `footerOptionsY/footerQuitY/footerWidth`); it does not touch `FriendSidebarStateMachine`, `FriendsSidebarFacade`, or any other feature.

## UI
- Bug 1's fix has no visible layout change — it only makes existing visuals reliably clickable. No new visual state is introduced.
- Bug 2's fix visibly shrinks the panel height from `0.62·height` to `0.56·height` and repositions its bottom edge upward to `0.78·height` from the top (i.e. `panelY() + panelHeight() = 0.22h + 0.56h = 0.78h`, leaving a `0.22h` gap to the tab bar's bottom, matching the top gap) — this is an intentional, spec'd visual change, not a side effect to avoid; manual verification must confirm the panel now reads as vertically centered within the tab bar's span at multiple window sizes/GUI scales (since all these ratios are proportion-of-`height`, they should hold at any resolution).
- Bug 3's fixes are per-panel visual changes (grid additions, swatch resizing, missing control additions, relative-time text) — each must be manually verified against the design doc's stated values/screenshots per the existing manual-verification discipline (`features/main-menu/specification.md` UI section, "Manual, per-supported-Minecraft-version in-game verification is required").
- Color literals: any new fill/text call introduced by these fixes (e.g. a relative-time string, a new latency dropdown, a resized swatch) must carry a full `0xFF` alpha byte, per the standing project-wide caution already documented (`features/main-menu/specification.md:150`).

## Configuration
No configuration changes. None of the three bugs touch `config/main-menu-store-catalog.json` or `config/main-menu-wardrobe.json` schemas or read/write behavior.

## Events
No new events. No change to `ClientLifecycleEvents.CLIENT_STARTED` wiring or any existing state-machine transition semantics (`MainMenuStateMachine`, `FriendSidebarStateMachine`) — Bug 1's fix only changes what bounds `isMouseOver()` tests against, not any state transition logic.

## Networking
No networking changes. All three bugs are pure client-side rendering/hit-testing/layout fixes.

## Persistence
No persistence changes.

## Compatibility
- Same three platform modules as the base feature (`platform/fabric-1.21.11`, `platform/fabric-26.1`, `platform/fabric-26.2`) — each has its own copy of `FriendSidebarWidget.java` and the four panel classes; planning must confirm each copy's exact line numbers independently before patching (this spec's line references are all against the `fabric-26.2` copy, confirmed structurally identical across modules per the base feature spec's own Compatibility section, but not re-verified line-for-line here for the other two).
- No new Minecraft/Fabric API surface is introduced by any of these three fixes — all changes stay within already-used `GuiGraphicsExtractor`/`AbstractWidget`/`Screen` primitives this codebase already relies on.
- Bug 2's formula change (`panelHeight()`) is pure arithmetic on already-available `int height` — no version-specific behavior expected, but must still be confirmed empirically per version per this repo's standing discipline.

## Performance
No performance impact expected from any of the three fixes:
- Bug 1's fix trades "recompute width/height from constants" for "read a cached field set once per frame in `renderNow()`" — strictly cheaper, not more expensive.
- Bug 2's fix is a single extra method call replacing an inline arithmetic expression — negligible.
- Bug 3's fixes (an added 2×2 thumbnail grid, a relative-time string computation, an added dropdown widget, resized swatch fills) are all cheap per-frame operations already within the cost envelope of what these panels already do every frame (they already draw multiple fills/text calls per row/card).

## Future Extensions
- Bug 1's identified-but-not-reported latent duplicate issue in `mouseScrolled()` (FR-B1.4) — same recomputed-target-width pattern, not fixed now since it wasn't reported as broken, but should be fixed for consistency in a future pass.
- A general proportional GUI-scale/reference-canvas scaling utility for the four tab panels (Bug 3's systemic finding) — this spec only documents the absence and its symptoms; designing the actual scaling mechanism (a shared scale-factor helper, or converting every panel's literals to ratios of `panelWidth()`/`panelHeight()`) is left to a future feature/planning pass, not prescribed here.
- Real 2×2 world/server preview thumbnails (distinct per-corner tile images) once real per-world/server preview assets exist, beyond the four-tile grid layout fix this spec requires now (this spec only requires the *layout* — a 2×2 grid instead of one icon — using the same existing icon/placeholder texture repeated or color-varied into four tiles, not new asset-loading machinery).
