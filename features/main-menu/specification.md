# Main Menu — Feature Specification

## Overview
Adds `features/main-menu`: a complete replacement for the vanilla `TitleScreen`, implementing the "Stonebound" main-menu redesign captured in `design_handoff_main_menu/README.md` (the authoritative design source; `design_handoff_main_menu/Main Menu.dc.html` is a non-literal HTML/CSS/JS reference used only for exact per-item sample values not stated in the README prose). The new screen presents:

- A continuously-rendered, real 3D background scene (dusk sky, sun glow, mountain silhouettes, ground plane, an idle animated blocky player character) — see Architecture/3D Background.
- A right-hand vertical tab bar (Worlds / Servers / Store / Wardrobe) toggling a center content panel.
- A right sidebar (collapsed icon rail, expands on hover) showing the local player's own status, a "who can join" policy control, and a friends list — built by composing the existing `features/friends-sidebar` state/data, not duplicating it.
- A Store panel backed by real Steamworks ownership/DLC data (see Store Panel / Compatibility for the honest feasible scope, given this repo's steamworks4j binding has no `ISteamInventory`/`ISteamMicrotransaction` wrapper).
- A Wardrobe panel (cosmetic equip-per-slot), Worlds panel (delegates world creation to vanilla), and Servers panel (Saved + Browser sub-views, the Browser sub-view backed by `features/server-browser`'s existing query/session/table-model logic).

This is the first feature in this repo that **replaces** `TitleScreen` outright (`ClientLifecycleEvents.CLIENT_STARTED` + `Minecraft.getInstance().setScreen(new MainMenuScreen(...))`, the "full title-screen-replacement variant" explicitly flagged as a Future Extension in `features/hello-world-main-menu/specification.md:178`) rather than only overlaying a widget on the vanilla screen (Pattern 1) or opening a new screen from an existing vanilla button (`features/server-browser`'s shape). It is also the first feature to drive a genuine 3D-perspective render pass from within a `Screen` (vanilla's own `TitleScreen`/`PanoramaRenderer` cubemap-rotation background is the closest existing in-engine precedent and is used as this feature's rendering-cost baseline, see Performance).

**Scope includes deleting `features/hello-world-main-menu`** (Requirements, FR0) — it is superseded outright: this feature's `MainMenuScreen` becomes the new title screen, so the old feature's `ScreenEvents.AFTER_INIT`-added label has no vanilla `TitleScreen` instance left to attach to.

## Goals
- Replace the vanilla title screen with `MainMenuScreen`, matching `design_handoff_main_menu/README.md`'s layout, colors, typography, and interaction states "pixel-for-pixel in spirit," expressed with each target Minecraft version's real `Screen`/`GuiGraphics`/widget primitives — no HTML/CSS concepts ported literally.
- Render a genuine, continuously-updating 3D background (camera, sky/lighting, ground plane, an animated placeholder character) behind the entire UI, performant enough to run every frame without a noticeable hitch (Performance).
- Implement all four tab panels (Worlds, Servers, Store, Wardrobe) with the specific content/behavior the design doc describes, translated into concrete widget/state terms (Requirements).
- Reuse `features/friends-sidebar`'s existing state machine/services (`FriendSidebarStateMachine`, `FriendsSidebarFacade`, `FriendsService`/`FriendsDataSource`, `JoinPolicy`) for the right sidebar's player card, join-policy control, and friends list — no parallel friend-list/join-policy logic in this feature.
- Reuse `features/server-browser`'s existing query/session/table-model logic (`ServerBrowserQuery`, `ServerBrowserSessionFactoryImpl`/`ServerBrowserSessionImpl`, `ServerBrowserTableModel`) for the Servers panel's Browser sub-view — no parallel Steam-matchmaking query logic in this feature.
- Ship a real, working Store panel backed by Steamworks DLC ownership (`SteamApps.isSubscribedApp`/`isDlcInstalled`) for "owned" state and the Steam Overlay store page for "buy" — the most honest feasible scope given this repo's current steamworks4j binding (see Store Panel, Compatibility). Flag real-money Steam Microtransactions (`ISteamMicrotransaction`) as out of reach with the current dependency and a documented Future Extension.
- Delete `features/hello-world-main-menu` as part of this feature's scope (dir removal, `settings.gradle` entry removal, each `platform/fabric-*/build.gradle` dependency-line removal, `HelloWorldMainMenuClientInitializer`-equivalent entrypoint removal) — an explicit task for planning to sequence, not re-litigated here.

## Non-goals
- Not a pixel-identical reproduction of the HTML prototype's exact CSS blur/shadow rendering — `backdrop-filter: blur()`/box-shadow glow are approximated with Minecraft-native equivalents (a translucent-fill overlay, and/or a cheap multi-sample blur pass if profiling allows; see UI/3D Background).
- Not a real Blender-authored idle-character model in v1 — the design doc's own Assets section says "no real game assets are used" and that the character is a stand-in for a future asset; this spec calls for a concrete, functioning placeholder model/animation pipeline (a hand-built `ModelPart` hierarchy, vanilla-player-blockiness proportions), not a static image, so the pipeline is exercised end-to-end (see Architecture/3D Background). Swapping in a real authored model later is a Future Extension, not blocked by anything this spec introduces.
- Not a real-money Steam Microtransactions checkout flow in v1 (no `ISteamMicrotransaction` binding exists in this repo's steamworks4j dependency, confirmed absent — see Compatibility). "Buy Now"/"Buy" open the Steam Overlay's store-page checkout for that item's App ID/DLC (an external, already-Steam-hosted payment flow), not an in-mod payment UI.
- Not a full cosmetics/inventory content pipeline (item authoring, icon rendering from real assets) — Store/Wardrobe item data is a small config-driven catalog (Configuration) mapping to DLC App IDs; real per-item icon textures are a Future Extension, same "no real assets yet" caveat as the 3D character.
- Not a generalized "extend any vanilla screen" framework — this feature owns its own screen outright; it does not need `architecture.md`'s "Shared-screen extension point" collision-avoidance machinery for the vanilla `TitleScreen` itself, because it replaces that screen rather than layering on top of it. (It does still need to be aware of the existing collision precedent between `friends-sidebar` and `server-browser` on the vanilla Multiplayer screen, called out in `features/server-browser/specification.md:90`, since this feature's Servers-panel Browser sub-view reuses `server-browser`'s logic but renders it inside `MainMenuScreen`'s own layout, not by re-injecting a widget onto a vanilla screen.)
- No server-side/dedicated-server behavior of any kind — 100% client-only, exactly like `hello-world-main-menu` (FR2 there) and every screen-only feature in this repo.
- No in-game "About"/credits/mod-list screen beyond what vanilla's footer buttons already provided — out of scope unless the design doc calls for it (it doesn't).
- No hot-reload of Store/Wardrobe catalog config while `MainMenuScreen` is open — config is read once per screen construction (Configuration).
- No multiplayer voice/text chat, no Realms integration changes — this feature does not touch Realms; a "Realms" affordance is not called out in the design doc and is not added.
- Real password verification for password-protected servers in the Servers panel's Browser sub-view remains exactly the same documented v1 stub `features/server-browser/specification.md` already establishes (FR4.3 there) — this feature does not change that scope, only re-hosts the same session/query objects inside its own panel layout.

## Requirements

### FR0 — Removal of `features/hello-world-main-menu`
- **FR0.1** Delete `features/hello-world-main-menu/` in its entirety (its `api`/`config`/`services` classes and `specification.md`/`plan.md`/`README.md`/`verification-report.md`).
- **FR0.2** Remove `include 'features:hello-world-main-menu'` from `settings.gradle:23`.
- **FR0.3** Remove the `implementation project(':features:hello-world-main-menu')` dependency line from each `platform/fabric-*/build.gradle` (confirmed present at `platform/fabric-26.2/build.gradle:15`; the sibling `fabric-26.1`/`fabric-1.21.11` modules are expected to have the equivalent line — planning must verify each one directly rather than assume identical line numbers).
- **FR0.4** Remove each platform module's `HelloWorldMainMenuClientInitializer`-equivalent client entrypoint class and its `fabric.mod.json` `"client"` entrypoint registration for that class (confirmed present at `platform/fabric-26.2/src/main/java/de/lazuli/HelloWorldMainMenuClientInitializer.java`), since `MainMenuScreen`'s own composition root supersedes it. If a platform module's single `"client"` entrypoint currently does double duty (hello-world plus something else), planning must confirm before deleting wholesale rather than assuming a 1:1 file-to-entrypoint mapping.
- **FR0.5** This removal is a prerequisite/parallel task to this feature, not a follow-up — a rebuild after this feature ships must not reference the old module anywhere (no dangling `settings.gradle`/`build.gradle` line, no orphaned class).

### FR1 — Screen replacement / lifecycle
- **FR1.1** `MainMenuScreen` becomes the client's title screen: shown on `ClientLifecycleEvents.CLIENT_STARTED` via `Minecraft.getInstance().setScreen(new MainMenuScreen(...))` (Mojang mappings, 26.x) / `MinecraftClient.getInstance().setScreen(...)` (Yarn, 1.21.11) — the same non-mixin, Fabric-API-only mechanism `hello-world-main-menu`'s own spec already identified as the mixin-free full-replacement alternative (`features/hello-world-main-menu/specification.md:95`).
- **FR1.2** `MainMenuScreen` is also the screen returned to on disconnect/world-exit/server-leave (wherever vanilla would otherwise return to `TitleScreen`) — achieved by constructing `MainMenuScreen` (not vanilla's `TitleScreen`) at every call site vanilla itself uses to return to the title screen. Planning/implementation must enumerate those call sites per Minecraft version (typically the disconnect screen's "Back to Title Screen" button action, and the world-exit path) since replacing only the initial boot screen would silently regress back to vanilla's title screen after the first disconnect.
- **FR1.3** All top-level state (Overview/State Management below) resets to defaults each time a fresh `MainMenuScreen` instance is constructed — no state persists in memory across a full screen teardown/recreate (matches the design doc's own "resets to defaults each time the screen is freshly opened" convention already established for `server-browser`'s filters, `features/server-browser/specification.md:53`).
- **FR1.4** `MainMenuScreen`'s background render (3D Background) continues rendering every frame regardless of which tab (if any) is active — "no tab active" is a first-class, fully valid state where only the background, title/subtitle text, tab bar, and collapsed sidebar are visible (Overview's design doc line: "Transparent/inactive when no tab is selected").

### FR2 — Tab bar
- **FR2.1** Four vertical tab buttons (Worlds, Servers, Store, Wardrobe), fixed 108px-equivalent column (scaled to the actual GUI scale/window size, not a literal 108px at every resolution — see UI/Scaling), each rendering icon + label per the design doc's Tab Bar section.
- **FR2.2** Selected/active tab state is nullable (`Optional<MainMenuTab>`/a nullable enum field) — clicking a tab selects it (opens the center panel); clicking the already-active tab again deselects it (closes the center panel back to fully-transparent). Clicking a different tab while one is already active switches directly (no intermediate deselected frame required).
- **FR2.3** Active/inactive/hover visual states match the design doc's colors (Configuration/Design Tokens carries the literal OKLCH values for implementation to convert to sRGB/ARGB int constants at build or init time — Minecraft's color APIs take ARGB, not OKLCH, so a one-time OKLCH→sRGB conversion table is part of this feature's own constants, not a runtime dependency).

### FR3 — Worlds panel
- **FR3.1** Header row: "Singleplayer Worlds" label + "Create New World" button.
- **FR3.2** Scrollable list of saved singleplayer worlds sourced from vanilla's own world-list data (`LevelStorageSource`/`LevelSummary` equivalents per version — the same data vanilla's own Singleplayer screen already reads; this feature does not invent a new world-discovery mechanism, only its own rendering of that data).
- **FR3.3** Each row toggles expanded/compact on click; the design doc's own prose (`design_handoff_main_menu/README.md:45`) flags this as an open behavioral question — **resolved for this spec**: single-expand (accordion) behavior, selecting a new row collapses any previously-expanded row, matching the "confirm intended behavior" note's own default assumption and the simplest state shape (one nullable "selected world id" field, Overview/State Management). Planning may revisit multi-expand only if a concrete usability reason surfaces.
- **FR3.4** Expanded row shows a 2×2 thumbnail placeholder grid, world name, mode·difficulty, "Last played X" (relative time from the world's own last-played timestamp), Play + Edit buttons. Compact row shows a single thumbnail, truncated name, mode·last-played.
- **FR3.5** "Create New World" invokes vanilla's real "Create World" screen (`CreateWorldScreen`/equivalent, opened the same way vanilla's own Singleplayer screen opens it) — **not** a toast placeholder; the design doc's toast (`README.md:47`) is explicitly called out there as a mock stand-in for this transition, and this spec requires the real transition. A brief (design doc's ~1.6s figure is a non-binding suggestion, not a hard requirement) transitional toast/spinner is optional polish, not required, since the real screen open is likely near-instant.
- **FR3.6** Play launches that world exactly as vanilla's own Play button does (`Minecraft.getInstance().createWorldOpenFlows()`/whatever the target version's real "load and enter this world" call is — reuse vanilla's own method, do not reimplement world-loading).
- **FR3.7** Edit opens vanilla's own world-edit screen/flow for that world (rename, backup, delete, etc. — whatever vanilla's existing per-world "Edit" action already opens).

### FR4 — Servers panel
- **FR4.1** Two sub-views: Saved (default) and Browser, toggled by a header button; sub-view choice is one piece of screen state (nullable/enum, resets to Saved per FR1.3 on fresh screen open).
- **FR4.2** Saved sub-view: lists vanilla's own saved multiplayer servers (`ServerList`/equivalent — same data vanilla's Multiplayer screen already reads), same expand/compact row pattern as Worlds (FR3.3), expanded row shows a Connect button instead of Play/Edit, compact row shows a ping-status-colored dot + player count.
- **FR4.3** Browser sub-view: renders `features/server-browser`'s existing table/session data inside this panel's own layout, not by opening the separate `ServerBrowserScreen`/`FabricServerBrowserButtonInjector` flow that feature already ships for the vanilla Multiplayer screen (Architecture/Server Browser Integration below details exactly which classes are reused vs. left untouched).
  - Filter bar (name search, latency `<select>`/dropdown, "Hide Full"/"Hide Password Protected" toggles) maps 1:1 onto `ServerBrowserFilterState`'s existing fields (`searchText`, `maxPing`, `hideFull`, `hidePasswordProtected` — confirmed field names via `ServerBrowserTableModel.matches`, `features/server-browser/src/main/java/de/lazuli/features/serverbrowser/services/ServerBrowserTableModel.java:72-93`). The design doc's latency `<select>` (Any/<50/<100/<200ms) is a UI convenience that resolves to the same `maxPing` int field `server-browser` already exposes (0 = no limit) — no new business-logic field needed.
  - Sortable columns (Lock/Name/Players/Latency) map onto `ServerBrowserColumn`'s existing enum values (`NAME`, `MAP`, `PLAYERS`, `PING`, `PASSWORD`, `SECURE` — confirmed, `ServerBrowserTableModel.comparatorFor`) — the design doc's 4-column subset (no explicit Map/Secure columns shown) is this feature's own column-visibility choice, not a change to the underlying model, which still carries all six.
  - "Direct Connect" and "+ Add Server" open modal dialogs (masked/plain text-field inputs, Cancel/Connect|Add) — reuse vanilla's own equivalent modal/screen if one already exists in the target version's Multiplayer flow (per-version confirmation is an implementation-time task, not assumed here); otherwise build small feature-owned modal screens/overlays following the same from-scratch custom-`Screen` precedent `server-browser`'s own `ServerBrowserPasswordPromptScreen` set (`features/server-browser/specification.md:83`, Public API item 7).
  - Refresh button calls the existing `ServerBrowserSession`'s refresh operation (backed by `ServerBrowserQuery.refresh()`, `features/server-browser/src/main/java/de/lazuli/features/serverbrowser/services/ServerBrowserQuery.java:97-106`) and spins its own icon 360° per click as a purely cosmetic animation, independent of the actual refresh's completion timing.
- **FR4.4** Connecting from either sub-view reuses vanilla's own connect flow exactly as `server-browser`'s own FR4.1 already establishes (`features/server-browser/specification.md:56`) — this feature does not reimplement connection handshake logic anywhere.
- **FR4.5** Password-protected servers in the Browser sub-view reuse `server-browser`'s existing `ServerBrowserPasswordPromptScreen` password-prompt flow verbatim, including its documented v1 stub (password captured but not transmitted/enforced, `features/server-browser/specification.md:58-61`) — this feature does not change that scope.
- **FR4.6** If Steam is unavailable (`SteamAvailability.isSteamAvailable() == false`), the Browser sub-view shows the same status-message state `server-browser`'s own FR5.1 already specifies, rendered inside this panel's layout rather than a full separate screen.

### FR5 — Store panel
- **FR5.1** Store catalog (featured item + "All Cosmetics" grid) is config-driven (Configuration): each entry is `{id, displayName, description, category, priceCents, originalPriceCents (nullable, for strikethrough), steamDlcAppId (nullable), featured (boolean)}`.
- **FR5.2** Ownership ("Owned"/purchasable state) is resolved via Steamworks DLC entitlement: `SteamApps.isSubscribedApp(steamDlcAppId)` and/or `SteamApps.isDlcInstalled(steamDlcAppId)` (confirmed present in this repo's bound steamworks4j 1.10.0, Compatibility) — an item with no `steamDlcAppId` configured (e.g. during dev/testing before real DLC App IDs exist) is treated as **not ownable via Steam**, rendered with a clearly-labeled placeholder/disabled "Buy" affordance rather than silently pretending ownership succeeded (see Compatibility for the concrete dev-time gap this creates and how to test around it).
- **FR5.3** "Buy Now"/"Buy" opens the Steam Overlay to that item's store page (the DLC App ID's own store page) via whatever `SteamFriends`/`SteamUtils` overlay-activation call this repo's steamworks4j binding actually exposes for an app/store-page target (confirmed pattern precedent: `SteamworksSteamFriendsGateway.activateOverlay`, `services/src/main/java/de/lazuli/services/steamworks/SteamworksSteamFriendsGateway.java:290-298`, currently only wired for `activateGameOverlayToUser`; whether an equivalent `activateGameOverlayToStore`-shaped method exists on this repo's exact steamworks4j version's `SteamFriends` class is an **open question flagged for planning** to confirm directly against the resolved jar, since this spec's research pass confirmed the class list — Compatibility — but not every method signature on every class). If no such call exists in this steamworks4j version, the fallback is opening the Steam client's storefront via the OS default browser/URI handler pointed at the store page URL (`steam://store/<appid>` URI scheme, Valve-documented, requires no new Steamworks API surface) — planning decides between these two once the direct-overlay call is confirmed present or absent.
- **FR5.4** No in-mod payment collection UI of any kind (no credit-card form, no price confirmation dialog beyond the Steam Overlay's own) — the entire payment step happens inside Steam's own overlay/storefront, external to this mod's own rendering.
- **FR5.5** After returning from the overlay, ownership state (FR5.2) is re-checked the next time the Store panel is opened/refreshed (no live push notification of a completed purchase is assumed — `SteamApps`/`SteamUser` in this repo's bound library version has no confirmed purchase-completion callback; polling on next-open is the honest, simple v1 behavior).

### FR6 — Wardrobe panel
- **FR6.1** Slot selector row: Head/Torso/Legs/Feet, each showing the currently-equipped item's placeholder swatch + name; clicking a slot switches which item grid is shown below.
- **FR6.2** Item grid for the active slot lists every catalog item (FR5.1's same config-driven catalog, filtered by `category`/slot) the player owns (FR5.2's same ownership check) or has equipped; clicking an owned item equips it into the active slot (single item per slot, replacing any prior equip).
- **FR6.3** Equip state (`Map<Slot, ItemId>`) persists across screen sessions (Persistence) — unlike filter/sort/tab-open state (FR1.3), a player's wardrobe choices are expected to survive a client restart.
- **FR6.4** Equipped cosmetics in v1 are **not** rendered onto the player's actual in-game skin/model — that visual application is explicitly out of scope for this pass (no skin-layer compositing pipeline exists yet in this repo); the Wardrobe panel only tracks and displays the equip choice. Actually rendering equipped cosmetics on the player model in-world is a Future Extension.

### FR7 — Right sidebar (reusing `friends-sidebar`)
- **FR7.1** Collapsed state shows: player avatar, friend avatars (colored per-friend, online/offline border), Settings icon, Quit icon — sourced from `FriendsSidebarFacade.localProfile()` (own avatar/name) and `FriendsSidebarFacade.friends()` (already-sorted-for-display list, confirmed via `FriendSidebarStateMachine.sortForDisplay`, `features/friends-sidebar/src/main/java/de/lazuli/features/friendssidebar/services/FriendSidebarStateMachine.java:197-203`).
- **FR7.2** Hovering the sidebar's collapsed footprint expands it (width transition), driven by `FriendSidebarStateMachine.isExpanded(mouseX, mouseY, ...)` (confirmed signature, `FriendSidebarStateMachine.java:36-39`) — this feature does not reimplement hover-bounds logic, it only supplies this screen's own sidebar bounds to that existing pure function every frame/input event.
- **FR7.3** Expanded state additionally shows: player name + "View profile" (wired to `FriendsDataSource.onShowProfile`/`FriendsSidebarFacade.actions().onShowProfile(steamId64)`, confirmed present via the `FriendActionListener` interface `FriendsService` implements), the "Who can join?" dropdown (`FriendsSidebarFacade.joinPolicy()`/`selectJoinPolicy(JoinPolicy)`, confirmed signatures at `FriendsSidebarFacade.java:183-209`), a divider, the "Friends" section, and the scrollable friends list (status line per friend sourced from `FriendsSidebarFacade.richPresenceStatus(steamId64)` falling back to `FriendSidebarStateMachine.statusLabel(personaState, inGame)`, confirmed at `FriendSidebarStateMachine.java:250-252`, the same first-Rich-Presence-then-persona-state-word precedence `friends-sidebar` itself already establishes).
- **FR7.4** Footer Settings/Quit buttons: Settings opens vanilla's own Options screen; Quit exits the client (`Minecraft.getInstance().stop()`/equivalent) — both icon-only collapsed, label+icon expanded, per the design doc.
- **FR7.5** If `SteamAvailability.isSteamAvailable()` is `false`, or the Friends Sidebar feature's own config disables it, the sidebar renders the same status-message fallback `friends-sidebar` FR6.1-6.7 already define (`FriendsSidebarFacade.isSteamAvailable()`/`steamUnavailableMessage()`, confirmed at `FriendsSidebarFacade.java:114-135`) instead of the player card/friends list — this feature reads that existing status surface rather than inventing a new one.
- **FR7.6** This feature's `MainMenuScreen` becomes the sole platform-side consumer that renders `friends-sidebar`'s existing hook/facade shape inside a **new** screen context (previously only ever rendered as an overlay across many *existing* vanilla screens via `FabricFriendsSidebarInjector`, `platform/fabric-26.2/src/main/java/de/lazuli/friends/FabricFriendsSidebarInjector.java`) — planning must decide whether `MainMenuScreen`'s sidebar rendering is a) a second, independent Version-Adapter-level widget construction reusing the same `FriendsSidebarFacade`/`FriendSidebarWidget`-equivalent rendering code by extracting it into a shared, reusable rendering helper (preferred, avoids duplicating rendering logic — this is exactly the "graduate a widget once a second consumer needs the identical shape" case `ui-guidelines.md:204-216` describes), or b) a parallel, `MainMenuScreen`-only rendering implementation. This spec requires (a) as the default expectation; planning may deviate with a documented reason if `FriendSidebarWidget`'s current shape turns out to be too vanilla-Multiplayer-screen-specific to reuse directly.

### FR8 — 3D Background
- **FR8.1** A perspective 3D scene renders continuously behind the entire `MainMenuScreen` UI, every frame, regardless of tab state (FR1.4) — camera, sky, ground plane, and the idle character (below) are all real 3D-rendered geometry, not a 2D texture/gradient standing in for one.
- **FR8.2** Sky: a fixed (or very slowly panning, if planning chooses to add subtle parallax — not required) dusk gradient matching the design doc's OKLCH stops (Configuration/Design Tokens), rendered as a simple 3D skybox/background quad or vertex-colored sky dome — whichever the target versions' existing sky/panorama-rendering primitives make cheapest (vanilla's own `TitleScreen` panorama-cubemap machinery is the nearest existing precedent for "a rotating/static 3D background behind title-screen UI" and should be the first thing implementation examines for reuse, even though this feature's content differs).
- **FR8.3** Sun/glow: a billboarded quad (always facing the camera) with a radial-gradient-approximating texture or vertex-colored falloff, positioned per the design doc's upper-right placement, with an additive-blended soft outer glow.
- **FR8.4** Mountains: two semi-transparent silhouette layers, implementable as simple flat-shaded 3D meshes (extruded jagged polygons) or camera-facing billboards with an alpha-cutout silhouette shape — either satisfies "real 3D scene" since both are genuine 3D-space geometry positioned via the camera/projection matrix, not 2D-screen-space overlay quads.
- **FR8.5** Ground: a flat, textured or vertex-colored ground plane (green gradient per the design doc) extending from the camera's near field into the scene, with a lighter top-edge highlight strip.
- **FR8.6** Idle character: a placeholder blocky humanoid model (head+hair, torso, two arms, two legs — vanilla-player-blockiness proportions per the design doc), built as a real 3D model (Architecture/Idle Character Model Pipeline) with three independent, looping animations layered simultaneously: a whole-body bob (±6px-equivalent, 2.6s ease-in-out), an arm-swing, and a leg-sway — all pure functions of elapsed time (unit-testable on a plain JVM, no Minecraft imports, given the animation math is kept in a small feature-owned class rather than baked into rendering code).
- **FR8.7** Camera/lighting: a fixed camera position/angle framing the scene as the design doc's layout describes (character bottom-left, sun upper-right, mountains/ground along the bottom) with simple directional/ambient lighting sufficient to shade the character's blocks distinctly per-face (matching "the game's own player-skin blockiness" descriptor) — no dynamic time-of-day cycle or camera movement is required for v1 (Future Extensions).
- **FR8.8** Rendering must not block the render thread waiting on any I/O, network, or Steamworks call — the entire background pass is self-contained geometry/animation math plus draw calls, with zero dependency on `FriendsSidebarFacade`/`ServerBrowserQuery`/`SteamApps` or any other feature's data.

## Public API
Illustrative shapes only; final names/signatures are a planning-phase decision, consistent with this repo's convention (`features/server-browser/specification.md:74`).

1. **`api/src/main/java/de/lazuli/api/mainmenu/`** (zero Minecraft imports):
   - `MainMenuTab` — enum `{WORLDS, SERVERS, STORE, WARDROBE}`.
   - `StoreItem` — plain record: `id`, `displayName`, `description`, `category`, `priceCents`, `originalPriceCents` (nullable/`OptionalInt`), `steamDlcAppId` (nullable/`OptionalInt`), `featured` (boolean).
   - `WardrobeSlot` — enum `{HEAD, TORSO, LEGS, FEET}`.
   - `CharacterPose` — plain record capturing one frame's worth of the idle animation's output (bob offset, arm-swing angle, leg-sway angle) — the pure output of the animation function (FR8.6), consumable by a platform Version Adapter's model-posing code without that adapter needing to know the animation math itself.

2. **`features/main-menu/services/`**:
   - `MainMenuStateMachine` — plain-JVM-testable pure logic: active-tab toggle (FR2.2), world/server row expand toggle (FR3.3/FR4.2), servers sub-view toggle (FR4.1), wardrobe active-slot/equip-map transitions (FR6.1/FR6.2), modal-visibility flags — mirrors `FriendSidebarStateMachine`'s own "pure functions the UI layer merely reads from" shape (`ui-guidelines.md:250-253`).
   - `IdleCharacterAnimator` — pure function `CharacterPose poseAt(double elapsedSeconds)` implementing FR8.6's three-loop composition; unit-tested on a plain JVM.
   - `StoreCatalog` — loads/holds the config-driven `List<StoreItem>` (FR5.1), and a small ownership-lookup seam (`OwnershipChecker` functional interface, `boolean isOwned(StoreItem item)`) that a platform Version Adapter implements against `SteamApps` (FR5.2) — kept as an interface here specifically so `StoreCatalog`'s own filtering/grouping logic (featured item selection, category grouping for the "All Cosmetics" grid) stays plain-JVM-testable against a fake `OwnershipChecker`.
   - `WardrobeConfig`/`WardrobeConfigIO` — equip-map persistence (FR6.3), following the same hand-rolled-JSON, fail-closed-to-defaults convention `SteamWorldHostingConfigIO` already establishes (`features/steam-world-hosting/src/main/java/de/lazuli/features/worldhosting/config/SteamWorldHostingConfigIO.java`).
   - `StoreCatalogConfigIO` — same convention, for the Store catalog itself (Configuration).

3. **`platform/fabric-<version>/.../mainmenu/`** (Version Adapters):
   - `MainMenuScreen` — the new `Screen` subclass, composition of: the 3D background renderer, the tab bar, the four tab-panel renderers, and the reused-sidebar rendering (FR7.6).
   - `MainMenuBackgroundRenderer` — owns the 3D scene (FR8), consuming `IdleCharacterAnimator`/`CharacterPose` from `services` but doing all actual Minecraft rendering-API calls itself (camera/projection setup, draw calls) — the version-glue boundary, per this repo's `Feature -> Platform API -> Version Adapter -> Minecraft` layering.
   - `MainMenuStoreOwnershipChecker` — implements `services`' `OwnershipChecker` against `SteamApps` (FR5.2), the sole `com.codedisaster.steamworks.SteamApps`-importing class this feature introduces, following the same "one gateway/service class, not scattered" discipline `server-browser` NFR3 already established (`features/server-browser/specification.md:70`).
   - `MainMenuClientInitializer` — the new client entrypoint (composition root) per platform module: constructs the `MainMenuStateMachine`/`IdleCharacterAnimator`/`StoreCatalog`/`WardrobeConfig` (feature-layer), obtains the already-published `FriendsSidebarFacade`/`ServerBrowserSessionFactory` handoffs (Architecture, below — these already exist as static holders per `SteamworksServiceHandoff`'s established pattern), and registers `ClientLifecycleEvents.CLIENT_STARTED` to set `MainMenuScreen` as the initial screen (FR1.1), plus whatever additional hook FR1.2's "return to title screen after disconnect" requires per version.

## Architecture
Layering: `features/main-menu` depends on `api`/`services` only, never another feature (`architecture.md:64-71`) — it does **not** depend on `features/friends-sidebar` or `features/server-browser` directly. Instead, per the Composition-root exception (`architecture.md:78`), each `platform/fabric-<version>` module's composition root already constructs those other features' facades/sessions today (`FriendsSidebarClientInitializer`, `ServerBrowserClientInitializer`, confirmed present under `platform/fabric-26.2/src/main/java/de/lazuli/`) and can hand the same already-constructed `FriendsSidebarFacade`/`ServerBrowserSessionFactory` instances to `MainMenuClientInitializer` at the platform layer, exactly as `SteamworksServiceHandoff`/`SteamFriendsGatewayHandoff`/`WorldHostingBridgeHandoff` already broker cross-feature-adjacent instances between platform-composed features today. This keeps the Feature -> Feature dependency forbidden at the source-code layer while still letting one screen visually compose data/behavior two other features already produce — the integration point is the **platform composition root**, not `features/main-menu`'s own Java classes importing another feature's package.

**Server Browser integration, concretely:** `MainMenuClientInitializer` obtains the same `ServerBrowserSessionFactory` (`features/server-browser/src/main/java/de/lazuli/features/serverbrowser/services/ServerBrowserSessionFactoryImpl.java`) the platform's existing `ServerBrowserClientInitializer` already constructs, and opens a fresh `ServerBrowserSession` (`newSession()`, confirmed signature) when the Servers panel's Browser sub-view becomes active (FR4.1), closing it when the sub-view is left/the screen closes — mirroring `ServerBrowserScreen`'s own session lifecycle discipline (open on screen-show, `releaseRequest` via `ServerBrowserQuery.close()` on screen-hide, `features/server-browser/specification.md:36`/`ServerBrowserQuery.java:158-168`) rather than the app-lifetime-persistent shape `friends-sidebar`'s facade uses. **Gap flagged for planning**: `ServerBrowserSessionFactory`/`ServerBrowserSession` are `api`-layer interfaces (confirmed via `ServerBrowserSessionFactoryImpl implements ServerBrowserSessionFactory`, package `de.lazuli.api.serverbrowser`) — this feature's `services` layer can depend on them directly with zero new gap, since `api` is available to every layer. No new public surface needs to be added to `server-browser` for the Browser sub-view to work; this feature only needs a Version Adapter reading `ServerBrowserSession`'s existing row/refresh/sort/filter accessors and rendering them in its own panel layout instead of `server-browser`'s own `ServerBrowserScreen` layout. Planning should still open `ServerBrowserSessionImpl.java`/the `api/serverbrowser` package directly (not read in this spec pass) to confirm the exact accessor method names on `ServerBrowserSession` before implementation.

**Friends Sidebar integration, concretely:** `MainMenuClientInitializer` obtains the same `FriendsSidebarFacade` the platform's existing `FriendsSidebarClientInitializer` constructs (backed by `FriendsService`/`NoopFriendsService` per Steam availability, `FriendsSidebarFacade.java`) and renders it inside `MainMenuScreen`'s own sidebar region using `FriendSidebarStateMachine.isExpanded(...)` with this screen's own sidebar bounds (FR7.2) instead of `friends-sidebar`'s existing per-vanilla-screen overlay bounds. **No gap found** in `FriendsSidebarFacade`'s current public surface for anything this spec's sidebar (FR7) needs — every accessor cited in FR7.1-7.5 already exists with the signature quoted there. The one open design decision (not a missing-API gap) is FR7.6's rendering-code-reuse question, left to planning.

**3D Background — no existing precedent to reuse verbatim.** No feature in this repo currently renders a perspective 3D scene from inside a `Screen`; `WorldRestoreScreen` (`platform/fabric-*/.../cloudsync/WorldRestoreScreen.java`) is this repo's only prior from-scratch custom-`Screen` precedent, and it is a plain 2D screen. Vanilla's own `TitleScreen` panorama background (a rotating 3D cubemap rendered behind vanilla's 2D title-screen buttons) is the closest existing in-engine analog for "3D scene behind screen UI, running every frame, at acceptable cost" and should be implementation's first reference point for how to set up a perspective camera/projection matrix inside `Screen.render`/`extractRenderState` (the same render-state-extraction model `hello-world-main-menu`'s spec already flagged as the current rendering entry point, `features/hello-world-main-menu/specification.md:107`) without fighting Minecraft's own 2D-orthographic `GuiGraphics` draw calls used for the rest of the UI in the same frame.

**Idle Character Model Pipeline — concrete approach (research finding).** Rather than introducing a new third-party model-loading library (glTF, etc. — no such dependency exists anywhere in this repo's `build.gradle`s today, and none is needed), this feature builds the placeholder character the same way vanilla itself builds every entity model: a hand-authored `ModelPart`/`ModelPart.Cube` hierarchy (the same primitive vanilla's own `PlayerModel`/`HumanoidModel` classes use — cuboid parts with pivot points, exactly matching the design doc's own "flat rectangular blocks ... thin dark border ... matching the game's own player-skin blockiness" description) posed per-frame from `IdleCharacterAnimator`'s pure `CharacterPose` output, and rendered with a flat/solid-color material (no real skin texture yet, consistent with Non-goals) via the target version's existing model-rendering pipeline (`PoseStack`/`VertexConsumer` calls the same way any vanilla entity renderer already issues them, adapted to run inside `MainMenuBackgroundRenderer`'s own camera setup rather than the entity-render pipeline's own camera). This is the same category of solution `ui-guidelines.md` already recommends elsewhere in this repo (prefer reusing an existing vanilla rendering primitive over inventing new asset-loading machinery, `ui-guidelines.md:241-243`) applied to 3D models instead of 2D textures. Swapping in a real Blender-authored model later (Future Extensions) means replacing this `ModelPart` hierarchy's construction with a loaded asset — a bounded, version-adapter-local change, not an architecture change, provided `IdleCharacterAnimator`'s `CharacterPose` output (bob/arm/leg values) stays the stable hand-off contract between `services` and `platform`.

**Steamworks (Store) integration, concretely:** this repo's steamworks4j 1.10.0 binding (confirmed via direct enumeration of `code-disaster/steamworks4j`'s `java-wrapper/src/main/java/com/codedisaster/steamworks/` source tree) exposes **no** `SteamInventory`/`ISteamInventory` class and **no** `SteamMicrotransaction`/`ISteamMicrotransaction` class at all — neither interface is wrapped by this library at any version, not merely unused in this repo. The only Steamworks-native ownership signal available is `SteamApps` (confirmed methods: `isSubscribed()`, `isSubscribedApp(int appID)`, `isDlcInstalled(int appID)`, `getDLCCount()`, `installDLC`/`uninstallDLC`, `getEarliestPurchaseUnixTime`, among others) — i.e., **DLC-based ownership**, not a generic virtual-item inventory. This is why FR5's Store scope models each purchasable cosmetic as its own Steam DLC App ID rather than as an inventory-service item instance; this is the honest ceiling of what's reachable without adding a new native dependency this repo doesn't have. See Compatibility for the concrete flag on `activateGameOverlayToStore`'s presence/absence, still unconfirmed at method-signature granularity as of this spec pass.

**Config module/service placement:** no shared Config service exists in `services/` yet beyond the graduate-on-second-use rule's own bar (`architecture.md:26`) — this feature owns its two small config files (Store catalog, Wardrobe equip-map) locally, following the exact precedent `SteamWorldHostingConfigIO`/`HelloWorldMainMenuConfigIO` already set (hand-rolled JSON, fail-closed-to-defaults, no external JSON library).

## UI
- **Entry point / lifecycle**: no button click opens this screen — it *is* the title screen (FR1.1/FR1.2); no vanilla `TitleScreen` widget/button injection is involved anywhere in this feature (contrast every other UI-touching feature in this repo, which is Pattern-1/2/3 additive to an existing vanilla screen).
- **Layout**: full-bleed 3D background (z-order 0) behind a foreground row: transparent spacer, center content panel (semi-transparent dark backdrop only while a tab is active), fixed-width tab bar, and an overlaid (non-reflowing) right sidebar that expands over the tab bar/center-panel region on hover, exactly as the design doc's flex-row layout describes (`design_handoff_main_menu/README.md:23-28`) — reimplemented as absolute/computed pixel placement scaled to the actual window size and Minecraft's own GUI-scale setting (the design doc's numbers are against a 1920×1080 reference canvas; this feature must scale every measurement proportionally to the real `scaledWidth`/`scaledHeight` the target `Screen` actually receives, the same scaling discipline every other screen in this codebase already follows implicitly via Minecraft's own GUI-scale system).
- **Modals** (Direct Connect, Add Server, any Store/Wardrobe confirmation surfaces): centered overlay on a dark blurred/tinted scrim; clicking the scrim or Cancel closes it without side effects; clicking inside the modal does not close it — same interaction contract the design doc specifies (`README.md:88`) and the same shape `server-browser`'s own `ServerBrowserPasswordPromptScreen` already establishes as this repo's from-scratch custom-`Screen`/overlay precedent.
- **Color literals**: every text/fill color this feature draws must carry a full `0xFF` alpha byte, never a bare 3-byte RGB literal — this repo has already hit the exact "text silently renders nothing on 1.21.11" bug from this mistake once (`features/server-browser/specification.md:97`) and the same caution applies identically here, especially since this feature introduces many new OKLCH-derived color constants (Configuration/Design Tokens) that must each be converted to a full-alpha ARGB int, not a bare RGB one.
- **Manual, per-supported-Minecraft-version in-game verification is required** (UI/3D-rendering code is not unit-testable, `ui-guidelines.md:245-253`) — verification should cover: every tab's open/close/active-state visuals, Worlds/Servers row expand-collapse, the Servers Browser sub-view's full filter/sort/connect/password-prompt flow (reusing `server-browser`'s own manual-verification checklist, `features/server-browser/specification.md:98`), Store panel with/without Steam available and with/without any DLC actually owned (dev-time will very likely have **zero** owned DLC — see Compatibility for how to test the "owned" branch honestly), Wardrobe equip/persist-across-restart, sidebar hover-expand/collapse and Steam-unavailable status state, and the 3D background's frame-time cost on each target version/representative hardware tier (Performance).

## Configuration
Two new small, per-feature JSON files under Fabric Loader's per-instance config directory, following the exact hand-rolled-JSON/fail-closed convention `SteamWorldHostingConfigIO` already establishes (`features/steam-world-hosting/src/main/java/de/lazuli/features/worldhosting/config/SteamWorldHostingConfigIO.java`):

- **`config/main-menu-store-catalog.json`** — the Store/Wardrobe item catalog (FR5.1/FR6.2):
  ```json
  {
    "items": [
      {
        "id": "moss-cloak",
        "displayName": "Moss Cloak",
        "description": "A traveler's cloak, dyed in forest tones.",
        "category": "TORSO",
        "priceCents": 499,
        "originalPriceCents": 799,
        "steamDlcAppId": null,
        "featured": true
      }
    ]
  }
  ```
  - `steamDlcAppId: null` is the expected dev-time default until real DLC App IDs are registered on Steamworks (Compatibility) — items with a `null` App ID render as configured-but-not-purchasable-via-Steam-yet (FR5.2), not as owned.
  - If the file is missing, it is created with a small built-in default catalog (a handful of placeholder items covering all four `WardrobeSlot`s plus one featured Store item) on first run; malformed content falls back to that same default with a logged warning, never crashing screen construction.
- **`config/main-menu-wardrobe.json`** — the equip-map (FR6.3):
  ```json
  {
    "equipped": {
      "HEAD": null,
      "TORSO": "moss-cloak",
      "LEGS": null,
      "FEET": null
    }
  }
  ```
  - Read once at `MainMenuClientInitializer` construction, written whenever `MainMenuStateMachine`'s equip action changes a slot (FR6.2) — not hot-reloaded, not re-read while `MainMenuScreen` is open (Non-goals).
- No config file governs 3D-background quality/detail level in v1 (no "low/medium/high" graphics-preset toggle) — if profiling (Performance) finds the background too expensive on low-end hardware, adding such a toggle is a Future Extension, not required up front.
- No config file replaces `MainMenuTab`/sub-view/filter/sort/modal state (FR1.3) — that is intentionally session-only, matching `server-browser`'s own FR3.7 precedent (`features/server-browser/specification.md:53`).

## Events
- Consumes `net.fabricmc.fabric.api.client.event.lifecycle.v1.ClientLifecycleEvents.CLIENT_STARTED` (FR1.1) to set the initial screen — the same Fabric API surface `hello-world-main-menu`'s own spec already identified for this exact purpose (`features/hello-world-main-menu/specification.md:138`), now actually used for a full replacement rather than the label-overlay alternative that spec left as a Future Extension.
- No new cross-feature event/callback type on a shared event bus — `services/` still has no event-bus capability (graduate-on-second-use rule, `architecture.md:26`), and this feature's integration with `friends-sidebar`/`server-browser` happens via direct facade/session objects handed across at the platform composition root (Architecture), not via a published event.
- `MainMenuStateMachine`'s own internal state transitions (tab toggle, row expand, sub-view switch, modal open/close, wardrobe equip) are plain method calls from `MainMenuScreen`'s input handlers, not events in the pub/sub sense.

## Networking
No new client-server packet, no new protocol. Every network-touching action this feature exposes reuses an existing path unchanged:
- World Play/world-loading: vanilla's own singleplayer world-load path (FR3.6).
- Server Connect (Saved and Browser sub-views): vanilla's own multiplayer connect path, identical to `server-browser`'s own FR4.1 (FR4.4).
- Steam matchmaking queries (Browser sub-view): Steam-client IPC via `ISteamMatchmakingServers`, exactly as `server-browser` already performs it (Architecture) — this feature issues no new query type.
- Steam DLC ownership checks / store overlay (FR5.2/FR5.3): Steam-client IPC via `ISteamApps`/`ISteamFriends` (or an external `steam://store/<appid>` URI hand-off if no direct overlay-to-store call is confirmed present, FR5.3), not a network packet.
This feature's own client-only entrypoint (`MainMenuClientInitializer`) keeps 100% of its code off the dedicated-server path, same discipline as `hello-world-main-menu`'s own client-only entrypoint (`features/hello-world-main-menu/specification.md:141-142`).

## Persistence
- `config/main-menu-store-catalog.json` — the Store/Wardrobe item catalog (Configuration); config-file persistence only, no world/player-save data.
- `config/main-menu-wardrobe.json` — the per-player wardrobe equip-map (Configuration); persisted across client restarts (FR6.3), still purely a local config file, not account-linked/cloud-synced in v1 (contrast `features/steam-cloud-sync`, which this feature does not touch or reuse — wardrobe equip choices are not world data and have no established precedent in this repo for Steam Cloud sync; adding that is a Future Extension, not required now).

- No new NBT/world-save data, no player-account-linked storage beyond the two local config files above.

## Compatibility
- **Minecraft/Fabric versions**: same three platform modules as every other feature in this repo — `platform/fabric-1.21.11` (Yarn, obfuscated, Java 21), `platform/fabric-26.1`/`platform/fabric-26.2` (Mojang mappings, unobfuscated, Java 25) — confirmed via `gradle.properties:16` and the three `platform/fabric-*` directories. This feature needs a full Version Adapter (`MainMenuScreen`, `MainMenuBackgroundRenderer`, `MainMenuStoreOwnershipChecker`, `MainMenuClientInitializer`) per module; none of its rendering code is expected to be shareable verbatim across the Yarn/Mojang mapping boundary, same as every prior custom-`Screen` feature in this repo.
- **`ClientLifecycleEvents.CLIENT_STARTED` / full-screen-replacement mechanism**: not yet exercised by any existing feature in this repo (every prior UI feature uses Pattern 1/2/3 additive injection, `ui-guidelines.md`) — `hello-world-main-menu`'s own spec explicitly named this as the *deferred* alternative (`features/hello-world-main-menu/specification.md:95,178`); this feature is the first to actually build it. No divergence between the three target versions is expected for this specific Fabric API call (it is not one of `minecraft.md`'s currently-tracked cross-version divergences), but implementation must still confirm empirically per version and log any real divergence found, per this repo's established discipline.
- **`Screen` rendering entry point (render-state extraction)**: applies identically to this feature's 2D UI drawing as it already does to every other custom-`Screen` feature (`features/server-browser/specification.md:116`) — additionally, this feature's 3D background pass must coexist with that same render-state model within one `Screen.render`/`extractRenderState` cycle; confirming the exact call sequencing (when the 3D pass's `PoseStack`/matrix state must be pushed/popped relative to the 2D `GuiGraphics` calls for the rest of the UI) is implementation-time work, not resolved by this spec.
- **`SteamApps` API surface — confirmed present in this repo's bound steamworks4j 1.10.0**: `isSubscribed()`, `isLowViolence()`, `isCybercafe()`, `isVACBanned()`, `getCurrentGameLanguage()`, `getAvailableGameLanguages()`, `isSubscribedApp(int appID)`, `isDlcInstalled(int appID)`, `getEarliestPurchaseUnixTime(int appID)`, `isSubscribedFromFreeWeekend()`, `getDLCCount()`, `installDLC(int appID)`, `uninstallDLC(int appID)`, `getAppOwner()`, `getAppBuildId()`, `setDlcContext(int appID)` — sourced by directly enumerating `code-disaster/steamworks4j`'s GitHub source tree at `java-wrapper/src/main/java/com/codedisaster/steamworks/SteamApps.java` (same repo/tag steamworks4j 1.10.0 is published from, `gradle.properties:47`). This is a hard ceiling, not a configuration gap: real per-item virtual-inventory tracking and real-money microtransaction checkout are **not reachable** through this repo's current steamworks4j binding without adding a materially different/newer native dependency (a real architectural change, an ADR-level decision, out of this spec's scope to prescribe). ## Performance
- **Frame budget**: the 3D background (FR8) renders every frame `MainMenuScreen` is visible, so its cost is continuous, not one-shot — target keeping the *background pass alone* to a small, bounded slice of frame time (a single-digit percentage of a 16.6ms/60fps frame budget is a reasonable target ceiling for a background element sharing the frame with the rest of the UI; exact profiling-derived numbers are an implementation-time measurement, not asserted here without having run it) rather than assuming "it's just a menu screen" excuses unbounded cost — this is explicitly flagged by the requester as a real constraint, not a minor nice-to-have.
- **No render-thread blocking**: FR8.8 requires the background pass to never wait on I/O/network/Steamworks; the same discipline applies to the Store/Wardrobe/Servers panels' own data fetches (Steam DLC checks, `ServerBrowserSession` refresh) — all of which are either already-async/non-blocking Steamworks calls (per `NFR2`-equivalent guarantees `server-browser`/`friends-sidebar` already provide) or simple local-JSON reads at screen-construction time, never per-frame.
- **Idle-character animation** (`IdleCharacterAnimator.poseAt`) is O(1) trivial math per call — negligible CPU cost regardless of call frequency (once per frame is more than sufficient, no need to cache/throttle).
- **Mountains/ground/sky/sun** are static (or near-static) geometry — no per-frame mesh regeneration; if implementation finds itself rebuilding vertex buffers every frame for these, that is a correctness bug to fix (build once, only re-issue draw calls with the fixed camera/projection each frame), not an accepted cost.
- **Sidebar/Servers-panel reuse**: rendering `FriendsSidebarFacade`/`ServerBrowserSession` data inside this screen adds no new per-tick cost beyond what those features' own composition roots already pay today (`SteamworksService.pumpCallbacks()` already running every client tick regardless of this feature, per `server-browser`'s own Performance section, `features/server-browser/specification.md:129`) — this feature does not add a second callback pump or a second refresh-sweep timer for either.
- **Store catalog/ownership checks**: `SteamApps.isDlcInstalled`/`isSubscribedApp` are cheap local Steamworks-client calls (no network round-trip per Valve's own documented behavior for these calls) — safe to call once per Store-panel open/refresh, not required to cache aggressively, though caching per screen-session (not re-querying every frame while the Store tab is simply sitting open) is still sensible hygiene.
