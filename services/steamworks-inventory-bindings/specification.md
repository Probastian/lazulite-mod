# Steamworks Inventory/Microtransaction Bindings Fork — Specification

## Overview
Lazuli's only Steamworks Java binding is `com.code-disaster.steamworks4j:steamworks4j:1.10.0` (`gradle.properties:44-47`), consumed via a one-gateway-per-interface pattern in `services/src/main/java/de/lazuli/services/steamworks/` (e.g. `SteamworksSteamFriendsGateway.java`). Direct enumeration of upstream's source tree (`code-disaster/steamworks4j`, `java-wrapper/src/main/java/com/codedisaster/steamworks/`) confirms it wraps `SteamRemoteStorage`, `SteamFriends`, `SteamUGC`, `SteamMatchmaking`/`SteamMatchmakingServers`, `SteamApps`, `SteamUser`, `SteamUtils`, and others — but has **no wrapper at all** for Valve's `ISteamInventory` interface, and (a finding from this spec's own research, see Architecture — Microtransactions Reality Check) **no client-side `ISteamMicrotransaction` C++ interface exists in the Steamworks SDK to wrap in the first place**.

This is standalone infrastructure work: forking steamworks4j to add a real `ISteamInventory` binding, and — with corrected scope — the one genuinely client-side piece of Valve's microtransactions flow (`ISteamUser::MicroTxnAuthorizationResponse_t`, a callback on the *existing* wrapped `SteamUser` interface, not a new interface). This is a hard prerequisite for a planned main-menu Store panel feature (`features/main-menu/specification.md:9,22,28,232-233`), which explicitly documents this gap and defers real inventory/purchase integration to it. Per explicit instruction, no other work (including the main-menu feature) proceeds until this fork is ready. This spec is scoped purely to the binding-layer fork; it does not design the Store panel UI or consumption feature.

## Goals
- Produce a maintained fork of `code-disaster/steamworks4j` that adds a `SteamInventory`/`SteamInventoryNative` Java/JNI binding pair for Valve's `ISteamInventory`, covering the method subset needed for an in-mod cosmetic store (ownership/inventory queries + Steam-Inventory-Service-based purchase initiation — see Public API).
- Add the one client-side microtransactions primitive that actually exists at the C++ SDK level: an `ISteamUser::MicroTxnAuthorizationResponse_t` callback extension to steamworks4j's *existing* `SteamUserCallback`/`SteamUser` wrapper (not a new "SteamMicrotransaction" interface, since none exists — see Architecture).
- Rebuild the native glue/binaries for whichever platforms this mod actually ships on, using the existing premake+jnigen native toolchain, without breaking the existing wrapped interfaces this mod already depends on (Friends, RemoteStorage, etc.).
- Get the resulting fork jar consumable by `services/build.gradle` in place of (or alongside, during transition) the Maven Central `steamworks4j` artifact, with `platform/fabric-*` Jar-in-Jar `include` wiring unchanged in shape.
- Establish a sustainable process for rebasing the fork onto upstream steamworks4j as it evolves, so this doesn't become a permanently-frozen, drifting copy.
- Clearly and honestly document what genuine end-to-end microtransaction purchases require beyond this fork (a publisher-operated backend server calling Valve's server-side Web API `ISteamMicroTxn`) so nobody downstream mistakes "the Java binding exists" for "in-mod real-money purchases work end-to-end."

## Non-goals
- Not implementing a publisher backend/web service that calls Valve's server-side `ISteamMicroTxn` Web API (`InitTxn`/`FinalizeTxn`/`QueryTxn`/`GetReport`/`RefundTxn`) — that is a server-side HTTPS/REST integration requiring a securely-held Steamworks Web API publisher key, categorically not something a client Fabric mod or this JNI-binding fork can or should hold. Flagged as a hard, separate prerequisite the main-menu Store feature (or a later initiative) must address on its own, likely never inside this mod's own process.
- Not designing or implementing the main-menu Store panel UI, its consumption of these bindings, or any `de.lazuli.services.steamworks.SteamInventoryGateway`-style gateway class beyond what's needed to prove the binding works (a thin smoke-test/manual-verification harness only — see Testing/Verification Strategy). The gateway class itself is Future Extension / next initiative's job, though this spec documents the shape it should take.
- Not wrapping the full `ISteamInventory` method surface (it is large: dynamic item-property editing, promo-item eligibility queries, crafting/exchange recipes, serialize/deserialize-for-trading, etc.). Only the subset serving "does the player own this cosmetic, and can they buy it via Steam Inventory Service's own purchase flow" is in scope; the rest is flagged as extensible-later (Future Extensions).
- Not adding wrappers for any other currently-unwrapped Steamworks interface (e.g. `ISteamGameServer`, `ISteamNetworkingSockets`) — strictly `ISteamInventory` plus the one `SteamUser` callback addition.
- Not standing up new CI infrastructure beyond documenting what the existing `.github/workflows/build.yml` (Ubuntu-only, `runs-on: ubuntu-24.04`) can and cannot verify for a native-binding change (see Native Build/CI Implications).
- Not resolving whether Lazuli has (or needs) a real registered Steamworks App ID with sandbox purchase capability — flagged as an open, unverifiable-by-this-agent dependency (see Open Questions/Assumptions), same caveat `features/main-menu/specification.md` already carries for DLC App IDs.

## Requirements

**Functional**
- **FR1.** The fork adds `com.codedisaster.steamworks.SteamInventory` (public Java class) and `SteamInventoryNative` (JNI-declaring class), following the existing file-pair convention used by every other wrapped interface (e.g. `SteamUGC.java`/`SteamUGCNative.java`).
- **FR2.** `SteamInventory` exposes, at minimum: requesting/reading the local user's full inventory result (`GetAllItems` + the async `SteamInventoryResultReady_t` callback + `GetResultItems`/`GetResultStatus`/result-handle lifecycle, i.e. `DestroyResult`), and initiating a Steam-Inventory-Service purchase (`StartPurchase` + the `SteamInventoryStartPurchaseResult_t` callback) plus price lookups needed to display a price before purchase (`RequestPrices` + `SteamInventoryRequestPricesResult_t`, `GetItemPrice`).
- **FR3.** `SteamInventory`'s callback delivery integrates with the existing per-tick pump model: results surface only when `SteamworksService.pumpCallbacks()` (`SteamAPI.runCallbacks()`) is called, exactly like every existing wrapped interface's callbacks (`SteamworksSteamFriendsGateway`'s `Callback`/`UtilsCallback`/`UserCallback` pattern) — no separate polling thread, no new pump mechanism.
- **FR4.** The fork extends the existing `SteamUser`/`SteamUserCallback` wrapper with an `onMicroTxnAuthorizationResponse(int appId, long orderId, boolean authorized)`-shaped callback method (mirroring `MicroTxnAuthorizationResponse_t`'s fields), delivered through the same pump. This is additive to the existing `SteamUser.java`/`SteamUserNative.java`/`SteamUserCallback.java` files, not a new top-level interface class.
- **FR5.** Native binaries are rebuilt via the existing `jnigen`/premake toolchain against Valve's real `ISteamInventory.h` (for the new glue) and the existing `ISteamUser.h` (for the callback addition), for the platform/arch set this mod actually ships (see Native Build/CI Implications — Open Question on exact target list).
- **FR6.** All pre-existing wrapped interfaces (Friends, RemoteStorage, UGC, Matchmaking, Apps, Utils, User's existing surface) continue to build and behave identically after the fork's changes — this is an additive fork, not a rewrite.
- **FR7.** The fork jar is consumable by `services/build.gradle` via the same `api "<coordinate>:<version>"` + per-platform `include` Jar-in-Jar shape currently used for the upstream Maven Central artifact (see Architecture — Distribution).

**Non-functional**
- **NFR1.** The fork's own new Java-side code (`SteamInventory.java`, the `SteamUser` callback addition) carries JavaDoc consistent with this repo's own documentation conventions (`.claude/context/documentation.md`), even though it physically lives in a separate forked repo, so that anyone reading generated sources understands intent without cross-referencing this spec.
- **NFR2.** No behavioral surface is exposed for `ISteamInventory` methods this mod does not use (FR2's subset) at the *Java* level beyond what upstream's own convention would produce for a fully-wrapped interface — i.e., don't invent a narrower ad hoc Java API than upstream's shape would naturally produce, but also don't hand-wrap methods with no current consumer if it meaningfully increases native glue surface/risk for no benefit (judgment call for planning, informed by FR2's explicit subset).
- **NFR3.** The fork must remain rebase-friendly: changes are additive new files (`SteamInventory*.java`) plus small, isolated diffs to existing files (`SteamUser.java`/`SteamUserNative.java`/`SteamUserCallback.java`, native glue registration lists), not a restructuring of upstream's existing layout, to keep future `git rebase`/merge conflicts tractable.
- **NFR4.** Any committed or distributed native binaries built by this fork must respect the Valve Steamworks SDK's redistribution license the same way upstream's own `steamworks4j-server`/`sdkencryptedappticket` modules already do (upstream does not distribute prebuilt binaries for those; this fork must make the same license-driven call explicitly, not silently, for its own Inventory-related binaries — see Native Build/CI Implications).

## Public API

Illustrative Java shapes only, mirroring `SteamUGC`'s existing size/shape as an effort/structure proxy (`code-disaster/steamworks4j`, `java-wrapper/.../SteamUGC.java`); final method names/signatures are a planning-phase decision made against Valve's actual `ISteamInventory.h` header text, not this spec's paraphrase.

**New: `com.codedisaster.steamworks.SteamInventory`**
```
public class SteamInventory {
    SteamInventory(SteamInventoryCallback callback);

    boolean getAllItems(SteamInventoryResult resultOut);
    boolean getItemsByID(SteamInventoryResult resultOut, int[] itemInstanceIDs);
    int getResultStatus(SteamInventoryResult result);
    int getResultItems(SteamInventoryResult result, SteamItemDetails[] itemsOut);
    void destroyResult(SteamInventoryResult result);

    boolean requestPrices();
    int getNumItemsWithPrices();
    boolean getItemPrice(int itemDefId, long[] priceOut, long[] basePriceOut);

    boolean startPurchase(int[] itemDefIds, int[] quantities);
    // + accessors on the SteamInventoryStartPurchaseResult_t-shaped callback payload
    //   (order ID / transaction ID) once the callback fires.
}

public interface SteamInventoryCallback {
    void onResultReady(SteamInventoryResult result, SteamResult status);
    void onStartPurchaseResult(SteamResult status, long orderId, long transId);
    void onRequestPricesResult(SteamResult status);
}
```
- `SteamInventoryResult` (opaque handle wrapper) and `SteamItemDetails` (POJO: item def ID, item instance ID, quantity, flags) follow the existing pattern of other opaque-handle-plus-POJO pairs already in steamworks4j (e.g. `SteamUGCDetails`, `SteamPublishedFileId`).
- Deliberately **excluded** from this fork (Non-goals): `AddPromoItem(s)`, `ConsumeItem`, `ExchangeItems`, `GenerateItems` (dev-only), `TriggerItemDrop`, `SerializeResult`/`DeserializeResult` (peer-to-peer trading), `GetItemDefinitionProperty`/`StartUpdateProperties`/`SubmitUpdateProperties`/`SetProperty`/`RemoveProperty` (dynamic property editing), `GetEligiblePromoItemDefinitionIDs`. None serve "check ownership, show price, buy" for a cosmetic store; each is a Future Extension if a later feature needs it.

**Existing-file addition: `SteamUser`/`SteamUserCallback`**
```
public interface SteamUserCallback {
    ... // existing methods unchanged
    default void onMicroTxnAuthorizationResponse(int appId, long orderId, boolean authorized) {}
}
```
- Given as a `default` no-op to avoid breaking every existing implementer of `SteamUserCallback` in this repo and elsewhere (this repo's own `SteamworksSteamFriendsGateway.UserCallback` is currently a no-op implementer, `SteamworksSteamFriendsGateway.java:361-362`) — planning should confirm whether upstream's actual `SteamUserCallback` is an interface (supports `default`) or an abstract class (would need a different non-breaking-addition strategy) before committing to this exact mechanism.
- **No new `SteamMicrotransaction`/`ISteamMicrotransaction` class is produced** — this corrects the initiative's original framing. Valve's C++ Steamworks SDK has no client-facing `ISteamMicrotransaction` interface; the only client-side piece of the microtransactions flow is this one `ISteamUser` callback. The actual transaction-initiation/finalization API (`ISteamMicroTxn`: `InitTxn`, `FinalizeTxn`, `QueryTxn`, `GetReport`, `RefundTxn`) is a server-to-server Web API called over HTTPS by a publisher-operated backend holding a Steamworks Web API publisher key — categorically not a JNI/native-binding concern, and not something this Java-binding fork produces (see Architecture and Non-goals).

**Fork-repo-level surface (not Java API, but part of "Public API" of the fork as a build artifact):** the fork publishes the same Maven coordinates shape as upstream but under this project's own group/artifact (e.g. `de.lazuli.steamworks4j:steamworks4j:<fork-version>` or `com.github.<org>.steamworks4j:steamworks4j:<commit-hash>`, exact coordinate a planning decision — see Architecture, Distribution) so `services/build.gradle` can depend on it via ordinary Gradle dependency resolution.

## Architecture

### Where the fork lives and how it's built
- **Repository:** a forked GitHub repository (e.g. `Probastian/steamworks4j` or an org-owned equivalent), with `code-disaster/steamworks4j` added as a git remote (`upstream`) to support periodic `git fetch upstream && git rebase upstream/master` (or merge, if rebase conflicts become unmanageable over time — planning/maintenance decision). This is a separate repository from this mod's own repo, consistent with steamworks4j being a general-purpose third-party library, not mod-specific code.
- **Layout, unchanged from upstream** (confirmed via GitHub source-tree enumeration): `java-wrapper/src/main/java/com/codedisaster/steamworks/` (this fork's new/changed Java files land here), `jnigen/` (JNI C++ glue generator — must be re-run/extended to declare the new `SteamInventoryNative` methods and generate matching C++ stubs calling into Valve's real `ISteamInventory.h`), `build-natives/` (premake-based Windows/MSVC, Linux/gcc, macOS/Xcode native build scripts — used unchanged, just re-run against the updated generated glue), `loader/` (native library loading — no changes needed, since this fork does not add new native library *files*, only new exported symbols inside the existing per-OS native bridge library).
- **Building requires Valve's Steamworks C++ SDK** (`sdk/public/steam/isteaminventory.h`, `isteamuser.h`, etc., and `sdk/redistributable_bin/`) copied into the fork's root per upstream's own build instructions — not redistributed in either repo, obtained via a Steamworks partner/developer account. **Assumption flagged for user confirmation** (Open Questions): this project's existing Steamworks integration (App ID, existing Friends/Cloud-adjacent features) implies a partner account already exists, but this agent cannot verify partner-portal access, App ID status, or SDK download rights directly — confirm before implementation planning proceeds.
- **Consumption by this mod:** `services/build.gradle`'s current dependency line (`services/build.gradle:8`, `api "com.code-disaster.steamworks4j:steamworks4j:${steamworks4j_version}"`) is repointed at the fork's published coordinate once the fork jar exists in a repository Gradle can resolve. Two viable mechanisms, a planning-phase decision:
  1. **Published-jar mechanism (recommended default):** the fork publishes a jar (containing the same "one jar bundles native resources for all supported OS/arch" shape upstream already uses) to a repository this build already knows how to reach — either JitPack (zero infrastructure: JitPack builds directly from a tagged GitHub release/commit of the fork repo on request, works well for "small permissively-licensed fork" scenarios) or a self-hosted/GitHub-Packages Maven repo if JitPack's build environment can't satisfy the Valve-SDK-required native build (likely, since JitPack's build containers won't have Valve's SDK available — **this is a real blocker for JitPack specifically and should be flagged to planning**: native artifacts requiring a private, licensed SDK to build are generally incompatible with a public CI-triggered build-on-demand service like JitPack unless the *prebuilt* natives are committed to the fork repo itself and JitPack only compiles the thin Java jar around them).
  2. **Gradle composite/included build:** `settings.gradle` adds `includeBuild '../steamworks4j-fork'` (or a git-submodule checkout path) so Gradle builds the fork from source as part of this mod's own build — avoids needing any external repository, but requires the Valve SDK to be present on every machine that builds this mod (including CI), which conflicts with the SDK's license-gated distribution and is likely impractical for a shared/CI build. Recommended only if native rebuilds are rare and always done locally by one maintainer who then commits **prebuilt binaries** (not source) into the fork, with the composite build only recompiling the thin Java layer.
  - **Recommended shape, pending planning confirmation:** fork repo commits prebuilt native binaries (built locally by whoever has SDK access) alongside source; publishes a jar (JitPack against the fork repo, since JitPack only needs to compile Java + package already-committed native resources, not run the SDK-dependent native build) that `services/build.gradle` depends on via JitPack's Maven-repo coordinate convention (`com.github.<org>:steamworks4j:<tag-or-commit>`), with `platform/fabric-*/build.gradle`'s existing `include "com.code-disaster.steamworks4j:steamworks4j:${steamworks4j_version}"` Jar-in-Jar lines updated to the new coordinate.

### Native build/CI implications
- **Target platforms — needs confirmation, not assumed.** This mod's Fabric platform modules (`platform/fabric-26.2`, `platform/fabric-26.1`, `platform/fabric-1.21.11`, `settings.gradle:29-31`) are ordinary client-side Fabric mods; nothing in `gradle.properties`, `.github/workflows/build.yml`, or the platform `build.gradle` files inspected constrains target OS/arch beyond "wherever a player runs Minecraft with this mod installed" — i.e., the *mod's* target surface is likely the same Windows 64-bit / Linux 64-bit / macOS (x86_64 + arm64) set upstream steamworks4j 1.10.0 already bundles (per `services/specification.md:125`), not a narrower subset. **Recommendation:** rebuild for the same four native targets upstream already supports, rather than assuming a reduced set — but flag this as something planning should confirm against any actual release/distribution channel (e.g. if this mod is only ever distributed via a specific launcher/platform) rather than this agent guessing.
- **CI (`.github/workflows/build.yml`):** runs on `ubuntu-24.04` only (`build.yml:11`), and only builds/tests this *mod's* Gradle project — it does not build steamworks4j (upstream or forked) from source at all; it only resolves the already-published jar as an ordinary dependency. Therefore: **this mod's existing CI has zero native-rebuild responsibility** and needs no changes for this initiative beyond the dependency-coordinate swap once the fork jar exists — the *fork repository* is where any native-rebuild CI (if the maintainer chooses to add one) would live, and that CI would face the same Valve-SDK-availability problem as any other native build here (a GitHub Actions runner has no legal way to fetch the licensed SDK automatically; a self-hosted runner with the SDK pre-installed, or fully manual local builds with commit-then-push of the resulting binaries, are the two realistic options).
- **Prebuilt binaries: committed, not built-on-demand.** Given the Valve SDK's access-gated distribution, the practical/recommended answer is that native binaries are built locally by a maintainer with SDK/toolchain access (Windows: MSVC via the existing premake script; Linux: gcc; macOS: Xcode) and committed into the fork repository as jar resources, the same way upstream itself ships prebuilt binaries in its published jar without requiring every *consumer* of steamworks4j to own the SDK. Anyone who only *consumes* the fork (this mod's own build, including CI) never needs the SDK; only whoever *builds new native glue for the fork itself* does.
- **Toolchain availability on this project's actual build machine(s):** not verifiable by this agent — flagged as an open question (see below) whether the person building the fork's natives has MSVC/Xcode/gcc toolchains available for all four targets, or only a subset (e.g. Windows-only, if that's the primary dev machine), which would determine whether all four platforms ship in v1 or a reduced set ships first with others as documented Future Extensions.

### Java-side wrapper design (consumption pattern, once the fork exists)
- Once the fork jar is wired into `services/build.gradle`, a future `SteamworksSteamInventoryGateway` (naming illustrative) would follow the exact pattern already established by `SteamworksSteamFriendsGateway.java`: owns the single `SteamInventory` instance, constructed with a callback object, exposes a narrow non-steamworks4j-typed surface (primitives/simple POJOs) to feature code, fails closed (catches `RuntimeException`/`SteamException`, logs via a warning sink, returns safe defaults — never throws), and is constructed by the platform composition root only when `SteamAvailability.isSteamAvailable()` is true, mirroring `services/specification.md`'s existing bootstrap-service architecture (`services/specification.md:51-60`). Building this gateway class itself is out of scope here (Non-goals) — this fork's job is to make `SteamInventory`/the `SteamUser` callback addition exist so that gateway becomes buildable later.
- The `MicroTxnAuthorizationResponse_t` addition would similarly extend whatever future or existing `SteamUser`-owning gateway registers `SteamUserCallback` (currently `SteamworksSteamFriendsGateway`'s private `UserCallback`, `SteamworksSteamFriendsGateway.java:361-362`, which is presently a no-op) — planning for the *consuming* feature, not this fork, decides where that callback's result is surfaced.

### Callback/async model
- `SteamInventoryResultReady_t`, `SteamInventoryStartPurchaseResult_t`, and `SteamInventoryRequestPricesResult_t` are all standard steamworks4j-style callbacks: Valve's native SDK queues them internally and they are only delivered into Java when `SteamAPI_RunCallbacks()` executes. This fork's `SteamInventory` JNI glue registers these exactly like every existing wrapped callback (e.g. `SteamUGCCallback`'s existing async result delivery), meaning **no new pump mechanism is needed** — the existing `SteamworksService.pumpCallbacks()` (`services/specification.md:54`, calling `SteamAPI.runCallbacks()` from `ClientTickEvents.END_CLIENT_TICK`) already drives delivery of these new callbacks the moment they're registered, with zero changes to `SteamworksService` itself.
- Same reasoning applies to the added `onMicroTxnAuthorizationResponse` callback on `SteamUserCallback` — it rides the same existing `SteamUser` callback registration and the same tick-driven pump.
- **Result-handle lifecycle note (a real correctness detail for planning, not resolved here):** `SteamInventoryResult_t` handles returned by `GetAllItems`/`StartPurchase`/etc. must be explicitly destroyed via `DestroyResult` once consumed, per Valve's documented pattern — the Java wrapper must make this lifecycle unambiguous (e.g. `SteamInventoryResult` implementing `AutoCloseable`, or the gateway owning single reusable result objects) to avoid native handle leaks; final approach is a planning decision informed by how `SteamUGCQuery`-style existing handle-owning types in steamworks4j are already shaped.

### Microtransactions reality check (a load-bearing finding — read before scoping)
Valve's Steamworks SDK does **not** expose a client-side C++ interface named `ISteamMicrotransaction`. The actual mechanism (confirmed via Valve's own Microtransactions Implementation Guide, `partner.steamgames.com/doc/features/microtransactions/implementation`) is:
1. A publisher-operated backend server calls Valve's **server-side Web API** `ISteamMicroTxn` (`InitTxn`, `FinalizeTxn`, `QueryTxn`, `GetReport`, `RefundTxn`) over HTTPS, authenticated with a Steamworks Web API publisher key that must never be embedded in a client binary/mod.
2. The Steam client shows the user an in-overlay authorization prompt (triggered by that backend's `InitTxn` call, not by anything the game process calls directly).
3. The **only** client-side C++/Java-bindable piece is a single `ISteamUser` callback, `MicroTxnAuthorizationResponse_t`, telling the running game process whether the user approved or denied the transaction (AppID, OrderID, authorized bool).
This means: **a genuinely "real" end-to-end in-mod microtransaction purchase is not achievable by any Java/JNI binding fork alone**, no matter how complete — it requires a securely-hosted backend server this initiative does not build (flagged as Non-goal and a hard prerequisite for any future feature wanting real-money purchases beyond Steam-Inventory-Service-mediated ones). `ISteamInventory`'s own `StartPurchase`/`SteamInventoryStartPurchaseResult_t` (Steam Inventory Service purchasing, in scope for FR2) is a **separate, self-contained mechanism** that does *not* require a publisher backend — Valve's Inventory Service itself handles the transaction server-side once `StartPurchase` is called from the client — and is the practically achievable "real purchase flow" this fork should prioritize over chasing a nonexistent `ISteamMicrotransaction` client interface.

## Configuration
- **Fork version pin:** `gradle.properties` gains a new/replacement property (e.g. `steamworks4j_version` continues to exist but now points at the fork's published version string, or a distinctly-named `steamworks4j_fork_version` alongside a comment explaining the switch — exact naming a planning decision), following the existing convention of documenting *why* a pinned version was chosen (`gradle.properties:44-47`'s existing comment pattern for the upstream dependency).
- **Rebase/update cadence:** not a runtime config concern, but an operational one this spec should still name: the fork should be re-synced against upstream on a deliberate cadence (e.g. whenever this mod needs a new upstream feature/fix, or at minimum before each major Minecraft/Fabric version bump this project itself does), not left to drift indefinitely — concrete cadence is a maintenance-process decision for whoever owns the fork, not a build-time setting.
- No new player-facing or dev-facing JSON/config file is introduced by this initiative itself.

## Events
- No new cross-feature event bus or event type (consistent with `services/specification.md:109-113`'s existing "no event bus yet" stance) — this initiative only adds new steamworks4j-native callback plumbing (`SteamInventoryCallback`, the `SteamUserCallback` addition), which is Valve's own callback model, not this repo's.
- These new callbacks are delivered exclusively through the existing tick-driven `SteamworksService.pumpCallbacks()` path (see Architecture — Callback/async model); no new event source is added to the platform composition root.

## Networking
- `ISteamInventory`'s inventory-query and Steam-Inventory-Service purchase calls are handled entirely by the local Steam client process over its own internal channel to Valve's backend (the same "local IPC to Steam client, which does the real internet-facing work" model already documented for every other wrapped interface, `services/specification.md:116`) — this fork introduces no new sockets, ports, or custom network protocol of its own.
- The one genuinely new networking fact worth flagging: **this fork does not, and should not, ever make an HTTPS call to Valve's `ISteamMicroTxn` Web API directly from mod/client code** — that call, if it is ever made at all, belongs to a separate publisher backend server, entirely outside this fork's and this mod's process (see Non-goals, Microtransactions reality check).

## Persistence
- No new persisted artifact. `SteamInventoryResult` handles are transient, in-process, native-SDK-managed state (destroyed via `DestroyResult`, not serialized to disk by this fork).
- Any future consuming feature's own persistence needs (e.g. caching last-known ownership state to disk) are that feature's concern, not this binding layer's.

## Compatibility
- **Minecraft/Fabric versions:** the fork itself is Minecraft-independent (plain JVM + native library), identical to the compatibility story already documented for the existing steamworks4j dependency (`services/specification.md:123`) — the same fork jar works unchanged across `platform/fabric-26.2`, `platform/fabric-26.1`, `platform/fabric-1.21.11`.
- **Java:** must remain compiled at a bytecode level compatible with this repo's Java 21 floor (`services/specification.md:70`), same constraint upstream already satisfies (Java 8 bytecode). No reason for the fork to raise this unless upstream itself has since raised its own target — verify against upstream's current `build.gradle`/toolchain config at fork time.
- **Steamworks SDK version:** upstream's current baseline is ~v1.62 per prior research; `ISteamInventory` and `ISteamUser::MicroTxnAuthorizationResponse_t` have both been stable, long-present parts of the SDK for many versions (per public documentation and non-JVM reference implementations like `steamworks-rs`/Facepunch.Steamworks, which both expose equivalent surface), so no SDK-version-specific gating is expected, but should be confirmed against whichever exact SDK version is used to build the fork.
- **OS/architecture:** see Native Build/CI Implications — recommended default is to match upstream's existing four-target set (Windows 64-bit, Linux 64-bit, macOS x86_64 + arm64) unless toolchain-availability constraints (Open Questions) force a reduced initial set.
- **Upstream steamworks4j version this fork is based on:** should be based on upstream's *current* release at fork time (tracking forward, per Goals), not frozen at this mod's currently-pinned 1.10.0, so the fork inherits any interim upstream fixes rather than compounding a second, independent staleness problem on top of the fork's own divergence.

## Performance
- Startup cost: unchanged from the existing bootstrap service's characterization (`services/specification.md:129-132`) — one native library load, one `SteamAPI.init()`. This fork adds new *exported symbols* inside the same native bridge library, not a new native library file, so no additional load-time cost beyond a marginally larger binary.
- Per-tick cost: unchanged — the new callbacks ride the existing `SteamAPI.runCallbacks()` call already happening every client tick; no new per-tick native call is introduced by this fork itself (a future gateway class calling `GetAllItems`/`RequestPrices`/`StartPurchase` would do so on-demand, not per-tick, but that's the consuming feature's concern).
- Inventory/price-result JNI marshaling (copying native item-detail arrays into Java POJOs) is bounded by the player's actual inventory/catalog size, expected to be small (a cosmetic store's item catalog, not thousands of items) — no special performance engineering anticipated, but not independently benchmarked here.

## Future Extensions
- The full remainder of `ISteamInventory`'s method surface not covered here: `ConsumeItem`, `ExchangeItems` (crafting/recipes), `TriggerItemDrop`, `SerializeResult`/`DeserializeResult` (peer-to-peer trading), dynamic item-property editing (`GetItemDefinitionProperty`/`StartUpdateProperties`/`SubmitUpdateProperties`/`SetProperty`/`RemoveProperty`), `AddPromoItem(s)`/`GetEligiblePromoItemDefinitionIDs`, `GenerateItems` (dev/admin tooling) — add if/when a future feature has a genuine need.
- A real publisher-backend integration with the server-side `ISteamMicroTxn` Web API, if this project ever needs microtransactions beyond what Steam Inventory Service's own `StartPurchase` already covers — this is a substantial separate initiative (backend hosting, secrets management, a completely different trust boundary than this mod's client code) and should get its own dedicated spec/ADR rather than being retrofitted into this binding fork.
- The `SteamworksSteamInventoryGateway`-style consumer class and its wiring into the platform composition roots, once this fork's jar exists — the natural next initiative, feeding directly into the main-menu Store panel feature.
- Automating fork-repo native-binary rebuilds via a self-hosted CI runner with the Valve SDK pre-installed, if manual local rebuilds by a single maintainer become a bottleneck.
- Revisiting the reduced native-target list (if v1 ships fewer than all four platforms due to toolchain-availability constraints) once broader toolchain access is available.

## Testing/Verification Strategy
- **Unit-testable (Java-side, no native code, on a plain JVM):** any pure Java glue logic this fork's `SteamInventory`/`SteamUser` additions introduce beyond direct JNI passthrough (e.g. converting native result-status ints to a Java enum, POJO field mapping) can be unit-tested against hand-built fake native return values, the same way this repo's own `SteamNativeLibraryNamesTest.java` and `SteamworksServiceTest.java` already test steamworks4j-adjacent logic without a live Steam client (confirmed present in `services/src/test/java/de/lazuli/services/steamworks/`).
- **Not unit-testable, requires the real Steamworks SDK + a live Steam client:** the actual JNI glue calling into `ISteamInventory.h`/`ISteamUser.h`, and any behavior of `GetAllItems`/`RequestPrices`/`StartPurchase`/`MicroTxnAuthorizationResponse_t` against Valve's real backend. This requires manual verification: a running Steam client, a `steam_appid.txt`-resolvable App ID (test App ID `480` for basic "does the interface respond at all" smoke-testing; this mod's own real App ID for anything ownership/purchase-specific, since Inventory Service item definitions are per-App-ID and `480` has none configured for this project), and — for `StartPurchase`/authorization testing specifically — whatever sandbox/test-purchase capability the partner portal offers (Open Question 6).
- **Recommended minimal fork-level verification before declaring this initiative "ready":** a small manual smoke-test harness (not part of this mod's own test suite) that (a) initializes `SteamAPI` against a test App ID, (b) constructs `SteamInventory`, (c) calls `GetAllItems`, (d) confirms `SteamInventoryResultReady_t` fires on the next `runCallbacks()` pump and `GetResultItems` returns without native crash — proving the JNI glue itself is sound, independent of this mod's own build. Full purchase-flow verification (`StartPurchase` + `MicroTxnAuthorizationResponse_t`) is deferred until Open Questions 3/6 are resolved.
- No automated CI coverage of the native glue is expected or proposed here, consistent with this being fundamentally a native/JNI concern outside what `.github/workflows/build.yml`'s Ubuntu-only, dependency-resolving build can exercise (see Native Build/CI Implications).
