# Steamworks Bootstrap Service — Specification

## Overview
Lazuli's entire purpose is Steamworks-powered features — Cloud sync, Friends, Workshop, and server discovery/matchmaking (`README.md:3-19`) — and all four depend on one thing: a live, initialized Steamworks API session in the client process. Today `services/` is an empty scaffold module (`services/build.gradle:1-3`, only `api project(':api')`). This spec covers building the *first* thing in `services/`: a Steamworks SDK bootstrap that owns the Steam client library's process lifecycle (native library loading, `SteamAPI` init, the mandatory per-frame callback pump, and shutdown) and exposes a small, stable "is Steam available" surface that every future Steam-powered feature depends on instead of each reimplementing this plumbing.

This is deliberately built directly in `services/` rather than waiting for a second consumer, which is an explicit, called-out exception to `architecture.md`'s "graduate-on-second-use" rule (`.claude/context/architecture.md:26`): unlike a generic Config/Event-Bus service, this capability has four *known, already-documented* simultaneous consumers (Cloud, Friends, Workshop, matchmaking) and cannot be meaningfully scoped to "one feature's own needs" the way the hello-world feature's config I/O was (`features/hello-world-main-menu/specification.md:123`) — there is exactly one Steam client session per process, so building it once, shared, from day one is the only coherent design.

## Goals
- Provide a single, shared owner of the Steamworks native library load, `SteamAPI` initialization, per-tick callback pump, and shutdown, so no consumer feature reimplements this.
- Degrade gracefully to "Steam unavailable" in every failure mode (Steam not running, no `steam_appid.txt` in dev, native library load failure, wrong/missing App ID) — this service must never throw an uncaught exception into Minecraft's startup or tick loop.
- Expose a minimal, steamworks4j-free contract in `api/` (`isAvailable()`-shaped) that any layer can depend on without pulling in the Steamworks binding library itself, mirroring the existing `MainMenuHook` "stable abstraction" pattern (`api/src/main/java/de/lazuli/api/mainmenu/MainMenuHook.java:1-45`).
- Expose the concrete steamworks4j-typed access point in `services/` for feature code that needs to construct actual Steamworks interfaces (`SteamFriends`, `SteamRemoteStorage`, `SteamUGC`, `SteamMatchmaking`, etc.) once available.
- Support the Valve-standard dev-App-ID workflow (test App ID `480`, `steam_appid.txt` in the working directory) without requiring a real Steamworks App ID to exist yet.
- Integrate with Fabric's client tick loop with no blocking work on the tick/render thread.

## Non-goals
- No feature-specific wrapper (no `SteamCloudService`, `SteamFriendsService`, `SteamWorkshopService`, matchmaking service). Those belong to their own future `features/*` modules and, per the graduate-on-second-use rule, only get promoted into `services/` once two of them need the same capability (`.claude/context/architecture.md:26`).
- No dedicated-server / `SteamGameServer` API integration (steamworks4j's separate `steamworks4j-server` artifact). All four planned features are client-side; server-side Steamworks integration is a Future Extension.
- No UI of any kind (see UI section).
- No shared cross-feature event bus. Steam availability is a synchronous fact resolved once at client startup, not a stream of async lifecycle events, for v1 (see Events).
- No product/store decision about how Lazuli itself is distributed (e.g., whether it is ever launched *as* a Steam-registered app/tool, which would change App ID handling). Flagged as an open question, not resolved here.
- No handling of Steam Deck / Proton-specific concerns beyond "Linux 64-bit is a supported native platform" — no bespoke Deck detection.

## Requirements

**Functional**
- **FR1.** At client startup, this service attempts to initialize the Steamworks API for a configured App ID and reports success/failure as a simple boolean via `isAvailable()`. It never throws out of this attempt.
- **FR2.** While available, the service pumps Steam's callback dispatch queue once per client tick, from the client tick thread.
- **FR3.** On client shutdown, the service releases the Steamworks API session cleanly if it was initialized.
- **FR4.** If Steam is not running, not installed, or the process lacks a resolvable App ID (no `steam_appid.txt` and not launched via Steam), the service reports `isAvailable() == false` and Minecraft continues to start and run normally — no crash, no blocked startup.
- **FR5.** The service supports the Valve public test App ID `480` ("Spacewar") as the default for local development, and a way to override the App ID for CI/real builds once a real App ID is issued (see Configuration).
- **FR6.** Consumers that only need to ask "is Steam available" depend on a steamworks4j-free `api`-module type; consumers that need actual Steamworks capability (e.g. a future Cloud feature) depend on the concrete `services`-module type.

**Non-functional**
- **NFR1.** No blocking I/O or long-running work happens on the client tick/render thread beyond `SteamAPI.runCallbacks()` itself, which Valve's own docs describe as safe to call at normal frame rates (see Architecture — Threading).
- **NFR2.** All native-library-load and init failures are caught and converted into a logged warning plus `isAvailable() == false`, never an uncaught exception (steamworks4j's `SteamAPI.loadLibraries(...)`/`SteamAPI.init()`/`SteamAPI.initEx()` are documented to throw a checked `SteamException` on native-library failure; `init()` alone returns `false`, without throwing, for "Steam not running").
- **NFR3.** No global mutable static Steam-session state (`.claude/context/philosophy.md:32` lists "Global state" under Things to Avoid) — the service is an ordinary object constructed once by each platform module's composition root and threaded through explicitly, the same pattern already used for `HelloWorldMainMenuService` (`platform/fabric-26.2/src/main/java/de/lazuli/HelloWorldMainMenuClientInitializer.java:36-49`). A single Java-level static field is unavoidable only insofar as the underlying native Steam API itself is a process-wide singleton (only one `SteamAPI_Init` per process) — this is a property of Valve's C API, not a Java design choice, and should not be compounded by adding a *Java-level* singleton/registry on top of it.
- **NFR4.** Public classes/interfaces carry JavaDoc with a usage example, per `.claude/context/philosophy.md:19` and `.claude/context/documentation.md:8-14`.
- **NFR5.** `services`/`api` remain buildable and testable on a plain JVM with no Minecraft classes on the classpath (`architecture.md`'s Dependency Rules, `.claude/context/architecture.md:64-71`); this holds automatically here since steamworks4j itself has no Minecraft dependency.

## Public API

Illustrative shapes only; final names/signatures are a planning-phase decision (same convention as `features/hello-world-main-menu/specification.md:53`).

**1. `api` module** — new package `de.lazuli.api.steamworks`, zero external dependencies (matches the existing constraint that `api/` has no `build.gradle`/dependencies at all — confirmed by its absence from the module tree, unlike every other module):
- `SteamAvailability` (interface) — the only contract that must be binding-library-agnostic:
  - `boolean isSteamAvailable();`
  - possibly `long steamAppId();` for diagnostics/logging — a raw primitive, not a steamworks4j `SteamID`/app-id type.
- Unlike `MainMenuHook`, this is **not** a "Platform API + Version Adapter" pair — steamworks4j behaves identically regardless of which Minecraft version/platform module hosts it (it is a plain Java library with no Minecraft dependency), so there is no per-Minecraft-version implementation to adapt. The reason this lives in `api/` at all is purely the "zero dependencies, safe for any layer to reference" property `api/` already guarantees, not the multi-version pattern documented in `architecture.md:47-62`. This distinction should be called out in code comments so a future reader doesn't go looking for a `FabricSteamworksHook` per platform module — there isn't one, and shouldn't be.

**2. `services` module** — new package `de.lazuli.services.steamworks`, depends on `api` (already does, `services/build.gradle:1-3`) plus the new steamworks4j dependency:
- A concrete class (e.g. `SteamworksService`) implementing `SteamAvailability`, owning the actual lifecycle:
  - A factory/constructor path that performs native-library loading + `SteamAPI.init()`/`initEx()`, catching `SteamException` and treating a `false`/failed result identically: unavailable, logged, no throw.
  - `void pumpCallbacks();` (or `tick()`) — calls `SteamAPI.runCallbacks()`; a no-op if unavailable.
  - `void shutdown();` — calls `SteamAPI.shutdown()` if it was ever successfully initialized; idempotent, safe to call even if never initialized or already shut down.
  - `boolean isSteamAvailable();` (implements the `api` contract).
  - Deliberately does **not** hand back per-interface objects (`SteamFriends`, `SteamRemoteStorage`, `SteamUGC`, `SteamMatchmaking`) itself — those are lightweight steamworks4j wrapper objects that any code holding a reference to an *available* `SteamworksService` may construct directly once a real feature needs them (e.g. `new SteamFriends(callback)`), guarded by `isSteamAvailable()`. Pre-building generic accessors for interfaces no feature yet exists to use would be speculative surface this ticket should not add (mirrors `philosophy.md:34`, "Premature optimization" and the graduate-on-second-use spirit for anything *beyond* the shared bootstrap itself).
- A small `SteamLibraryLoader` implementation (steamworks4j's own extension point — see Architecture) responsible for physically locating and `System.load()`-ing the three native library files from wherever they end up on the mod's runtime classpath.

**3. Consumption by future features:** a future `features/steam-cloud` (etc.) depends on `api` + `services` (permitted per the Dependency Rules table, `.claude/context/architecture.md:64-71`, "Features: API, Services"), is handed the shared `SteamworksService` instance by its platform composition root (same wiring style as `HelloWorldMainMenuClientInitializer`, and covered by the existing composition-root precedent in `docs/adr/0001-platform-composition-root-may-depend-on-feature-classes.md:46-50`, generalized here from "Platform may depend on a Feature to wire it" to "Platform wires a shared Service into a Feature"), checks `isSteamAvailable()`, and only then constructs its own steamworks4j interface objects.

## Architecture

**Chosen binding library: [steamworks4j](https://github.com/code-disaster/steamworks4j) (`com.code-disaster.steamworks4j:steamworks4j`).**

Justification:
- **License:** MIT — permissive, compatible with this repo's CC0 licensing (`README.md:49-51`).
- **Maintenance:** actively maintained; commit history shows activity as recent as May 2026 (e.g. "Add Linux ARM64 build script"), current release 1.10.0 on Maven Central (published ~7 months prior to this research), built against Steamworks SDK v1.62. This is the de facto standard Java Steamworks binding (544 GitHub stars) with no actively-maintained competitor for plain-JVM (non-LibGDX-specific) use.
- **Coverage:** wraps `SteamRemoteStorage` (Cloud), `SteamFriends` (Friends), `SteamUGC` (Workshop), and `SteamMatchmaking`/`SteamMatchmakingServers` (matchmaking/server discovery) — the exact four interfaces this project's four planned features need, per `README.md:6-12`.
- **Java version:** the published jar is compiled at Java 8 bytecode level; this is strictly older than and therefore compatible with both this repo's shared-module floor (Java 21, `build.gradle:13-24`, `.claude/context/minecraft.md:120-127`) and `platform/fabric-26.2`'s Java 25 target (`platform/fabric-26.2/build.gradle:27-29`) — older `--release` bytecode always runs on newer JVMs.
- **Native platform coverage:** single artifact bundles natives for Windows 64-bit, Linux 64-bit, and macOS (a "fat" dylib covering both x86_64 and arm64 since 1.10.0) directly as jar resources — no separate classifier jars to manage, no 32-bit support (dropped in 1.7.0/1.8.0, acceptable since Minecraft 1.21+/26.x itself requires 64-bit).
- **Rejected alternatives:** hand-writing a JNI/JNA binding from scratch (reinvents this library for no benefit); Facepunch.Steamworks (C#/.NET-only, not usable from Java); steamworks4j's own `-gdx`/`-lwjgl3` companion loader modules (designed for those specific frameworks' asset/classloading conventions, not applicable to a Fabric mod — see Native Libraries below, this service must supply its own `SteamLibraryLoader`).

**Lifecycle flow:**
```
platform/fabric-<version> client entrypoint (composition root)
    creates SteamworksService(appId, warnLogger)
        -> SteamAPI.loadLibraries(fabricLibraryLoader)   // may throw SteamException -> caught, unavailable
        -> SteamAPI.init() / initEx()                    // false/failure -> caught, unavailable
    registers ClientTickEvents.END_CLIENT_TICK -> steamworksService.pumpCallbacks()
    registers a shutdown hook (client stop) -> steamworksService.shutdown()
```
Client tick integration: Fabric API's `ClientTickEvents` (module `fabric-lifecycle-events-v1`), already transitively available via the existing `fabric-api` dependency in every `platform/fabric-*/build.gradle` (same module family already relied on by the hello-world feature's `ClientLifecycleEvents`, `features/hello-world-main-menu/specification.md:45`) — no new Gradle dependency required for the Fabric side. Per this repo's own precedent (`.claude/context/minecraft.md:56`, the `Screens.getButtons` → `Screens.getWidgets` rename between 1.21.11 and 26.x), implementation must verify `ClientTickEvents`' exact class/method name is unchanged across all three supported Fabric API versions by compiling against each, not by assuming; if it did rename, treat it the same as any other cross-version Fabric API difference (thin per-platform glue, not exposed past the composition root).

**Threading:** Valve's Steamworks API is documented as requiring `SteamAPI_RunCallbacks` to be called from the same thread `SteamAPI_Init` ran on; Minecraft's client tick callback and the client's main/render thread are the same thread in this repo's supported versions, so calling `pumpCallbacks()` from `ClientTickEvents.END_CLIENT_TICK` satisfies this. `runCallbacks()` itself is a fast poll (Valve recommends ≥15 Hz; Minecraft ticks at a fixed 20 Hz, comfortably above that). This bootstrap service does no heavy work inside the pump call; any future feature registering its own steamworks4j callback objects (e.g. a Cloud download-progress callback) must not perform blocking I/O synchronously inside that callback — it must hand off to a background executor and only marshal results back onto the tick thread. This constraint is documented here for future feature authors, not solved by this service.

**Native libraries — the two-binary distinction (needs empirical confirmation during implementation, flagging now rather than asserting):** steamworks4j ships its own small JNI bridge library (`libsteamworks4j.{dll,so,dylib}`) as a resource inside its jar. Valve's actual redistributable Steamworks client library (`steam_api64.dll` / `libsteam_api.so` / `libsteam_api.dylib`) is separately licensed by Valve as part of the Steamworks SDK's `redistributable_bin/` folder, explicitly intended for redistribution with Steam-integrated apps; steamworks4j's own build process pulls those files from a locally-installed Steamworks SDK during *its* build. Whether the officially *published* steamworks4j jar bundles Valve's binary too (so a plain Maven Central dependency is sufficient), or only its own JNI bridge (requiring this project to separately obtain and vendor Valve's `redistributable_bin` files under the Steamworks SDK's own license), must be confirmed empirically before/during planning — this is a functional and potentially licensing-relevant fact, not to be guessed.

`SteamLibraryLoader` (steamworks4j's own extension point) ships with only a no-op default implementation in the core `java-wrapper` artifact; concrete implementations exist only in steamworks4j's separate `-gdx` and `-lwjgl3` companion modules, neither of which applies to a Fabric mod's classloading model. `services/steamworks` must therefore supply its own minimal `SteamLibraryLoader` that resolves the correct per-OS/arch native file name, extracts it from the classpath resource (steamworks4j's own jar, reachable like any normal dependency once bundled per below) to a writable location (e.g. Fabric Loader's cache/config directory, not necessarily `java.io.tmpdir`, to sidestep the antivirus-related temp-directory issues reported against steamworks4j's own default extraction path), and `System.load()`s it before `SteamAPI.init()` is attempted.

**Fabric/Loom packaging implications:** steamworks4j is a plain, Minecraft-independent Java library — it needs no Loom remapping (only code referencing `net.minecraft.*`/intermediary/Yarn symbols needs remapping, per `.claude/context/minecraft.md:63-76`). It must, however, actually end up on the runtime classpath of each `platform/fabric-*` module's shipped jar. The standard Fabric Loom mechanism for this is the `include` configuration ("Jar-in-Jar"), which nests a dependency's jar inside the mod's own output jar and lets Fabric Loader extract/expose it at mod-load time — planning should confirm the exact current syntax against Fabric Loom `1.17-SNAPSHOT` (`gradle.properties:12`) documentation rather than assume it is unchanged from older Loom versions, consistent with this repo's own stated policy of confirming exact tooling coordinates via primary sources (`.claude/context/minecraft.md:80-96`).

**Composition root wiring:** Steam's client-facing API is inherently client-only (it talks to the locally-running desktop Steam client). Following the existing precedent (`platform/fabric-26.2/src/main/resources/fabric.mod.json:17-24`, the `"client"` vs `"main"` entrypoint split), this service is constructed and driven exclusively from each platform module's `client` entrypoint, never from the shared `"main"` entrypoint (`LazuliMod`, environment `"*"`, also loaded on dedicated servers, `platform/fabric-26.2/src/main/java/de/lazuli/LazuliMod.java:10-19`) — a dedicated server has no local Steam client to talk to.

**Gradle wiring:** add a new `steamworks4j_version` property to `gradle.properties` (matching the existing pattern for other pinned dependency versions, `gradle.properties:19-30`), and in `services/build.gradle` add the dependency as `api "com.code-disaster.steamworks4j:steamworks4j:${steamworks4j_version}"` rather than `implementation` — because the concrete `SteamworksService`'s public surface is expected to expose/accept steamworks4j-typed values to feature code (mirroring the documented rationale already in this repo for exactly this `api` vs `implementation` choice, `features/hello-world-main-menu/build.gradle:2-4`). Each `platform/fabric-*/build.gradle` then needs an `include "com.code-disaster.steamworks4j:steamworks4j:${steamworks4j_version}"` (Jar-in-Jar) so the native-bearing jar actually ships inside the built mod.

## UI
N/A — this is backend/infrastructure plumbing with no player-visible screen, widget, or HUD element of its own. (Individual future features built on top of this service, e.g. a Friends list overlay, will have their own UI specs.)

## Configuration
- **App ID resolution**, in priority order, illustrative for planning:
  1. An explicit override (e.g. a JVM system property or this project's own config value, not a Valve-native mechanism) for CI/release builds once a real Steamworks App ID exists.
  2. Default to Valve's public test App ID `480` ("Spacewar") for local development — the standard placeholder used before a real App ID is issued.
- **`steam_appid.txt`:** Valve's *only* officially documented mechanism for supplying an App ID to a process not launched directly by the Steam client is a plain-text file named `steam_appid.txt`, containing just the App ID digits, present in the process's current working directory at the moment `SteamAPI_Init` runs; Valve's own docs explicitly say this file must never ship in a distributed build. Valve's docs do not document a `SteamAppId` environment variable as part of the public API — any "environment variable" configuration this project offers (e.g. reading a `LAZULI_STEAM_APP_ID` env var to decide what to write into a generated `steam_appid.txt`, or to select which literal App ID to pass to `SteamAPI.initEx()`/`restartAppIfNecessary`) is this project's own convenience layer on top of Valve's file-based mechanism, not a Steamworks-native feature — must be documented as such so nobody later assumes Valve reads that variable itself.
  - For each `platform/fabric-<version>`'s Loom-managed `run/` working directory (already `.gitignore`'d, `.gitignore:33`), local development needs a `steam_appid.txt` containing `480` present before `runClient`. This should be a documented, reproducible dev-setup step (e.g. a small Gradle task or a checked-in template copied by a setup script) rather than a manually-created, easily-forgotten file — left to planning.
- **Real App ID / distribution:** once a real Steamworks App ID is issued, planning must decide how a release build supplies it (packaging a generated `steam_appid.txt` at build time vs. relying on being launched in a context where Steam already knows the App ID) — this is coupled to an unresolved, out-of-scope product question (how Lazuli/Minecraft is actually distributed with respect to Steam) flagged under Non-goals/Future Extensions, not decided by this spec.
- No JSON/user-editable config file is required for this service itself (unlike the hello-world feature's `config/hello-world-main-menu.json`, `features/hello-world-main-menu/specification.md:122-135`) — the only "configuration" is the App ID resolution above, which is a build/dev-environment concern, not a player-facing setting.

## Events
- This service does not define, nor does it need, a new cross-feature event type or shared event bus (`architecture.md:16-19` lists "Event Bus" as a services-layer capability, but per the graduate-on-second-use rule, `architecture.md:26`, none exists yet and this ticket is not the trigger to build one).
- Availability is a synchronous fact: resolved once, early, by the platform composition root before any dependent feature runs, and queried via `isSteamAvailable()` — not pushed asynchronously.
- This service's job is precisely to keep pumping the queue (`SteamAPI.runCallbacks()`) that *steamworks4j's own* per-interface callback objects (`SteamFriendsCallback`, etc.) depend on for delivery; it defines no callback types of its own. Those interface-specific callbacks belong to whichever future feature constructs that interface.
- Known limitation, explicitly out of scope for v1: steamworks4j's simple `init()`/`initEx()` model has no concept of Steam later "becoming available" mid-session after a failed startup init (e.g., user starts the Steam client after Minecraft is already running) — `isAvailable()` reflects the one-time startup attempt only. Detecting and reacting to such a change is a Future Extension requiring genuine polling/event-bus infrastructure.

## Networking
Largely N/A for this bootstrap service specifically: it opens no sockets and sends no custom network packets of its own, and Minecraft's client-server protocol is untouched. Note for context (not something this spec designs): steamworks4j's `SteamAPI` calls communicate with the *locally running* Steam client process (a local IPC pipe/socket), which in turn performs any actual internet-facing networking on Valve's/Steam's behalf — so this service introduces no new firewall, latency, or client-server networking concerns of its own. Future Cloud/matchmaking features built on top of `SteamRemoteStorage`/`SteamMatchmaking` will have their own real networking behavior and specs.

## Persistence
- The only persisted artifact this service is concerned with is the dev-only `steam_appid.txt` described under Configuration — not player data, not world data, not a config file with a schema to version.
- No other file I/O, no NBT, no save-data interaction. (Steam Cloud persistence is entirely a future feature's concern, built on top of this service's `isSteamAvailable()`.)

## Compatibility
- **Minecraft/Fabric versions:** this service is Minecraft-version-agnostic by construction — steamworks4j has no Minecraft dependency, so the same `services/steamworks` code runs unchanged under `platform/fabric-26.2`, `platform/fabric-26.1`, and `platform/fabric-1.21.11`. The only per-platform-module work is: (a) the `include` Jar-in-Jar Gradle wiring (repeated per module, since each has its own `build.gradle`), and (b) the client-entrypoint composition-root wiring plus the `ClientTickEvents` registration, both of which are boilerplate wiring, not business logic, and thus not subject to the "no version checks inside features" rule (`.claude/context/minecraft.md:42-45`) since none of this is feature business logic.
- **Java:** compatible with the shared-module floor (Java 21) and with `platform/fabric-26.2`'s Java 25 target, per the bytecode-compatibility reasoning under Architecture.
- **OS/architecture:** Windows 64-bit, Linux 64-bit, macOS (x86_64 and Apple Silicon arm64) are all supported by steamworks4j 1.10.0's bundled natives; no 32-bit support, which is acceptable given this repo's supported Minecraft versions are 64-bit-only.
- **Steamworks SDK version:** steamworks4j 1.10.0 wraps Steamworks SDK v1.62; future steamworks4j upgrades should be tracked the same way this repo already tracks other pinned third-party versions (`gradle.properties`).

## Performance
- Startup cost: one native-library extraction (first run) or load (subsequent runs), plus one `SteamAPI.init()`/`initEx()` call — a one-time, bounded cost at client startup, not on any hot path.
- Per-tick cost: one `SteamAPI.runCallbacks()` call, documented by Valve as cheap enough for real-time game loops at typical frame/tick rates; Minecraft's fixed 20 Hz tick rate is comfortably within the ≥15 Hz Valve recommends.
- No retained per-tick allocation; the service itself holds only its initialization-result state (available/unavailable, App ID) for the process's lifetime.
- Failure paths (Steam not running, bad App ID) must be equally cheap and must not retry in a loop — a single resolved availability state for the process lifetime, not repeated re-attempts on later ticks.

## Future Extensions
- Feature-specific service wrappers (`SteamCloudService`, `SteamFriendsService`, `SteamWorkshopService`, a matchmaking service) built by their respective future `features/*` modules, each consuming this service's availability check plus constructing their own steamworks4j interface objects.
- Promoting any of those feature-specific wrappers into `services/` if/when a second feature needs the identical capability, per the graduate-on-second-use rule.
- Async "Steam availability changed" notification (would require introducing this repo's first real shared Event Bus service — a bigger, separate architectural decision, not to be bundled into this ticket).
- Dedicated-server `SteamGameServer` integration (steamworks4j's `steamworks4j-server` artifact) if a future feature needs server-side Steam functionality (e.g. server-browser registration, VAC).
- Resolving the open product question of whether/how Lazuli is ever launched in a genuinely Steam-native context (affecting real-App-ID/`steam_appid.txt` handling in release builds) — likely warrants its own ADR once a real Steamworks App ID exists.
- Revisiting the native-library packaging approach if the "does steamworks4j's published jar already bundle Valve's redistributable binary" question (flagged under Architecture) resolves unfavorably and this project needs to vendor those binaries itself under the Steamworks SDK license.
